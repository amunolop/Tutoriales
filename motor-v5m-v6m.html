DOS SISTEMAS, UN PROPÓSITO

El sistema de migración FMI se compone de dos piezas que operan en niveles diferentes. V6M es el cerebro: un orquestador que planifica toda la migración en N fases y decide el orden, los contratos y la estrategia. V5M es el brazo: un motor de ejecución que recibe instrucciones de V6M y genera código en paralelo con tests-first. V6M llama a V5M una vez por cada fase.

V6M — Orquestador (Cerebro)
Meta-Architect (Opus) planifica la migración completa. SCAN del legacy → decide fases → define contratos entre fases → ejecuta V5M por fase → certifica resultado final. Estrategia: Consumer-Driven Contract (frontend primero, backend después).
V5M — Motor de Ejecución (Brazo)
Architect (Opus) genera Blueprint + DIGEST + TEST SPECS → Oleada 1 de Test Workers escribe tests a disco → GATE bloqueante verifica coherencia → Oleada 2 de Code Workers lee tests y escribe código → Smoke (Haiku) verifica mecánicamente.
ARQUITECTURA GENERAL
PRINCIPIOS CLAVE
TDD-as-Spec
Tests se escriben ANTES del código. Actúan como especificación ejecutable. Los tests son la verdad: si el código no los satisface, el código está mal, nunca el test.
Consumer-Driven Contract
Frontend primero → SCAN extrae contratos API → Backend implementa exactamente esos contratos. Elimina el bug clásico de JSON shape mismatch.
SHARED CONTRACTS
Un vocabulario cerrado que TODOS los workers respetan: nombres de entidades, firmas de constructores, paquetes canónicos, mutabilidad de DTOs. Libertad total dentro, contratos fuera.
Knowledge Injection
Bugs conocidos del legacy inyectados como reglas: nombreProfesor (no getFormatos), titulacion (no especialidad), "year" entrecomillado en SQL. Previenen errores antes de que ocurran.
V6M: ORQUESTADOR MULTI-FASE

V6M es el nivel superior. El Meta-Architect (Opus) recibe un objetivo de migración y decide cuántas fases, en qué orden, y qué contratos fluyen entre ellas. Cada fase se ejecuta como una instancia independiente de V5M.

FLUJO DETALLADO V6M
0
SCAN Legacy (NO cuenta como fase V5M)
Sonnet workers leen código fuente en paralelo. Reportan: ficheros, tipos, SQL, dependencias, complejidad. Output: INVENTARIO estructurado. 6 ficheros/worker (lectura es más rápida que escritura). Coste: ~$1.17 · ~3 min.
1
Meta-Architect (Opus) — Planificación
Lee inventario + objetivo + constraints. Decide cuántas fases (≤4 recomendado), scope de cada una, orden por dependencias, contratos entre fases, y knowledge injection específico por fase. Output: PLAN DE FASES.
2
Loop de Fases (secuencial)
Para cada fase: Meta-Architect pasa instrucciones a V5M (objetivo, archivos, contratos, KI) → V5M ejecuta fase completa (Architect→TW→GATE→CW→Smoke) → V5M reporta resultado → Meta-Architect ajusta siguiente fase si necesario.
⊕
SCAN Intermedio (si Front→Back)
Entre fase frontend y backend. Sonnet workers leen services/*.js generados, extraen endpoints exactos: method, path, request body, response fields. Output: contratos API que el backend implementa tal cual. Coste: ~$0.30 · ~1 min.
3
Certificación
Meta-Architect consolida: contratos alineados (13/13 endpoints), tests generados (50 ficheros), smoke totales (28/28), coste real vs estimado, coherencia test↔code.
Regla: Front antes que Back La evidencia empírica (PoC ServletIdentificacion) demostró que Back→Front produce bugs de integración: el backend inventa un JSON shape y el frontend tiene que adivinar. Front→Back con SCAN intermedio hace esto imposible.
V5M: MOTOR DE EJECUCIÓN PARALELO

V5M recibe instrucciones de V6M (o de un humano) y ejecuta una fase completa de generación de código. Su innovación es el flujo de dos oleadas: primero tests, después código. El GATE entre ambas oleadas es la pieza crítica que garantiza coherencia.

LOS 4 ARTEFACTOS DEL ARCHITECT
Blueprint
Agrupación por afinidad funcional. Cada worker tiene columna ESCRIBE con carpetas que le pertenecen exclusivamente. Split si grupo > FILES_PER_WORKER. Merge si grupo = 1 trivial.
DIGEST (~2K tokens)
Patrones extraídos de la referencia: arquitectura, seguridad, API contract, frontend. Workers reciben DIGEST, NO leen referencia directamente. Ahorro: ~15% tokens.
SHARED CONTRACTS
Sección dentro del DIGEST obligatoria para TODOS los workers. Entity names, constructor signatures, mutabilidad, repos, DTOs, paquetes. Libertad total en implementación interna.
TEST SPECS (~500 tok/grupo)
Contratos compactos por grupo. NO archivos reales — solo specs que los Test Workers materializan como JUnit/Jest. Constructors, method sigs, return types, field names.

POR QUÉ EXISTE EL GATE
Sin GATE (M2, 2026-04-21)
Architect generó DIGEST pero NO tests. Workers sin spec formal. Tests escritos DESPUÉS como documentación. Resultado: TDD-as-spec no se cumplió. Knowledge injection salvó, pero fue suerte.
Con GATE (M16+)
Test Workers escriben tests a disco → GATE verifica coherencia → Code Workers los leen. Si tests no existen o son incoherentes → ABORT. Imposible gastar tokens en código basado en tests rotos.
⚠️ Post-Mortem M16 — Errores que motivaron el GATE
11 usecase tests importaban domain.repositories.* — paquete inexistente → 0/11 compilaban.
5 tests devolvían thenReturn(entity) en vez de thenReturn(Optional.of(entity)) → type mismatch.
DTOs: LoginRequest(2 args) y SolicitudFilter(1 arg) — constructores all-args inventados que no existían.
Métodos: ListSolicitudesTest llamaba findAll() en repos que solo tienen findByFilters/findByDateRange.
Todos estos errores habrían propagado a los Code Workers, multiplicando el daño.

PROMPT — TEST WORKER
Prompt · Test Worker
Genera tests JUnit 4 / Jest que especifiquen los contratos de tu grupo.
Recibes TEST SPEC + DIGEST (incluye SHARED CONTRACTS).
Output: archivos reales en tests/{tipo}/

Constraints:
- Java 8: no records, no var, no List.of()
- JUnit 4: @Test, assertEquals, assertNotNull
- Mockito 1.x: mock(), when(), verify()
- Reflection para verificar ausencia de métodos prohibidos
- Tests DEBEN compilar (no se ejecutan ahora)
- Si tu test necesita instanciar una entity de OTRO grupo,
  usa EXACTAMENTE el constructor de SHARED CONTRACTS. No inventes otro.

REGLAS DE COHERENCIA (obligatorias):
- Imports: domain.interfaces.* para repos
  (NUNCA domain.repositories.*)
- Optional: si repo retorna Optional<T>,
  mockear con thenReturn(Optional.of(x))
  Caso "no encontrado": thenReturn(Optional.empty())
  (NUNCA thenReturn(null))
- DTOs mutables: new Dto() + setters
  (NO inventar constructores all-args)
- Métodos repo: SOLO llamar métodos listados en SHARED CONTRACTS
  (NO asumir findAll() si interface solo declara findByFilters())
PROMPT — CODE WORKER
Prompt · Code Worker
ANTES de escribir cualquier archivo, LEE los tests de tu grupo:
  tests/{tipo}/{NombreTest}.java

Contratos EXACTOS que tu código debe cumplir:
  - Constructors: argumentos en orden exacto
  - Method signatures: nombre, parámetros, return type
  - Field names: EXACTAMENTE los del test
  - Exceptions: las que el test captura
Si tu código no satisface el test, ESTÁ MAL. El test es la verdad.

REGLA DE AISLAMIENTO (obligatoria):
  - SOLO escribe archivos en TU carpeta asignada por el Blueprint
  - NUNCA sobreescribas archivos de otros workers
  - Si un test referencia una clase que NO es tuya,
    ADÁPTATE al contrato que el test define — NO reescribas la clase

Coste real: $12–$22 por fase.

GATE detecta incoherencias en <10 seg. Fixes automáticos pre-oleada2. Code Workers generan sobre tests coherentes. Código compila al primer intento. Fixes manuales: 0.

Coste real: $4.82 por fase.
