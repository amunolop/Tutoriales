Filosofía: Ramas para Trabajar, Tags para Fotografiar
La clave: Las ramas son efímeras — son el taller donde se trabaja. Los Git Tags son permanentes — son la fotografía del éxito de cada fase. Combinados, generan una narrativa técnica que el tribunal del TFM puede recorrer como una línea temporal.
🔀

Ramas = Taller

Cada fase tiene su rama aislada. Se trabaja, se rompe, se arregla. Cuando la fase está validada con tests, se mergea a main y se crea el tag.

Rama por fase, nunca por feature suelto
🏷️

Tags = Hito

Un tag anotado (git tag -a) congela el momento exacto en que la fase fue validada. Permite saltar en el tiempo durante la presentación.

"Señores del tribunal, volvamos a la v1.0…"
🚀

Main = Producción

Solo se mergea a main lo que ha pasado todos los tests. Cada merge a main dispara un despliegue automático en DigitalOcean.

main siempre funciona, siempre desplegable

Dos Caminos en DigitalOcean
WebDTE ya está dockerizado. Ambas opciones parten de tu Dockerfile existente. La diferencia: cuánto automatizar vs. cuánto controlar.
☁️
App Platform (PaaS)
La opción "Pro"
Conectas GitHub a DigitalOcean. Cada merge a main construye la imagen y despliega automáticamente. Cero administración de servidor.
SSL automático con Let's Encrypt
Postgres como servicio gestionado
Deploy automático por push a main
Escalado horizontal sin configuración
Más caro (~$12–25/mes con BD)
Menor control sobre la infra subyacente
🖥️
Droplet (VPS)
La opción "Guerrillera"
Un servidor Linux puro. Instalas Docker y docker-compose. Un script de Bash gestiona el ciclo de vida: pull, build, stop, up.
Control total del entorno
Más barato (~$6/mes el Droplet básico)
Múltiples contenedores (legacy + nuevo)
Ideal para side-by-side en el TFM
SSL manual (Certbot/Nginx)
Mantenimiento del servidor (updates)
Recomendación para el TFM
🎯
Droplet + docker-compose = Máximo valor demostrativo
Para el TFM, un Droplet con docker-compose permite tener ambas versiones corriendo simultáneamente (legacy en puerto 8080, migrada en 8081) y hacer la comparación en vivo durante la defensa. App Platform es mejor para producción real, pero un Droplet es mejor para la narrativa técnica.
Coste estimado TFM: Droplet básico ($6/mes) + Managed Postgres ($15/mes) = ~$21/mes. Alternativa guerrillera: Postgres también dockerizado en el mismo Droplet = $6/mes total. Para un TFM de 3 meses, ~$18 totales.
docker-compose.yml — Legacy + Postgres
Este compose soporta la Fase 1 completa: levanta el WAR legacy en Tomcat 5.5 + JDK 1.5 junto con un Postgres 15. Variables de entorno para que en DO solo cambies la conexión sin tocar código.
docker-compose.ymlYAML
version: '3.8'

services:

  # ── LEGACY: WAR original sobre Tomcat 5.5 / JDK 1.5 ──
  webdte-legacy:
    build:
      context: .
      dockerfile: Dockerfile.legacy
    container_name: webdte-legacy
    ports:
      - "8080:8080"
    environment:
      - DB_URL=jdbc:postgresql://postgres:5432/webdte?stringtype=unspecified
      - DB_USER=${DB_USER:-webdte}
      - DB_PASS=${DB_PASS:-webdte_secret}
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - webdte-net

  # ── BASE DE DATOS ──
  postgres:
    image: postgres:15-alpine
    container_name: webdte-db
    environment:
      - POSTGRES_DB=webdte
      - POSTGRES_USER=${DB_USER:-webdte}
      - POSTGRES_PASSWORD=${DB_PASS:-webdte_secret}
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./sql/init.sql:/docker-entrypoint-initdb.d/init.sql
    ports:
      - "5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER:-webdte}"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks:
      - webdte-net

volumes:
  pgdata:

networks:
  webdte-net:
    driver: bridge
docker-compose.override.yml — Side-by-Side (Fase 3+)
Para la defensa del TFM: este override añade el servicio migrado en paralelo. Ambos backends corriendo simultáneamente contra la misma BD.
docker-compose.override.ymlYAML
version: '3.8'

services:

  # ── MIGRADO: 3 capas + Clean Code ──
  webdte-migrated:
    build:
      context: .
      dockerfile: Dockerfile.migrated
    container_name: webdte-migrated
    ports:
      - "8081:8080"    # Puerto diferente al legacy
    environment:
      - DB_URL=jdbc:postgresql://postgres:5432/webdte?stringtype=unspecified
      - DB_USER=${DB_USER:-webdte}
      - DB_PASS=${DB_PASS:-webdte_secret}
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - webdte-net
Variable crítica: stringtype=unspecified en la URL de Postgres. Permite que los tipos Java antiguos (como setObject() sin tipo explícito) funcionen contra Postgres. Sin él, el driver JDBC rechaza queries del código legacy de 2005 que asumían tipado implícito.
GitHub Actions — Pipeline por Fase
Objetivo: Cada push a una rama de fase ejecuta los tests automáticamente. Los "checks" en verde antes de mergear dan seguridad al desarrollador y credibilidad al tribunal.
.github/workflows/ci-webdte.ymlYAML
name: WebDTE CI Pipeline

on:
  push:
    branches:
      - main
      - 'phase-*'     # Todas las ramas de fase
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:15-alpine
        env:
          POSTGRES_DB: webdte
          POSTGRES_USER: webdte
          POSTGRES_PASSWORD: webdte_ci
        ports: ['5432:5432']
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
      - uses: actions/checkout@v4

      - name: Build Docker image
        run: docker compose build

      - name: Start services
        run: docker compose up -d

      - name: Wait for app readiness
        run: |
          for i in $(seq 1 30); do
            curl -sf http://localhost:8080/webdte/ && break
            sleep 2
          done

      - name: Run integration tests
        run: npx playwright test
        env:
          BASE_URL: http://localhost:8080

      - name: Stop services
        if: always()
        run: docker compose down -v

Git Tags como Hitos

Fotografiar cada victoria

Cada vez que termines una fase y la valides con tests, crea un tag anotado. Los tags anotados guardan fecha, autor y mensaje — son más ricos que los tags ligeros.

Esto te permite saltar en el tiempo durante la presentación: "Señores del tribunal, volvamos un momento a la v1.0 para ver el desastre que teníamos antes de la migración…"

Crear tag anotadoBash
git tag -a v1.0-docker -m "Fase 1: Entorno inmutable · Dockerfile + Postgres"
git tag -a v2.0-api-rest -m "Fase 2: Desacople HTML/Servlet · REST puro"
git tag -a v3.0-3layers -m "Fase 3: Clean Code · 3 capas FMI"
git tag -a v4.0-final -m "Fase 4: E2E completo · Versión premium"
git push origin --tags
🔐

Variables de Entorno

Cero secretos en el código

No metas la URL de Postgres a fuego en el código. La conexión con stringtype=unspecified viaja como variable de entorno en Docker. En DigitalOcean solo cambias la variable y la app se conecta a la BD de producción sin tocar una línea.

.env (NO comitear — incluir en .gitignore)ENV
DB_URL=jdbc:postgresql://localhost:5432/webdte?stringtype=unspecified
DB_USER=webdte
DB_PASS=webdte_dev_password

# En DigitalOcean: se configuran como App Variables
# DB_URL=jdbc:postgresql://db-host.ondigitalocean.com:25060/webdte?...
📡

Status Codes HTTP Correctos

El "Capa a Capa" real

El código de 2005 solía devolver siempre un 200 aunque hubiera un error catastrófico dentro de la página HTML. En la fase de desacople, los Servlets devuelven códigos semánticos:

CódigoCuándoEjemplo WebDTE
200 OKGET exitosoListar cuentas, consultar expediente
201 CreatedPOST que crea recursoAlta de cuenta exitosa
400 Bad RequestValidación fallidaEmail inválido, DNI malformado
404 Not FoundRecurso no existeExpediente no encontrado
409 ConflictDuplicadoUsername ya registrado
500 InternalError del servidorFallo de conexión a BD

GitHub Actions

CI como red de seguridad

Un pipeline mínimo que ejecute los tests en cada push a rama de fase. Ver los "checks" en verde antes de desplegar en DigitalOcean da seguridad al desarrollador y evidencia de rigor al tribunal. El workflow completo está en la pestaña CI/CD.

Workflow Completo — Fase a Fase
Copia-pega secuencial: estos comandos te llevan desde crear la rama hasta tener el tag en producción.
Fase 1 — Docker + PostgresBash
# ── 1. Crear rama de fase ──
git checkout main
git pull origin main
git checkout -b phase-01-docker

# ── 2. Desarrollar (commits atómicos) ──
git add Dockerfile docker-compose.yml .env.example
git commit -m "feat(docker): add legacy WAR containerization"

git add sql/init.sql
git commit -m "feat(db): add Postgres 15 with init schema"

# ── 3. Validar localmente ──
docker compose up --build -d
curl -sf http://localhost:8080/webdte/   # ← debe responder
docker compose down

# ── 4. Push y crear PR ──
git push -u origin phase-01-docker
# → Abrir PR en GitHub: phase-01-docker → main
# → GitHub Actions ejecuta tests automáticamente

# ── 5. Merge + Tag ──
git checkout main
git merge --no-ff phase-01-docker   # --no-ff preserva la historia
git tag -a v1.0-docker -m "Fase 1 completada: entorno inmutable"
git push origin main --tags

# ── 6. Limpiar rama (opcional) ──
git branch -d phase-01-docker
git push origin --delete phase-01-docker
Despliegue en Droplet
deploy.sh — Script de despliegueBash
#!/bin/bash
# deploy.sh · Ejecutar en el Droplet de DigitalOcean
set -e

echo "🔄 Pulling latest from main..."
cd /opt/webdte
git pull origin main

echo "🐳 Rebuilding containers..."
docker compose down
docker compose build --no-cache
docker compose up -d

echo "⏳ Waiting for app readiness..."
for i in $(seq 1 30); do
  curl -sf http://localhost:8080/webdte/ && break
  sleep 2
done

echo "✅ Deploy complete. Running containers:"
docker compose ps
