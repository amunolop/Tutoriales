02 — Patrones por contexto

Universales, Frontend y Backend

Selecciona el contexto y el lenguaje. Cada patrón incluye explicación, cuándo usarlo, tip de entrevista y código en JS, Python y Java.

Creacional

Singleton

Garantiza que una clase tenga una única instancia y proporciona un punto de acceso global a ella.

▶
Cuándo usarlo

Conexiones a base de datos, configuración de app, loggers, cachés, pools de conexiones. Cuando necesitas exactamente UNA instancia compartida.

💡 Tip de entrevista

Menciona que en JS los módulos ya son singletons (se cachean al importar). En Java, habla de thread-safety y el double-checked locking. En Python, menciona el patrón con __new__ o módulos.

// JavaScript — Singleton con módulo ES
class Database {
  constructor() {
    if (Database.instance) return Database.instance;
    this.connection = "db://localhost:5432";
    Database.instance = this;
  }
}

const db1 = new Database();
const db2 = new Database();
console.log(db1 === db2); // true ✅
# Python — Singleton con __new__
class Database:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.connection = "db://localhost:5432"
        return cls._instance

db1 = Database()
db2 = Database()
print(db1 is db2)  # True ✅
// Java — Singleton thread-safe con enum
public enum Database {
    INSTANCE;

    private String connection = "db://localhost:5432";

    public String getConnection() {
        return connection;
    }
}
// Uso: Database.INSTANCE.getConnection()
// El enum garantiza una sola instancia (thread-safe gratis)
Creacional

Factory Method

Define una interfaz para crear objetos, pero deja que las subclases decidan qué clase instanciar.

▶
Cuándo usarlo

Cuando no sabes de antemano qué tipo de objeto necesitas crear. Procesadores de pago, parsers de distintos formatos, creación de elementos UI según plataforma.

💡 Tip de entrevista

La clave es que el código cliente no usa new directamente — delega la creación. Esto cumple el Open/Closed Principle (SOLID): puedes añadir nuevos tipos sin modificar código existente.

// JavaScript — Factory de notificaciones
class EmailNotification {
  send(msg) { console.log(`📧 Email: ${msg}`); }
}
class SMSNotification {
  send(msg) { console.log(`📱 SMS: ${msg}`); }
}
class PushNotification {
  send(msg) { console.log(`🔔 Push: ${msg}`); }
}

function createNotification(type) {
  const map = {
    email: EmailNotification,
    sms: SMSNotification,
    push: PushNotification,
  };
  return new map[type]();
}

const notif = createNotification("sms");
notif.send("Hola!"); // 📱 SMS: Hola!
# Python — Factory de notificaciones
from abc import ABC, abstractmethod

class Notification(ABC):
    @abstractmethod
    def send(self, msg): ...

class EmailNotification(Notification):
    def send(self, msg): print(f"📧 Email: {msg}")

class SMSNotification(Notification):
    def send(self, msg): print(f"📱 SMS: {msg}")

def create_notification(type_: str) -> Notification:
    factories = {"email": EmailNotification, "sms": SMSNotification}
    return factories[type_]()

notif = create_notification("sms")
notif.send("Hola!")  # 📱 SMS: Hola!
// Java — Factory de notificaciones
interface Notification {
    void send(String msg);
}

class EmailNotification implements Notification {
    public void send(String msg) {
        System.out.println("📧 Email: " + msg);
    }
}

class NotificationFactory {
    public static Notification create(String type) {
        return switch (type) {
            case "email" -> new EmailNotification();
            case "sms"   -> new SMSNotification();
            default -> throw new IllegalArgumentException();
        };
    }
}
Comportamiento

Observer

Define una dependencia uno-a-muchos: cuando un objeto cambia de estado, todos sus dependientes son notificados automáticamente.

▶
Cuándo usarlo

Eventos del DOM, sistemas de eventos, notificaciones en tiempo real, data binding, pub/sub. Es la base de la reactividad en frameworks frontend.

💡 Tip de entrevista

Relaciona con addEventListener en JS, signals en frameworks modernos, o @EventListener en Spring. Si mencionas que React useState es un observer simplificado, sumas puntos.

// JavaScript — EventEmitter simple
class EventEmitter {
  constructor() { this.listeners = {}; }

  on(event, callback) {
    (this.listeners[event] ??= []).push(callback);
  }

  emit(event, data) {
    this.listeners[event]?.forEach(cb => cb(data));
  }
}

const store = new EventEmitter();
store.on("userLogin", user => console.log(`👋 ${user}`));
store.on("userLogin", user => analytics(user));
store.emit("userLogin", "Ana"); // notifica a ambos
# Python — Observer
class EventEmitter:
    def __init__(self):
        self._listeners: dict[str, list] = {}

    def on(self, event: str, callback):
        self._listeners.setdefault(event, []).append(callback)

    def emit(self, event: str, data=None):
        for cb in self._listeners.get(event, []):
            cb(data)

store = EventEmitter()
store.on("login", lambda u: print(f"👋 {u}"))
store.emit("login", "Ana")
// Java — Observer con interfaces
interface Observer {
    void update(String event, Object data);
}

class EventEmitter {
    private Map<String, List<Observer>> listeners = new HashMap<>();

    public void on(String event, Observer obs) {
        listeners.computeIfAbsent(event, k -> new ArrayList<>()).add(obs);
    }

    public void emit(String event, Object data) {
        listeners.getOrDefault(event, List.of())
                 .forEach(obs -> obs.update(event, data));
    }
}
Comportamiento

Strategy

Define una familia de algoritmos, encapsula cada uno y los hace intercambiables. El cliente elige cuál usar en runtime.

▶
Cuándo usarlo

Distintos métodos de pago, algoritmos de ordenación, validaciones, estrategias de caché, cálculos de descuento, compresión de archivos.

💡 Tip de entrevista

Es el patrón anti-if/else gigante. En vez de un switch con 10 casos, cada caso es una estrategia independiente. Menciona que en JS/Python las funciones de primera clase lo hacen trivial (pasas la función directamente).

// JavaScript — Strategy con funciones
const strategies = {
  creditCard: (amount) => console.log(`💳 Cobrado ${amount}€`),
  paypal:     (amount) => console.log(`🅿️ PayPal ${amount}€`),
  crypto:     (amount) => console.log(`₿ Crypto ${amount}€`),
};

function checkout(amount, method) {
  strategies[method](amount); // sin if/else
}

checkout(99, "paypal"); // 🅿️ PayPal 99€
# Python — Strategy con callable
from typing import Callable

def credit_card(amount): print(f"💳 Cobrado {amount}€")
def paypal(amount):      print(f"🅿️ PayPal {amount}€")
def crypto(amount):      print(f"₿ Crypto {amount}€")

strategies = {"card": credit_card, "paypal": paypal, "crypto": crypto}

def checkout(amount: float, method: str):
    strategies[method](amount)

checkout(99, "paypal")  # 🅿️ PayPal 99€
// Java — Strategy con interfaces
interface PaymentStrategy {
    void pay(double amount);
}

class CreditCard implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("💳 Cobrado " + amount + "€");
    }
}

class Checkout {
    private PaymentStrategy strategy;
    public Checkout(PaymentStrategy s) { this.strategy = s; }
    public void process(double amt) { strategy.pay(amt); }
}
// new Checkout(new CreditCard()).process(99);
Estructural

Decorator

Añade responsabilidades a un objeto dinámicamente, sin modificar su clase. Alternativa flexible a la herencia.

▶
Cuándo usarlo

Middleware en Express/Django, decoradores Python (@login_required), HOCs en React, logging, caché, validación, compresión. Cada "capa" añade funcionalidad.

💡 Tip de entrevista

Los decoradores de Python (@) son literalmente este patrón. En JS, los middlewares de Express (app.use()) son decorators en cadena. Mencionar esto demuestra que entiendes el patrón más allá de la teoría.

// JavaScript — Decorar funciones (middleware)
function withLogging(fn) {
  return function(...args) {
    console.log(`⏱ Llamando ${fn.name}`);
    const result = fn(...args);
    console.log(`✅ Resultado: ${result}`);
    return result;
  };
}

function withCache(fn) {
  const cache = new Map();
  return function(...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) return cache.get(key);
    const result = fn(...args);
    cache.set(key, result);
    return result;
  };
}

const calculate = withLogging(withCache((x) => x * 2));
# Python — Decoradores nativos
import functools, time

def timer(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        print(f"⏱ {func.__name__}: {time.time()-start:.3f}s")
        return result
    return wrapper

def retry(max_attempts=3):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for i in range(max_attempts):
                try: return func(*args, **kwargs)
                except Exception: pass
        return wrapper
    return decorator

@timer
@retry(max_attempts=3)
def fetch_data(url): ...
// Java — Decorator clásico
interface DataSource {
    String read();
}

class FileDataSource implements DataSource {
    public String read() { return "raw data"; }
}

class EncryptionDecorator implements DataSource {
    private final DataSource wrapped;
    public EncryptionDecorator(DataSource ds) { this.wrapped = ds; }
    public String read() {
        return decrypt(wrapped.read()); // añade comportamiento
    }
}
// new EncryptionDecorator(new FileDataSource()).read()
Estructural

Adapter

Convierte la interfaz de una clase en otra que el cliente espera. Permite que clases incompatibles trabajen juntas.

▶
Cuándo usarlo

Integrar APIs de terceros, legacy code, normalizar datos de distintas fuentes, abstraer librerías para que sean intercambiables.

// JS — Adapter para APIs con distinto formato
// API vieja devuelve: { first_name, last_name }
// Tu app espera:     { fullName }

class UserAdapter {
  adapt(legacyUser) {
    return {
      fullName: `${legacyUser.first_name} ${legacyUser.last_name}`,
      email: legacyUser.email_address,
    };
  }
}

const adapter = new UserAdapter();
const user = adapter.adapt({
  first_name: "Ana", last_name: "García",
  email_address: "ana@mail.com"
}); // { fullName: "Ana García", email: "ana@mail.com" }
# Python — Adapter para librería de terceros
class LegacyPrinter:
    def print_old(self, text):
        print(f"[OLD] {text}")

class PrinterAdapter:
    def __init__(self, legacy: LegacyPrinter):
        self._legacy = legacy

    def print(self, text):  # interfaz que tu app espera
        self._legacy.print_old(text)

printer = PrinterAdapter(LegacyPrinter())
printer.print("Hola")  # [OLD] Hola
// Java — Adapter clásico
interface ModernPrinter {
    void print(String text);
}

class LegacyPrinter {
    void printOld(String t) { System.out.println("[OLD] " + t); }
}

class PrinterAdapter implements ModernPrinter {
    private final LegacyPrinter legacy;
    public PrinterAdapter(LegacyPrinter lp) { this.legacy = lp; }
    public void print(String t) { legacy.printOld(t); }
}
Componente

Container / Presentational

Separa la lógica de datos (container) de la UI pura (presentational). El container maneja estado y API calls; el presentational solo recibe props y renderiza.

▶
Cuándo usarlo

Componentes que mezclan fetch de datos con renderizado. Separa para poder reutilizar la UI con distintas fuentes de datos y testear más fácil.

💡 Tip de entrevista

Aunque Dan Abramov (creador de Redux) dijo que hoy prefiere hooks a este patrón, sigue siendo válido conceptualmente. Los custom hooks son el container moderno.

// Container — lógica
function useUsers() {
  const [users, setUsers] = useState([]);
  useEffect(() => {
    fetch("/api/users").then(r => r.json()).then(setUsers);
  }, []);
  return users;
}

// Presentational — solo UI
function UserList({ users }) {
  return (
    <ul>
      {users.map(u => <li key={u.id}>{u.name}</li>)}
    </ul>
  );
}

// Uso combinado
function UsersPage() {
  const users = useUsers();          // container (hook)
  return <UserList users={users} />; // presentational
}
React

Custom Hook

Extrae lógica reutilizable con estado en una función use*. Es el patrón de composición nativo de React moderno.

▶
💡 Tip de entrevista

Los hooks reemplazaron HOCs y Render Props como patrón principal de reutilización. Son más simples, componibles y fáciles de testear. Siempre di que prefieres hooks sobre HOCs.

// Custom hook reutilizable
function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    const stored = localStorage.getItem(key);
    return stored ? JSON.parse(stored) : initialValue;
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue];
}

// Uso — misma API que useState
const [theme, setTheme] = useLocalStorage("theme", "light");
const [lang, setLang] = useLocalStorage("lang", "es");

Compound Components

Componentes que trabajan juntos compartiendo estado implícitamente. Como <select> y <option> en HTML — no funcionan solos.

▶
Cuándo usarlo

Tabs, acordeones, menús, formularios complejos. Cuando quieres una API declarativa y flexible para el consumidor del componente.

<Tabs defaultTab="home">
  <Tabs.List>
    <Tabs.Tab id="home">Inicio</Tabs.Tab>
    <Tabs.Tab id="settings">Config</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel id="home">Contenido inicio</Tabs.Panel>

// Implementación con Context
const TabsContext = createContext();

function Tabs({ children, defaultTab }) {
  const [active, setActive] = useState(defaultTab);
  return (
    <TabsContext.Provider value={{ active, setActive }}>
      {children}
    </TabsContext.Provider>
  );
}

Tabs.Tab = ({ id, children }) => {
  const { active, setActive } = useContext(TabsContext);
  return <button onClick={() => setActive(id)}>{children}</button>;
};

  login(credentials: Credentials): Observable<User> {
    return this.http.post<User>('/api/login', credentials)
      .pipe(tap(user => this.user = user));
  }
}

@Component({ selector: 'app-login', template: '...' })
class LoginComponent {
  // Angular inyecta AuthService automáticamente
  constructor(private auth: AuthService) {}

  onSubmit() {
    this.auth.login(this.form.value).subscribe();
  }
}

Vue 3

Composables (equivalente a Custom Hooks)

Funciones use* que encapsulan lógica reactiva reutilizable con la Composition API.

▶ 
// composables/useFetch.js
import { ref, watchEffect } from 'vue';

export function useFetch(url) {
  const data = ref(null);
  const error = ref(null);
  const loading = ref(true);

  watchEffect(async () => {
    try {
      const res = await fetch(url.value);
      data.value = await res.json();
    } catch (e) { error.value = e; }
    finally { loading.value = false; }
  });

  return { data, error, loading };
}

// En componente
const { data: users, loading } = useFetch(ref('/api/users'));

Arquitectural

Flux / Redux (Store unidireccional)

Estado global centralizado con flujo unidireccional: Action → Dispatcher → Store → View. Predecible y debuggeable.

▶
💡 Tip de entrevista

Menciona que hoy se prefieren alternativas más ligeras como Zustand (React), Pinia (Vue) o signals (Angular). Redux sigue siendo relevante pero la tendencia es hacia menos boilerplate.

// Flujo unidireccional simplificado

// 1. ESTADO (Store)
let state = { count: 0, items: [] };

// 2. ACTIONS (qué pasó)
const increment = { type: "INCREMENT" };
const addItem  = { type: "ADD_ITEM", payload: "Café" };

// 3. REDUCER (cómo cambia el estado)
function reducer(state, action) {
  switch(action.type) {
    case "INCREMENT":
      return { ...state, count: state.count + 1 };
    case "ADD_ITEM":
      return { ...state, items: [...state.items, action.payload] };
    default: return state;
  }
}

// 4. DISPATCH (View → Action → Reducer → New State → View)
state = reducer(state, increment); // { count: 1 }
Estructural

Module Pattern

Encapsula código en módulos con interfaz pública y datos privados. Es la base de los módulos ES (import/export).

▶ 
// Módulo ES moderno — el archivo ES el módulo

// userService.js
const API_URL = "/api/users";  // privado (no exportado)
let cache = null;                // privado

export async function getUsers() {  // público
  if (cache) return cache;
  cache = await fetch(API_URL).then(r => r.json());
  return cache;
}

export function clearCache() {     // público
  cache = null;
}

// Solo getUsers y clearCache son accesibles
// API_URL y cache están encapsulados
Express

Middleware Pattern

Cadena de funciones que procesan la request secuencialmente. Cada middleware puede modificar req/res, o pasar al siguiente. Es el Decorator pattern aplicado a HTTP.

▶
💡 Tip de entrevista

Explica que es una cadena de responsabilidad (Chain of Responsibility): cada middleware decide si procesa, modifica o pasa la request. El orden importa.

// Cada middleware: (req, res, next) => { ... next() }

// 1. Logger
app.use((req, res, next) => {
  console.log(`${req.method} ${req.url}`);
  next(); // pasa al siguiente
});

// 2. Auth
function authMiddleware(req, res, next) {
  const token = req.headers.authorization;
  if (!token) return res.status(401).json({ error: "No token" });
  req.user = verifyToken(token); // decora req
  next();
}

// 3. Aplicar a rutas específicas
app.get("/api/profile", authMiddleware, (req, res) => {
  res.json(req.user); // req.user ya existe
});
Node.js

Repository Pattern

Abstrae el acceso a datos detrás de una interfaz. El servicio no sabe si los datos vienen de PostgreSQL, MongoDB o un JSON. Facilita testing y cambiar de BD.

▶ 
// userRepository.js — abstrae la BD
class UserRepository {
  constructor(db) { this.db = db; }

  async findById(id) {
    return this.db.query("SELECT * FROM users WHERE id = $1", [id]);
  }
  async create(data) {
    return this.db.query(
      "INSERT INTO users (name, email) VALUES ($1, $2)",
      [data.name, data.email]
    );
  }
}

// userService.js — no sabe qué BD hay debajo
class UserService {
  constructor(userRepo) { this.repo = userRepo; }

  async getUser(id) {
    const user = await this.repo.findById(id);
    if (!user) throw new Error("Not found");
    return user;
  }
}

// En tests: new UserService(mockRepo) → fácil
Django / FastAPI

Middleware (Django) / Depends (FastAPI)

Django usa middleware como clases; FastAPI usa Depends() para inyección de dependencias, que también actúa como middleware funcional.

▶ 
# FastAPI — Depends como inyección + middleware
from fastapi import Depends, FastAPI, HTTPException

app = FastAPI()

# Dependencia reutilizable (como middleware)
async def get_current_user(token: str = Header()):
    user = verify_token(token)
    if not user:
        raise HTTPException(status_code=401)
    return user

# Dependencia que depende de otra
async def get_db():
    db = SessionLocal()
    try: yield db
    finally: db.close()

@app.get("/profile")
async def profile(
    user = Depends(get_current_user),
    db = Depends(get_db)
):
    return db.query(User).filter_by(id=user.id).first()
# Django — Middleware como clase
class RequestTimingMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        start = time.time()
        response = self.get_response(request)  # siguiente
        duration = time.time() - start
        response["X-Request-Duration"] = str(duration)
        return response

# settings.py
MIDDLEWARE = [
    "myapp.middleware.RequestTimingMiddleware",
    "django.middleware.security.SecurityMiddleware",
    ...
]

Spring

Dependency Injection + IoC Container

Spring gestiona la creación y ciclo de vida de objetos (beans). Tú declaras qué necesitas; Spring lo inyecta. Es el corazón del framework.

▶
💡 Tip de entrevista

Menciona la inversión de control (IoC): tú no creas objetos con new, el contenedor lo hace. Esto facilita testing (inyectar mocks), desacopla componentes y permite cambiar implementaciones sin tocar código cliente.

// Repository
@Repository
public interface UserRepository
    extends JpaRepository<User, Long> {
  Optional<User> findByEmail(String email);
}

// Service — Spring inyecta el Repository
@Service
public class UserService {
    private final UserRepository repo;

    public UserService(UserRepository repo) {
        this.repo = repo; // inyectado por Spring
    }

    public User register(UserDTO dto) {
        repo.findByEmail(dto.email())
            .ifPresent(u -> { throw new ConflictException(); });
        return repo.save(new User(dto));
    }
}

// Controller — Spring inyecta el Service
@RestController
@RequestMapping("/api/users")
public class UserController {
    private final UserService service;

    public UserController(UserService s) { this.service = s; }

    @PostMapping
    public User create(@RequestBody UserDTO dto) {
        return service.register(dto);
    }
}
Estructural

DTO (Data Transfer Object)

Objeto simple para transferir datos entre capas. Separa lo que recibe el API de lo que guarda la BD. Seguridad y limpieza.

▶ 
// Lo que el cliente envía (sin id, sin password hash)
public record CreateUserDTO(
    String name,
    String email,
    String password  // texto plano
) {}

// Lo que el cliente recibe (sin password)
public record UserResponseDTO(
    Long id,
    String name,
    String email
) {}

// Entidad de BD (tiene todo)
@Entity
public class User {
    @Id @GeneratedValue
    private Long id;
    private String name;
    private String email;
    private String passwordHash; // nunca sale al API
}

Arquitectural

MVC (Model-View-Controller)

Separa datos (Model), presentación (View) y lógica de coordinación (Controller). Es el patrón arquitectural más usado en backend web.

▶
💡 Tip de entrevista

Django usa MTV (Model-Template-View) que es MVC renombrado. Spring MVC es MVC clásico. Express no es MVC por defecto pero se puede estructurar así. Menciona que en APIs REST la "View" es el JSON response.

// Estructura MVC típica en backend

📁 src/
├── models/        ← Model (datos + BD)
│   └── User.js         esquema, validaciones, queries
│
├── controllers/   ← Controller (recibe HTTP, orquesta)
│   └── UserController.js   parsea req, llama service, devuelve res
│
├── services/      ← Lógica de negocio (opcional, recomendado)
│   └── UserService.js      reglas, validaciones, cálculos
│
├── routes/        ← Mapeo URL → Controller
│   └── userRoutes.js       GET /users → UserController.list
│
└── views/         ← View (JSON response / templates)
    └── En APIs REST, el "view" es la respuesta JSON

// Flujo: Request → Route → Controller → Service → Model → Response
Arquitectural

CQRS (Command Query Responsibility Segregation)

Separa las operaciones de lectura (Query) de las de escritura (Command). Cada una puede tener su propio modelo, BD e incluso servicio.

▶
Cuándo usarlo

Sistemas con alta carga donde leer y escribir tienen requerimientos muy distintos. E-commerce (miles leen catálogo, pocos compran), dashboards analíticos, sistemas financieros.

💡 Tip de entrevista

No siempre se necesita CQRS. Menciona que añade complejidad y solo vale la pena cuando leer y escribir tienen patrones de acceso muy diferentes. Muchas apps funcionan bien con un solo modelo.

// Sin CQRS — un solo modelo para todo
UserService.getUser(id)         // lectura
UserService.updateUser(id, data) // escritura
// Mismo modelo, misma BD, mismo servicio

// ─────────────────────────────────────

// Con CQRS — separado

// QUERIES (lectura) — optimizado para leer rápido
UserQueryService.getUser(id)     // puede leer de caché/read replica
UserQueryService.search(filters) // puede usar Elasticsearch

// COMMANDS (escritura) — optimizado para consistencia
UserCommandService.create(data)  // escribe en BD principal
UserCommandService.update(data)  // validaciones estrictas

// La BD de lectura se sincroniza con la de escritura
// (eventual consistency via eventos)
