DIAGRAMA DEL SISTEMA

El sistema FMI v4.5 implementa una orquestación jerárquica multi-agente con 5 fases. La petición de migración entra al Supervisor de Orquestación Global, que invoca la Pre-Scan Tool para inventariar el legacy, y luego pasa el control al Arquitecto (Opus) y al Capataz/Dispatcher (Sonnet). Estos coordinan la ejecución paralela en batch de Workers con contexto mínimo (Caveman Lite), validados al final por Smoke Check.

Sistema FMI v4.5 · Arquitectura jerárquica multi-agente
DOS NIVELES, UN PROPÓSITO

El sistema se compone de dos piezas que operan en niveles diferentes. V6M es el cerebro: un orquestador que planifica toda la migración en N fases. V5M es el brazo: un motor de ejecución que recibe instrucciones y genera código en paralelo con tests-first. V6M llama a V5M una vez por cada fase.

V6M — Orquestador (Cerebro)
Meta-Architect (Opus) planifica la migración completa. SCAN del legacy → decide fases → define contratos entre fases → ejecuta V5M por fase → certifica resultado final. Estrategia: Consumer-Driven Contract (frontend primero, backend después).
V5M — Motor de Ejecución (Brazo)
Architect (Opus) genera Blueprint + DIGEST + TEST SPECS → Oleada 1 de Test Workers escribe tests a disco → GATE bloqueante verifica coherencia → Oleada 2 de Code Workers lee tests y escribe código → Smoke (Haiku) verifica mecánicamente.

PRINCIPIOS CLAVE
TDD-as-Spec
Tests se escriben ANTES del código. Actúan como especificación ejecutable. Si el código no los satisface, el código está mal — nunca el test.
Consumer-Driven Contract
Frontend primero → SCAN extrae contratos API → Backend implementa exactamente esos contratos. Elimina el bug clásico de JSON shape mismatch.
SHARED CONTRACTS
Vocabulario cerrado que TODOS los workers respetan: nombres de entidades, firmas de constructores, paquetes canónicos, mutabilidad de DTOs. Libertad total dentro, contratos fuera.
Knowledge Injection
Bugs conocidos del legacy inyectados como reglas: nombreProfesor (no getFormatos), titulacion (no especialidad), "year" entrecomillado. Previenen errores antes de que ocurran.
Caveman Lite
Cada worker opera con contexto mínimo aislado. No conoce a otros workers. Solo ve su TEST SPEC, su DIGEST y su carpeta. Tokens optimizados, sin ruido.
GATE Bloqueante
Entre Oleada 1 y Oleada 2. Si los tests no son coherentes entre sí, ABORT antes de gastar tokens en code workers. 7 checks mecánicos derivados del post-mortem M16.

Por qué Subagents y no contextos en CLAUDE.md Un subagent en Claude Code recibe su propia ventana de contexto, su propio modelo, y puede tener tools restringidas. Si metieras los prompts de los workers en CLAUDE.md tendrías: (1) todo el prompt de Architect, TestWorker y CodeWorker cargado en CADA conversación aunque solo necesites debug, (2) un solo modelo (no podrías usar Haiku para Smoke), (3) los workers se "verían" entre sí en el contexto — adiós caveman lite.
Por qué Skills y no Subagent monolítico Podrías meter todo el flujo V5M en un único subagent gigante, pero perderías la modularidad: el Architect quiere Opus, los Workers quieren Sonnet, el Smoke quiere Haiku. Un Skill describe el flujo y delega cada paso a un subagent específico con su modelo óptimo. El Skill es el director, los Subagents son los músicos.

V6M: ORQUESTADOR MULTI-FASE

V6M es el nivel superior. El Meta-Architect (Opus) recibe un objetivo de migración y decide cuántas fases, en qué orden, y qué contratos fluyen entre ellas. Cada fase se ejecuta como una instancia independiente de V5M.

V6M · Loop multi-fase con SCAN intermedio para Consumer-Driven Contract
FLUJO DETALLADO V6M
0
SCAN Legacy (no cuenta como fase V5M)
Sonnet workers leen código fuente en paralelo. Reportan: ficheros, tipos, SQL, dependencias, complejidad. Output: INVENTARIO estructurado. 6 ficheros/worker (lectura más rápida que escritura). Coste: ~$1.17 · ~3 min.
1
Meta-Architect (Opus) — Planificación
Lee inventario + objetivo + constraints. Decide cuántas fases (≤4 recomendado), scope de cada una, orden por dependencias, contratos entre fases, y knowledge injection específico por fase. Output: PLAN DE FASES.
2
Loop de Fases (secuencial)
Para cada fase: Meta-Architect pasa instrucciones a V5M (objetivo, archivos, contratos, KI) → V5M ejecuta fase completa (Architect→TW→GATE→CW→Smoke) → V5M reporta resultado → Meta-Architect ajusta siguiente fase si necesario.
⊕
SCAN Intermedio (si Front→Back)
Entre fase frontend y backend. Sonnet workers leen services/*.js generados, extraen endpoints exactos: method, path, request body, response fields. Output: contratos API que el backend implementa tal cual. Coste: ~$0.30 · ~1 min.
3
Certificación
Meta-Architect consolida: contratos alineados (13/13 endpoints), tests generados (50 ficheros), smoke totales (28/28), coste real vs estimado, coherencia test↔code.

V5M: MOTOR DE EJECUCIÓN PARALELO

V5M recibe instrucciones de V6M (o de un humano) y ejecuta una fase completa de generación de código. Su innovación es el flujo de dos oleadas: primero tests, después código. El GATE entre ambas oleadas es la pieza crítica que garantiza coherencia.

LOS 4 ARTEFACTOS DEL ARCHITECT

El Architect (Opus) es invocado UNA vez al inicio de cada V5M. Su output son 4 artefactos en un único markdown que se escribe a disco (_logs/.../01_architect_blueprint.md) y se distribuye a los workers de ambas oleadas.

1. Blueprint
Agrupación por afinidad funcional. Cada worker tiene columna ESCRIBE con carpetas que le pertenecen exclusivamente. Split si grupo > FILES_PER_WORKER. Merge si grupo = 1 trivial.
2. DIGEST (~2K tokens)
Patrones extraídos de la referencia: arquitectura, seguridad, API contract, frontend. Workers reciben DIGEST, NO leen referencia directamente. Ahorro: ~15% tokens.
3. SHARED CONTRACTS
Sección dentro del DIGEST obligatoria para TODOS los workers. Entity names, constructor signatures, mutabilidad, repos, DTOs, paquetes. Libertad total en implementación interna.
4. TEST SPECS (~500 tok/grupo)
Contratos compactos por grupo. NO archivos reales — solo specs que los Test Workers materializan como JUnit/Jest. Constructors, method sigs, return types, field names.

IMPLEMENTACIÓN DEL GATE

#!/bin/bash
# gate.sh — Run after Oleada 1, before Oleada 2

set -e
LOGS="_logs/v5m_$(date +%Y-%m-%d_%H%M)_runXX"
EXPECTED_TESTS=39

# G1: count test files
COUNT=$(find tests/ -name "*Test.java" -o -name "*Test.js" | wc -l)
[ "$COUNT" -ge "$EXPECTED_TESTS" ] || { echo "G1 FAIL"; exit 1; }

# G2: forbidden imports
if grep -r "domain.repositories" tests/; then
  echo "G2 FAIL: forbidden import domain.repositories"; exit 1
fi

# G5: Optional usage
RAW=$(grep -rE "thenReturn\(\w+\)" tests/usecases/ | grep -v "Optional" | wc -l)
[ "$RAW" -eq 0 ] || { echo "G5 FAIL: $RAW raw thenReturn"; exit 1; }

echo "GATE PASS"
DOS OLEADAS, REGLAS DIFERENTES

Los workers operan en dos oleadas con reglas distintas. Test Workers reciben TEST SPECS y las materializan como código JUnit/Jest. Code Workers reciben los tests escritos por los TWs y deben generar código que los satisfaga. Ambos tipos están sujetos a la regla de aislamiento estricto.

PROMPT — TEST WORKER
Prompt · Test Worker (Sonnet)
Genera tests JUnit 4 / Jest que especifiquen los contratos de tu grupo.
Recibes TEST SPEC + DIGEST (incluye SHARED CONTRACTS).
Output: archivos reales en tests/{tipo}/

Constraints:

Migración legacy Java Servlets (2005) → arquitectura hexagonal moderna,
