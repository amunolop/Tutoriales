Un contenedor es una unidad estándar de software que empaqueta código y todas sus dependencias, garantizando ejecución consistente. Es portable entre entornos y comparte el kernel del sistema operativo anfitrión.

▸ Ventajas de la contenerización
⚡
Lightweight
Contenedores pesan MB vs VMs que pesan GB. Arranque en segundos vs minutos.
🔄
Consistencia
Funciona igual en dev, staging y producción. Elimina el "en mi máquina funciona".
📦
Portabilidad
Un contenedor corre en cualquier máquina con Docker: laptop, servidor, nube.
🔀
Escalabilidad
Réplicas instantáneas. Escala horizontalmente con un comando o automáticamente.
🏗️
Microservicios
Cada servicio en su propio contenedor. Deploys independientes y aislamiento de fallos.
🚀
Velocidad de desarrollo
Entornos reproducibles al instante. CI/CD simplificado con imágenes versionadas.

Objeto
Función
Pod
Unidad mínima de despliegue. 1+ contenedores que comparten red y almacenamiento. Nunca se crean directamente en producción. Atómico
Deployment
Gestiona pods stateless. Rolling updates, rollbacks, escalado. Crea ReplicaSets internamente. ★ Más usado
Service
IP estable + DNS interno + load balancing para acceder a pods. Tipos: ClusterIP, NodePort, LoadBalancer. Network
ConfigMap
Datos de configuración no sensibles en key-value. Se inyectan como env vars o ficheros montados. Config
Secret
Datos sensibles: passwords, tokens, certificados. Base64 por defecto (no es cifrado). Sensible
Ingress
Expone servicios HTTP/S al exterior con routing por host/path y TLS. Necesita un Ingress Controller. HTTP
ReplicaSet
Mantiene N réplicas de un pod. Recurso interno del Deployment, casi nunca se usa directamente. Interno
StatefulSet
Apps stateful: bases de datos, colas. Identidad estable (pod-0, pod-1), orden de arranque, PVs por pod. Stateful
DaemonSet
Ejecuta exactamente un pod por nodo. Agentes de logs (Fluentd), métricas (Node Exporter), CNI. Cada nodo
Job / CronJob
Job: ejecuta hasta completarse (migraciones, batch). CronJob: programado con expresión cron. Batch
El Control Plane es el cerebro del cluster. Toma todas las decisiones: dónde ejecutar pods, qué hacer si un nodo cae, cómo reconciliar estado deseado vs real.
kube-apiserver
▸
Puerta de entrada al cluster. Toda comunicación pasa por aquí
▸
API REST que expone todos los recursos de Kubernetes
▸
Valida y autentica cada request (RBAC, tokens, certificados)
▸
Persiste el estado en etcd tras validar
▸
Escalable horizontalmente con múltiples réplicas
kube-scheduler
▸
Decide en qué nodo se ejecutará cada pod pendiente
▸
Evalúa recursos, afinidad, taints/tolerations, spread constraints
▸
2 fases: filtrado (nodos válidos) + scoring (mejor nodo)
▸
Solo asigna — el kubelet del nodo hace el trabajo real
kube-controller-manager
▸
Loops de reconciliación: compara estado deseado vs real y corrige
▸
ReplicaSet Controller: mantiene el nº correcto de pods
▸
Node Controller: detecta nodos caídos y reacciona
▸
Endpoint Controller: actualiza endpoints de los Services
etcd
▸
Base de datos key-value distribuida: almacena TODO el estado
▸
Consistencia fuerte (Raft). Quórum: 3 o 5 nodos etcd
▸
Solo el API Server habla con etcd — nunca directamente
▸
Backups obligatorios: si se pierde etcd, se pierde el cluster Crítico
cloud-controller-manager
▸
Integra K8s con APIs del cloud provider (AWS, GCP, Azure)
▸
Gestiona load balancers, rutas de red, nodos cloud
▸
Cuando creas Service type: LoadBalancer → crea el LB real en AWS/GCP
Los Worker Nodes son las máquinas donde se ejecutan tus aplicaciones. Cada nodo tiene tres componentes que cooperan para mantener los pods corriendo.
Componente
Función
kubelet
Agente principal. Recibe instrucciones del API Server sobre qué pods ejecutar. Monitoriza salud de contenedores y reinicia según restartPolicy. ★ Core
kube-proxy
Gestiona reglas de red usando iptables o IPVS. Redirige tráfico al pod correcto según la IP del Service. Load balancing interno. Network
CRI Runtime
Ejecuta contenedores. K8s usa la interfaz CRI. Runtimes: containerd (estándar), CRI-O. Docker fue deprecado en v1.24. containerd
▸ Health Probes y Resources
Health Probes
▸
livenessProbe: ¿está vivo? Falla → reinicia contenedor
▸
readinessProbe: ¿acepta tráfico? Falla → se quita del Service
▸
startupProbe: ¿ha arrancado? Para apps con inicio lento
▸
Tipos: httpGet, tcpSocket, exec
Resources & Limits
▸
requests: mínimo garantizado. Scheduler usa esto para elegir nodo
▸
limits: máximo. CPU → throttle. RAM → OOMKill
▸
LimitRange: defaults por namespace
▸
ResourceQuota: límite total por namespace
Red flat: todos los pods se comunican sin NAT. Services dan IPs estables + DNS. Ingress gestiona tráfico externo. Storage con PV/PVC para persistencia.

IP interna. Default. Solo accesible dentro del cluster. DNS: svc-name.namespace.svc.cluster.local ★ Default
NodePort
Puerto estático (30000-32767) en cada nodo. Accesible desde fuera vía nodeIP:port. Para dev. Dev
LoadBalancer
Crea un LB cloud real (AWS ELB, GCP LB...). Cada Service = un LB = coste. Cloud

▸ Docker Hub — Registro de imágenes
Docker Hub es el registro público de imágenes, AI Models y MCP Servers. Contiene imágenes oficiales (nginx, postgres, redis, alpine...) y comunitarias. Se integra con CI/CD para distribución y versionado automático. Alternativas: Amazon ECR, Google GCR, GitHub Container Registry, Azure ACR.
Kubernetes es declarativo: describes el estado deseado en YAML y K8s converge hacia él. kubectl es tu herramienta para interactuar con el cluster.
▸ Deployment + Service completo
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
spec:
  replicas: 3
  selector:
    matchLabels: { app: api-server }
  template:
    metadata:
      labels: { app: api-server }
    spec:
      containers:
      - name: api
        image: myrepo/api:v2.1.0
        ports: [{ containerPort: 8080 }]
        resources:
          requests: { cpu: "250m", memory: "256Mi" }
          limits:   { cpu: "500m", memory: "512Mi" }
        livenessProbe:
          httpGet: { path: /health, port: 8080 }
        env:
        - { name: DB_HOST, valueFrom: { configMapKeyRef: { name: cfg, key: db-host } } }
        - { name: DB_PASS, valueFrom: { secretKeyRef: { name: sec, key: password } } }
---
apiVersion: v1
kind: Service
metadata: { name: api-svc }
spec:
  selector: { app: api-server }
  ports: [{ port: 80, targetPort: 8080 }]
  type: ClusterIP

Conclusión

Docker aporta portabilidad, consistencia, eficiencia de recursos y velocidad de desarrollo. Kubernetes añade auto-scaling, self-healing, rolling deployments, service discovery y load balancing. Juntos forman la base de la infraestructura moderna: contenerizas con Docker, orquestas con Kubernetes, despliegas en cualquier cloud vendor.
