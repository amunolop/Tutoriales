Kubernetes (K8s) es un sistema de orquestación de contenedores open-source creado por Google. Automatiza el despliegue, el escalado y la gestión de aplicaciones contenerizadas. Su arquitectura se divide en dos grandes bloques: el Control Plane (cerebro) y los Worker Nodes (músculo).

▸ Conceptos clave
⎈
Cluster
Conjunto de máquinas (nodos) que ejecutan aplicaciones contenerizadas gestionadas por Kubernetes.
📦
Pod
Unidad mínima de despliegue. Uno o más contenedores que comparten red y almacenamiento.
🔄
Deployment
Gestiona réplicas de Pods. Rolling updates, rollbacks y escalado declarativo.
🌐
Service
Abstracción de red estable para acceder a un grupo de Pods. IP fija + DNS interno + load balancing.
📂
Volume
Almacenamiento persistente que sobrevive a reinicios de contenedores. PV, PVC y StorageClasses.
🔐
ConfigMap / Secret
Configuración externalizada. ConfigMaps para datos no sensibles, Secrets para credenciales (base64).
📋
Namespace
Aislamiento lógico dentro del cluster. Divide equipos, entornos (dev/staging/prod) o proyectos.
🚪
Ingress
Expone servicios HTTP/S al exterior con reglas de routing, TLS y virtual hosts. Necesita un Ingress Controller.
📏
HPA
Horizontal Pod Autoscaler. Escala pods automáticamente según CPU, memoria o métricas custom.
El Control Plane es el cerebro del cluster. Toma todas las decisiones globales: dónde ejecutar pods, qué hacer si un nodo cae, cómo gestionar el estado deseado vs el estado real.
kube-apiserver
▸
Puerta de entrada al cluster. Toda comunicación pasa por aquí: kubectl, kubelet, dashboard
▸
API REST que expone todos los recursos de Kubernetes (pods, services, deployments...)
▸
Valida y autentica cada request (RBAC, tokens, certificados)
▸
Persiste el estado en etcd después de validar
▸
Escalable horizontalmente: puedes tener múltiples réplicas detrás de un load balancer
kube-scheduler
▸
Decide en qué nodo se ejecutará cada pod pendiente
▸
Evalúa: recursos disponibles (CPU/RAM), afinidad, taints/tolerations, spread constraints
▸
Proceso en 2 fases: filtrado (nodos válidos) y scoring (mejor nodo)
▸
No ejecuta pods — solo asigna. El kubelet del nodo elegido hace el trabajo
kube-controller-manager
▸
Ejecuta loops de reconciliación: compara estado deseado vs real y corrige
▸
ReplicaSet Controller: mantiene el número correcto de réplicas de pods
▸
Node Controller: detecta nodos caídos y reacciona (timeout + eviction)
▸
Job Controller: gestiona pods que deben ejecutarse hasta completarse
▸
Endpoint Controller: actualiza los endpoints de los Services
etcd
▸
Base de datos key-value distribuida: almacena TODO el estado del cluster
▸
Consistencia fuerte (protocolo Raft): se necesitan quórum (3 o 5 nodos etcd)
▸
Solo el API Server se comunica con etcd — nunca directamente
▸
Crítico: si etcd se pierde, se pierde el cluster. Backups obligatorios Crítico
cloud-controller-manager
▸
Integra K8s con APIs del cloud provider (AWS, GCP, Azure)
▸
Gestiona: load balancers cloud, rutas de red, nodos de la cloud
▸
Solo presente en clusters gestionados en la nube (EKS, GKE, AKS)
▸
Cuando creas un Service tipo LoadBalancer, este controller crea el LB real en AWS/GCP

Componente
Función en el nodo
kubelet
Agente principal del nodo. Recibe instrucciones del API Server sobre qué pods ejecutar. Monitoriza la salud de los contenedores y reporta al control plane. Si un contenedor falla, lo reinicia según la restartPolicy. ★ Core
kube-proxy
Gestiona las reglas de red del nodo. Implementa Services de Kubernetes usando iptables o IPVS. Redirige tráfico al pod correcto según la IP del Service. Maneja load balancing interno. Network
Container Runtime
Ejecuta los contenedores. Kubernetes usa la interfaz CRI (Container Runtime Interface). Runtimes soportados: containerd (estándar), CRI-O, y otros. Docker fue deprecado como runtime en v1.24. containerd
cAdvisor
Integrado en kubelet. Recolecta métricas de uso de CPU, memoria, red y disco de cada contenedor. Alimenta al HPA y a herramientas de monitoreo como Prometheus. Métricas
▸ Taints, Tolerations y Node Affinity
Taints & Tolerations
▸
Taint: marca en el nodo que rechaza pods por defecto
▸
Toleration: marca en el pod que le permite ejecutarse en nodos con ese taint
▸
Ejemplo: nodos GPU solo aceptan pods con toleration gpu=true
▸
Efectos: NoSchedule, PreferNoSchedule, NoExecute
Node Affinity
▸
nodeSelector: forma simple — el pod va a nodos con esa label
▸
nodeAffinity: reglas avanzadas con operadores (In, NotIn, Exists...)
▸
requiredDuringScheduling: obligatorio
▸
preferredDuringScheduling: preferencia, no obligación

Para qué sirve
Deployment
El más común. Gestiona pods stateless. Rolling updates, rollbacks, escalado. Crea ReplicaSets internamente. ★ Más usado
ReplicaSet
Mantiene N réplicas de un pod. Casi nunca se usa directamente — es el recurso interno que crea el Deployment. Interno
StatefulSet
Para apps stateful: bases de datos, colas. Garantiza identidad estable (pod-0, pod-1), orden de arranque y volúmenes persistentes por pod. Stateful
DaemonSet
Ejecuta exactamente un pod en cada nodo. Ideal para agentes: logs (Fluentd), métricas (Node Exporter), CNI plugins. Cada nodo
Job
Ejecuta un pod hasta que se complete con éxito. Para tareas batch, migraciones de BD, procesamiento de datos. Batch
CronJob
Job programado con expresión cron. Backups nocturnos, reportes, limpieza periódica. schedule: "0 2 * * *" Cron
▸ Anatomía de un Pod
Contenedores
▸
Un pod tiene 1+ contenedores que comparten misma IP y mismo localhost
▸
Init containers: se ejecutan antes que el container principal (migraciones, waits)
▸
Sidecar containers: complementan al principal (proxy, logging, mesh)
Health Probes
▸
livenessProbe: ¿está vivo? Si falla → reinicia el contenedor
▸
readinessProbe: ¿puede recibir tráfico? Si falla → se quita del Service
▸
startupProbe: ¿ha arrancado? Para apps con inicio lento
▸
Tipos: httpGet, tcpSocket, exec
Resources & Limits
▸
requests: mínimo garantizado. El scheduler usa esto para elegir nodo
▸
limits: máximo permitido. Si se excede CPU → throttle. Si excede RAM → OOMKill
▸
LimitRange: defaults y máximos por namespace
▸
ResourceQuota: límite total de recursos por namespace

Tipo de Service
Comportamiento
ClusterIP
IP interna del cluster. Default. Solo accesible desde dentro del cluster. Otros pods lo llaman por nombre DNS: api-svc.default.svc.cluster.local. ★ Default
NodePort
Expone el servicio en un puerto estático (30000-32767) en cada nodo. Accesible desde fuera vía nodeIP:nodePort. Útil para dev, no producción. Dev
LoadBalancer
Crea un load balancer cloud (AWS ELB, GCP LB...) que dirige tráfico al servicio. Requiere cloud-controller-manager. Cada servicio = un LB = coste. Cloud
ExternalName
Mapea el servicio a un DNS externo (CNAME). Sin proxy ni selección de pods. Útil para apuntar a servicios externos al cluster. DNS
Headless
clusterIP: None. Sin IP virtual. DNS devuelve directamente las IPs de los pods. Usado por StatefulSets para descubrimiento directo. StatefulSet
▸ Ingress vs Service vs Gateway API
Ingress
▸
Routing HTTP/S basado en host y path
▸
Requiere un Ingress Controller: nginx, traefik, HAProxy, ALB
▸
Un solo LB para múltiples servicios
▸
TLS termination configurable por host
Gateway API (nuevo)
▸
Evolución de Ingress: más expresivo y extensible
▸
Recursos: Gateway, HTTPRoute, GRPCRoute, TCPRoute
▸
Separación de roles: infraestructura vs app team
▸
Soporte nativo para gRPC, TCP, UDP Futuro
CNI Plugins
▸
Implementan la red entre pods: Calico, Cilium, Flannel, Weave
▸
Calico: Network Policies avanzadas, BGP routing
▸
Cilium: eBPF-based, observabilidad L7, service mesh integrado
▸
NetworkPolicy: firewall a nivel de pod (allow/deny por label, namespace, IP)
El almacenamiento en K8s es efímero por defecto: si un pod muere, sus datos desaparecen. Para persistencia se usa el sistema de Volumes, PersistentVolumes (PV) y PersistentVolumeClaims (PVC).

Concepto
Descripción
Volume
Directorio accesible por los contenedores del pod. Tipos: emptyDir (temporal), hostPath (disco del nodo), configMap, secret, persistentVolumeClaim. Básico
PersistentVolume
Recurso de almacenamiento provisionado en el cluster. Puede ser un disco EBS, un NFS, un bloque GCE. Tiene su propio ciclo de vida, independiente del pod. Cluster-level
PersistentVolumeClaim
Petición de almacenamiento por parte de un pod. Especifica tamaño y access mode. K8s busca un PV que encaje o lo crea dinámicamente. Pod-level
StorageClass
Define cómo se provisiona un PV dinámicamente. Parámetros: tipo de disco (gp3, ssd), zona, replication. Cada cloud tiene sus propios provisioners. Dynamic
Access Modes
ReadWriteOnce (RWO): un solo nodo. ReadOnlyMany (ROX): lectura desde varios. ReadWriteMany (RWX): escritura desde varios (NFS, EFS). Importante
Reclaim Policy
Retain: el PV se conserva tras borrar el PVC. Delete: se borra automáticamente (default en cloud). Recycle: deprecated. Cuidado
▸ ConfigMaps y Secrets
ConfigMap
▸
Datos de configuración no sensibles en key-value
▸
Se inyectan como variables de entorno o como ficheros montados
▸
Cambios en ConfigMap no se propagan automáticamente (necesitas restart o Reloader)
Secret
▸
Datos sensibles: passwords, tokens, certificados TLS
▸
Base64 por defecto — NO es encriptación. Usa Sealed Secrets o Vault para cifrado real
▸
Tipos: Opaque, kubernetes.io/tls, kubernetes.io/dockerconfigjson
Kubernetes es declarativo: describes el estado deseado en YAML y K8s se encarga de converger hacia él. Aquí los manifests más importantes que usarás día a día.
▸ Deployment + Service
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
  labels:
    app: api-server
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-server
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1              # Crea 1 pod extra durante update
      maxUnavailable: 0       # Nunca menos de 3 pods activos
  template:
    metadata:
      labels:
        app: api-server
    spec:
      containers:
      - name: api
        image: myrepo/api-server:v2.1.0
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: "250m"          # 0.25 CPU mínimo
            memory: "256Mi"     # 256 MB mínimo
          limits:
            cpu: "500m"          # 0.5 CPU máximo
            memory: "512Mi"     # 512 MB máximo (OOMKill si excede)
        livenessProbe:
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 15
        readinessProbe:
          httpGet:
            path: /ready
            port: 8080
        env:
        - name: DB_HOST
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: db-host
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-secrets
              key: password
---
# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: api-svc
spec:
  selector:
    app: api-server          # Conecta con pods que tengan esta label
  ports:
  - port: 80                 # Puerto del Service
    targetPort: 8080         # Puerto del contenedor
  type: ClusterIP
▸ Ingress + HPA
Ingress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
spec:
  tls:
  - hosts: [api.myapp.com]
    secretName: api-tls
  rules:
  - host: api.myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80
HPA (Autoscaler)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-server
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
kubectl es la herramienta CLI para interactuar con Kubernetes. Estos son los comandos que usarás el 90% del tiempo organizados por categoría.
Información del cluster
$
kubectl cluster-info — Datos del cluster y API server
$
kubectl get nodes — Lista nodos y su estado
$
kubectl get namespaces — Lista todos los namespaces
$
kubectl api-resources — Todos los recursos disponibles
$
kubectl top nodes — Uso de CPU y RAM por nodo
Gestión de Pods
$
kubectl get pods -n my-ns — Pods en un namespace
$
kubectl get pods -o wide — Con IP y nodo asignado
$
kubectl describe pod my-pod — Detalle completo + eventos
$
kubectl logs my-pod -f — Logs en streaming
$
kubectl logs my-pod -c sidecar — Logs de un container específico
$
kubectl exec -it my-pod -- bash — Shell dentro del pod
Deployments & Scaling
$
kubectl apply -f deploy.yaml — Aplicar manifiesto
$
kubectl scale deploy api --replicas=5 — Escalar
$

kubectl rollout undo deploy/api — Rollback a la versión anterior
$
kubectl set image deploy/api api=img:v3 — Actualizar imagen
$
kubectl rollout history deploy/api — Historial de versiones

Conclusión

Kubernetes es un ecosistema complejo pero modular. Cada pieza tiene un propósito claro: el Control Plane decide, los Worker Nodes ejecutan, los Services conectan, y los Volumes persisten. Dominar la relación entre Pods, Deployments, Services e Ingress cubre el 80% de los casos de uso. El YAML es tu lenguaje para declarar el estado deseado, y kubectl tu herramienta para interactuar con todo.
