"Con un procedimiento basado en el comportamiento de una app — como si fuera una caja negra — se extrae la lógica de las respuestas para todas las entradas posibles mediante el HAR, se convierte en tests E2E, y con esos E2E y un programa de agentes en Claude Code se refactoriza o migra conservando la semántica. La idea del proyecto — versión final
EL ENFOQUE DE CAJA NEGRA
La app legacy es una caja negra. No importa cómo funciona por dentro — importa qué hace. Para cada entrada posible, el sistema produce una salida. El HAR captura esas parejas entrada/salida exhaustivamente. Los E2E convierten esas parejas en especificación ejecutable. A partir de ahí, cualquier implementación que produzca las mismas salidas para las mismas entradas es semánticamente equivalente — sin importar si está en Java, en Python o en WebComponents.
Paso 1 — Reproducir
Con Docker y .devContainer se reproduce el entorno original en desarrollo. La app funciona exactamente como en producción. Esto es lo que permite hacer pruebas exhaustivas — sin un entorno reproducible, no hay cartografía posible.
Paso 2 — Observar
Se ejecutan todas las entradas posibles contra la caja negra con Playwright grabando. El HAR captura cada request, response, header, cookie, redirect, error. Eso es el comportamiento real — la lógica de la app expresada en datos observables.
Paso 3 — Especificar
El HAR se convierte en E2E tests. Cada pareja entrada/salida observada se convierte en un test ejecutable. La suite completa ES la especificación de la app — no una documentación, sino un contrato verificable automáticamente.
Paso 4 — Comprender y migrar
El motor de agentes en Claude Code comprende todo el código primero — no migra parte a parte. Entiende las dependencias, la semántica, las relaciones entre componentes. Y solo entonces decide por fases y subfases qué cambiar, en qué orden, preservando los E2E en verde en cada paso.
EL PRINCIPIO CLAVE — COMPRENDER PRIMERO, DECIDIR DESPUÉS
⚠️ Lo que hacen otros: migrar parte a parte
El enfoque habitual de migración es coger un servlet, migrarlo, pasar al siguiente. El problema: cada servlet tiene dependencias implícitas con otros. Migrar uno sin entender el conjunto produce conflictos de integración que solo se detectan al final — cuando es caro corregirlos.
💡 Lo que hace este sistema: comprender todo, luego decidir
El Meta-Architect (Opus) no divide el código en trozos arbitrarios. Lee todo el sistema, entiende las dependencias entre servlets, entre tablas, entre flujos de negocio. Y solo entonces decide: "la Fase 1 es el frontend porque no tiene dependencias descendentes, la Fase 2 es el backend de contratos porque cuentas depende de él, la Fase 3 es cuentas porque ya tiene el contrato de contratos resuelto". Cada fase tiene sentido porque el Meta-Architect entiende el todo antes de tocar las partes. La semántica se extrae del código pero se valida contra los E2E — si el Meta-Architect malinterpreta una dependencia, el GATE lo detecta cuando los tests de integración fallan.
EL CAMINO — 5 DESCUBRIMIENTOS
Callejón sin salida
Tests unitarios generados desde el código legacy
La primera intuición: que la IA lea el espagueti y genere tests unitarios. El problema: los tests reproducían la implementación — incluyendo los bugs. Un test del espagueti solo verifica que el espagueti hace lo que hace, no lo que debería hacer. No captura semántica, captura sintaxis. La idea de generar tests de integración después iba en la misma dirección errónea.
Descubrimiento 1
devContainer — para migrar, primero hay que hacer funcionar el original
Con VSCode y .devContainer se puede reproducir el entorno original (JDK 1.5, Tomcat 5.5, PostgreSQL) en Docker. Arrancarlo, depurarlo, verlo funcionar como en 2005. Eso cambia todo: ya no imaginas qué hacía el legacy — lo ves funcionar y observas su comportamiento directamente. Primer principio: antes de migrar, consigue que funcione exactamente como estaba.
Descubrimiento 2
E2E con Playwright para cartografiar — correcto pero lento
Con el legacy corriendo, la idea de usar tests E2E para cartografiar el comportamiento observable (happy path, errores, límites, roles) era la dirección correcta. Pero hacerlo manualmente — diseñar cada test, ejecutar, analizar HAR — llevaba semanas por servlet. La semántica estaba ahí, la velocidad no.
Descubrimiento 3 — el que lo desbloqueó todo
Caveman + agentes paralelos + plan Max = el batch de refactorización
Hasta hace un mes, los agentes paralelos agotaban la sesión de Claude Code antes de terminar. Demasiado contexto acumulado, demasiados tokens por sesión. El descubrimiento de Caveman Lite — cada agente con contexto mínimo aislado — resolvió el problema de raíz: al no compartir contexto entre workers, cada uno consume solo los tokens de su trozo. Combinado con el plan Max de Claude (que da sesiones largas) y 2 semanas de ajuste de prompts, el sistema se convirtió en un batch que genera tests primero y código después. No es un proceso ligero — consume muchos tokens — pero realiza toda la migración/refactorización de golpe. Extraer la semántica de código embarullado, espagueti y acoplado requiere mucha potencia inicial. Caveman Lite es lo que permite usarla sin que la sesión se agote.
Descubrimiento 4
Los .har de las pruebas son oro para generar E2E
Los ficheros HAR capturan exactamente el comportamiento real del sistema: requests, responses, headers, cookies, redirects, errores. Eso es semántica pura — no interpretada por una IA leyendo código, sino observada en el sistema vivo. Con el HAR como input, el agente genera E2E que capturan el comportamiento real, no el implementado. La pieza que faltaba para cerrar el ciclo.
Resultado
V5M/V6M — el motor que modela un equipo de arquitectura
Todo junto: Meta-Architect (Opus) que escanea y planifica, Architect (Opus) que distribuye trabajo, Test Workers (Sonnet ×N) en paralelo, GATE bloqueante de 7 checks, Code Workers (Sonnet ×N) que leen los tests y los satisfacen, Smoke (Haiku) que valida mecánicamente. El motor no inventa nada nuevo — codifica el comportamiento de los buenos equipos de arquitectura y lo hace ejecutable.

LOS 4 PRINCIPIOS QUE HACEN QUE FUNCIONE
Caja negra + HAR
La app se trata como una caja negra. No importa cómo funciona por dentro — importa qué responde para cada entrada. El HAR captura ese comportamiento exhaustivamente. Los E2E lo convierten en especificación. Cualquier implementación que produzca las mismas salidas es equivalente.
Comprender primero, decidir después
El Meta-Architect no divide el código arbitrariamente. Lee todo el sistema, entiende las dependencias entre componentes y solo entonces decide las fases y subfases de migración. Cada fase tiene sentido porque el sistema entiende el todo antes de tocar las partes.
Restricción de contexto = precisión
Cada worker opera con contexto mínimo aislado (Caveman Lite). Solo su TEST SPEC + DIGEST. Eso impide confusión, fuerza precisión, evita llenar la ventana de contexto. Es bajo acoplamiento aplicado a agentes de IA.
TDD-as-Spec + GATE bloqueante
Tests antes que código — siempre. Los Test Workers definen el contrato. Los Code Workers los satisfacen. Entre ambas oleadas, 7 checks de coherencia. Si algo no cuadra → ABORT antes de gastar tokens en código incoherente.

💡 Por qué Subagents y no todo en CLAUDE.md
Cada subagent = su propia ventana de contexto + su propio modelo + tools restringidas. Si todo estuviera en CLAUDE.md: (1) se cargaría en cada conversación aunque solo depures, (2) un solo modelo para todo, (3) los workers se "verían" entre sí — adiós Caveman Lite, adiós precisión. Los subagents son la pieza que hace posible el paralelismo sin llenar la ventana de contexto.
COSTE REAL — NO ES UN PROCESO LIGERO
Extraer la semántica de código espagueti, embarullado y acoplado requiere mucha potencia inicial. El motor consume muchos tokens — el Meta-Architect (Opus) lee todo el código para comprenderlo, el Architect genera el Blueprint y el DIGEST, y luego N workers en paralelo generan tests y código. Una ejecución completa de V6M sobre WebDTE puede consumir el equivalente a varias sesiones largas de Claude Code. Por eso el plan Max es un requisito — sin sesiones largas, el motor no puede completar las fases.
El trade-off
Alta inversión de tokens al principio a cambio de una migración completa en un solo ciclo. Sin Caveman Lite, esa inversión se desperdiciaba — la sesión se agotaba antes de terminar. Con Caveman, cada token va a un worker que produce un resultado concreto (un test o un fichero de código) en lugar de acumularse en un contexto que se degrada.
Por qué vale la pena
La alternativa es migrar manualmente — semanas de trabajo humano de arquitecto senior. El motor consume en tokens lo que un equipo de 3-4 personas consumiría en semanas de salario. Y produce resultados deterministas: mismas entradas → mismas salidas, verificado en los runs n18-n23.
