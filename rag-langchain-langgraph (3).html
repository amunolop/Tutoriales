TRES PROBLEMAS DISTINTOS, TRES HERRAMIENTAS DISTINTAS
⚠️ El error de vocabulario más común: mezclar los tres
RAG no es un framework — es una técnica. LangChain es un framework que te ayuda a implementar esa técnica (entre otras cosas). LangGraph es una librería de orquestación construida por el mismo equipo, para un problema distinto: bucles, ramas y estado explícito — no cadenas lineales. Puedes usar RAG sin LangChain, LangChain sin RAG, y LangGraph sin ninguno de los dos.

Por qué esto no sustituye lo que ya sabes, lo complementa. Claude API/Agent SDK/MCP y Copilot resuelven "cómo interactúo con un modelo y sus herramientas". Este ecosistema resuelve dos preguntas distintas: "¿de dónde saca el modelo información que no tiene?" (RAG) y "¿cómo controlo un flujo de trabajo complejo, con bucles y múltiples proveedores de LLM?" (LangChain/LangGraph).
LOS 4 CONCEPTOS EN UNA FRASE CADA UNO
RAG
Recuperar información externa relevante y metérsela al modelo en el prompt antes de que responda — en vez de reentrenarlo.
LangChain
Framework para encadenar prompts, modelos, retrievers y parsers con una sintaxis común, sea cual sea el proveedor de LLM.
LangGraph
Modela el flujo de un agente como un grafo de estados — nodos, aristas, y aristas condicionales que permiten ciclos.
Vector DB
Base de datos especializada en buscar por similitud semántica, no por coincidencia exacta — la pieza que hace posible RAG.
"LangChain es el framework base con los bloques (modelos, prompts, cadenas, memoria, tools, retrievers) para flujos lineales. LangGraph extiende LangChain para aplicaciones complejas, con estado y multi-agente, representando el flujo como un grafo con ramas, bucles y transiciones condicionales."
La distinción oficial entre los dos frameworks, en una frase
✅ Dato que conecta esto con tu TFM
Lo que hiciste a mano en FMI — orquestar varios agentes con estado compartido y decisiones condicionales sobre qué paso viene después — es exactamente lo que LangGraph formaliza como primitiva de "grafo de estados". No es una casualidad de diseño: es el mismo problema que resolviste, con una librería que ya lo tiene resuelto de fábrica.
EL PROBLEMA QUE RESUELVE
Un LLM tiene dos límites: su conocimiento se congela en la fecha de corte del entrenamiento, y su ventana de contexto es finita — no puedes meterle toda tu documentación interna en cada prompt. RAG conecta el modelo con datos externos (privados, actualizados, específicos de tu empresa) sin reentrenarlo: recupera solo lo relevante para cada pregunta concreta.

Ingesta y chunking: tus documentos (PDFs, docs internos, tickets) se trocean en fragmentos manejables.
Embeddings: cada chunk se convierte en un vector numérico que representa su significado, usando un modelo de embeddings.
Almacenamiento: esos vectores se guardan en una base de datos vectorial, indexados para búsqueda rápida.
En tiempo de consulta: la pregunta del usuario también se convierte en vector, y se buscan los chunks más parecidos por similitud (normalmente coseno).
Aumento del prompt: los chunks recuperados se insertan como contexto junto a la pregunta original.
Generación: el modelo responde basándose en ese contexto — no solo en lo que "recuerda" de su entrenamiento.
CHUNKING — LA DECISIÓN QUE MÁS IMPACTA LA CALIDAD
EstrategiaQué haceCuándo usarla
Fixed-sizeCorta cada N caracteres/tokens, con solapamiento (overlap) entre chunksRápido de implementar, punto de partida razonable
Recursive characterIntenta cortar por párrafo o frase antes que a lo bruto, respetando la estructura del textoDocumentación general, casi siempre mejor que fixed-size
SemánticaAgrupa frases por similitud de significado antes de cortar, no por longitudContenido denso donde cortar mal a mitad de una idea es costoso
Por documento/secciónRespeta encabezados y estructura real del documento (Markdown, HTML)Documentación técnica ya bien estructurada
RETRIEVAL AVANZADO
Hybrid search
Combina búsqueda semántica (vectores) con búsqueda por palabra clave (BM25) — captura tanto significado como términos exactos que el embedding puede diluir.
Re-ranking
Recupera más candidatos de los necesarios y usa un segundo modelo, más preciso pero más lento, para reordenar solo esos pocos.
Contextual retrieval
Técnica de Anthropic: añade contexto explicativo a cada chunk antes de indexarlo, para que tenga sentido aislado de su documento original.
⚠️ RAG reduce las alucinaciones, no las elimina
Si el retrieval falla — el chunk relevante no se recupera, o se recupera uno irrelevante — el modelo puede alucinar igual, o mezclar contexto que no viene a cuento como si fuera la respuesta. RAG es tan bueno como su retrieval, no más.
EJEMPLO MÍNIMO CON LANGCHAIN
from langchain_anthropic import ChatAnthropic
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_voyageai import VoyageAIEmbeddings

embeddings = VoyageAIEmbeddings(model="voyage-3")
vectorstore = InMemoryVectorStore(embeddings)
vectorstore.add_texts(["...", "..."])  # tus chunks

retriever = vectorstore.as_retriever(search_kwargs={"k": 3})
docs = retriever.invoke("¿cómo se configura el rate limiting?")

model = ChatAnthropic(model="claude-sonnet-5")
context = "\n\n".join(d.page_content for d in docs)
response = model.invoke(f"Contexto:\n{context}\n\nPregunta: ¿cómo se configura el rate limiting?")
Voyage AI es el proveedor de embeddings que recomienda Anthropic — buen punto de partida si ya estás en su ecosistema.
MÁS EJEMPLOS — CON CHROMA (PERSISTENTE EN DISCO)
InMemoryVectorStore se pierde al reiniciar el proceso — sirve para probar, no para producción. Chroma persiste en disco: el paquete correcto es langchain_chroma, no langchain_community.vectorstores.Chroma (deprecado desde la versión 0.2.9 de LangChain). 
from langchain_chroma import Chroma
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_voyageai import VoyageAIEmbeddings

splitter = RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=100)
chunks = splitter.split_text(documento_largo)

embeddings = VoyageAIEmbeddings(model="voyage-3")
vectorstore = Chroma.from_texts(
    chunks, embeddings,
    persist_directory="./chroma_db"  # sobrevive a un reinicio del proceso
)

retriever = vectorstore.as_retriever(search_kwargs={"k": 4})
⚠️ Chroma tiene un historial de roturas de compatibilidad
Chroma reescribió su servidor en Rust (chromadb 1.x), lo que ha causado incompatibilidades documentadas con versiones de langchain-chroma que esperaban el servidor anterior. Si usas Chroma en modo cliente-servidor (no embebido), fija las versiones de ambos paquetes juntas y comprueba la matriz de compatibilidad antes de actualizar cualquiera de los dos.
QUÉ ES
Framework open-source (Python y JS) creado por Harrison Chase en 2022, con más de 600 integraciones. Da bloques reutilizables — modelos, prompts, cadenas, memoria, tools, retrievers — para no reescribir el "pegamento" entre un LLM y el resto de tu aplicación cada vez. Versión estable actual: LangChain 1.2 (requiere Python 3.10+).
LCEL — LA SINTAXIS MODERNA (EL OPERADOR |)
LCEL (LangChain Expression Language) es la forma actual de construir cadenas, con el operador | conectando piezas — sustituye a clases antiguas como LLMChain, ya deprecadas. 
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_anthropic import ChatAnthropic

prompt = ChatPromptTemplate.from_template("Resume esto en una frase: {texto}")
model = ChatAnthropic(model="claude-sonnet-5")
parser = StrOutputParser()

chain = prompt | model | parser   # esto es LCEL
resultado = chain.invoke({"texto": "..."})
LOS BLOQUES BASE
PromptTemplate
Plantilla de prompt con variables — el equivalente a un prompt file, pero definido en código.
Chains (LCEL)
Composición de piezas con |: prompt → modelo → parser → lo que necesites.
Retrievers
Interfaz común para consultar cualquier vector store, sin acoplarte a un proveedor concreto.
Memory
Gestión del historial de conversación — qué se recuerda entre turnos y cómo se resume.
CREAR UN AGENTE — LA SINTAXIS ACTUAL (NO LA QUE VERÁS EN LA MAYORÍA DE TUTORIALES)
⚠️ La mayoría de tutoriales de LangChain están desactualizados
Un análisis de abril de 2026 encontró que la mayoría de tutoriales de LangGraph mejor posicionados en Google todavía usan create_react_agent de langgraph.prebuilt — deprecado desde octubre de 2025. La forma actual es create_agent desde langchain.agents.
# ✅ Sintaxis actual (LangChain/LangGraph v1, 2026)
from langchain.agents import create_agent
from langchain_anthropic import ChatAnthropic

def buscar_incidencia(id: str) -> str:
    """Busca el estado de una incidencia por su ID."""
    return f"Incidencia {id}: en progreso"

agent = create_agent(
    ChatAnthropic(model="claude-sonnet-5"),
    tools=[buscar_incidencia],
    system_prompt="Eres un asistente de soporte técnico.",
)

resultado = agent.invoke({"messages": [{"role": "user", "content": "¿Estado de INC-4521?"}]})
create_agent corre por debajo sobre LangGraph — no es una alternativa a LangGraph, es una capa de conveniencia construida encima, con un sistema de middleware añadido.
MÁS EJEMPLOS — CADENA RAG COMPLETA CON LCEL
El patrón idiomático para combinar retriever + prompt + modelo en una sola cadena, en vez de concatenar el contexto a mano como en el ejemplo mínimo de la pestaña RAG. 
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_anthropic import ChatAnthropic

prompt = ChatPromptTemplate.from_template(
    "Contexto:\n{context}\n\nPregunta: {question}"
)
model = ChatAnthropic(model="claude-sonnet-5")

# "retriever" viene del ejemplo de Chroma en la pestaña RAG
rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | model
    | StrOutputParser()
)

respuesta = rag_chain.invoke("¿cómo se configura el rate limiting?")
RunnablePassthrough() deja pasar la pregunta original sin tocarla, mientras retriever la transforma en contexto en paralelo — ambas ramas del diccionario se resuelven antes de llegar al prompt.
LA CRÍTICA HONESTA
⚠️ Sobre-abstracción para casos simples
Si solo necesitas 1-2 llamadas a Claude, la API cruda (lo que ya sabes de tu preparación CCDV-F) es más simple, más rápida y menos frágil ante cambios de versión que meter LangChain de por medio. LangChain gana cuando necesitas cambiar de proveedor fácilmente o ensamblar una RAG estándar rápido con integraciones ya hechas — no como capa por defecto para todo.
POR QUÉ EXISTE — EL LÍMITE DE LAS CADENAS LINEALES
Las chains de LangChain son lineales: A → B → C, sin vuelta atrás. Los agentes reales necesitan ciclos (reintentar, iterar hasta que algo pase el test), ramas condicionales (según el resultado, ir a un sitio u otro) y estado explícito y persistente. LangGraph — del mismo equipo, estable desde octubre de 2025 (v1.0) — modela esto como un grafo: nodos (pasos de cómputo) conectados por aristas (control de flujo), compartiendo un objeto de estado común.

CONCEPTOS CLAVE
ConceptoQué es
StateUn TypedDict (o similar) compartido — cada nodo lo lee y devuelve las actualizaciones que quiere fusionar
NodeUna función que recibe el estado y devuelve cambios sobre él — puede ser una llamada a un LLM, una tool, lo que sea
EdgeUna transición fija: al terminar el nodo A, siempre se ejecuta el nodo B
Conditional edgeUna función "router" decide a qué nodo ir según el estado actual — esto es lo que permite bucles y ramas
CheckpointPersistencia del estado en cada paso — permite pausar, reanudar, o recuperar un flujo tras un reinicio
EJEMPLO — GRAFO CON RAMA CONDICIONAL (SINTAXIS ACTUAL)
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class EstadoRevision(TypedDict):
    codigo: str
    valido: bool

def revisar(state: EstadoRevision) -> EstadoRevision:
    state["valido"] = "TODO" not in state["codigo"]
    return state

def decidir_ruta(state: EstadoRevision) -> str:
    return "aprobar" if state["valido"] else "pedir_cambios"

def aprobar(state: EstadoRevision) -> EstadoRevision:
    print("✅ Aprobado"); return state

def pedir_cambios(state: EstadoRevision) -> EstadoRevision:
    print("🔁 Necesita cambios"); return state

graph = StateGraph(EstadoRevision)
graph.add_node("revisar", revisar)
graph.add_node("aprobar", aprobar)
graph.add_node("pedir_cambios", pedir_cambios)

graph.add_edge(START, "revisar")
graph.add_conditional_edges("revisar", decidir_ruta, {
    "aprobar": "aprobar",
    "pedir_cambios": "pedir_cambios"
})
graph.add_edge("aprobar", END)
graph.add_edge("pedir_cambios", END)

workflow = graph.compile()
workflow.invoke({"codigo": "def foo(): pass", "valido": False})
✅ Esto es literalmente lo que diseñaste a mano en FMI
Un nodo que evalúa, una función de decisión que enruta según el resultado, y la posibilidad de volver atrás si algo no pasa la validación — es el mismo patrón de tu framework de migración de intención, aquí con la primitiva ya resuelta por la librería en vez de construida desde cero.
HUMAN-IN-THE-LOOP Y PERSISTENCIA
interrupt_before
Pausa el grafo antes de un nodo concreto para esperar tu aprobación — igual que el freno de mano de un agente con demasiada autonomía.
Checkpointer
Guarda el estado en cada paso (memoria o Postgres) — el flujo sobrevive a un reinicio y puede reanudarse donde se quedó.
Fan-out paralelo
Varios nodos pueden ejecutarse en paralelo cuando no dependen entre sí, en vez de uno detrás de otro.
PATRONES MULTIAGENTE
Supervisor
Un agente coordinador decide a qué agente especializado delegar cada parte de la tarea.
Jerárquico
Equipos de agentes, cada uno con su propio supervisor, reportando a un nivel superior — útil para tareas muy grandes.
Red (peer-to-peer)
Los agentes se pueden pasar el control entre sí directamente, sin un coordinador central fijo.
MÁS EJEMPLOS — PATRÓN SUPERVISOR
Un create_agent compilado es en sí mismo un grafo — puede usarse directamente como nodo dentro de un StateGraph más grande. Este es el patrón recomendado para construir sistemas multiagente. 
from langgraph.graph import StateGraph, START, END
from langchain.agents import create_agent

class EstadoEquipo(TypedDict):
    tarea: str
    resultado: str

agente_backend = create_agent(model, tools=[tool_backend],
                                system_prompt="Eres experto en APIs y bases de datos.")
agente_frontend = create_agent(model, tools=[tool_frontend],
                                 system_prompt="Eres experto en componentes Angular.")

def supervisor(state: EstadoEquipo) -> str:
    # Enruta según el contenido de la tarea — en producción, esto
    # sería otra llamada al modelo clasificando la petición
    return "backend" if "api" in state["tarea"].lower() else "frontend"

graph = StateGraph(EstadoEquipo)
graph.add_node("backend", agente_backend)
graph.add_node("frontend", agente_frontend)
graph.add_conditional_edges(START, supervisor, {
    "backend": "backend",
    "frontend": "frontend",
})
graph.add_edge("backend", END)
graph.add_edge("frontend", END)

equipo = graph.compile()
Simplificado con fines didácticos — un supervisor real casi siempre enruta con otra llamada al modelo (clasificación de la tarea), no con una condición de texto como el ejemplo.
LLAMAINDEX — LA ALTERNATIVA ESPECIALIZADA EN DATOS
Donde LangChain es un framework de propósito general (chains, agentes, memoria, integraciones de todo tipo), LlamaIndex nació enfocado casi exclusivamente en indexación y recuperación de datos — RAG es su caso de uso central, no uno más entre muchos. Si tu proyecto es "sobre todo RAG" y poco más, suele requerir menos código boilerplate que montarlo en LangChain.

EVALUACIÓN — RAGAS
RAGAS (RAG Assessment) es un framework para medir la calidad de un pipeline RAG con métricas concretas en vez de "a ojo": faithfulness (¿la respuesta se sostiene en el contexto recuperado, o se lo inventa?), answer relevance (¿responde realmente a la pregunta?), y context precision/recall (¿el retrieval trajo los chunks correctos, ni de más ni de menos?).

QUÉ ES Y DE DÓNDE VIENE
OpenClaw no es una librería que importas en tu código — es una plataforma que despliegas. Framework de agentes open-source, agnóstico de modelo (Claude, GPT, Gemini, Grok, Mistral, DeepSeek, o modelos locales vía Ollama), que corre como servicio 24/7 en tu propio hardware o en la nube. Nació en noviembre de 2025 como "Clawdbot" (del desarrollador austríaco Peter Steinberger) y se asentó en el nombre OpenClaw en enero de 2026. Se ha convertido en uno de los proyectos open-source de más rápido crecimiento de la historia reciente.
Con matiz, no como certeza absoluta: las fuentes consultadas no coinciden del todo entre sí — unas mencionan un paso intermedio breve por el nombre "Moltbot" antes de OpenClaw, otras no lo recogen; el número de estrellas en GitHub varía entre ~145.000 y ~250.000 según la fuente y el momento en que se midió. Dato real: crecimiento excepcionalmente rápido. Cifra exacta: no verificable con precisión a día de hoy.
ARQUITECTURA — GATEWAY, HEARTBEAT Y BUCLE DE RAZONAMIENTO
Gateway central
Un único proceso multiplexa WebSocket y HTTP en un solo puerto — gestiona el ciclo de vida de sesiones, el despacho de herramientas y el enrutado entre canales.
Heartbeat
Ciclo de sondeo programado — el agente se despierta solo para monitorizar archivos o bases de datos, sin que nadie le hable primero. Proactivo, no solo reactivo.
Bucle de razonamiento
El mismo patrón que ya conoces: el modelo recibe historial + system prompt, genera llamadas a herramientas, las ejecuta, y reenvía el contexto actualizado hasta que una respuesta de solo texto termina el ciclo.

SEGURIDAD — BUENAS PRÁCTICAS Y RIESGOS DOCUMENTADOS
⚠️ La superficie de riesgo es real, no teórica
Varios papers de investigación de seguridad de 2026 documentan vulnerabilidades concretas en distintas fases de ejecución — procesamiento del prompt de usuario, uso de herramientas y recuperación de memoria — precisamente por la amplitud de su superficie de acción (múltiples canales, acceso a recursos del sistema operativo). Antes de darle acceso a canales corporativos o datos sensibles, esto merece una evaluación de seguridad propia, no solo confiar en que "es open-source y muy popular".
Mínimo privilegio
Mapea solo las carpetas que el agente necesita de verdad. Nunca tu carpeta de usuario completa ni tus claves SSH — usa un workspace dedicado y aislado.
Aprobación humana selectiva
Leer un archivo puede auto-aprobarse; escribir o ejecutar un comando de shell debería exigir confirmación manual antes de correr.
Prompt injection
Si le pides que resuma una web y esa página contiene texto oculto diseñado para manipular al modelo, el agente puede intentar seguir esas instrucciones como si fueran tuyas.
Higiene de credenciales
chmod 600 en el archivo de configuración y en credentials/, verificar que el puerto del Gateway solo escucha en localhost, y revisar logs en busca de claves expuestas.
Comandos de diagnóstico mencionados en guías de la comunidad: openclaw doctor (valida la configuración), openclaw doctor --fix (corrige problemas detectados), openclaw security audit --deep (auditoría de seguridad).
PROBLEMA ACTUAL — EL BLOQUEO DE ABRIL DE 2026
⚠️ Anthropic bloqueó el uso de tokens OAuth de suscripción desde herramientas de terceros
El 4 de abril de 2026, Anthropic bloqueó de forma inmediata y del lado del servidor que herramientas de terceros —incluido OpenClaw— usaran los tokens OAuth de las suscripciones Claude (Pro $20/mes, Max $200/mes). Mucha gente enrutaba su suscripción personal a través de OpenClaw para evitar pagar por token vía API; ese atajo dejó de funcionar de la noche a la mañana. Boris Cherny, responsable de Claude Code en Anthropic, lo justificó así: "nuestro modelo de suscripción no estaba diseñado para el patrón de uso de estas herramientas de terceros — meten una tensión desproporcionada en nuestros sistemas".
✅ Lo que NO significa este bloqueo
Puedes seguir usando Claude desde OpenClaw sin ningún problema — con clave de API normal, pagando por token, no con el atajo de la suscripción. La propia documentación de proveedores de OpenClaw ya gestiona esto (modelos claude-opus-5, claude-fable-5, etc. vía API key directa).
Ventana de precio relevante ahora mismo: el precio introductorio de Claude de $2/$10 (millón de tokens entrada/salida) rige hasta el 31 de agosto de 2026 — sube a $3/$15 estándar a partir del 1 de septiembre.
Dato sin confirmar, tratar con cautela: circula una afirmación (de una fuente poco solvente) de que Claude Code escanea mensajes de commit y bloquea o cobra extra si mencionan "OpenClaw". No lo he podido corroborar en ninguna fuente seria — se menciona aquí como rumor no verificado, no como hecho.
OPENCODE — HERRAMIENTA COMPLEMENTARIA, NO UN BACKEND ALTERNATIVO
OpenCode no sustituye a OpenClaw ni es una forma de "reconectar" con Claude Code — es un agente de código de terminal (TUI) distinto, open-source y agnóstico de modelo (75+ proveedores soportados). La distinción real: "OpenCode escribe tu código, OpenClaw opera tus sistemas" — son complementarios, no sustitutos entre sí.
HerramientaQué hace
OpenCodeSesión interactiva en terminal: lees el repo, describes una tarea, edita archivos, ejecuta tests, itera contigo delante — como un Claude Code abierto y multi-proveedor
OpenClawGateway siempre encendido: agentes con memoria, horarios, canales — actúa mientras tú haces otra cosa
La integración real entre ambos: opencode-controller es una skill verificada de OpenClaw (instalable desde ClawHub) que deja que un agente de OpenClaw lance y controle sesiones de OpenCode desde dentro, exponiendo comandos /opencode. Como no toca el sistema de archivos ni la terminal directamente por sí misma —delega en OpenCode—, es una de las skills más seguras del catálogo.

⚠️ Dos matices que rompen esto si los ignoras
1) La clave de API de Alibaba Model Studio no es portable entre regiones — si tu clave se generó en la consola de Pekín, usa el baseUrl de esa región, no el internacional (Singapur) del ejemplo. 2) El nombre exacto de las claves del JSON (providers, apiKeyEnv, etc.) sigue el patrón documentado por guías de la comunidad de OpenClaw — verifica siempre contra openclaw doctor en tu versión instalada antes de darlo por bueno, porque el esquema puede variar entre releases.
Por qué esto conecta con el resto de la guía: es exactamente el patrón "modelo barato para lo rutinario, modelo potente solo cuando hace falta" que mencionamos en la sección de MCP y en la pestaña de CUÁNDO USAR QUÉ — Qwen 3.8 a $2/$6 es un candidato natural para el heartbeat y tareas de bajo riesgo, reservando Claude o un modelo frontera para lo que de verdad lo exija.

EL CASO: ASISTENTE SOBRE LA DOCUMENTACIÓN INTERNA DE ISOLUTION
El escenario: un asistente que responde preguntas de soporte usando la documentación interna de ISOLution (RAG), pero que no contesta a ciegas — si su propia confianza en la respuesta es baja, pausa y espera que un humano la revise antes de entregarla. Combina las tres piezas de esta guía en un único flujo real, de principio a fin.

→

↓ no

FASE 1 — INGESTA (se ejecuta una vez, no en cada pregunta)
Chunking recursivo (el que recomendamos en la pestaña RAG para documentación general), embeddings con Voyage AI, y un vector store en memoria para el ejemplo — en producción sería Chroma, Pinecone o pgvector. 
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_voyageai import VoyageAIEmbeddings

splitter = RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=100)
chunks = splitter.split_text(documentacion_isolution)  # tu documentación interna, ya cargada

embeddings = VoyageAIEmbeddings(model="voyage-3")
vectorstore = InMemoryVectorStore(embeddings)
vectorstore.add_texts(chunks)
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})
FASE 2 — ESTADO DEL GRAFO
El TypedDict que viaja entre nodos — cada campo es algo que un nodo lee o escribe, tal como viste en la pestaña LANGGRAPH. 
from typing import TypedDict, Optional

class EstadoAsistente(TypedDict):
    pregunta: str
    contexto: str
    respuesta: str
    confianza: float
    aprobado_por_humano: Optional[bool]
FASE 3 — LOS NODOS
Tres nodos: uno recupera contexto (RAG), otro genera la respuesta y se autoevalúa, y el tercero pausa el grafo con interrupt() cuando la confianza es baja — el mismo patrón de aprobación humana que viste como tarjeta en LANGGRAPH, aquí implementado de verdad. 
from langchain_anthropic import ChatAnthropic
from langgraph.types import interrupt, Command

model = ChatAnthropic(model="claude-sonnet-5")

def retrieve(state: EstadoAsistente) -> dict:
    docs = retriever.invoke(state["pregunta"])
    return {"contexto": "\n\n".join(d.page_content for d in docs)}

def generate(state: EstadoAsistente) -> dict:
    prompt = (
        f"Contexto de la documentación de ISOLution:\n{state['contexto']}\n\n"
        f"Pregunta: {state['pregunta']}\n\n"
        "Responde SOLO con lo que dice el contexto. Si no tienes "
        "suficiente información, dilo explícitamente. Termina "
        "SIEMPRE con una línea: CONFIANZA: <número entre 0 y 1>"
    )
    salida = model.invoke(prompt).content
    texto, confianza_str = salida.rsplit("CONFIANZA:", 1)
    return {"respuesta": texto.strip(), "confianza": float(confianza_str.strip())}

def decidir_ruta(state: EstadoAsistente) -> str:
    return "responder" if state["confianza"] >= 0.75 else "revision_humana"

def revision_humana(state: EstadoAsistente) -> dict:
    decision = interrupt({
        "pregunta": state["pregunta"],
        "respuesta_propuesta": state["respuesta"],
        "confianza": state["confianza"],
    })
    # "decision" es el valor que llega cuando el humano reanuda con Command(resume=...)
    return {
        "respuesta": decision.get("respuesta_editada", state["respuesta"]),
        "aprobado_por_humano": True,
    }
⚠️ El código antes de interrupt() se re-ejecuta al reanudar
Si revision_humana tuviera efectos secundarios (escribir en una base de datos, enviar un email) antes de llamar a interrupt(), se ejecutarían dos veces: una al pausar, otra al reanudar. Por eso el nodo de arriba no hace nada más que pasar datos — cualquier efecto secundario real iría después del interrupt(), no antes.
FASE 4 — CONSTRUCCIÓN DEL GRAFO
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver

graph = StateGraph(EstadoAsistente)
graph.add_node("retrieve", retrieve)
graph.add_node("generate", generate)
graph.add_node("revision_humana", revision_humana)

graph.add_edge(START, "retrieve")
graph.add_edge("retrieve", "generate")
graph.add_conditional_edges("generate", decidir_ruta, {
    "responder": END,
    "revision_humana": "revision_humana",
})
graph.add_edge("revision_humana", END)

# El checkpointer es obligatorio para que interrupt() funcione —
# sin él no hay estado que pausar ni que reanudar.
checkpointer = MemorySaver()  # en producción: PostgresSaver
app = graph.compile(checkpointer=checkpointer)
FASE 5 — EJECUCIÓN, INCLUYENDO LA PAUSA Y REANUDACIÓN
config = {"configurable": {"thread_id": "consulta-482"}}

resultado = app.invoke(
    {"pregunta": "¿Cómo configuro una alerta de severidad crítica?"},
    config
)

if "__interrupt__" in resultado:
    # El grafo se ha pausado — esto es lo que vería el humano revisor
    print("Necesita revisión:", resultado["__interrupt__"])

    # ... el humano revisa y decide reanudar con su respuesta editada ...
    resultado_final = app.invoke(
        Command(resume={"respuesta_editada": "Ve a Configuración → Alertas → Nueva regla..."}),
        config  # MISMO thread_id — si no, el grafo pausado nunca recibe la respuesta
    )
    print(resultado_final["respuesta"])
else:
    # Confianza alta — respondió sin pasar por revisión
    print(resultado["respuesta"])
✅ Por qué está diseñado así
Cada decisión de este ejemplo conecta con algo que ya viste: chunking recursivo (pestaña RAG) porque es documentación general no muy estructurada; arista condicional (pestaña LANGGRAPH) porque la ruta depende de un dato que solo se conoce en tiempo de ejecución, la confianza; y checkpointer + interrupt() porque un asistente que puede equivocarse necesita un freno de mano real, no solo la promesa de que "normalmente acierta". Es la misma filosofía de mínimo privilegio que viste en los agentes de Copilot, aplicada aquí como umbral de confianza en vez de restricción de herramientas.
