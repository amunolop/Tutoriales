Arqueología de Caja Negra

Cómo extraer la semántica de un sistema legacy sin ahogar la IA revisando código espagueti.
Una metodología de ingeniería inversa basada en comportamiento observable.
El problema: código espagueti vs. economía de tokens
El fracaso de los 2 meses
CASO REAL
Durante dos meses intenté extraer tests de integración desde el código legacy de WebDTE (2005). El resultado fue un fracaso rotundo. ¿La razón? El código está completamente acoplado: lógica de negocio mezclada con SQL, HTML generado en servlets, validaciones duplicadas en 5 lugares diferentes. Los tests unitarios no servían porque no había "unidades" — todo dependía de todo.
La revelación: No se puede obtener semántica desde código mal estructurado. La única forma viable es tratar el sistema como caja negra, observar su comportamiento real, capturar la intención mediante tests de caracterización (Golden Master), y LUEGO refactorizar con esa red de seguridad activa.
Por qué caja negra > revisión de código
❌ Enfoque ingenuo
Estrategia: "La IA revisará las 50,000 líneas de código legacy y extraerá la lógica de negocio"

Costo: 500,000 tokens (contexto + análisis)

Riesgo: Alucinaciones — la IA inventa lógica que no existe al intentar interpretar condicionales anidados de 8 niveles

Resultado: Agotamiento cognitivo sin garantías. Los tests generados no validan nada real.
✅ Arqueología de Caja Negra
Estrategia: web.xml + vistas HTML → parámetros descubiertos → sistema funcionando (comportamiento observable) → Golden Master

Costo: 5,000 tokens (solo artefactos declarativos)

Riesgo: Mínimo — el sistema real no miente. Si responde X para entrada Y, esa es la verdad absoluta.

Resultado: Inventario funcional en 2 horas vs. 15 días. Tests que validan comportamiento REAL.
Economía de Tokens: El código espagueti es ruido semántico. La IA gasta tokens descifrando estructuras sintácticas caóticas en lugar de capturar la intención de negocio. Al usar artefactos declarativos (web.xml, formularios HTML), obtienes el 80% de la semántica con el 1% del costo.

Tu enfoque no es improvisado — es la aplicación correcta de BDD (Behavior-Driven Development) a sistemas legacy. Gherkin se inventó precisamente para esto: capturar intención observable sin asumir implementación.

Tu metodología validada por los maestros
No estás inventando nada nuevo — estás aplicando correctamente principios validados por décadas de ingeniería de software. La diferencia es que los adaptas al contexto de IA con restricciones de tokens.
"When changing legacy code, the biggest risk is that you'll break something without knowing it. The only way to work safely is to create characterization tests — tests that describe the current behavior of the system, not what you think it should do."
Michael Feathers, "Working Effectively with Legacy Code" (2004)
Michael Feathers: Characterization Tests
TU GOLDEN MASTER
Feathers formalizó el concepto de Characterization Tests: tests que capturan el comportamiento actual del sistema (aunque esté mal diseñado) para crear una red de seguridad antes de refactorizar. No validan "corrección" — validan "consistencia".
Concepto Feathers Characterization Test: Captura comportamiento observable sin juzgarlo
Tu equivalente FMI Golden Master: HTTP request → respuesta capturada → futuras ejecuciones deben dar lo mismo
Propósito Red de seguridad para refactorizar sin romper funcionalidad
Cuándo usarlo ANTES de tocar una sola línea de código legacy
"The Strangler Fig pattern involves gradually creating a new system around the edges of the old, letting it slowly replace the original until the old system can be strangled and removed."
Martin Fowler, "Refactoring" (2018 edition)
Martin Fowler: Strangler Fig Pattern
TU MIGRACIÓN INCREMENTAL
Fowler propone NO hacer migraciones Big Bang. En lugar de reescribir todo el sistema de golpe, sustituyes funcionalidades una a una mientras el viejo sistema sigue funcionando. Eventualmente, el nuevo sistema "estrangula" al viejo.
Concepto Fowler Strangler Fig: Migración incremental pieza a pieza
Tu equivalente FMI Servlet a servlet: Cada funcionalidad migrada pasa tests de intención antes de "estrangular" la versión legacy
Ventaja Coexistencia viejo/nuevo → rollback trivial si algo falla
Validación Golden Master garantiza que nuevo ≡ viejo en comportamiento
"The ubiquitous language is a language structured around the domain model and used by all team members to connect all activities of the team with the software. A change in the language is a change to the model."
Eric Evans, "Domain-Driven Design" (2003)
Eric Evans: Ubiquitous Language
TU NOMENCLATURA CERRADA
Evans insiste en que el código debe hablar el lenguaje del dominio, no el lenguaje de la tecnología. Los nombres deben revelar intención de negocio, no detalles de implementación.
Concepto Evans Ubiquitous Language: Código que habla el idioma del negocio
Tu equivalente FMI Vocabulario cerrado: Finder, Store, Validator, Calculator, UseCase — nunca Service, Manager, Helper, Util
Propósito Nombres correctos = compresión de tokens para IA. Un CertificadoValidator no necesita explicación.
Anti-patrón CertificadoServiceManagerHelperImpl → ruido semántico que confunde IA
"Make it work, make it right, make it fast — in that order. Don't optimize prematurely. First get the behavior right with tests."
Kent Beck, "Test-Driven Development by Example" (2002)
Kent Beck: Test-First Development
TU RED DE SEGURIDAD
Beck popularizó el ciclo Red-Green-Refactor: primero el test (que falla), luego el código mínimo para pasarlo, finalmente refactorizar con confianza porque el test valida que no rompiste nada.
Concepto Beck Test-First: Test antes que código
Tu equivalente FMI Golden Master antes de refactorizar: Capturas comportamiento actual, luego migras, el test valida que nueva implementación ≡ vieja
Filosofía "Make it work" (sistema legacy funciona) → "Make it right" (refactor 3 capas) → test garantiza que funcionalidad se preserva

Las 5 fases de la arqueología
Este es el flujo completo, desde el sistema legacy opaco hasta el refactor 3 capas validado. Cada fase tiene entregables concretos y criterios de completitud.
0
Rescate Arqueológico
Dockerizar el WAR binario legacy (JDK 1.5 + Tomcat 5.5) para tener un sistema ejecutable como referencia viva. Sin esto, no puedes hacer tests de intención porque el sistema no arranca.
1
Inventario de Funcionalidades
Analizar web.xml + vistas HTML/JSP para crear matriz de trazabilidad: Servlet → URL → Parámetros. Esto es ingeniería inversa pasiva — NO tocas código todavía.
2
Golden Master (Tests de Intención)
Atacar sistema legacy vía HTTP con parámetros descubiertos. Capturar respuesta (HTML, JSON, lo que sea) como "verdad absoluta". Si futuras ejecuciones dan lo mismo → comportamiento preservado.
3
Arqueología Selectiva
Solo AHORA abres el código Java. Buscas semántica rescatable (validaciones, cálculos, algoritmos) guiado por los tests. Ignoras ruido tecnológico (SQL inline, renderizado HTML).
4
Refactorización con Red de Seguridad
Construyes nueva arquitectura 3 capas (Domain/Infrastructure/Transport). Cada servlet migrado pasa tests de intención antes de "estrangular" la versión legacy. Coexistencia hasta completar.
Criterios de decisión: ¿Cuándo mirar código?
Escenario % Caja Negra % Arqueología Criterio
CRUD simple 100% 0% Crear/Leer/Actualizar/Eliminar → comportamiento observable completo
Validación formato 100% 0% Email, NIF, fecha → test detecta qué rechaza, algoritmo se infiere o busca en 2 min
Validación compleja 80% 20% Unicidad, reglas de negocio → test detecta CUANDO falla, código explica POR QUÉ
Cálculos 70% 30% Precio, descuentos, impuestos → test da ejemplos, código revela fórmula exacta
Lógica criptográfica 40% 60% Firmas, hashes → algoritmo específico requiere revisar implementación
Flujos multi-paso 80% 20% Wizards, workflows → test captura secuencia completa, código muestra estado intermedio
Regla de oro: Empieza siempre con caja negra (100%). Solo miras código cuando el test NO explica algo crítico (algoritmo, fórmula, condicional oculto). Esto minimiza tokens gastados en ruido.

Paso 1: Analizar web.xml
El web.xml es tu mapa del tesoro. Cada <servlet-mapping> te dice: "Aquí hay una funcionalidad expuesta". No te dice QUÉ hace ni CÓMO, pero te dice que EXISTE.

<servlet-mapping>

Casos edge: descubrir parámetros ocultos
Técnica: Inspección de tráfico HTTP
DEVTOOLS
Algunos parámetros NO están en formularios (cookies, headers HTTP, campos ocultos dinámicos). Para descubrirlos:
1. Abrir sistema legacy en navegador
2. Ejecutar funcionalidad manualmente (ej: firmar documento)
3. Inspeccionar request completo en DevTools → Network → Headers + Payload
4. Copiar request EXACTO (incluye cookies, tokens CSRF, etc.)
5. Replicar en test con esos parámetros adicionales
Filosofía del Golden Master
Golden Master NO valida corrección — valida consistencia. Si el sistema legacy tiene un bug (ej: calcula mal un impuesto), el Golden Master captura ese comportamiento bugueado como "verdad". Más tarde, cuando refactorices, el test DEBE pasar con el mismo bug. Arreglar el bug es una tarea separada que requiere cambiar el test también.
"A characterization test is a test that characterizes the actual behavior of a piece of code. There's no 'Well, it should do this' or 'I think it does that.' The tests document the actual current behavior of the system."
Michael Feathers, "Working Effectively with Legacy Code"

import static io.restassured.RestAssured.*;
import static org.hamcrest.Matchers.*;

public class FirmarDocumentoGoldenTest {

  // Preparación: insertar datos de prueba en BD
  @BeforeEach
  void prepararDatosPrueba() {
    insertarDocumento("DOC-001", "contrato.pdf");
    insertarCertificado("CERT-123", "12345678Z", "2026-12-31");
  }

  // Test: capturar respuesta legacy como Golden Master
  @Test
  void firmar_documento_valido_responde_ok() {
    // Atacar sistema legacy
    String respuestaLegacy = given()
        .formParam("documentoId", "DOC-001")
        .formParam("certificadoId", "CERT-123")
    .when()
        .post("http://legacy.webdte.com/firmarDocumento")
    .then()
        .statusCode(200)
        .extract().asString();

    // Guardar Golden Master (primera vez)
    guardarGoldenMaster("firma_ok", respuestaLegacy);

    // Verificar (siguientes veces)
    String goldenMaster = cargarGoldenMaster("firma_ok");
    assertEquals(goldenMaster, respuestaLegacy,
      "El comportamiento del sistema legacy cambió");
  }

  // Test: validar que certificado caducado da error
  @Test
  void certificado_caducado_responde_error() {
    insertarCertificado("CERT-VIEJO", "87654321X", "2020-01-01");

    given()
        .formParam("documentoId", "DOC-001")
        .formParam("certificadoId", "CERT-VIEJO")
    .when()
        .post("http://legacy.webdte.com/firmarDocumento")
    .then()
        .statusCode(400)
        .body(containsString("caducado"));
  }
}

Script 1: Analizar web.xml
#!/bin/bash
# analizar_webxml.sh - Extrae servlets y mappings a CSV

WEBXML="WEB-INF/web.xml"
OUTPUT="inventario_servlets.csv"

# Header CSV
echo "Servlet,Clase,URLPattern" > $OUTPUT

# Extraer servlets (nombre + clase)
grep -A 2 "<servlet>" $WEBXML | \
grep -E "servlet-name|servlet-class" | \
sed 's/.*>\(.*\)<.*/\1/' | \
paste - - >> servlets_temp.txt

# Extraer mappings (nombre + URL)
grep -A 2 "<servlet-mapping>" $WEBXML | \
grep -E "servlet-name|url-pattern" | \
sed 's/.*>\(.*\)<.*/\1/' | \
paste - - >> mappings_temp.txt

# Combinar (join por nombre servlet)
join -t $'\t' -1 1 -2 1 servlets_temp.txt mappings_temp.txt | \
tr '\t' ',' >> $OUTPUT

# Limpiar temporales
rm servlets_temp.txt mappings_temp.txt

echo "✅ Inventario generado: $OUTPUT"
Salida: CSV con 3 columnas. Cada fila = 1 funcionalidad documentada sin abrir código Java.
Script 2: Extraer parámetros de vistas
#!/usr/bin/env python3
# extraer_parametros.py - Analiza JSP/HTML buscando formularios

import re
import sys
from pathlib import Path

def extraer_parametros(archivo_vista):
    contenido = Path(archivo_vista).read_text()
    
    # Buscar formularios
    forms = re.findall(
        r'<form[^>]*action="([^"]*)"[^>]*>(.*?)</form>',
        contenido,
        re.DOTALL
    )
    
    resultados = []
    for action, form_body in forms:
        # Extraer inputs con name
        inputs = re.findall(r'name="([^"]*)"', form_body)
        resultados.append({
            'url': action,
            'parametros': inputs
        })
    
    return resultados

# Uso: python3 extraer_parametros.py formulario_firma.jsp
if __name__ == "__main__":
    vista = sys.argv[1]
    params = extraer_parametros(vista)
    
    for p in params:
        print(f"URL: {p['url']}")
        print(f"Params: {', '.join(p['parametros'])}")
        print("-" * 40)

#!/usr/bin/env python3
# generar_test.py - Crea esqueleto de test Gherkin

import sys

def generar_feature(servlet, url, parametros):
    params_table = "\n      | ".join(parametros)
    
    template = f"""# language: es
Característica: {servlet}
  Como usuario del sistema
  Quiero usar la funcionalidad {servlet}
  Para [COMPLETAR: objetivo de negocio]

  Antecedentes:
    Dado que el sistema legacy está en "http://legacy.webdte.com"
    Y el sistema refactorizado está en "http://refactor.webdte.com"

  Escenario: Caso exitoso
    Dado [COMPLETAR: precondiciones]
    Cuando envío POST a "{url}" con:
      | {params_table} |
    Entonces el sistema legacy responde HTTP 200
    Y [COMPLETAR: validaciones de negocio]
"""
    return template

# Uso: python3 generar_test.py FirmaServlet /firmarDocumento "documentoId,certificadoId"
if __name__ == "__main__":
    servlet = sys.argv[1]
    url = sys.argv[2]
    params = sys.argv[3].split(',')
    
    feature = generar_feature(servlet, url, params)
    
    filename = f"features/{servlet.lower()}.feature"
    with open(filename, 'w') as f:
        f.write(feature)
    
    print(f"✅ Test generado: {filename}")

Los errores que cometí (2 meses perdidos)
Lección dolorosa: Intenté extraer tests de integración leyendo código legacy. Pasé 2 meses atascado porque el código está tan acoplado que no hay forma de escribir tests unitarios sin refactorizar primero. Pero refactorizar sin tests es suicidio. Es un deadlock metodológico.
❌ Anti-patrón 1: Leer código antes que comportamiento
Error: Abrir el servlet Java y tratar de entender qué hace leyendo 500 líneas de if-else anidados con SQL inline.

Consecuencia: Gastas tokens de IA en ruido sintáctico. La IA alucina lógica que no existe. Inviertes 2 días y no tienes ni un solo test funcional.

Corrección: Primero ataca el sistema vía HTTP. Observa qué hace. LUEGO miras código solo si el comportamiento no explica algo.
❌ Anti-patrón 2: Tests unitarios en código acoplado
Error: Intentar escribir tests unitarios para un servlet que mezcla lógica + SQL + renderizado HTML.

Consecuencia: Los tests son inútiles porque mockear req/resp/BD/sesión es más complejo que el código mismo. Terminas testeando Mockito, no lógica de negocio.

Corrección: Tests de integración (caja negra) primero. Refactorizar a 3 capas. LUEGO tests unitarios del Domain.
❌ Anti-patrón 3: Confiar en documentación Word de 2005
Error: Leer especificación funcional en Word/PDF escrita hace 20 años y asumir que el sistema hace eso.

Consecuencia: La documentación miente. El sistema evolucionó pero nadie actualizó el Word. Escribes tests basados en specs obsoletas.

Corrección: El sistema FUNCIONANDO es la única spec confiable. Ignora documentación, captura comportamiento real.
❌ Anti-patrón 4: Migración Big Bang
Error: "Reescribiré todo el sistema en Express de golpe y luego testeo".

Consecuencia: 3 meses después tienes un sistema nuevo que no funciona. No puedes rollback. No sabes qué rompiste.

Corrección: Strangler Fig — migra servlet a servlet. Cada pieza pasa tests de intención antes de "estrangular" la versión legacy.
❌ Anti-patrón 5: Refactorizar sin tests
Error: "Este código es tan malo que primero lo limpio y luego escribo tests".

Consecuencia: Introduces bugs sutiles. No tienes forma de saber si el refactor preservó funcionalidad.

Corrección: Golden Master PRIMERO. Refactorizar DESPUÉS. El test te avisa si rompiste algo.
❌ Anti-patrón 6: Asumir que la IA entiende código viejo
Error: "Le paso 10,000 líneas de servlets a GPT-4 y que genere los tests".

Consecuencia: La IA inventa lógica. Los tests generados no validan nada real. Gastas 200K tokens en basura.

Corrección: IA para generar PLANTILLAS de tests (estructura .feature). Tú completas con comportamiento observado real.
Señales de que estás haciendo algo mal
Señal de Alarma Qué significa Solución
Llevas 3 días leyendo código y no tienes un test Parálisis por análisis — estás en modo "entender todo" STOP. Ataca el sistema vía HTTP. 1 test por hora mínimo.
Tus tests mockean 10 dependencias Código acoplado — no hay unidades testeables Cambia a tests de integración (caja negra). Refactoriza después.
La IA te genera código que no compila Le pasaste demasiado contexto / código legacy ruidoso Reduce input. Solo artefactos declarativos (web.xml, .feature)
No sabes qué testear primero Falta inventario — no sabes qué funcionalidades existen Ejecuta script analizar_webxml.sh. Prioriza por criticidad negocio.
El test pasa pero no estás seguro de por qué Test demasiado genérico / falta validación semántica Agrega asserts específicos. Valida BD, no solo status HTTP.
🚨
Regla de oro del TFM
Si una técnica te tiene atascado más de 2 días sin producir un entregable concreto (test funcional, inventario CSV, semántica extraída), esa técnica está mal. Cambia de enfoque inmediatamente. El fracaso de los 2 meses ocurrió porque no apliqué esta regla — seguí insistiendo en leer código cuando debí atacar el sistema como caja negra desde el día 1.
