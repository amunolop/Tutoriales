Arquitectura del Proyecto

Tres aplicaciones Angular independientes que trabajan juntas en tiempo de ejecución.

📐 Diagrama de la solución
🔵 Shell — App Host (puerto 4200)
Punto de entrada · Navegación · Layout global · Carga los MFEs dinámicamente
↕ carga en runtime via remoteEntry.js
🟢 MFE Productos (4201)
Catálogo · Detalle · Búsqueda
Expone → ProductosModule
🟠 MFE Carrito (4202)
Cesta · Checkout · Pagos
Expone → CarritoModule
📦 Shared Libraries
@angular/core · @angular/router · rxjs (singleton compartidos)
¿Cómo funciona? Webpack 5 Module Federation permite que el shell descargue módulos Angular de otras apps en tiempo de ejecución. El archivo remoteEntry.js actúa como el "contrato" que expone lo que cada MFE ofrece.

Instalación y Setup

Sigue estos pasos para configurar el proyecto desde cero.

1
Crear las tres apps Angular
Usa el Angular CLI para generar cada proyecto.
ng new shell --routing ng new mfe-productos --routing ng new mfe-carrito --routing
2
Instalar el plugin de Module Federation en cada app
Este paquete configura Webpack automáticamente para Angular.
cd shell && ng add @angular-architects/module-federation --project shell --port 4200 --type host cd mfe-productos && ng add @angular-architects/module-federation --project mfe-productos --port 4201 --type remote cd mfe-carrito && ng add @angular-architects/module-federation --project mfe-carrito --port 4202 --type remote
3
Configurar webpack.config.js en cada app
Definir qué expone cada MFE y qué consume el shell (ver secciones del menú).
4
Levantar los tres proyectos
# Terminal 1 cd mfe-productos && ng serve # Terminal 2 cd mfe-carrito && ng serve # Terminal 3 cd shell && ng serve
Tip: En producción cada MFE se despliega en su propio servidor/CDN. El shell solo necesita saber la URL del remoteEntry.js de cada uno.

Shell — webpack.config.js

El host declara qué apps remotas va a consumir y qué librerías se comparten como singletons.

⚙️ webpack.config.js shell (host) — puerto 4200 
const { ModuleFederationPlugin } = require('webpack/lib/container/ModuleFederationPlugin');
const mf = require('@angular-architects/module-federation/webpack');
const path = require('path');
const share = mf.share;

const sharedMappings = new mf.SharedMappings();
sharedMappings.register(
  path.join(__dirname, 'tsconfig.json')
);

module.exports = {
  output: { uniqueName: 'shell', publicPath: 'auto' },
  optimization: { runtimeChunk: false },
  plugins: [
    new ModuleFederationPlugin({
      // ✅ Apps remotas que el shell va a consumir
      remotes: {
        'mfeProductos': 'mfeProductos@http://localhost:4201/remoteEntry.js',
        'mfeCarrito': 'mfeCarrito@http://localhost:4202/remoteEntry.js',
      },

      // ✅ Librerías compartidas (se cargan una sola vez)
      shared: share({
        '@angular/core': { singleton: true, strictVersion: true, requiredVersion: 'auto' },
        '@angular/common': { singleton: true, strictVersion: true, requiredVersion: 'auto' },
        '@angular/router': { singleton: true, strictVersion: true, requiredVersion: 'auto' },
        'rxjs': { singleton: true, strictVersion: true, requiredVersion: 'auto' },
        ...sharedMappings.getDescriptors()
      })
    }),
    ...sharedMappings.getPlugins()
  ]
};
singleton: true es crucial. Garantiza que Angular se cargue una sola vez aunque cada MFE lo incluya en su bundle. Sin esto, tendrías múltiples instancias de Angular y errores extraños.

Shell — Routing

El shell usa lazy loading para cargar cada MFE solo cuando el usuario navega a esa ruta.

🔀 app-routing.module.ts shell (host) 
import { NgModule } from '@angular/core';
import { RouterModule, Routes } from '@angular/router';
import { loadRemoteModule } from '@angular-architects/module-federation';

const routes: Routes = [
  {
    path: '',
    pathMatch: 'full',
    redirectTo: 'productos'
  },
  {
    // 🟢 Carga el MFE Productos dinámicamente
    path: 'productos',
    loadChildren: () =>
      loadRemoteModule({
        type: 'module',
        remoteEntry: 'http://localhost:4201/remoteEntry.js',
        exposedModule: './ProductosModule'
      }).then(m => m.ProductosModule),
  },
  {
    // 🟠 Carga el MFE Carrito dinámicamente
    path: 'carrito',
    loadChildren: () =>
      loadRemoteModule({
        type: 'module',
        remoteEntry: 'http://localhost:4202/remoteEntry.js',
        exposedModule: './CarritoModule'
      }).then(m => m.CarritoModule),
  },
  { path: '**', redirectTo: 'productos' }
];

@NgModule({
  imports: [RouterModule.forRoot(routes)],
  exports: [RouterModule]
})
export class AppRoutingModule {}
¿Por qué loadRemoteModule? Es la función de @angular-architects/module-federation que reemplaza al import() dinámico. Permite especificar la URL del remoteEntry.js directamente, facilitando su configuración mediante variables de entorno en producción.

El MFE declara qué módulos expone para que el shell (u otros MFEs) los consuman.

    uniqueName: 'mfeProductos',
    publicPath: 'auto'

MFE Productos — Module y Routing

El módulo funciona exactamente igual que cualquier módulo Angular con lazy loading.

📦 productos.module.ts mfe-productos 
import { NgModule } from '@angular/core';
import { CommonModule } from '@angular/common';
import { RouterModule, Routes } from '@angular/router';
import { ProductosComponent } from './productos.component';
import { DetalleComponent } from './detalle/detalle.component';

const routes: Routes = [
  { path: '', component: ProductosComponent },
  { path: ':id', component: DetalleComponent }
];

@NgModule({
  declarations: [ProductosComponent, DetalleComponent],
  imports: [
    CommonModule,
    RouterModule.forChild(routes)   // forChild, NO forRoot
  ]
})
export class ProductosModule {}
// ☝️ Este es el módulo que el shell carga remotamente

MFE Productos — Componente

El componente es un componente Angular normal. No sabe que vive en un microfrontend.

🎨 productos.component.ts mfe-productos 
import { Component, OnInit } from '@angular/core';
import { ProductosService } from './productos.service';

interface Producto {
  id: number;
  nombre: string;
  precio: number;
  imagen: string;
}

@Component({
  selector: 'app-productos',
  template: `
    <div class="productos-container">
      <h2>🛍️ Catálogo de Productos</h2>
      <div class="grid">
        <div *ngFor="let p of productos" class="card">
          <img [src]="p.imagen" [alt]="p.nombre">
          <h3>{{ p.nombre }}</h3>
          <p class="precio">{{ p.precio | currency:'EUR' }}</p>
          <button (click)="agregarAlCarrito(p)">Añadir al carrito</button>
        </div>
      </div>
    </div>
  `
})
export class ProductosComponent implements OnInit {
  productos: Producto[] = [];

  constructor(private productosService: ProductosService) {}

  ngOnInit() {
    this.productosService.getProductos()
      .subscribe(p => this.productos = p);
  }

  agregarAlCarrito(producto: Producto) {
    // Comunicación con MFE Carrito via Custom Events
    window.dispatchEvent(new CustomEvent('agregar-al-carrito', {
      detail: { producto }
    }));
  }
}

Comunicación entre MFEs

Como los MFEs son independientes, no pueden inyectarse servicios entre sí directamente.

Opción 1 — Custom Events (más simple)

📡 Emisor — MFE Productos 
// Emite un evento nativo del browser
agregarAlCarrito(producto: Producto) {
  window.dispatchEvent(
    new CustomEvent('agregar-al-carrito', {
      detail: { producto }, bubbles: true
    })
  );
}
📡 Receptor — MFE Carrito 
// Escucha el evento en ngOnInit
ngOnInit() {
  window.addEventListener('agregar-al-carrito', (event: Event) => {
    const { producto } = (event as CustomEvent).detail;
    this.items.push(producto);
  });
}

Opción 2 — Shared Service con BehaviorSubject

🔗 cart.service.ts (librería compartida) 
import { Injectable } from '@angular/core';
import { BehaviorSubject } from 'rxjs';

@Injectable({ providedIn: 'root' })
export class CartService {
  private items$ = new BehaviorSubject<any[]>([]);
  items = this.items$.asObservable();

  agregar(producto: any) {
    this.items$.next([...this.items$.value, producto]);
  }

  eliminar(id: number) {
    this.items$.next(
      this.items$.value.filter(p => p.id !== id)
    );
  }
}
// Publicar como librería y ambos MFEs la importan como singleton
Recomendación: para eventos simples usa Custom Events — no acoplan los MFEs. Para estado compartido complejo, una librería compartida con BehaviorSubject o NgRx es la mejor opción.

Comparativa de estrategias

📋 Resumen 
Estrategia          | Acoplamiento | Complejidad | Recomendado para
--------------------|--------------|-------------|--------------------
Custom Events       | Bajo         | Baja        | Eventos simples
URL / Query Params  | Ninguno      | Baja        | Navegación entre MFEs
Shared Service      | Medio        | Media       | Estado compartido
NgRx / Store        | Alto         | Alta        | Apps muy complejas
