PRECONDICIÓN — DOCUMENTAR ANTES DE MIGRAR
Antes de tocar una sola línea de código, genera documentación completa de tu app Angular 18. Si la migración rompe algo y la app no arranca, tendrás una referencia exacta del estado anterior. Es el mismo principio que el HAR en el FMI — capturar el comportamiento conocido antes de cambiar nada.

Para cada documento sé exhaustivo y específico — no generes descripciones
genéricas. Cada componente, ruta, guard e interceptor debe estar nombrado
con su ruta exacta en el repositorio.

Para flujos/, identifica tú los flujos críticos de negocio de esta
aplicación y crea un .md por cada uno.

El objetivo es que un desarrollador pueda reconstruir el comportamiento
de la app solo leyendo estos docs, sin acceso al código original.
Después de generar los docs — hacer commit git add docs/ && git commit -m "docs: snapshot pre-migración Angular 18→19"
Así tienes el estado documentado en el historial de Git. Si la migración va mal, git diff entre el estado actual y el commit anterior te dice exactamente qué cambió.
Si algo falla tras la migración — cómo usar los docs Abre Copilot Chat y dile: "La app no arranca tras migrar a Angular 19. Revisa /docs/migracion/estado-previo.md y /docs/arquitectura/routing.md y compáralos con el estado actual del código. Identifica qué ha cambiado que pueda estar causando el problema."
💡 Por qué funciona mejor que confiar en la memoria del modelo
Copilot no tiene memoria entre sesiones. Si abres una sesión nueva para diagnosticar el problema post-migración, el modelo no recuerda cómo estaba la app antes. Los ficheros .md en /docs son la memoria persistente — el modelo los lee y tiene contexto exacto del estado previo sin depender de suposiciones.
EL CAMBIO CONCEPTUAL
De "el módulo define el contexto" a "el componente se define a sí mismo" En Angular 18, cada componente pertenecía a un NgModule que declaraba qué conocía y qué importaba. En Angular 19, cada componente es standalone — sabe por sí mismo qué necesita. El módulo como unidad de compilación desaparece.

POR QUÉ VALE LA PENA MIGRAR
BeneficioAngular 18Angular 19
Bundle inicial Todo el módulo se carga junto aunque no se use Cada componente se carga cuando se necesita (loadComponent)
Tree-shaking El compilador ve el módulo completo El compilador ve solo lo que cada componente importa
Testing Necesitas montar el módulo completo para testear un componente El componente es autónomo — se testea solo con sus imports
Legibilidad Para saber qué usa un componente, busca en su módulo El componente dice exactamente qué usa en su propio decorador
Reutilización Hay que exportar del módulo para usar en otro módulo Cualquier componente standalone se importa directamente
APPMÓDULE → APP.CONFIG.TS
AppModule desaparece completamente. Su trabajo se divide en dos: la configuración global va a app.config.ts y el bootstrap va a main.ts. El @NgModule no existe en Angular 19.
app.module.ts
import { NgModule } from '@angular/core';
import { BrowserModule } from '@angular/platform-browser';
import { HttpClientModule } from '@angular/common/http';
import { AppRoutingModule } from './app-routing.module';
import { AppComponent } from './app.component';
import { HomeComponent } from './pages/home/home.component';

@NgModule({
  declarations: [
    AppComponent,
    HomeComponent,     // declarado aquí
  ],
  imports: [
    BrowserModule,
    HttpClientModule,  // HTTP global
    AppRoutingModule,  // routing
  ],
  bootstrap: [AppComponent]
})
export class AppModule { }
app.config.ts
import { ApplicationConfig } from '@angular/core';
import { provideRouter } from '@angular/router';
import { provideHttpClient } from '@angular/common/http';
import { routes } from './app.routes';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),  // routing
    provideHttpClient(),    // HTTP global
  ]
};
// Sin @NgModule. Sin declarations. Sin bootstrap aquí.
// HomeComponent ya no se declara en ningún sitio central.

💡 La regla de los imports en standalone
Si un template usa <router-outlet> → importar RouterOutlet.
Si usa routerLink → importar RouterLink.
Si usa routerLinkActive → importar RouterLinkActive.
Si usa @if / @for → no importar nada (son nativos del compilador desde v17).
Si usa *ngIf / *ngFor → importar NgIf / NgFor directamente (o migrar a @if/@for).
APPROUTINGMODULE → APP.ROUTES.TS
RouterModule.forRoot() desaparece. En su lugar, provideRouter(routes) en el app.config.ts. Las rutas son un array de Routes puro — sin @NgModule, sin RouterModule, sin exports.
app-routing.module.ts
import { NgModule } from '@angular/core';
import { RouterModule, Routes } from '@angular/router';
import { HomeComponent } from './pages/home/home.component';

const routes: Routes = [
  { path: '', component: HomeComponent },
];

@NgModule({
  imports: [RouterModule.forRoot(routes)],
  exports: [RouterModule]   // ← necesario para el template
})
export class AppRoutingModule { }
app.routes.ts
import { Routes } from '@angular/router';

export const routes: Routes = [
  {
    path: '',
    // loadComponent en lugar de component
    loadComponent: () =>
      import('./pages/home/home.component')
        .then(c => c.HomeComponent)
  },
];
// Sin @NgModule. Sin RouterModule. Sin exports.
// Es solo un array de Routes exportado.
OPCIONES DE PROVIDEROUTER
Las opciones que antes iban en RouterModule.forRoot(routes, options) ahora son funciones que se pasan a provideRouter(). 
// app.config.ts — con todas las opciones
import {
  provideRouter,
  withComponentInputBinding,   // parámetros de ruta como @Input
  withDebugTracing,            // logs de navegación en consola
  withHashLocation,            // URLs con #hash
  withInMemoryScrolling,       // scroll al cambiar de ruta
  withPreloading,              // estrategia de precarga
  withRouterConfig,            // configuración avanzada
  PreloadAllModules,
} from '@angular/router';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(
      routes,
      withComponentInputBinding(),        // ruta :id → @Input() id
      withInMemoryScrolling({
        scrollPositionRestoration: 'top'  // scroll arriba al navegar
      }),
      withPreloading(PreloadAllModules),  // precarga lazy routes
      withRouterConfig({
        onSameUrlNavigation: 'reload'    // recargar si misma URL
      }),
    )
  ]
};
WITHCOMPONENTINPUTBINDING — PARÁMETROS COMO @INPUT
Una de las mejoras más cómodas de Angular 19. Con withComponentInputBinding(), los parámetros de la ruta (:id), query params y datos del resolver llegan automáticamente como @Input() al componente — sin inyectar ActivatedRoute.
sin withComponentInputBinding
import { Component, OnInit } from '@angular/core';
import { ActivatedRoute } from '@angular/router';

@Component({ ... })
export class UserDetailComponent
    implements OnInit {

  userId: string;

  constructor(private route: ActivatedRoute) {}

  ngOnInit() {
    // Hay que suscribirse o usar snapshot
    this.userId = this.route
      .snapshot.params['id'];
  }
}
con withComponentInputBinding
import { Component, Input } from '@angular/core';
// Sin ActivatedRoute

@Component({ ... })
export class UserDetailComponent {

  // El router lo inyecta automáticamente
  @Input() id!: string;  // de /users/:id
  @Input() q?: string;  // de ?q=búsqueda

  // También los datos del resolver:
  @Input() user?: User; // resolve: { user: userResolver }
}
LAS TRES FORMAS DE LAZY LOADING
Angular 19 añade loadComponent al ya existente loadChildren. Ahora puedes hacer lazy loading de un componente individual — no solo de un módulo o grupo de rutas. Esto es la diferencia más importante para el bundle size.
FormaCuándo usarAngular 18Angular 19
Módulo completo Grupo de rutas con su propio contexto loadChildren: () => import(...Module) Desaconsejado (sigue funcionando)
Grupo de rutas Sección con sub-rutas (admin, panel) No existe loadChildren: () => import(...routes)
Componente individual Una ruta = un componente No existe loadComponent: () => import(...Component)

COMPONENTE DECLARADO → COMPONENTE STANDALONE
En Angular 18, el componente era "ciudadano de segunda" del módulo. El módulo declaraba qué componentes conocía. En Angular 19, cada componente es autónomo — importa explícitamente lo que necesita en su propio @Component.
componente en NgModule
// home.component.ts — Angular 18
import { Component } from '@angular/core';
// No importa nada — lo recibe del módulo

@Component({
  // standalone: false (implícito)
  selector: 'app-home',
  template: `
    <ul>
      <li *ngFor="let i of items">{{i}}</li>
    </ul>
    <a routerLink="/about">About</a>
  `
})
export class HomeComponent {
  items = ['a', 'b', 'c'];
}
// CommonModule y RouterModule vienen del AppModule
componente standalone
// home.component.ts — Angular 19
import { Component } from '@angular/core';
import { RouterLink } from '@angular/router';
// NgFor no se importa: @for es nativo

@Component({
  // standalone: true (implícito en v19)
  imports: [RouterLink], // solo lo que usa
  selector: 'app-home',
  template: `
    <ul>
      @for (i of items; track i) {
        <li>{{ i }}</li>
      }
    </ul>
    <a routerLink="/about">About</a>
  `
})
export class HomeComponent {
  items = ['a', 'b', 'c'];
}
NUEVA SINTAXIS DE CONTROL DE FLUJO
Desde Angular 17, @if, @for y @switch son nativos del compilador. En Angular 19, con componentes standalone ya no hay razón para usar las directivas de CommonModule. La nueva sintaxis es más legible y más eficiente.
sintaxis de directivas
<!-- Requiere CommonModule en el módulo -->
<ul *ngIf="items.length > 0">
  <li *ngFor="let item of items;
              trackBy: trackById">
    {{ item.name }}
  </li>
</ul>

<div [ngSwitch]="status">
  <span *ngSwitchCase="'active'">Activo</span>
  <span *ngSwitchCase="'inactive'">Inactivo</span>
  <span *ngSwitchDefault>Desconocido</span>
</div>
sintaxis nativa @if / @for
<!-- Sin importar nada — nativo del compilador -->
@if (items.length > 0) {
  <ul>
    @for (item of items; track item.id) {
      <li>{{ item.name }}</li>
    }
    @empty {
      <li>Sin elementos</li>
    }
  </ul>
}

@switch (status) {
  @case ('active') { <span>Activo</span> }
  @case ('inactive') { <span>Inactivo</span> }
  @default { <span>Desconocido</span> }
}

GUARDS — DE CLASES A FUNCIONES
Los guards de clase con implements CanActivate se reemplazan por funciones puras. Las funciones son más simples, más fáciles de testear y no necesitan ser registradas como providers en ningún módulo. Pueden inyectar servicios con inject().
Guard como clase (v18)
// auth.guard.ts
import { Injectable } from '@angular/core';
import { CanActivate, Router } from '@angular/router';
import { AuthService } from './auth.service';

@Injectable({ providedIn: 'root' })
export class AuthGuard implements CanActivate {

  constructor(
    private auth: AuthService,
    private router: Router
  ) {}

  canActivate(): boolean {
    if (this.auth.isLoggedIn()) {
      return true;
    }
    this.router.navigate(['/login']);
    return false;
  }
}

// En la ruta:
{ path: 'admin', canActivate: [AuthGuard], ... }
Guard como función (v19)
// auth.guard.ts
import { inject } from '@angular/core';
import { CanActivateFn, Router } from '@angular/router';
import { AuthService } from './auth.service';

export const authGuard: CanActivateFn = () => {
  const auth = inject(AuthService);
  const router = inject(Router);

  if (auth.isLoggedIn()) {
    return true;
  }
  return router.createUrlTree(['/login']);
};

// En la ruta:
{ path: 'admin', canActivate: [authGuard], ... }
TIPOS DE GUARD — TODOS FUNCIONALIZAN
// guards/index.ts — todos los guards como funciones
import {
  CanActivateFn,
  CanActivateChildFn,
  CanDeactivateFn,
  CanMatchFn,
  ResolveFn,
} from '@angular/router';
import { inject } from '@angular/core';

// CanActivate — controla si se puede activar la ruta
export const authGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);
  return auth.isLoggedIn() || inject(Router).createUrlTree(['/login']);
};

// CanActivateChild — controla acceso a rutas hijas
export const adminChildGuard: CanActivateChildFn = (childRoute) => {
  return inject(AuthService).hasRole('admin');
};

// CanDeactivate — confirmar antes de salir
export const unsavedChangesGuard: CanDeactivateFn<EditComponent> =
  (component) => {
    if (component.hasUnsavedChanges()) {
      return confirm('¿Salir sin guardar?');
    }
    return true;
  };

// CanMatch — controla si la ruta se evalúa (más eficiente que canActivate)
export const featureFlagGuard: CanMatchFn = () => {
  return inject(FeatureService).isEnabled('new-dashboard');
};

// Resolve — carga datos antes de activar el componente
export const userResolver: ResolveFn<User> = (route) => {
  return inject(UserService).getById(route.params['id']);
};

INTERCEPTORES — MULTI-PROVIDER → FUNCIONES
Interceptor clase (v18)
// auth.interceptor.ts
@Injectable()
export class AuthInterceptor
    implements HttpInterceptor {

  constructor(private auth: AuthService) {}

  intercept(
    req: HttpRequest<any>,
    next: HttpHandler
  ) {
    const token = this.auth.getToken();
    const cloned = req.clone({
      setHeaders: { Authorization: `Bearer ${token}` }
    });
    return next.handle(cloned);
  }
}

// app.module.ts
providers: [{
  provide: HTTP_INTERCEPTORS,
  useClass: AuthInterceptor,
  multi: true               // ← obligatorio
}]
Interceptor función (v19)
// auth.interceptor.ts
import { HttpInterceptorFn } from '@angular/common/http';
import { inject } from '@angular/core';

export const authInterceptor: HttpInterceptorFn =
  (req, next) => {
    const token = inject(AuthService).getToken();
    const cloned = req.clone({
      setHeaders: { Authorization: `Bearer ${token}` }
    });
    return next(cloned);
  };

// app.config.ts
providers: [
  provideHttpClient(

    provideHttpClient(
      withInterceptors([
        authInterceptor,     // 1º — añade token
        loggingInterceptor,  // 2º — loguea la petición
        retryInterceptor,    // 3º — reintenta en error
        errorInterceptor,    // 4º — maneja errores globales
      ])
    )
  ]
};
SERVICES Y PROVIDERS — SIN CAMBIOS
Los servicios no cambian. Un servicio con @Injectable({ providedIn: 'root' }) funciona exactamente igual en Angular 18 y 19. No necesitas migrarlo. Solo cambia cómo se registran los providers a nivel de app. 
// Esto NO cambia entre v18 y v19
@Injectable({ providedIn: 'root' })
export class UserService {
  constructor(private http: HttpClient) {}

  getById(id: string) {
    return this.http.get<User>(`/api/users/${id}`);
  }
}

// Lo que sí cambia: providers de módulo → providers de config

// ANTES (app.module.ts):
providers: [{ provide: MY_TOKEN, useValue: config }]

// AHORA (app.config.ts):
providers: [
  { provide: MY_TOKEN, useValue: config },
  // o con InjectionToken:
  provideEnvironmentInitializer(() => {
    inject(AnalyticsService).init();  // init al arrancar
  })
]
MIGRACIÓN PROGRESIVA — MODO MIXTO
No tienes que migrarlo todo a la vez. Angular 18 ya soporta componentes standalone. Angular 19 soporta NgModules legados. Puedes migrar módulo por módulo, o incluso componente por componente dentro del mismo proyecto.
ESCENARIO A — PROYECTO V18 CON COMPONENTES STANDALONE
Puedes tener componentes standalone en un proyecto v18 con NgModules. Un componente standalone se importa en un NgModule como si fuera un módulo externo. 
// nuevo-componente.component.ts — standalone en proyecto v18
@Component({
  standalone: true,       // ← explícito en v18
  imports: [RouterLink],
  selector: 'app-nuevo',
  template: `<a routerLink="/">Inicio</a>`
})
export class NuevoComponent { }

// app.module.ts — importa el componente standalone como si fuera un módulo
@NgModule({
  declarations: [AppComponent, HomeComponent],
  imports: [
    BrowserModule,
    AppRoutingModule,
    NuevoComponent,   // ← standalone se importa, no se declara
  ],
  bootstrap: [AppComponent]
})
export class AppModule { }
ESCENARIO B — PROYECTO V19 CON NGMODULES LEGADOS
Si tienes un NgModule de una librería de terceros que no ha migrado todavía. Puedes importarlo en el app.config.ts usando importProvidersFrom(). 
// app.config.ts — importar NgModule legado en proyecto v19
import { importProvidersFrom } from '@angular/core';
import { BrowserAnimationsModule } from '@angular/platform-browser/animations';
import { StoreModule } from '@ngrx/store';   // librería con NgModule
import { SomeLibraryModule } from 'some-legacy-library';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideHttpClient(),
    // importProvidersFrom convierte NgModules en providers funcionales
    importProvidersFrom(
      BrowserAnimationsModule,   // necesario para Angular Material
      StoreModule.forRoot(reducers), // NgRx todavía en transición
      SomeLibraryModule,             // librería legacy
    )
  ]
};
PLAN DE MIGRACIÓN RECOMENDADO
1
Actualizar Angular a v19
Ejecutar ng update @angular/core @angular/cli. El proyecto sigue funcionando — los NgModules son compatibles en v19.
2
Usar el migration schematics de Angular
ng generate @angular/core:standalone convierte automáticamente componentes, directivas y pipes a standalone. Ejecutar en modo --mode=convert-to-standalone primero para ver los cambios.
# Convertir componentes a standalone
ng generate @angular/core:standalone \
  --mode=convert-to-standalone

# Eliminar NgModules innecesarios
ng generate @angular/core:standalone \
  --mode=prune-ng-modules

# Convertir el bootstrap (AppModule → app.config.ts)
ng generate @angular/core:standalone \
  --mode=standalone-bootstrap
3
Migrar guards y resolvers a funciones
Convertir las clases que implementan CanActivate, Resolve, etc. a funciones con CanActivateFn, ResolveFn. El schematics no hace esto automáticamente.
4
Migrar interceptores HTTP
Convertir clases con implements HttpInterceptor a HttpInterceptorFn. Cambiar HttpClientModule por provideHttpClient(withInterceptors([...])) en el app.config.ts.
5
Migrar NgFor/NgIf a @for/@if
Opcional pero recomendado. Mejor rendimiento, sin necesitar CommonModule. El schematics ng generate @angular/core:control-flow hace la migración automáticamente.
ng generate @angular/core:control-flow
6
Migrar loadChildren de módulo a loadComponent/rutas
Reemplazar loadChildren: () => import(...Module) por loadChildren: () => import(...routes) o loadComponent donde sea posible. El lazy loading por componente mejora el bundle size.
⚠️ Cuidado con los NgModules de terceros
Librerías como Angular Material, NgRx, PrimeNG pueden estar en transición. Antes de migrar, verifica que la versión de la librería que usas tenga soporte standalone. Si no: usar importProvidersFrom() como puente mientras la librería actualiza.

💡 Verificar si un componente es standalone
En Angular 19, todos los componentes son standalone por defecto. Si tienes un componente legado con standalone: false explícito, seguirá siendo de módulo. Si no tiene standalone, es standalone. Para saberlo rápido: si el componente tiene imports: [...] en el decorador → es standalone.
