Skills & Agents para el FMI

Arquitectura completa de skills, subagents paralelos y commands para ejecutar migraciones semánticas en Cursor, VSCode y Claude Code.

01 — Los tres pilares

Skills, Agents y Commands

El FMI se descompone en tres tipos de componentes que cooperan: skills reutilizables por fase, subagents paralelos para front/back, y commands para la experiencia del desarrollador.

🧠
Skills

Conocimiento ejecutable

Un SKILL.md por cada paso del FMI. Encapsulan el "cómo hacer" de cada fase: generar diagramas, crear tests, destilar contratos. Son reutilizables entre proyectos y publicables en el marketplace de Cursor.

fmi-sequence-diagrams fmi-integration-tests fmi-system-knowledge fmi-semantic-distillation fmi-architecture-design fmi-tdd-strategy fmi-implementation
🤖
Subagents

Ejecución en paralelo

Cursor 2.4 permite lanzar subagents con contexto aislado. El orquestador delega análisis de backend y frontend simultáneamente. Cada subagent solo ve su capa, evitando contaminación de contexto.

fmi-orchestrator fmi-backend-analyst fmi-frontend-analyst
⚡
Commands & Rules

Control del pipeline

Commands para arrancar, reanudar y verificar el pipeline. Rules always-on que actúan como guardias permanentes contra la traducción sintáctica y la saturación de contexto.

/fmi-start /fmi-resume /fmi-checkpoint /fmi-status no-syntax-translation

AGENTS.md

AGENTS.md — El orquestador principal

Fichero raíz que cualquier herramienta (Cursor, Claude Code, Codex, Gemini) lee primero. Coordina el pipeline y delega a skills.

▶
✅ Compatibilidad multi-herramienta

AGENTS.md es un estándar abierto soportado nativamente por Cursor, Codex, Gemini CLI, y mediante symlink por Claude Code (echo 'See @AGENTS.md' > CLAUDE.md).

# FMI — Framework de Migración de Intención

## Configuración
SISTEMA:     {{nombre}}
ORIGEN:      ./legacy/src
DESTINO:     ./migrado/src
LENGUAJE_A:  {{origen}}
LENGUAJE_B:  {{destino}}

## Principio Operativo
La fuente de verdad NO es el código sino los artefactos semánticos:
diagramas de secuencia, tests de integración y SYSTEM_KNOWLEDGE.md.
Nunca traduzcas código directamente de un lenguaje a otro.
Siempre genera código desde los Contratos de Intención.

## Pipeline de Ejecución
Ejecutar las fases en orden. En cada checkpoint ⚠️, detenerse
y mostrar resumen al desarrollador.

### Fase 1: Adquisición de Conocimiento
- Invocar skill `fmi-sequence-diagrams`
- PARALELIZAR: backend y frontend simultáneamente
- Invocar skill `fmi-integration-tests`
- Invocar skill `fmi-system-knowledge`
- ⚠️ CHECKPOINT: validación humana

### Fase 2: Destilación Semántica
- Invocar skill `fmi-semantic-distillation`
- Input: diagramas + SYSTEM_KNOWLEDGE.md (NUNCA código fuente)
- ⚠️ CHECKPOINT: validación de contratos

### Fases 3-5: Diseño, TDD e Implementación
- Invocar skills correspondientes en secuencia
- A partir de aquí NO cargar código origen en contexto
- ⚠️ CHECKPOINT antes de Fase 5

## Regla de Contexto
A partir de la Fase 3, el agente NO debe leer ficheros de ./legacy/.
Todo el conocimiento necesario está en fmi/SYSTEM_KNOWLEDGE.md
y fmi/contratos_intencion.md.

Skill

fmi-sequence-diagrams

Genera diagramas de secuencia Mermaid a partir de código fuente siguiendo el protocolo FMI. Un punto de entrada = un diagrama mínimo.

▶
Cuándo se activa

Fase 1 del pipeline. Es el primer skill que se ejecuta. Los subagents de backend y frontend lo invocan en paralelo, cada uno sobre su parte del código.

💡 Por qué el diagrama es anterior al test

Un test generado directamente desde el código hereda el acoplamiento a la implementación. Un test generado desde el diagrama captura la intención funcional independientemente de cómo esté implementada. Esta distinción hace los tests portables a cualquier implementación futura.

---

description: Genera diagramas de secuencia Mermaid a partir de código
  fuente siguiendo el protocolo FMI.
version: 1.0.0
---

# Skill: Generación de Diagramas de Secuencia FMI

## Procedimiento

### Paso 1: Identificar Puntos de Entrada
Buscar en el código:
- Endpoints HTTP (anotaciones @GET, @POST, decoradores de ruta)
- Métodos públicos de servicios
- Event listeners y handlers
- Tareas programadas (cron jobs)

### Paso 2: Trazar Flujos
Para cada punto de entrada:
1. Seguir la cadena de llamadas completa
2. Documentar las interacciones entre componentes
3. Registrar los datos que fluyen entre ellos
4. Identificar flujos alternativos (errores, validaciones)

### Paso 3: Generar Mermaid
Formato obligatorio por diagrama:

```mermaid
sequenceDiagram
    participant Actor
    participant API
    participant Service
    participant Repository
    participant DB

    Actor->>API: POST /recurso {datos}
    API->>Service: crearRecurso(datos)
    Service->>Service: validar(datos)
    alt datos válidos
        Service->>Repository: guardar(entidad)
        Repository->>DB: INSERT
        DB-->>Repository: OK
        Service-->>API: 201 Created
    else datos inválidos
        Service-->>API: ValidationError
        API-->>Actor: 400 Bad Request {errores}
    end
```

### Paso 4: Nombrado
- Nivel sistema:  sistema_[flujo]_[resultado].mermaid
- Nivel backend:  backend_[componente]_[accion].mermaid
- Nivel frontend: frontend_[componente]_[estado].mermaid

### Paso 5: Verificación
- Cada bifurcación IF/SWITCH del código → en algún diagrama
- Cada flujo alternativo tiene su bloque alt/else
- No omitir flujos de error

## Output
Ficheros .mermaid en {{ruta_artefactos}}/diagramas_secuencia/
Skill

fmi-integration-tests

Genera tests de integración ejecutables a partir de los diagramas de secuencia Mermaid. Un diagrama = exactamente un test. Nunca genera tests desde el código fuente.

▶
⛔ Restricción fundamental

La fuente de cada test es un diagrama de secuencia, NUNCA el código. Un diagrama produce exactamente un test. El test es caja negra, portable y determinista.

# Skill: Generación de Tests de Integración FMI

## Principio
NUNCA generar tests directamente del código fuente.
La fuente es siempre el diagrama de secuencia.

### Paso 1: Leer Diagrama
Parsear cada .mermaid e identificar:
- Participante que inicia (actor)
- Punto de entrada (endpoint/método)
- Input (datos enviados)
- Interacciones esperadas
- Output final esperado
- Flujos alternativos (bloques alt/else)

### Paso 2: Generar Test
Cada diagrama se convierte en un test:

# Ejemplo Python — adaptar al LENGUAJE_A
class TestLoginExitoso:
    """
    Fuente: diagramas_secuencia/backend/backend_auth_login.mermaid
    Contrato: El sistema autentica usuario válido y retorna token
    """

    def test_flujo_principal(self):
        # GIVEN: precondiciones del diagrama
        # WHEN: activar el punto de entrada
        # THEN: verificar output final observable

    def test_credenciales_invalidas(self):
        # Un test por cada bloque alt/else

### Paso 3: Propiedades obligatorias
- Caja negra: no referencia clases internas
- Portable: lógica idéntica en cualquier lenguaje
- Determinista: mismo input → mismo output
- Independiente: sin dependencias entre tests

## Output
Ficheros en {{ruta_tests}}/integracion/{sistema,backend,frontend}/
Skill

fmi-system-knowledge

Sintetiza todo el conocimiento del sistema en un SYSTEM_KNOWLEDGE.md con 9 secciones obligatorias. Es el artefacto más diferencial del FMI.

▶
💡 Por qué es transformador

Con el SYSTEM_KNOWLEDGE.md, los diagramas y los tests disponibles, cualquier agente LLM adquiere conocimiento completo del sistema en el inicio de la primera sesión. El onboarding cognitivo colapsa de semanas a minutos.

## 1. Propósito del Sistema
Qué problema de negocio resuelve, para quién y en qué contexto.

## 2. Invariantes de Negocio
Reglas que nunca pueden romperse. Cada invariante debe ser
verificable por al menos un test de integración.

## 3. Mapa de Flujos Funcionales
Referencia a cada diagrama de secuencia con descripción
de su propósito y precondiciones.

## 4. Contratos Implícitos
Asunciones no documentadas: encoding, zonas horarias,
precisión numérica, orden de colecciones, transacciones.

## 5. Dependencias Externas
Inventario de librerías, SDKs, APIs y servicios de terceros.
Función + impacto de su fallo.

## 6. Decisiones de Arquitectura
Qué se eligió, alternativas descartadas y por qué.
Incluye decisiones que son deuda técnica.

## 7. Deuda Técnica Documentada
Qué existe que no debería existir. Distinguir entre
deuda a preservar y deuda a eliminar.

## 8. Guía de Extensión
Cómo añadir funcionalidad sin romper contratos.
Dónde vive cada tipo de lógica.

## 9. Guía de Migración
Qué información basta para reconstruir el sistema
en otro lenguaje: refs a diagramas, tests y contratos.
Skill

fmi-semantic-distillation

Extrae Contratos de Intención purificando la lógica de negocio de deuda técnica, bugs y limitaciones del lenguaje origen. Fase 2 del FMI.

▶
⛔ Fuentes permitidas

Input: diagramas de secuencia + SYSTEM_KNOWLEDGE.md. NUNCA el código fuente del sistema origen. La destilación opera sobre los artefactos semánticos, no sobre la implementación.

Cada diagrama de secuencia se convierte en uno o más Contratos de Intención con la siguiente estructura:

CampoDescripción
ReglaNombre semántico de la regla de negocio
Flujo origenReferencia al diagrama de secuencia
ContextoCuándo y por qué se aplica
ComportamientoInput → Output sin referencia a implementación
InvarianteReferencia al SYSTEM_KNOWLEDGE si aplica
ValidacionesRequisitos OWASP de seguridad y saneamiento
Dependencia resueltaEquivalente funcional en contexto destino
Deuda técnicaQué comportamiento NO debe replicarse y por qué
1

Abstracción: Para cada diagrama, extraer qué regla de negocio implementa, cuándo se activa y qué produce.

2

Purificación: Clasificar cada comportamiento como PRESERVAR (lógica legítima), ELIMINAR (workarounds/bugs) o MEJORAR (inyectar OWASP).

3

Resolución de dependencias: Mapear cada lib/SDK del origen a su equivalente funcional en el destino.

Skill

fmi-architecture-design

Diseña la arquitectura Clean Architecture idiomática del lenguaje destino. Esta fase habilita los tests unitarios de la Fase 4.

▶
💡 Integración con Copilot Plan Mode

Esta fase es ideal para usar Plan Mode de Copilot: le das los contratos de intención y te propone la estructura antes de crear ficheros. Plan Mode piensa antes de generar código.

El skill genera tres segregaciones de capas adaptadas idiomáticamente al lenguaje destino:

D

Dominio: Entidades y reglas puras. Cada Contrato de Intención se implementa aquí. Sin dependencias externas.

A

Aplicación: Casos de uso que orquestan el dominio. Cada flujo de los diagramas de secuencia se implementa aquí.

I

Infraestructura: Adaptadores hacia BD, APIs, frameworks y servicios externos. Interfaces definidas por el dominio.

Output: arquitectura.md + convenciones.md + estructura_carpetas/ + actualización del SYSTEM_KNOWLEDGE.md

Skill

fmi-tdd-strategy

Completa la suite de tests portando los tests de integración al lenguaje destino y creando tests unitarios en Red derivados de la arquitectura.

▶

Este skill combina dos fuentes de tests con naturalezas distintas:

TipoFuentePortabilidadPropósito
Integración (portados)Diagramas Fase 1Idéntica lógica en cualquier lenguajeParidad funcional
Unitarios (nuevos)Arquitectura Fase 3Específicos del lenguaje destinoVerificar lógica interna
Contrato adaptadoresInventario dependenciasEspecíficos del destinoEquivalencia de infra
SeguridadRequisitos OWASP Fase 2Adaptados al stackValidaciones de seguridad
⚠️ Señal de problema

Si un test de integración no puede portarse directamente, indica una ambigüedad en el Contrato de Intención que debe resolverse en la Fase 2 antes de continuar.

Skill

fmi-implementation

Codifica la lógica de negocio en Green phase hasta que todos los tests pasen. Aplica Clean Code + SOLID idiomáticos del lenguaje destino.

▶
1

Green phase: Implementar código mínimo para que cada test unitario pase. Sin lógica sin test.

2

Paridad: Ejecutar tests de integración portados. Un fallo = divergencia semántica → revisar Contrato en Fase 2, no parchear código.

3

Clean Code: Nombres que expresan intención, funciones con responsabilidad única, sin efectos secundarios, DRY.

4

SOLID: S (Responsabilidad Única), O (Abierto/Cerrado), L (Liskov), I (Segregación Interfaces), D (Inversión Dependencias).

5

Refactor: Con todos los tests en verde, eliminar duplicación y mejorar legibilidad sin cambiar comportamiento.

✅ Criterio de parada

100% de tests unitarios, de integración y de nivel sistema en estado Green. El SYSTEM_KNOWLEDGE.md actualizado con decisiones de implementación.

# FMI Orchestrator

Coordinas el pipeline FMI. Tu trabajo es:

## Fase 1: Adquisición (PARALELO)
1. Lanzar fmi-backend-analyst y fmi-frontend-analyst
   EN PARALELO
2. Esperar a que ambos completen sus diagramas y tests
3. Generar los diagramas de nivel sistema
   (cruzan front y back)
4. Sintetizar SYSTEM_KNOWLEDGE.md con ambos outputs
5. ⚠️ DETENER y mostrar resumen al desarrollador

## Fase 2: Destilación
6. Invocar skill `fmi-semantic-distillation`
7. Input: diagramas + SYSTEM_KNOWLEDGE.md
8. ⚠️ DETENER y mostrar contratos para validación

## Fases 3-5: Diseño → Implementación
9. NO cargar código de ./legacy/ en contexto
10. Invocar skills en secuencia: architecture → tdd → implementation
11. Persistir estado en fmi/pipeline_state.json

## Gestión de Estado
- Actualizar pipeline_state.json tras cada fase
- En cada checkpoint: mostrar artefactos generados
- Si el contexto se satura: sugerir nueva sesión

/fmi-resume

Reanuda el pipeline desde una fase específica. Lee el estado persistido y carga solo el contexto necesario para la fase actual.

▶ 
---
description: "Reanuda el pipeline FMI desde una fase"
---

Lee fmi/pipeline_state.json para estado actual.
Lee fmi/SYSTEM_KNOWLEDGE.md para cargar contexto.

  NO cargues código de {{ruta_origen}}.
  Solo lee: SYSTEM_KNOWLEDGE.md + contratos_intencion.md

Rule

fmi-no-syntax-translation.mdc

Guardia always-on que impide la traducción sintáctica directa entre lenguajes. La regla más importante del FMI.

▶
⛔ Esta es la regla más crítica del FMI

Sin esta guardia, los agentes tienden a copiar la estructura y patrones del código origen en lugar de generar código idiomático desde los Contratos de Intención. El resultado sería código con "acento" del lenguaje original.

---
description: "Impide traducción sintáctica directa"
alwaysApply: true
---

PROHIBIDO traducir código directamente de un
lenguaje a otro.

Todo código nuevo debe generarse desde los
Contratos de Intención (fmi/contratos_intencion.md),
NUNCA desde el código fuente origen.

Si detectas que estás:
- Copiando estructura del código origen
- Usando nombres de variables del origen
- Replicando patrones del lenguaje origen
→ DETENTE y vuelve a los contratos.

El código destino debe ser idiomático del
lenguaje destino, no una traducción literal
con "acento" del lenguaje origen.
Rule

fmi-conventions.mdc

Reglas generales del FMI que se aplican en toda sesión: jerarquía de prioridad, principio de pirámide invertida y gestión de contexto.

▶ 
---
description: "Convenciones del Framework FMI"
alwaysApply: true
---

## Jerarquía de Prioridad
1. Conocimiento verificable (artefactos > código)
2. Verificación ejecutable (nada existe sin test)
3. Seguridad (OWASP no es opcional)
4. Arquitectura idiomática (patrones nativos)
5. Clean Code + SOLID

## Invariantes
- Diagramas antes que tests
- Tests integración son agnósticos al lenguaje
- Tests unitarios son consecuencia de la arquitectura
- SYSTEM_KNOWLEDGE.md se actualiza en cada fase
- Un fallo en test integración = revisar Fase 2

## Gestión de Contexto
- Fases 1-2: código origen necesario
- Fases 3+: SOLO SYSTEM_KNOWLEDGE + contratos
- Si el agente referencia clases del origen en
  Fase 5 → saturación de contexto → nueva sesión

Nivel 1

Subagents de Cursor — Fase 1

El orquestador lanza backend-analyst y frontend-analyst simultáneamente. Cada uno genera diagramas y tests de su capa con contexto aislado.

▶ 
                      ┌─ fmi-backend-analyst ──────────────┐
                      │  • Analiza endpoints, servicios, BD │
                      │  • Genera diagramas backend         │
                      │  • Genera tests backend             │
  fmi-orchestrator ──┤                                      ├──► Síntesis
                      │  • Analiza componentes, estado, UI  │    • Diagramas sistema
                      │  • Genera diagramas frontend        │    • SYSTEM_KNOWLEDGE.md
                      │  • Genera tests frontend            │    • pipeline_state.json
                      └─ fmi-frontend-analyst ──────────────┘
💡 Contexto aislado = calidad superior

Cada subagent solo ve el código de su capa. Esto evita que el análisis del backend contamine el del frontend (y viceversa), y maximiza la ventana de contexto disponible para cada análisis.

Nivel 2

Sesiones independientes — Fases 3 a 5

Una vez destilados los contratos, backend y frontend se migran en sesiones de Cursor totalmente independientes y paralelas.

▶

Tras el checkpoint de la Fase 2, los contratos de intención son compartidos pero las implementaciones son independientes. Se pueden abrir dos sesiones de Cursor (o dos instancias de Claude Code) en paralelo:

Nivel 3

Módulos dentro de cada capa

Si el backend tiene múltiples módulos (auth, pagos, notificaciones), cada uno puede migrarse como un pipeline FMI independiente en paralelo.

▶

Este nivel es útil para sistemas grandes con módulos claramente delimitados. Cada módulo mantiene su propio subconjunto de contratos y diagramas, y los tests de nivel sistema se ejecutan al final contra el conjunto ensamblado.

⚠️ Precaución

Este nivel requiere que los módulos tengan interfaces bien definidas entre sí. Si hay acoplamiento fuerte entre módulos, es mejor migrarlos secuencialmente para evitar divergencias en los contratos de las interfaces compartidas.

Copilot

Integración con Plan Mode de Copilot

El modo Plan de Copilot encaja naturalmente en la Fase 3 (diseño arquitectónico) y la Fase 5 (implementación modular).

▶
3

Fase 3 — Diseño de Arquitectura: Plan Mode piensa antes de generar código. Le das los contratos de intención y propone la estructura de carpetas, interfaces entre capas y convenciones. Genera un plan revisable antes de crear ficheros.

5

Fase 5 — Implementación: Para cada módulo, Plan Mode propone qué ficheros va a crear/modificar antes de hacerlo. Te da el checkpoint natural del FMI integrado en el flujo del IDE.

✅ Combinación recomendada

Usar Cursor + subagents para las fases de análisis paralelo (1-2) y Copilot Plan Mode para las fases de diseño e implementación (3-5) donde la revisión humana del plan antes de la ejecución es más valiosa.

Paso 1

Empieza por los skills, no por los agents

Los skills son más fáciles de probar y refinar. Crea primero el skill de diagramas y valídalo contra un módulo pequeño.

▶
1

Crea .cursor/skills/fmi-sequence-diagrams/SKILL.md con el contenido de la pestaña Skills.

2

Elige un módulo pequeño y representativo del sistema legacy (ni el más simple ni el más complejo).

3

Pide al agente que genere los diagramas solo para ese módulo. Revisa la calidad y ajusta las instrucciones del skill.

4

Cuando los diagramas sean buenos, crea fmi-integration-tests y valida que los tests generados pasan contra el sistema original.

5

Solo cuando la cadena diagrama → test funcione bien, añade los subagents para paralelizar.

Paso 2

Módulo piloto antes de escalar

Ejecuta el pipeline completo (Fases 1 a 5) manualmente sobre un módulo representativo antes de automatizar todo.

▶

El módulo piloto te dará feedback sobre qué instrucciones del skill necesitan más detalle, dónde el agente se desvía, y cuánto contexto consume cada fase. Con esa información podrás calibrar la partición entre sesiones del pipeline completo.

✅ Criterio de selección del módulo piloto

Elige un módulo que tenga: al menos 3 endpoints, interacciones con base de datos, alguna validación de negocio no trivial, y al menos un flujo de error. Esto te dará cobertura representativa sin ser tan grande que sature el contexto.

Paso 3

Invierte en el SYSTEM_KNOWLEDGE.md

Es el artefacto que salva las sesiones. Si un agente se pierde o el contexto se satura, siempre puedes arrancar desde este fichero.

▶

Valida la calidad del SYSTEM_KNOWLEDGE.md en el primer checkpoint con el mayor rigor posible. Es más barato corregir errores en la Fase 1 que descubrirlos cuando los tests de integración fallan en la Fase 5.

⚠️ Señales de un SYSTEM_KNOWLEDGE de baja calidad

Invariantes de negocio genéricas sin tests que las validen, sección de "contratos implícitos" vacía o superficial, dependencias externas sin descripción de impacto de fallo, y ausencia de deuda técnica documentada (todos los sistemas legacy tienen deuda).

Paso 4

Usa modelos distintos por fase

Cada fase del FMI requiere habilidades distintas del LLM. Ajustar el modelo por fase mejora la calidad y reduce costes.

▶

Paso 5

Versionado y gestión de sesiones

Commitea los artefactos FMI en git. Son la documentación viva del sistema y el mecanismo de rollback entre fases.

▶
1

Un commit por fase: Al completar cada fase, commitea todos los artefactos generados con un mensaje descriptivo: fmi: fase 1 completa — 55 diagramas, 55 tests, SYSTEM_KNOWLEDGE

2

Branches por implementación: Si migras a dos lenguajes destino (como en tu caso de estudio), cada implementación va en su branch. Los artefactos de Fases 1-2 son compartidos en main.

3

Gestión de sesiones: El pipeline se divide naturalmente en 2-3 sesiones. Sesión 1: Fases 1-2 (requiere código origen). Sesión 2: Fases 3-5 (solo artefactos). Sesión 3 opcional: Fases 6-7.

💡 Regla crítica de contexto

A partir de la Fase 3, el agente NO debe cargar el código fuente origen. Todo el conocimiento está en los artefactos. Cargar el código origen desperdicia contexto y puede hacer que el agente genere código destino con "acento" del lenguaje origen.
