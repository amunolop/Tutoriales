@Component 
@Component
public class PedidoItemProcessor
    implements ItemProcessor<Pedido, PedidoDTO> {

  @Override
  public PedidoDTO process(Pedido p) {
    if (p.getImporte() <= 0) return null; // null = descartar ítem

    PedidoDTO dto = new PedidoDTO();
    dto.setId(p.getId());
    dto.setCliente(p.getCliente());
    dto.setImporteConIva(p.getImporte() * 1.21);
    return dto;
  }
}
BatchConfig — igual en ambos modos
Este fichero no cambia nunca. El Job no sabe cómo va a ser lanzado. La decisión auto/manual es externa a él.
🗂️BatchConfig.java
@Configuration 
@Configuration
public class BatchConfig {

  // ── READER ──
  @Bean
  public ItemReader<Pedido> pedidoReader() {
    return new FlatFileItemReaderBuilder<Pedido>()
      .name("pedidoReader") // id en BATCH_STEP_EXECUTION_CONTEXT para restart
      .resource(new ClassPathResource("pedidos.csv"))
      .delimited().delimiter(",")
      .names("id", "cliente", "importe")
      .targetType(Pedido.class)
      .build();
  }

  // ── WRITER ──
  @Bean
  public ItemWriter<PedidoDTO> pedidoWriter(DataSource ds) {
    return new JdbcBatchItemWriterBuilder<PedidoDTO>()
      .dataSource(ds)
      .sql("INSERT INTO pedidos (id, cliente, importe_iva) " +
           "VALUES (:id, :cliente, :importeConIva)")
      .beanMapped()
      .build();
  }

  // ── STEP ──
  @Bean
  public Step procesarStep(
      JobRepository repo,
      PlatformTransactionManager tx,
      ItemReader<Pedido>  pedidoReader,
      PedidoItemProcessor         processor,  // clase concreta → @Component, sin ambigüedad
      ItemWriter<PedidoDTO> pedidoWriter) {

    return new StepBuilder("procesarStep", repo)
      .<Pedido, PedidoDTO>chunk(100, tx)
      .reader(pedidoReader)
      .processor(processor)
      .writer(pedidoWriter)
      .build();
  }

  // ── JOB ──
  @Bean
  public Job importarPedidosJob(JobRepository repo, Step procesarStep) {
    return new JobBuilder("importarPedidosJob", repo)
      .start(procesarStep)
      .build();
  }
}

¿Qué ocurre? El JobLauncherApplicationRunner detecta importarPedidosJob y lo ejecuta al arrancar. Cuando termina, la aplicación se cierra.
Responsabilidades separadas: JobService centraliza la lógica de lanzamiento. JobController solo sabe de HTTP. BatchScheduler solo sabe de cron. Ninguno conoce al otro.

JobService — lógica común de lanzamiento
Pieza central. Tiene las únicas referencias a JobLauncher y Job. El resto de clases solo inyectan JobService.
⚙️JobService.java
@Service 
@Service
public class JobService {

  private final JobLauncher jobLauncher;
  private final Job         importarPedidosJob;

  public JobService(JobLauncher jobLauncher,
                    Job importarPedidosJob) {
    this.jobLauncher        = jobLauncher;
    this.importarPedidosJob = importarPedidosJob;
  }

  public String lanzar() throws Exception {
    // timestamp único → cada llamada es una JobExecution nueva
    JobParameters params = new JobParametersBuilder()
      .addLong("timestamp", System.currentTimeMillis())
      .toJobParameters();

    JobExecution exec = jobLauncher.run(importarPedidosJob, params);
    return "Estado: " + exec.getStatus();
  }
}

BatchDataSourceConfig — definición de los dos DataSources
🗂️BatchDataSourceConfig.java
@Configuration 
@Configuration
public class BatchDataSourceConfig {

  // ── DataSource PRINCIPAL (negocio) ──
  @Bean
  @Primary
  @ConfigurationProperties("spring.datasource")
  public DataSource dataSourceNegocio() {
    return DataSourceBuilder.create().build();
  }

  // ── DataSource BATCH (interno) ──
  @Bean
  @ConfigurationProperties("batch.datasource")
  public DataSource dataSourceBatch() {
    return DataSourceBuilder.create().build();
  }

  // ── JobRepository usa el DataSource de Batch ──
  @Bean
  public JobRepository jobRepository(
      @Qualifier("dataSourceBatch") DataSource dataSourceBatch,
      PlatformTransactionManager transactionManager) throws Exception {

    JobRepositoryFactoryBean factory = new JobRepositoryFactoryBean();
    factory.setDataSource(dataSourceBatch);
    factory.setTransactionManager(transactionManager);
    factory.setDatabaseType("H2");
    factory.afterPropertiesSet();
    return factory.getObject();
  }

  // ── TransactionManager para el DataSource principal ──
  @Bean
  @Primary
  public PlatformTransactionManager transactionManager(
      @Qualifier("dataSourceNegocio") DataSource dataSourceNegocio) {
    return new DataSourceTransactionManager(dataSourceNegocio);
  }

  // ── TransactionManager para Batch ──
  @Bean
  public PlatformTransactionManager batchTransactionManager(
      @Qualifier("dataSourceBatch") DataSource dataSourceBatch) {
    return new DataSourceTransactionManager(dataSourceBatch);
  }
}

¿Qué va dónde?

dataSourceNegocio (H2 o MySQL):
  └─ tabla pedidos (negocio)
  └─ TransactionManager principal

dataSourceBatch (H2 en memoria):
  └─ BATCH_JOB_INSTANCE
  └─ BATCH_JOB_EXECUTION
  └─ BATCH_STEP_EXECUTION
  └─ JobRepository
  └─ TransactionManager de batch
Cuándo usar cada estrategia:
• 1 DataSource (modo Manual básico) → simple, todo en un sitio, restart funciona. Recomendado para empezar.
• 2 DataSources separados (este modo) → aíslas el estado de Batch, útil si múltiples apps comparten el JobRepository.
• Batch en H2 memoria → solo desarrollo/testing. Pierdes el estado al reiniciar, no funciona restart.
Auto-lanzamiento vs Manual
Decisión clave: ¿Quién controla cuándo se ejecuta el Job?
Aspecto⚡ Auto🎯 Manual
Propiedad clave job.enabled=true (defecto) job.enabled=false
¿Quién dispara? Spring Boot al arrancar Tú: controller, scheduler, test
Clases extra Ninguna JobService + JobController o BatchScheduler
JobParameters Vacíos Los defines tú (timestamp)
App se cierra sola Sí, al terminar el Job No, sigue escuchando (web) o ejecutando (cron)
Cuándo usarlo Migraciones, scripts puntuales APIs, cron, múltiples ejecuciones
BatchConfig.java Idéntica. No cambia nada.
Regla simple: Si tu Job se ejecuta una sola vez o de forma puntual → Auto. Si necesitas control de cuándo ejecutarlo → Manual.
Manual: 1 DataSource vs 2 DataSources
Decisión clave: ¿Separas las tablas de Batch de las tablas de negocio?
Aspecto🎯 Manual (1 BD)💾 Manual (2 BDs)
DataSource(s) Uno solo auto-configurado Dos explícitos: dataSourceNegocio + dataSourceBatch
Dónde van las tablas de Batch Misma BD que las tablas de negocio BD separada (H2 en memoria)
Dónde van las tablas de negocio Misma BD que Batch BD separada (H2 o MySQL)
Clases extra necesarias Ninguna, todo auto-configurado BatchDataSourceConfig
@Qualifier necesarios No, solo hay un DataSource Sí, en pedidoWriter() y procesarStep()
Complejidad configuración Baja — properties bastan Media — defines Beans manualmente
Restart funciona Sí, todo persistente Solo si dataSourceBatch es persistente. Si es H2 memoria → NO
Cuándo usarlo Por defecto, para empezar, casos simples Múltiples apps comparten JobRepository, o aislas Batch de negocio
JobService, JobController, etc. Idénticos en ambos. Solo cambia la configuración de DataSources.
Recomendación: Empieza con 1 DataSource. Solo pasa a 2 DataSources si tienes una necesidad específica de aislar las BDs o compartir el JobRepository entre varias aplicaciones.
