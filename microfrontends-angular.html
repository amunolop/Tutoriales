Micro Frontends en Angular

Arquitectura, diferencias con monolito y ejemplo práctico — Webpack Module Federation
¿Qué es un micro frontend?
Concepto Micro Frontends
Son la extensión de los microservicios al frontend. En vez de una única aplicación Angular monolítica, divides la UI en aplicaciones independientes que se desarrollan, despliegan y escalan por separado — y se componen en runtime dentro de un contenedor (shell).

Shared Libraries
@angular/core, @angular/router, rxjs, auth-lib
Dependencias compartidas entre shell y remotes. Se cargan una sola vez (singleton).
Piezas fundamentales
Shell (Host)
App contenedora que carga los micro frontends. Controla el layout global, la navegación principal y la autenticación. Define qué remotes carga y bajo qué rutas.
Remote (MF)
Cada micro frontend es una app Angular completa e independiente. Expone uno o más módulos vía ModuleFederationPlugin. Se despliega y versiona por separado.
Module Federation
Plugin de Webpack 5 que permite cargar módulos de otras aplicaciones en runtime. Es el mecanismo que hace posible los micro frontends sin iframes ni Web Components.
Conceptos clave
Carga en runtime
Los remotes se cargan bajo demanda cuando el usuario navega a su ruta. No están en el bundle inicial del shell. Webpack descarga el remoteEntry.js del remote y lo integra dinámicamente.
Deploy independiente
Cada equipo tiene su propio repositorio, CI/CD pipeline y puede desplegar su micro frontend sin tocar ni redesplegar el shell ni otros remotes. Autonomía total.
Shared dependencies
Angular core, router y RxJS se marcan como shared: { singleton: true }. Webpack los carga una sola vez para evitar duplicados y conflictos de versión. Reduce el tamaño total.
Estrategias de integración
Module Federation (Webpack 5) es el estándar de facto. Alternativas: Native Federation (esbuild, Angular 17+), Single-SPA, iframes (legacy) o Web Components.
¿Cuándo usar micro frontends?
✓ Sí, cuando...

• Múltiples equipos trabajan en la misma app
• Necesitas deploys independientes por equipo
• La app es muy grande (10+ módulos, 50+ devs)
• Quieres migrar gradualmente de AngularJS o React
• Cada dominio tiene ciclos de release distintos
✗ No, cuando...

• Un solo equipo pequeño (< 8 devs)
• La app es de tamaño mediano o pequeño
• No necesitas deploys independientes
• El overhead de infra no se justifica
• Prioridad: velocidad de desarrollo sin complejidad

Impacto en el flujo de desarrollo
Monolito — flujo típico

1. Dev hace cambio en checkout.component.ts
2. Abre PR al repo principal
3. CI construye toda la app
4. Se despliega todo el bundle a producción
5. Si falla → rollback de toda la app
Micro Frontend — flujo típico

1. Dev hace cambio en mf-checkout
2. Abre PR al repo de checkout únicamente
3. CI construye solo mf-checkout
4. Se despliega solo el remoteEntry.js de checkout
5. Si falla → rollback solo de checkout
Ejemplo: e-commerce con catálogo y checkout
Escenario: Una app e-commerce con dos secciones principales: Catálogo (listar productos) y Checkout (carrito y pago). Veremos la misma app implementada como monolito y como micro frontends.
Versión monolito — una sola app

// Routing monolito: todo en un solo proyecto
const routes: Routes = [
  { path: '', redirectTo: 'catalog', pathMatch: 'full' },
  {
    path: 'catalog',
    loadChildren: () =>
      import('./catalog/catalog.module')
        .then(m => m.CatalogModule)
  },
  {
    path: 'checkout',
    loadChildren: () =>
      import('./checkout/checkout.module')
        .then(m => m.CheckoutModule)
  }
];

@NgModule({
  imports: [RouterModule.forRoot(routes)],
  exports: [RouterModule]
})
export class AppRoutingModule { }

@Component({
  selector: 'app-catalog',
  template: `
    <h2>Catálogo</h2>
    <div *ngFor="let p of products">
      {{ p.name }} - {{ p.price }}€
      <button (click)="addToCart(p)">
        Añadir
      </button>
    </div>
  `
})
export class CatalogComponent {
  products = inject(ProductService).getAll();

  // Servicio compartido directo
  private cart = inject(CartService);

  addToCart(p: Product) {
    this.cart.add(p);
  }
}

@Component({
  selector: 'app-checkout',
  template: `
    <h2>Checkout</h2>
    <div *ngFor="let item of items">
      {{ item.name }} x{{ item.qty }}
    </div>
    <p>Total: {{ total }}€</p>
    <button (click)="pay()">Pagar</button>
  `
})
export class CheckoutComponent {
  // Acceso directo al servicio
  private cart = inject(CartService);

  items = this.cart.getItems();
  total = this.cart.getTotal();

  pay() { /* ... */ }
}
Monolito: CatalogComponent y CheckoutComponent comparten CartService directamente vía inyección de dependencias. Un solo build, un solo deploy. Simple pero acoplado.
Versión micro frontends — apps separadas
Estructura de repos:
shell/ → App host (puerto 4200)
mf-catalog/ → Remote catálogo (puerto 4201)
mf-checkout/ → Remote checkout (puerto 4202)
Config webpack del shell (host)

const { share, withModuleFederationPlugin } =
  require('@angular-architects/module-federation/webpack');

module.exports = withModuleFederationPlugin({
  remotes: {
    // nombre → URL del remoteEntry.js
    "mfCatalog": "http://localhost:4201/remoteEntry.js",
    "mfCheckout": "http://localhost:4202/remoteEntry.js",
  },
  shared: share({
    "@angular/core":       { singleton: true, strictVersion: true },
    "@angular/common":     { singleton: true, strictVersion: true },
    "@angular/router":     { singleton: true, strictVersion: true },
    "rxjs":                { singleton: true, strictVersion: true },
  })
});
Routing del shell — carga los remotes

export const routes: Routes = [
  { path: '', redirectTo: 'catalog', pathMatch: 'full' },

Config del remote (mf-catalog)

module.exports = withModuleFederationPlugin({
  name: "mfCatalog",
  exposes: {
    // Qué módulo expone al shell
    "./CatalogModule": "./src/app/catalog/catalog.module.ts",
  },
  shared: share({
    "@angular/core":   { singleton: true, strictVersion: true },
    "@angular/common": { singleton: true, strictVersion: true },
    "@angular/router": { singleton: true, strictVersion: true },
    "rxjs":            { singleton: true, strictVersion: true },
  })
});
Comunicación entre MFs — Custom Events

// En mf-catalog: emite evento global al añadir al carrito
@Component({ ... })
export class CatalogComponent {

  addToCart(product: Product) {
    // Evento custom que el shell o mf-checkout puede escuchar
    window.dispatchEvent(
      new CustomEvent('cart:add', {
        detail: { id: product.id, name: product.name, price: product.price }
      })
    );
  }
}

// En mf-checkout: escucha eventos del carrito
@Component({ ... })
export class CheckoutComponent implements OnInit {

  items = signal<CartItem[]>([]);

  ngOnInit() {
    window.addEventListener('cart:add', (e: any) => {
      const product = e.detail;
      this.items.update(items => [...items, product]);
    });
  }
}
Diferencia clave: En el monolito, CartService se inyecta directamente. En micro frontends, cada app es independiente, así que la comunicación es vía Custom Events, shared state (localStorage, BroadcastChannel) o una librería compartida expuesta en Module Federation.
Flujo en runtime
Usuario navega a miapp.com/catalog │ ├─> Shell (4200) arranca, renderiza navbar ├─> Router detecta ruta /catalog ├─> Webpack descarga http://localhost:4201/remoteEntry.js ├─> Carga CatalogModule dinámicamente ├─> Renderiza CatalogComponent dentro del <router-outlet> │ // Usuario hace click en "Checkout" │ ├─> Router detecta ruta /checkout ├─> Webpack descarga http://localhost:4202/remoteEntry.js ├─> Carga CheckoutModule dinámicamente └─> Renderiza CheckoutComponent con los items del carrito
