LA TESIS
Tengo el código pero es ilegible, parcheado, espagueti. La documentación no existe. Las especificaciones originales se perdieron. Pero la aplicación funciona perfectamente.

No voy a intentar «entender» el código. Voy a usar la IA para extraer lo que el código intenta hacer (sus intenciones), diseñar pruebas que cartografíen esas intenciones, ejecutarlas como caja negra con Playwright, y con los resultados reales construir la red de seguridad para migrar.
Planteamiento FMI — Caja Negra Guiada con IA Dual
LA FRASE QUE LO RESUME TODO
IA1 extrae intenciones del código → IA2 cartografía cada intención con tests Playwright → Playwright ejecuta y los HAR revelan el comportamiento real → de los HAR se crean los tests que validan ese comportamiento en front y back → con esa red de seguridad, se migra.
TRES CONCEPTOS QUE CAMBIAN TODO
🧠 Intención ≠ Implementación
El código INTENTA validar un DNI — con un if anidado en 8 niveles, un regex roto, o una tabla de lookup. No nos importa cómo. Nos importa QUÉ intenta hacer. La IA1 extrae la intención; la sintaxis se descarta.
🗺️ Cartografiar ≠ Validar
La IA2 no genera tests para comprobar si algo funciona — la app funciona. Genera tests para mapear exhaustivamente cómo funciona: qué acepta, qué rechaza, qué errores da, qué formatos tolera. El conjunto de resultados es el mapa completo.
🔬 Tests cartografía ≠ Tests validación
Los tests de cartografía son exploratorios: existen para descubrir, se ejecutan una o dos veces, su valor está en los HAR que producen. Los tests de validación son permanentes: se generan DESDE los HAR, se ejecutan en cada cambio, son la red de seguridad para migrar.
📐 Dos IAs por diseño
IA1 (Claude Code / Cursor) está contaminada por la sintaxis — y eso es bueno para extraer intención del espagueti. IA2 (Opus / razonador) está libre de sintaxis — y eso es bueno para diseñar tests exhaustivos sin sesgo de implementación.
ARQUITECTURA DE IA DUAL
IA1 · ANALISTA
Claude Code / Cursor / OpenCode
Tiene acceso al repositorio. Navega ficheros. Lee código espagueti. Su trabajo es extraer intenciones, no entender implementación.
Recibe:
• web.xml (mapa de endpoints)
• DDL de tablas (entidades de dominio)
• Páginas HTML con POST/GET (contratos de UI)
• Código de servlets/lógica (espagueti)

Produce:
• Documento de intenciones por funcionalidad
• «Este servlet INTENTA hacer X, Y, Z»
• Sin opinión sobre calidad ni refactoring

NO produce:
• Tests
• Código refactorizado
• Juicios sobre implementación
IA2 · CARTÓGRAFO
Claude Opus 4.6 / Modelo razonador
NO ve el código. Solo recibe intenciones. Diseña tests de Playwright que cartografían exhaustivamente cada intención.
Recibe:
• Documento de intenciones (de IA1)
• En 2ª pasada: HAR + logs semánticos

Produce:
• Batería de tests Playwright (.spec.ts)
• Casos felices + errores + límites + combinaciones
• Tests de secuencia (flujos con estado)

NO produce:
• Tests unitarios
• Tests de integración
• Nada que asuma implementación
¿Por qué dos IAs y no una? Si la misma IA lee el espagueti y genera tests, genera tests contaminados por la implementación. Ve el if (dni.length() == 9) y genera UN test con DNI de 8 caracteres. Un modelo razonador que solo recibe «intención: validar formato DNI español» genera 15 variantes — porque piensa en la intención completa, no en el if concreto.
JERARQUÍA DE CONFIANZA
🥇 HAR
Verdad absoluta — datos reales de red
🥈 Intenciones IA1
Hipótesis informadas del código
🥉 Logs semánticos
Pistas — consulta, nunca verdad
Los logs son una consulta, no una autoridad. Están escritos por el mismo desarrollador que escribió el espagueti. Pueden ser caóticos, incompletos, o engañosos (catch(Exception e) { log.error("error"); }). Se consultan cuando algo no cuadra en el HAR, pero la pista se confirma o descarta siempre con otra ejecución de Playwright.
FASE 0 — INSTRUMENTACIÓN CON LOGS SEMÁNTICOS
Única modificación al legacy permitida antes de cartografiar. No cambia lógica, solo añade trazas. El objetivo es que los logs capturen intención de negocio, no trazas técnicas. Se le pide a la IA que añada logs que ayuden a extraer comportamiento — la IA sabe mejor que el desarrollador original qué es relevante loguear.
PROMPT PARA GENERAR LOGS SEMÁNTICOS
// Prompt para IA1 (Claude Code / Cursor) — Fase 0

`Analiza este servlet/página y añade logging semántico.

NO cambies NINGUNA lógica, flujo, validación ni respuesta.
SOLO añade líneas de log.

Los logs deben capturar INTENCIÓN DE NEGOCIO, no trazas técnicas.

FORMATO — una línea JSON por operación de negocio:
{
  "intent": "NOMBRE_OPERACION_NEGOCIO",
  "input": { campos relevantes de entrada },
  "validations": { resultado de cada validación detectada },
  "result": "CREATED|REJECTED|ERROR|UPDATED|DELETED",
  "detail": "razón si es rechazo o error"
}

REGLAS:
- El campo "intent" debe ser un verbo de negocio en MAYÚSCULAS
  (ALTA_CUENTA, VALIDAR_CERTIFICADO, BUSCAR_CONTRATO)
- NO loguees: "entrando en método X", "param = Y", "saliendo"
- SÍ loguea: qué operación de negocio se intentó, con qué datos
  relevantes, y cuál fue el resultado
- Si hay un catch genérico, loguea la excepción REAL, no "error"
- Si hay múltiples validaciones, loguea el resultado de CADA UNA
- En el front: loguea eventos de formulario relevantes
  (submit, validación front, respuesta recibida)

ANTI-PATRÓN — esto NO sirve:
  log.debug("entering doPost()");
  log.debug("param email = " + email);
  log.debug("calling dao.insert()");

PATRÓN CORRECTO:
  log.info(jsonLog("ALTA_CUENTA",
    Map.of("email",email,"dni",dni),
    Map.of("email","OK","dni","FORMATO_INVALIDO"),
    "REJECTED", "DNI no cumple formato"));`

💡 ¿Por qué la IA genera mejores logs que el desarrollador original?
Porque la IA lee el código con la misión de extraer comportamiento, no de depurar bugs. El desarrollador original ponía log.debug donde tenía problemas en ese momento. La IA pone logs semánticos donde hay operaciones de negocio — que es exactamente lo que necesitas para cartografiar.
⚠️ Recordatorio: los logs son CONSULTA, no verdad
Aunque los logs semánticos son mucho mejores que los técnicos, siguen siendo código añadido sobre espagueti. Si la IA interpretó mal una intención al instrumentar, el log mentirá. Siempre: HAR manda, logs consultan. Si el log dice "result":"REJECTED" pero el HAR muestra un 200 con el registro creado, el HAR tiene razón.

ESTRUCTURA DE CARTOGRAFÍA POR INTENCIÓN:
1. CAMINO FELIZ
   - Datos válidos completos → capturar respuesta exacta
   - Variantes del camino feliz (ej: tipo=persona vs tipo=empresa)

2. FRONTERAS DE CADA CAMPO
   - Campo vacío
   - Campo con formato inválido (según validación detectada)
   - Campo en el límite (maxlength, minlength)
   - Campo con caracteres especiales / inyección

3. INCERTIDUMBRES (prioridad alta)
   - Cada incertidumbre de IA1 → bloque de tests dedicado

4. COMPORTAMIENTO DE ESTADO
   - Crear → Leer → Verificar que existe
   - Crear duplicado → Capturar qué pasa
   - Crear → Borrar → Verificar que no existe (si aplica)

5. DETECCIÓN DE DÓNDE VALIDA (front vs back)
   - Intentar submit con campo inválido
   - Si :invalid en DOM → front valida
   - Si response HTTP con error → back valida
   - Registrar dónde vive cada validación

CADA TEST DEBE:
- Capturar el response completo (status, headers, body)
- Tomar screenshot antes y después
- Registrar un objeto "contrato" en JSON
- NO asumir status codes — capturar los reales
- NO inventar campos que no estén en las intenciones

- Si la intención dice INCIERTO, el test DESCUBRE — no asume

import { writeFileSync } from 'fs';

const contratos: any[] = [];
const guardar = () => writeFileSync(
  './cartografia/alta-cuenta.json', JSON.stringify(contratos, null, 2)

// ─── Utilidad: ejecutar un alta y capturar contrato ───
async function ejecutarAlta(page, datos, caso) {
  await page.goto('/cuentas.html');

  for (const [campo, valor] of Object.entries(datos)) {
    const el = page.locator(`#form-alta [name="${campo}"]`);
    const tag = await el.evaluate(e => e.tagName);
    if (tag === 'SELECT') await el.selectOption(valor);
    else await el.fill(valor);
  }

  await page.screenshot({ path: `./captures/${caso}-pre.png` });

  // Intentar submit y capturar respuesta O validación front
  const responsePromise = page.waitForResponse(
    r => r.url().includes('/api/cuentas'), { timeout: 3000 }
  ).catch(() => null);

  await page.click('#form-alta button[type="submit"]');
  const response = await responsePromise;

  await page.screenshot({ path: `./captures/${caso}-post.png` });

  // Detectar si la validación fue front o back
  const invalidFields = await page.$$eval(
    '#form-alta :invalid',
    els => els.map(e => e.getAttribute('name'))
  );

  const contrato = {
    caso,
    datos_enviados: datos,
    validacion_front: invalidFields.length > 0 ? invalidFields : null,
    llego_al_back: !!response,
    status: response?.status() ?? null,
    responseBody: response ? await response.text() : null,
    contentType: response?.headers()['content-type'] ?? null,
    timestamp: new Date().toISOString(),
  };

  contratos.push(contrato);
  return contrato;
}

test.afterAll(() => guardar());

FASE 3 — PRIMERA EJECUCIÓN DE PLAYWRIGHT
Playwright ejecuta la batería de IA2 contra la app legacy instrumentada (Fase 0). Se capturan tres artefactos en paralelo: HAR (tráfico HTTP), logs semánticos (intención de negocio del back y front), y screenshots/video (evidencia visual). 
// playwright.config.ts — Configuración para cartografía

export default defineConfig({
  use: {
    baseURL: process.env.LEGACY_URL || 'http://localhost:8080/WebDTE',

    // Captura HAR automáticamente
    recordHar: {
      path: './har/',
      mode: 'full',       // request + response body completo
      urlFilter: '**/api/**', // solo endpoints de la app
    },

FASE 4 — SEGUNDA PASADA: IA2 REFINA LA CARTOGRAFÍA
Ciclo de refinamiento
1
IA2 recibe: intenciones + HAR 1ª pasada + logs semánticos
Ahora sabe cómo respondió realmente el sistema a cada test. Los logs semánticos dan contexto extra (como consulta, no como verdad).
2
IA2 genera un DELTA, no tests desde cero
Tests nuevos que cubren lo descubierto. Tests modificados que ajustan expectations. Tests eliminados que eran redundantes. Se mantiene trazabilidad.
3
Playwright ejecuta segunda pasada
Cartografía refinada con tests más precisos. Los HAR de esta pasada son la versión definitiva.
PROMPT PARA IA2 — SEGUNDA PASADA
`Eres el mismo diseñador de tests de la primera pasada.

TE PASO AHORA:
1. Las intenciones originales (de IA1)
2. Los contratos capturados en la 1ª ejecución (JSON)
3. Los HAR de la 1ª ejecución
4. Los logs semánticos del back y front (COMO CONSULTA)

HALLAZGOS DE LA 1ª PASADA QUE DEBES INTEGRAR:
- El alta exitosa devuelve 302 redirect, no 201
- El email duplicado devuelve 200 con body HTML de error (no 409)
- El DNI NO se valida en back — solo en front (HTML5 pattern)
- El catch genérico devuelve 200 con página de error genérica
- El campo "tipo" acepta valores fuera del select (no valida back)

GENERA UN DELTA:
- Tests NUEVOS: explorar los descubrimientos (ej: si back no valida
  DNI, ¿qué pasa si envío caracteres unicode? ¿SQL injection en DNI?)
- Tests MODIFICADOS: ajustar expectations ahora que sabemos los
  status codes reales y formatos de respuesta
- Tests ELIMINADOS: quitar los que eran redundantes
- Tests de ESTADO más complejos basados en lo descubierto

SOBRE LOS LOGS SEMÁNTICOS:
Los logs son PISTAS, no verdad. Si un log dice "result: REJECTED"
pero el HAR muestra status 200 con registro creado, el HAR manda.
Usa los logs solo para entender contexto cuando el HAR no es
suficiente (ej: el log puede revelar que se ejecutó una query
aunque el response fue genérico).`

💡 Por qué dos pasadas y no tres
La primera pasada descubre el 80% del comportamiento. La segunda refina y cubre los huecos. Una tercera pasada tendría rendimientos decrecientes — la cartografía ya está suficientemente completa para construir tests de validación fiables. Si durante la migración aparece un caso no cubierto, se añade un test puntual, no una tercera cartografía completa.
FASE 5 — DE HAR A TESTS DE VALIDACIÓN (LA RED DE SEGURIDAD)
Aquí nacen los tests permanentes. Los tests de cartografía (Fase 2-4) ya cumplieron su misión — descubrieron cómo se comporta el sistema. Ahora, desde los HAR definitivos (2ª pasada), se crean los tests de validación que protegerán la migración. Separados en front y back.
DOS TIPOS DE TESTS, DOS MOMENTOS, DOS PROPÓSITOS
🗺️ Tests de CARTOGRAFÍA (Fases 2-4)
Propósito: Descubrir comportamiento
Momento: Antes de migrar
Frecuencia: Se ejecutan 1-2 veces
Valor: Los HAR que producen
Después: Se archivan como documentación
Analogía: Son las PREGUNTAS al sistema
🛡️ Tests de VALIDACIÓN (Fase 5)
Propósito: Proteger durante migración
Momento: Desde ahora, en cada cambio
Frecuencia: Se ejecutan en cada commit
Valor: La red de seguridad
Después: Viven para siempre en el repo
Analogía: Son las AFIRMACIONES sobre el sistema

// tests/validacion/back/cuenta-api.test.js
// GENERADO desde HAR de 2ª pasada — comportamiento REAL confirmado

import { describe, it, expect } from 'vitest';

const BASE = process.env.BACKEND_URL || 'http://localhost:8080/WebDTE';

describe('API Cuentas — Comportamiento confirmado', () => {

  // ─── Del HAR sabemos: alta exitosa → 302 redirect ───
  it('alta con datos válidos → 302 redirect a /cuentas', async () => {
    const res = await fetch(BASE + '/api/cuentas', {
      method: 'POST',
      redirect: 'manual', // no seguir redirect para capturarlo
      headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
      body: 'email=valid@test.com&nombre=Test&dni=12345678Z&password=Pass1234!&tipo=persona',
    });

    expect(res.status).toBe(302);
    expect(res.headers.get('location')).toContain('/cuentas');
  });

  // ─── Del HAR sabemos: duplicado → 200 con HTML de error ───
  it('email duplicado → 200 con mensaje de error en body', async () => {
    // Crear primero
    await fetch(BASE + '/api/cuentas', {
      method: 'POST', redirect: 'manual',
      headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
      body: 'email=dup@test.com&nombre=Dup&dni=99999999R&password=Pass1234!&tipo=persona',
    });
    // Duplicar
    const res = await fetch(BASE + '/api/cuentas', {
      method: 'POST',
      headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
      body: 'email=dup@test.com&nombre=Dup2&dni=88888888T&password=Pass1234!&tipo=persona',
    });

    expect(res.status).toBe(200); // sí, 200 — así funciona el legacy
    const body = await res.text();
    expect(body).toContain('ya existe'); // mensaje descubierto en HAR
  });

  // ─── Del HAR sabemos: back NO valida DNI ───
  it('DNI inválido → back lo acepta (no valida)', async () => {
    const res = await fetch(BASE + '/api/cuentas', {
      method: 'POST', redirect: 'manual',
      headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
      body: 'email=dnitest@test.com&nombre=Test&dni=INVALIDO&password=Pass1234!&tipo=persona',
    });

    // CONFIRMADO por cartografía: el back acepta cualquier DNI
    expect(res.status).toBe(302); // se crea aunque DNI sea basura
  });
});

import { describe, it, expect } from 'vitest';

describe('Front Cuenta — Validaciones confirmadas', () => {

  // ─── De la cartografía sabemos: front SÍ valida DNI (HTML5 pattern) ───
  it('campo DNI tiene pattern que valida formato español', () => {
    // El nuevo front DEBE mantener esta validación
    // porque es la ÚNICA validación de DNI (back no valida)
    const pattern = /^\d{8}[A-Z]$/;
    expect(pattern.test('12345678Z')).toBe(true);
    expect(pattern.test('12345678')).toBe(false);
    expect(pattern.test('ABCDEFGHI')).toBe(false);
  });

  // ─── De la cartografía sabemos: front valida email (required + type=email) ───
  it('campo email es required y valida formato', () => {

    expect('short'.length).toBeLessThan(8);

  // Esto es una DECISIÓN de migración: ¿añadir validación back?

💡 Los tests de validación documentan la REALIDAD, no el ideal
El test «DNI inválido → back lo acepta» no es un bug — es la documentación del comportamiento real. Durante la migración, se decide si mantener este comportamiento o mejorarlo. Pero la decisión se toma conscientemente, con datos, no por accidente al reescribir.
FASE 6 — MIGRAR CON RED DE SEGURIDAD
Ahora sí tocamos código. Con los tests de validación en verde (front + back), la IA ayuda a migrar servlet a servlet, página a página. Cada cambio se ejecuta contra la batería de validación. Si algo se pone rojo, el cambio está mal — no el test.
A
Elegir un servlet para migrar
Se recomienda empezar por el más sencillo (menos intenciones, menos incertidumbres). Hacer vertical completa: un servlet migrado de principio a fin antes de pasar al siguiente.
B
IA refactoriza apoyándose en el código + intenciones + contratos
Ahora sí la IA lee el código espagueti, pero con tres guías: las intenciones de IA1, los contratos confirmados del HAR, y los tests de validación como red de seguridad. Refactoriza a 3 capas (Transport / Domain / Infrastructure).
C
Ejecutar tests de validación tras cada cambio
Los tests de validación del back verifican que el comportamiento no cambió. Si un test falla, el refactoring introdujo una regresión — se corrige antes de continuar.
D
Decisiones conscientes de mejora
«El back no valida DNI — ¿añadimos validación?» Se toma como decisión explícita, se modifica el test de validación para reflejar el nuevo comportamiento, y se documenta.
REFACTORING A 3 CAPAS CON SEGURIDAD
Transport
Servlet / Controller — solo recibe request, extrae parámetros, delega en Domain, formatea response. Los tests de validación back protegen esta capa.
Domain
POJOs puros, sin dependencias. Lógica de negocio, validaciones, reglas. Se le pueden añadir unit tests ahora que está aislada.
Infrastr.
DAO / Adapters — acceso a BD, servicios externos. Tests de integración con H2 o testcontainers.
Los tests de validación no cambian durante el refactoring. Si el test dice «POST /api/cuentas con datos válidos → 302», eso se mantiene sea cual sea la estructura interna. Solo se modifican tests cuando se toma una decisión consciente de cambiar comportamiento (como añadir validación de DNI en back).
