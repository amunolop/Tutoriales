Timeline — lo que cambió y por qué
2005 — Tu punto de partida
document.getElementById + XMLHttpRequest + var
Todo era var, todo era global, cada navegador hacía lo que quería (IE6 vs Firefox). No había módulos, no había const/let. Los scripts se metían con <script src> en orden manual y rezabas para que no hubiera colisión de nombres. El servidor (Servlets/JSP) generaba HTML completo y AJAX devolvía fragmentos HTML, no JSON.
2006 — jQuery cambia todo
$(document).ready() — una API para gobernarlos a todos
jQuery resuelve el caos cross-browser: un $(selector) que funciona igual en IE6 y Firefox. $.ajax() unifica XMLHttpRequest. Plugins para todo: datepickers, sliders, modals. El 70% de las webs del mundo usarán jQuery. El problema: el DOM es la base de datos. El estado vive en atributos HTML y variables globales.
2009-2011 — Node.js + HTML5
JS sale del navegador · HTML5 estandariza
Node.js (2009) lleva JS al servidor. HTML5 (2011) trae <canvas>, <video>, localStorage, history.pushState (SPAs sin hash). <template> aparece tímidamente. Backbone.js (2010) introduce la idea de separar datos de vista — el primer paso hacia componentes.
2013-2015 — La guerra de los frameworks
Angular 1 → React → Angular 2: el Big Bang
AngularJS (2013) trae two-way binding y directivas. React (2013) responde con Virtual DOM y componentes funcionales. Angular 2 (2016) reescribe todo con TypeScript. Aparecen Webpack, npm/yarn, Babel, transpiladores. Para hacer un "Hello World" necesitas 200MB de node_modules. La web se complejifica enormemente.
2015 — ES6/ES2015
JavaScript renace: const, let, arrow, class, import, Promise
El salto más grande del lenguaje. const/let, arrow functions, template literals, destructuring, class, Promise, import/export (módulos nativos). Por primera vez no necesitas jQuery para escribir JS limpio. Pero los navegadores tardan 2-3 años en soportarlo todo — Babel transpila mientras tanto.
2017-2018 — El estándar contraataca
Custom Elements v1 + Fetch API + async/await
customElements.define() se estandariza. fetch() reemplaza a XMLHttpRequest. async/await hace el código asíncrono legible. <script type="module"> funciona sin bundler. CSS Grid y Flexbox maduran. Por primera vez, lo nativo es suficiente para muchos casos.
2019-2020 — Web Components maduran
Shadow DOM v1 + Constructable Stylesheets + PWA
Shadow DOM se estabiliza en todos los navegadores. adoptedStyleSheets permite compartir CSS entre componentes. Service Workers + Manifest hacen PWAs instalables. Lit (Google) aparece como wrapper ligero de Web Components. Ya no necesitas React para tener componentes reutilizables.
2021-2026 — El renacimiento vanilla
Import Maps · Declarative Shadow DOM · View Transitions
<script type="importmap"> elimina la necesidad de bundlers para imports. Declarative Shadow DOM permite SSR de Web Components. @property en CSS, Container Queries, View Transitions API. Navigation API. El estándar del navegador ahora cubre el 95% de lo que los frameworks hacían.

La conclusión para tu migración: En 2005 necesitabas jQuery porque el estándar era un caos. En 2026, el estándar nativo cubre todo lo que jQuery hacía, más lo que React/Angular añadieron (componentes, estado, módulos). Migrar a Web Components nativos = migrar al estándar, no a otro framework que morirá en 5 años.
Web Components — las 4 piezas del puzzle
Web Components NO es un framework. Es un conjunto de 4 APIs estándar del navegador que juntas permiten crear componentes encapsulados y reutilizables. Como los componentes de React o Angular, pero nativos del navegador — sin npm install, sin build, sin dependencias.
Pieza 1
Custom Elements
Definir etiquetas HTML propias: <contrato-card>, <user-form>. El navegador las reconoce como elementos de primera clase con ciclo de vida.
Pieza 2
Shadow DOM
Encapsulamiento total: el CSS y el DOM del componente son invisibles desde fuera. No hay conflictos de estilos. Es una burbuja aislada.
Pieza 3
HTML Templates
<template> y <slot>: plantillas HTML que no se renderizan hasta que las clonas. Los slots permiten inyectar contenido desde fuera.
Pieza 4
ES Modules
import/export nativos: cada componente en su fichero .js, se importa con <script type="module">. Sin bundler.
Custom Elements — tu primera etiqueta HTML propia
// contrato-card.js — un componente completo

class ContratoCard extends HTMLElement {

  // 1. Qué atributos observar para reaccionar a cambios
  static get observedAttributes() {
    return ['codigo', 'estado', 'titular'];
  }

  // 2. Constructor: crear Shadow DOM
  constructor() {
    super();
    this.attachShadow({ mode: 'open' });
  }

  // 3. Lifecycle: cuando se inserta en el DOM
  connectedCallback() {
    this.render();
  }

  // 4. Lifecycle: cuando un atributo observado cambia
  attributeChangedCallback(name, oldVal, newVal) {
    if (oldVal !== newVal) this.render();
  }

  // 5. Renderizar
  render() {
    const codigo = this.getAttribute('codigo') || '';
    const estado = this.getAttribute('estado') || 'Pendiente';
    const titular = this.getAttribute('titular') || '';

    this.shadowRoot.innerHTML = `
      <style>
        :host { display: block; border: 2px solid #d4c9b0; border-radius: 8px;
                padding: 16px; margin: 8px 0; font-family: monospace; }
        :host([estado="Activo"]) { border-color: #2a6e4e; }
        :host([estado="Cerrado"]) { opacity: 0.6; }
        .codigo { font-size: 18px; font-weight: 700; }
        .estado { font-size: 11px; padding: 2px 8px; border-radius: 4px; }
      </style>
      <div class="codigo">${codigo}</div>
      <div>${titular}</div>
      <span class="estado">${estado}</span>
      <slot></slot>
    `;
  }
}

// 6. Registrar la etiqueta
customElements.define('contrato-card', ContratoCard);

Shadow DOM — la burbuja de encapsulamiento
El Shadow DOM crea un árbol DOM aislado dentro de tu componente. El CSS de fuera no afecta al componente, y el CSS del componente no se escapa fuera. Es el equivalente nativo del CSS Modules o Styled Components de React — pero sin build step.
Sin Shadow DOM (2005-2015):
Tu .card { color: red } en un CSS global afecta a TODAS las clases .card de la página. Si dos librerías usan la misma clase, una pisa a la otra. Solución: BEM, CSS Modules, Scoped CSS — todos parches al problema.
Con Shadow DOM (2020+):
El CSS dentro del Shadow DOM solo afecta a ese componente. Puedes tener .card { color: red } en 10 componentes y cada uno es independiente. Sin BEM, sin hacks, sin conflictos. El navegador lo aísla por ti.

El anti-patrón #1 — el DOM como base de datos
Esto es lo que tienes en tu código legacy. El estado de la aplicación vive dentro del HTML: lees valores con getElementById().value, escribes con innerHTML, y el DOM es simultáneamente la vista Y los datos. Cuando algo cambia, no sabes si el DOM refleja el estado real o un estado anterior. Es la raíz de la mayoría de tus bugs.

Los 3 niveles de estado
Nivel 1 · Local
Campos privados (#)
Estado que solo necesita un componente. Campos privados de clase: #contratos, #loading, #error. El componente es el dueño exclusivo.
Nivel 2 · Padre↔Hijo
Atributos ↓ Eventos ↑
Padre pasa datos al hijo vía atributos HTML: <card codigo="CLT-001">. Hijo notifica al padre vía Custom Events: dispatchEvent(new CustomEvent(...)).
Nivel 3 · Global
Store compartido
Datos que necesitan 3+ componentes no relacionados (usuario logueado, tema, permisos). Un store centralizado con patrón pub/sub.
Store global vanilla — 25 líneas, sin dependencias
// js/store/app-store.js — esto reemplaza a Redux/Vuex/NgRx

class AppStore extends EventTarget {
  #state = {};

  get(key) {
    return this.#state[key];
  }

  set(key, value) {
    const old = this.#state[key];
    this.#state[key] = value;
    // Notifica SOLO a quien escucha esta key
    this.dispatchEvent(new CustomEvent('change', {
      detail: { key, value, old }
    }));
  }

  subscribe(key, callback) {
    const handler = (e) => {
      if (e.detail.key === key) callback(e.detail.value, e.detail.old);
    };
    this.addEventListener('change', handler);
    return () => this.removeEventListener('change', handler); // unsubscribe
  }
}

// Singleton — una instancia para toda la app
export const store = new AppStore();
  
// Uso en un componente:

class UserBadge extends HTMLElement {

    if (user) this.shadowRoot.querySelector('.name').textContent = user.nombre;
  }

    this.#unsub();  // Limpiar suscripción al desmontar

El servicio JS como frontera
El servicio JS es la capa que traduce entre tu API REST y tus componentes. Aquí se hace el fetch, se valida la respuesta, y se transforma si hace falta. Los componentes NUNCA llaman a fetch directamente — siempre a través del servicio.
// js/services/contrato-service.js

const BASE = '/api/v1/contratos';

async function handleResponse(res) {
  if (!res.ok) {
    const error = await res.json().catch(() => ({ message: res.statusText }));
    throw new Error(error.message || `HTTP ${res.status}`);
  }
  return res.json();
}

// Validar que el JSON tiene la estructura esperada
function validateContrato(data) {
  if (!data.codigo || typeof data.codigo !== 'string') {
    throw new Error(`Contrato inválido: falta 'codigo'`);
  }
  if (!data.estado) {
    throw new Error(`Contrato inválido: falta 'estado'`);
  }
  return data;
}

export async function findAll() {
  const data = await handleResponse(await fetch(BASE));
  return data.map(validateContrato); // Valida CADA contrato
}

export async function findById(id) {
  return validateContrato(
    await handleResponse(await fetch(`${BASE}/${id}`))
  );
}

export async function create(dto) {
  return validateContrato(
    await handleResponse(await fetch(BASE, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(dto)
    }))
  );
}

No son lo mismo — Shell-lite vs App Shell
Son dos niveles de la misma idea arquitectónica. El concepto base es el mismo: separar el "esqueleto fijo" (header, nav, layout) del "contenido dinámico" (lo que cambia según la ruta). La diferencia es cuánta infraestructura pones encima.
Shell-liteEl esqueleto mínimo
Un index.html con layout fijo + un outlet dinámico + un router JS. Sin Service Worker, sin manifest, sin offline, sin PWA. Es la arquitectura de una SPA clásica: el servidor devuelve un solo HTML y JavaScript cambia el contenido según la URL.
✅ Un solo index.html con estructura fija
✅ Router JS que cambia el <main>
✅ Web Components como páginas
✅ <script type="module">
❌ No hay Service Worker
❌ No hay manifest.json
❌ No funciona offline
❌ No es instalable
App Shell (completo)Shell-lite + PWA
Todo lo anterior MÁS Service Worker que cachea el shell + manifest que permite instalar. La app abre instantáneamente (shell del cache), funciona offline (al menos el esqueleto), y se puede "instalar" como app nativa en móvil/escritorio.
✅ Todo lo de Shell-lite, más:
✅ Service Worker cachea el shell
✅ manifest.json (icono, nombre, color)
✅ Funciona offline (shell cacheado)
✅ Instalable como "app" nativa
✅ Push notifications (opcional)
✅ Requiere HTTPS
✅ Estrategia cache-first / network-first
Para tu migración FMI: Empiezas con Shell-lite (fase 3 del FMI). Cuando el shell funcione y los componentes estén migrados, añades el Service Worker + manifest para convertirlo en App Shell completo / PWA (fase 4). Son capas incrementales, no alternativas.

export async function navigate(path) {
  const outlet = document.getElementById('outlet');

  for (const [pattern, loader] of Object.entries(routes)) {
    const match = matchRoute(pattern, path);
    if (match) {
      await loader();  // Lazy load: descarga el .js solo cuando se necesita
      const tag = routeToTag(pattern);
      outlet.innerHTML = `<${tag}></${tag}>`;
      if (match.params) {
        const el = outlet.firstElementChild;
        Object.entries(match.params).forEach(([k,v]) => el.setAttribute(k,v));
      }
      return;
    }
  }
  outlet.innerHTML = '<not-found></not-found>';
}

PWA — convierte tu SPA en "app instalable"
PWA = SPA + Service Worker + Manifest. Tu web se puede instalar como app en móvil y escritorio. Funciona offline (el shell cacheado). Recibe push notifications. Sin Play Store ni App Store.
Pieza 1
manifest.json
Metadatos de la app: nombre, icono, color, orientación. Lo que ve el sistema operativo al "instalar".
Pieza 2
Service Worker
Script que intercepta peticiones HTTP. Cachea el shell, sirve offline, gestiona actualizaciones.
Pieza 3
HTTPS
Obligatorio. Los Service Workers solo funcionan en HTTPS (o localhost para desarrollo).

const CACHE = 'webdte-shell-v1';
const SHELL_FILES = [
  '/', '/css/shell.css', '/js/app.js', '/js/router.js',
  '/js/components/app-header.js', '/js/components/app-sidebar.js',
  '/manifest.json', '/icon-192.png'

// Install: cachear el shell
self.addEventListener('install', e => {
  e.waitUntil(
    caches.open(CACHE).then(c => c.addAll(SHELL_FILES))
  );
});

// Fetch: shell del cache, datos de la red
self.addEventListener('fetch', e => {
  if (e.request.url.includes('/api/')) {
    // Datos del API: siempre red (network-first)
    e.respondWith(fetch(e.request).catch(() => caches.match(e.request)));
  } else {
    // Shell: primero cache, luego red (cache-first)
    e.respondWith(caches.match(e.request).then(r => r || fetch(e.request)));
  }
});

Lazy loading — solo carga lo que se ve
El router ya hace lazy loading de páginas con import() dinámico. Pero hay otra capa: componentes que están "below the fold" (debajo del scroll) no deberían renderizarse hasta que sean visibles.
// Componente que no renderiza hasta que es visible

class LazySection extends HTMLElement {
  #rendered = false;
  #observer;

  connectedCallback() {
    this.attachShadow({ mode: 'open' });
    this.shadowRoot.innerHTML = '<div class="placeholder">Cargando...</div>';

    // Observar cuando el componente entra en el viewport
    this.#observer = new IntersectionObserver((entries) => {
      if (entries[0].isIntersecting && !this.#rendered) {
        this.#rendered = true;
        this.#observer.disconnect();
        this.loadContent();  // Ahora sí: fetch + render
      }
    }, { rootMargin: '200px' }); // 200px antes de llegar → precarga suave

    this.#observer.observe(this);
  }

  async loadContent() {
    const data = await fetch('/api/estadisticas').then(r => r.json());
    this.shadowRoot.innerHTML = `<div class="stats">...${data}...</div>`;
  }

  disconnectedCallback() { this.#observer?.disconnect(); }
}

Las 3 fases de convivencia JSP ↔ Web Component
Fase A
WC dentro del JSP
El JSP sigue existiendo. Le añades un <script type="module"> que registra el Web Component. El JSP y el WC conviven en la misma página. jQuery sigue funcionando.
Fase B
JSP desaparece
La pantalla se mueve al Shell-lite (index.html + router). El Servlet ahora devuelve JSON (con el truco del Accept header). El JSP se puede borrar.
Fase C
Solo JSON
El Servlet solo devuelve JSON. Se elimina el código HTML del Servlet. Frontend y backend están desacoplados. La migración de esta pantalla está completa.

¿Por qué funciona? Los Web Components son elementos HTML estándar. El navegador los trata como un <div> o un <input>. jQuery los ve como cualquier otro nodo DOM: $(el).attr(), $(el).on(), $(el).find() — todo funciona. No hay conflicto. Por eso puedes migrar componente a componente sin romper nada.

import { findAll } from '@services/contrato-service.js';

class ContratoList extends HTMLElement {

    try {
      const contratos = await findAll();
