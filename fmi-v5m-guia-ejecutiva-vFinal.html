La evolución del proyecto
5 DESCUBRIMIENTOS QUE CAMBIARON EL PROYECTO
Callejón sin salida
Tests unitarios generados desde el código legacy
La primera intuición: que la IA lea el espagueti y genere tests unitarios. El problema: los tests reproducían la implementación — incluyendo los bugs. Un test del espagueti solo verifica que el espagueti hace lo que hace, no lo que debería hacer. No captura semántica, captura sintaxis. La idea de generar tests de integración después iba en la misma dirección errónea.
Descubrimiento 1
devContainer — para migrar, primero hay que hacer funcionar el original
Con VSCode y .devContainer se puede reproducir el entorno original (JDK 1.5, Tomcat 5.5, PostgreSQL) en Docker. Arrancarlo, depurarlo, verlo funcionar como en 2005. Eso cambia todo: ya no imaginas qué hacía el legacy — lo ves funcionar y observas su comportamiento directamente. Primer principio: antes de migrar, consigue que funcione exactamente como estaba.
Descubrimiento 2
E2E con Playwright para cartografiar — correcto pero lento
Con el legacy corriendo, la idea de usar tests E2E para cartografiar el comportamiento observable (happy path, errores, límites, roles) era la dirección correcta. Pero hacerlo manualmente — diseñar cada test, ejecutar, analizar HAR — llevaba semanas por servlet. La semántica estaba ahí, la velocidad no.
Descubrimiento 3 — el que lo cambió todo
Caveman + agentes paralelos = batch de refactorización TDD
Cada agente funciona mejor con contexto mínimo aislado. Esa restricción que parece una limitación es el mecanismo que produce precisión. Con 2 semanas de ajuste de prompts, el sistema se convirtió en un batch que genera tests primero y código después — como TDD pero con agentes especializados: un Architect (Opus) que piensa, Test Workers (Sonnet) que especifican, un GATE que verifica coherencia, Code Workers (Sonnet) que implementan, y un Smoke (Haiku) que valida.
Descubrimiento 4
Los .har de las pruebas son oro para generar E2E
Los ficheros HAR capturan exactamente el comportamiento real del sistema: requests, responses, headers, cookies, redirects, errores. Eso es semántica pura — no interpretada por una IA leyendo código, sino observada en el sistema vivo. Con el HAR como input, el agente genera E2E que capturan el comportamiento real, no el implementado. La pieza que faltaba para cerrar el ciclo.
Resultado
V5M/V6M — el motor que modela un equipo de arquitectura
Todo junto: Meta-Architect (Opus) que escanea y planifica, Architect (Opus) que distribuye trabajo, Test Workers (Sonnet ×N) en paralelo, GATE bloqueante de 7 checks, Code Workers (Sonnet ×N) que leen los tests y los satisfacen, Smoke (Haiku) que valida mecánicamente. El motor no inventa nada nuevo — codifica el comportamiento de los buenos equipos de arquitectura y lo hace ejecutable.
LA FRASE DEFINITIVA
El motor no inventa una nueva forma de migrar legacy. Codifica el comportamiento que ya tienen los buenos equipos de arquitectura — escanear, especificar con tests, implementar después, verificar antes de entregar — y lo hace ejecutable mediante agentes de IA especializados, cada uno con el modelo exacto y el contexto mínimo para máxima precisión.

LOS 3 PRINCIPIOS QUE HACEN QUE FUNCIONE
Restricción de contexto = precisión
Cada worker con contexto mínimo aislado (Caveman Lite). No ve a otros workers, no ve sus tests, no ve historial. Solo su TEST SPEC + DIGEST. Eso impide confusión, fuerza precisión, evita llenar la ventana de contexto y que Claude Code deje de funcionar. Es bajo acoplamiento aplicado a agentes de IA.
TDD-as-Spec
Tests antes que código — siempre. Los Test Workers definen el contrato. Los Code Workers leen los tests y los satisfacen. Si el código no pasa el test, el código está mal — nunca el test. El resultado: código que hace exactamente lo especificado, sin más ni menos.
GATE bloqueante
7 checks entre las dos oleadas de workers. Si los tests no son coherentes entre sí según SHARED CONTRACTS → ABORT antes de gastar tokens en código. Es el code review automático que impide que errores se propaguen silenciosamente.

Con 20h ibas justo — cualquier imprevisto te dejaba sin margen. Con 30h tienes 4h de buffer real y la memoria pasa de 6h (un sprint estresante) a 10h (tiempo para escribir bien). ⚠️ Lo que se come el buffer — y cómo evitarlo
Paso 4: si los E2E fallan mucho, no te quedes corrigiendo indefinidamente. Después de 3h, los que no estén en verde → test.skip + documentar. Son edge cases que puedes mencionar como limitación en la memoria.
Paso 5: si el GATE falla más de 2 veces en la misma fase, reduce scope de esa fase en lugar de iterar indefinidamente. Mejor 3 servlets migrados bien que 7 a medias.
Paso 7: la trampa del perfeccionismo. La memoria necesita ser suficiente para la nota, no perfecta. 25 páginas claras con evidencias reales > 40 páginas de relleno.

PASO 5 · V6M MIGRA (4h)
# Invocación V6M

Migra el legacy WebDTE a arquitectura moderna.

Frontend: Web Components (Vanilla JS, cero dependencias)
Backend: 3 capas (domain / infrastructure / transport)
  Naming: Finder/Storer/Sender/Renderer/Validator/Calculator/Mapper
  PROHIBIDO: Service/Manager/Helper/Util/Handler
Tests: tests/e2e/validacion/ son la especificación
Contratos: docs/contracts.json
Knowledge Injection:
  - titulacion (no especialidad)
  - nombreProfesor (no getFormatos)
  - "year" como int, no String

Estrategia Consumer-Driven Contract:
  FASE 1: Frontend WebComponents
  FASE 2: SCAN intermedio → contratos exactos
  FASE 3: Backend 3 capas
  FASE 4: E2E seguridad OWASP

V5M por fase: Architect → TEST WORKERS → GATE → CODE WORKERS → SMOKE
Output en: codigo-migrado/

FLUJO V5M
P
PRE-FLIGHT
Validar source · _logs/ scaffold · 00_config.json · Knowledge Injection.
A
ARCHITECT (Opus · una vez)
4 artefactos: Blueprint (agrupación), DIGEST (~2K tokens), SHARED CONTRACTS (nombres, constructores, paquetes), TEST SPECS (~500 tok/grupo). Workers no leen el legacy — leen el DIGEST.
T
OLEADA 1 — TEST WORKERS (Sonnet ×N · paralelo)
Cada worker recibe su TEST SPEC + DIGEST. Escribe tests a disco. Caveman Lite: no conoce a otros workers. La restricción de contexto fuerza la precisión.
G
GATE BLOQUEANTE — 7 CHECKS
≥ N archivos · imports domain.interfaces · Optional.of() · DTOs · constructores · paquetes. FALLA → ABORT. Nunca Code Workers con tests incoherentes.
C
OLEADA 2 — CODE WORKERS (Sonnet ×N · paralelo)
Cada worker LEE sus tests primero → escribe código que los satisfaga. No inventa contratos.
S
SMOKE (Haiku · 28 checks)
grep · count · exists. Mecánico. Escala a Sonnet si fallo complejo.

💡 Por qué Subagents y no todo en CLAUDE.md
Cada subagent = su propia ventana de contexto + su propio modelo + tools restringidas. Si todo estuviera en CLAUDE.md: (1) se cargaría en cada conversación aunque solo depures, (2) un solo modelo para todo, (3) los workers se "verían" entre sí — adiós Caveman Lite, adiós precisión. Los subagents son la pieza que hace posible el paralelismo sin llenar la ventana de contexto.
