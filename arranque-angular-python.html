DOS ECOSISTEMAS, DOS HISTORIAS MUY DISTINTAS
npm nació en 2010 junto con Node.js — como parte del mismo proyecto, diseñado desde el día uno. Python nació en 1991, casi 20 años antes de que "gestión de paquetes" fuera un problema con solución conocida. Su packaging se construyó en capas sueltas durante tres décadas, por grupos distintos, sin coordinación central. De ahí viene toda la fragmentación que has visto (pip, venv, pyenv, poetry, conda...).

Resumen habitual del problema — hasta hace muy poco
✅ El giro de 2026: esa ventaja de npm ya no es tan grande
uv (de Astral, la empresa detrás de Ruff, adquirida por OpenAI en marzo de 2026) ha consolidado casi todo el stack de Python en una sola herramienta — reemplaza pip, venv, pyenv, poetry y pipx a la vez. No es casualidad que se parezca al diseño de npm: Python tardó 35 años más en llegar a un diseño coherente, no es que fuera imposible de lograr.
EL MAPA RÁPIDO
npm install
Instala una dependencia de forma permanente en tu proyecto, la anota en package.json.
npx
Ejecuta un paquete sin instalarlo de forma permanente — de usar y tirar.
uv add
El equivalente Python a npm install — instala, anota en pyproject.toml y sincroniza el entorno, todo en un paso.
uv sync
El equivalente Python a npm ci — instala exactamente lo que dice el lockfile, para reproducibilidad total.

LOS DOS ARCHIVOS QUE LO SOSTIENEN TODO
package.json
El manifiesto: qué dependencias necesitas, en qué rango de versiones (^1.2.3, ~1.2.3), scripts del proyecto (npm run build), metadatos.
package-lock.json
El lockfile: las versiones EXACTAS que se resolvieron la última vez, con hashes de integridad — garantiza que todo el mundo instala lo mismo, byte a byte.
SEMVER — QUÉ SIGNIFICA CADA SÍMBOLO
NotaciónQué permite actualizar
1.2.3Versión exacta, sin margen
~1.2.3Solo parches: 1.2.4, 1.2.9 — nunca 1.3.0
^1.2.3Parches y minor: hasta 1.9.9 — nunca 2.0.0
NPM INSTALL VS. NPM CI
⚠️ Usa npm ci en CI/CD, no npm install
npm install puede actualizar el lockfile si package.json cambió. npm ci borra node_modules/ por completo e instala exactamente lo que dice package-lock.json — si no coincide con package.json, falla en vez de improvisar. Es más rápido y 100% reproducible: lo que usa cualquier pipeline de integración continua serio.
CREAR UN PROYECTO — NG NEW
Angular 22 (junio de 2026) es la versión estable actual. Desde Angular 19, los componentes son standalone por defecto — ya no hace falta escribir standalone: true; para volver al modelo antiguo de NgModules hay que poner explícitamente standalone: false. Se ha invertido la lógica respecto a hace unos años. 
# Instala el CLI de forma puntual y crea el proyecto en un solo paso
npx @angular/cli@latest new mi-app

cd mi-app
ng serve

EL MATIZ PROPIO DE ANGULAR EN PACKAGE.JSON
Angular exige que todos los paquetes @angular/* estén en la misma versión exacta entre sí — @angular/core, @angular/common, @angular/router... todos con ~22.1.0, nunca mezclados. Por eso Angular tiene su propio comando de actualización en vez de dejarlo a npm update suelto. 
// Fragmento típico de package.json en un proyecto Angular
{
  "dependencies": {
    "@angular/core": "~22.1.0",
    "@angular/common": "~22.1.0",
    "@angular/router": "~22.1.0",
    "rxjs": "~7.8.0"
  }
}
NG UPDATE — LA VENTAJA DE TENER UN CLI PROPIO
✅ Actualización coordinada con migraciones automáticas de código
ng update no es un npm update con otro nombre — actualiza todos los paquetes @angular/* a la vez, a la misma versión, y aplica schematics (migraciones automáticas de código) para adaptar tu código a los breaking changes de la nueva versión. Esto es algo que npm, por sí solo, no sabe hacer — es una capa que Angular construyó encima.
ng update @angular/core @angular/cli
LA FRAGMENTACIÓN HISTÓRICA — POR QUÉ HABÍA TANTAS HERRAMIENTAS
HerramientaQué resolvía (y solo eso)
pipInstalar paquetes desde PyPI — nada de entornos ni versiones de Python
virtualenv / venvAislar las dependencias de un proyecto de las de otro — nada de instalación ni versiones
pyenvTener varias versiones de Python instaladas a la vez — nada de paquetes ni entornos
pip-toolsGenerar un lockfile a partir de requirements.in — pip solo no lo hacía
Poetry / PipenvIntentos de unificar todo lo anterior — cada uno con su propio formato, sin ser el estándar
Cuatro problemas distintos, cuatro (o más) herramientas distintas, cada una con su propio formato de configuración. Aprender una no te servía para las otras tres.
UV — EL ESTÁNDAR DE 2026
uv (Astral, escrito en Rust, adquirida por OpenAI en marzo de 2026) resuelve los cuatro problemas con un solo binario, 10-100 veces más rápido que pip. Es, a día de hoy, la recomendación por defecto para cualquier proyecto Python nuevo. 
# Instalar uv (una sola vez, a nivel de sistema)
curl -LsSf https://astral.sh/uv/install.sh | sh

# Crear un proyecto nuevo
uv init mi-proyecto
cd mi-proyecto

# Añadir una dependencia — instala, actualiza pyproject.toml,
# regenera uv.lock y sincroniza .venv, todo en un solo paso
uv add anthropic langchain langgraph

# Ejecutar código dentro del entorno — sin activar nada a mano
uv run python main.py
GESTIONAR VERSIONES DE PYTHON (SIN PYENV)
# Instala una versión concreta de Python
uv python install 3.12

# Fija qué versión usa este proyecto (escribe .python-version)
uv python pin 3.12
EJECUTAR UNA HERRAMIENTA SIN INSTALARLA (EL NPX DE PYTHON)
# Equivalente a "npx create-react-app"
uvx ruff check .
SI TE ENCUENTRAS CÓDIGO LEGADO
Vas a seguir viendo requirements.txt + pip install -r requirements.txt en proyectos antiguos durante años — es la forma más extendida históricamente. uv lo lee y lo soporta como capa de compatibilidad, y también migra un proyecto Poetry existente: uv sync dentro de un repo con pyproject.toml de Poetry genera su propio uv.lock sin fricción.
LA CRONOLOGÍA QUE EXPLICA TODO
1991 — Nace Python. No existe "gestión de paquetes" como concepto resuelto en ningún lenguaje todavía.
1998-2004 — distutils y luego setuptools intentan resolver la instalación de paquetes, de forma independiente al núcleo del lenguaje.
2007-2008 — virtualenv y pip aparecen por separado, de comunidades distintas, para resolver problemas distintos (aislamiento vs. instalación).
2010 — Node.js y npm nacen juntos, como un único proyecto: registro central, CLI y lockfile pensados desde el primer día, con los aciertos y errores de Perl (CPAN) y Ruby (RubyGems) ya visibles para copiar o evitar.
2012-2020 — Python va incorporando venv a su librería estándar, estandariza el formato wheel, y llega a pyproject.toml (PEP 518 en 2016, PEP 621 en 2020) como intento tardío de unificación.
2018 — Poetry aparece como el primer intento serio de "todo en uno" — pero con su propio formato, compitiendo con el estándar oficial en vez de ser el estándar.
2024-2026 — uv llega y, por fin, consolida todo en una herramienta única y rápida — 35 años después de que Python naciera.
✅ La lección real, no la de "JS es mejor diseñado"
npm no ganó por mejor ingeniería en abstracto — ganó por nacer 19 años más tarde, cuando ya se sabía qué funcionaba en otros lenguajes y se pudo diseñar todo de una vez. Python cargaba con 20 años de código ya instalado en el mundo cuando llegó el momento de intentar unificar — eso hace el problema estructuralmente más difícil de arreglar de golpe, no es cuestión de talento de los equipos.
Dato curioso de cierre: uv está escrito en Rust y su diseño toma tanto o más prestado de Cargo (el gestor de paquetes de Rust) como de npm directamente. El principio de diseño ganador —todo-en-uno, lockfile+registro+CLI coherentes desde el origen— es el mismo que ya acertó npm en 2010.

DE CLONAR EL REPO A TENERLO CORRIENDO — LOS DOS CASOS
ANGULAR
git clone <repo> — te trae package.json y package-lock.json, nunca node_modules/ (va en .gitignore).
npm ci — no npm install. Instala exactamente lo que dice el lockfile, sin sorpresas ni actualizaciones inesperadas.
ng serve — arranca el servidor de desarrollo.
PYTHON
git clone <repo> — te trae pyproject.toml y uv.lock, nunca .venv/ (también va en .gitignore).
uv sync — lee ambos archivos, crea .venv si no existe, e instala exactamente lo que dice el lock, incluidas dependencias transitivas.
uv run python main.py — ejecuta dentro del entorno correcto, sin que tengas que activarlo a mano con source .venv/bin/activate.
✅ El paralelismo que por fin existe en 2026
npm ci y uv sync son, por primera vez, el mismo concepto exacto en los dos ecosistemas: instalación reproducible desde un lockfile, sin margen de interpretación. Hace tres años esta tabla no se podía escribir con tanta simetría del lado de Python.
