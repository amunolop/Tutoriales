LA INVERSIÓN DE PODER
Tesis central de spec-kit Durante décadas el código fue el rey: las specs eran andamiaje que se tiraba cuando empezaba el "trabajo real". SDD invierte la relación de poder: el código sirve a la especificación. La spec no guía la implementación — la genera. Mantener software pasa a ser evolucionar specs; el código es la última milla, regenerable.
El problema: vibe coding
Describes el objetivo, recibes un bloque de código que parece correcto y no funciona del todo. Compila pero pierde la intención. GitHub lo diagnostica así: tratamos a los agentes como buscadores cuando son pair programmers literales — excelentes en reconocimiento de patrones, pésimos leyendo mentes.
La solución: intención como fuente de verdad
Separar el QUÉ estable (spec) del CÓMO flexible (plan + código). Requisitos de seguridad, design system y restricciones organizativas van en la spec desde el día uno, no como parches posteriores. Cambiar de rumbo = actualizar spec, regenerar plan, dejar que el agente reconstruya.
QUÉ ES EXACTAMENTE (Y QUÉ NO)
Dos componentes, cero magia 1) Specify CLI: bootstrapper Python que descarga plantillas oficiales para tu agente y monta el scaffolding SDD. 2) Plantillas + scripts helper (bash/PowerShell): definen qué es una spec, qué es un plan, cómo se trocea en tareas. Puedes prescindir del CLI y copiar las plantillas a mano desde Releases. No hay runtime, no hay servidor, no hay lock-in: son prompts estructurados + convenciones de ficheros Markdown versionables en Git.
Estatus: experimento declarado GitHub lo etiqueta explícitamente como experimento para validar hipótesis: que SDD es independiente de stack, que sirve para apps mission-critical, que soporta exploración paralela de implementaciones (proceso 0→1, 1', 2, 3, N). Evoluciona rápido — 178 releases desde sept-2025.

El insight que te interesa para el TFM
El escenario brownfield de spec-kit es exactamente el problema de FMI: "la intención original se perdió en el tiempo". Pero su mecanismo de extracción es opuesto — spec-kit asume que un humano escribe la spec del sistema legacy; FMI la extrae mecánicamente (HAR + clasificación forzada por Clean Architecture). DECISIONES DE DISEÑO RELEVANTES
Feature = rama + carpeta numerada
/speckit.specify invoca create-new-feature.sh: crea la rama 001-nombre y specs/001-nombre/. La numeración da orden cronológico y trazabilidad de intención a implementación en el historial Git.
Scripts fuera del LLM
Todo lo que debe ser determinista (crear ramas, validar prerrequisitos, montar carpetas) es shell script invocado desde el prompt — no se le pide al modelo. Misma filosofía que tus launchers POSIX con jq: el LLM decide, el script ejecuta.
Markdown como representación intermedia
Cada artefacto es Markdown plano: diffeable, revisable en PR, legible por humano y agente. La spec es el fichero fuente; el código es artefacto derivado.
Memoria vs trabajo
.specify/memory/ (constitution) cambia casi nunca; specs/ cambia por feature. Idéntica separación a tu CLAUDE.md (sistema) vs task prompts (trabajo): las reglas no se tocan en cada ciclo.
Brownfield: dos ciclos de vida separados En proyectos existentes la guía oficial (Evolving Specs) recomienda no mezclar: los ficheros gestionados por el toolkit se refrescan al hacer upgrade de spec-kit; los artefactos de specs/ solo cambian cuando cambia el comportamiento pretendido del software. Tooling y de intención evolucionan por raíles independientes.

ANATOMÍA DE TASKS.MD
Fases por user story
Cada user story es una fase de implementación independiente con checkpoint de validación propio → entrega incremental, cada historia funciona por sí sola.
Dependencias explícitas
Orden forzado: models → services → endpoints. El agente no puede implementar el endpoint antes que el modelo que consume.
Marcador [P] de paralelismo
Tareas sin dependencias mutuas se marcan [P]. Equivalente conceptual a tus waves de workers en el SCHEDULER DAG — pero declarativo, no orquestado con procesos.
Rutas de fichero exactas
Cada tarea especifica exactamente en qué ficheros se implementa. Elimina la ambigüedad de "dónde va esto" — el mismo problema que resuelves con las 3 capas.
FAILURE MODES DOCUMENTADOS Y SUS CORRECCIONES
El agente sobre-ingenieriza
El propio README lo advierte: "Claude Code puede ser over-eager y añadir componentes que no pediste". Corrección oficial: antes de implement, pedirle que cross-checkee el plan buscando piezas sobre-ingenierizadas y justifique el origen de cada cambio, con la constitution como árbitro.
Research sin objetivo
Patrón anti-fallo del walkthrough: si el agente investiga ".NET Aspire en general", pararlo y forzar descomposición — lista de dudas concretas primero, luego una tarea de research paralela por duda. Research sin pregunta específica que resolver = ruido.
La primera spec nunca es final
El proceso asume iteración explícita en cada gate: revisar spec.md, ejecutar el Review & Acceptance Checklist, auditar plan.md ("¿la secuencia de tareas es obvia leyendo esto?"), y solo entonces implementar. Los gates humanos son parte del diseño, no burocracia añadida.
QUÉ ES LA CONSTITUTION
Principios innegociables del proyecto .specify/memory/constitution.md establece las reglas que TODOS los comandos posteriores consultan: /speckit.plan verifica el plan contra ella, /speckit.analyze la usa como árbitro de consistencia. Es la herramienta de las organizaciones para imponer stacks opinados: "toda app de este equipo es CLI-first", "testing así, siempre". Se escribe antes de cualquier iteración SDD y rara vez cambia.
ESTRUCTURA DE NUEVE ARTÍCULOS
Artículos fijos + slots del proyecto La plantilla define una estructura de nueve artículos. Los primeros codifican los principios core de SDD; los artículos IV, V y VI son intencionadamente placeholders que cada proyecto rellena con sus propios innegociables (testing de integración, observabilidad, versionado, breaking changes…). La estructura es estable; el contenido es tuyo. 
markdown · extracto conceptual# Constitution — artículo de testing (spec-driven.md)

This is NON-NEGOTIABLE: All implementation MUST follow strict
Test-Driven Development. No implementation code shall be written before:
  1. Unit tests are written
  2. Tests are validated and approved by the user
  3. Tests are confirmed to FAIL (Red phase)
TDD como inversión del flujo de generación — tu misma tesis
La justificación literal del proyecto: "esto invierte completamente la generación de código con IA. En lugar de generar código y esperar que funcione, el LLM debe primero generar tests que definen el comportamiento, conseguir aprobación, y solo entonces generar implementación". Es exactamente tu mecanismo anti-alucinación de FMI: test primero = contrato formal que el agente no puede rodear. Dos proyectos independientes convergen en el mismo principio — cita fuerte para la memoria del TFM.

Equivalencia con tu sistema Tu CLAUDE.md de FMI cumple AMBOS roles a la vez (reglas de arquitectura + contexto operativo). Spec-kit los separa: normativa en memory/, operativa en el fichero del agente. La separación permite que la normativa sobreviva a cambios de agente — la constitution es agnóstica de si ejecuta Claude, Copilot o Gemini.

EXTENSIONES · PRESETS · BUNDLES
Extensiones — capacidad nueva
Comandos y fases que el core no tiene: integración Jira/Azure DevOps, code review post-implementación, trazabilidad de tests V-Model, diagnósticos de salud del proyecto. Ecosistema comunitario de 70+ extensiones.

specify extension search · specify extension add <n>
Presets — cambiar el cómo
Sobrescriben plantillas del core Y de extensiones instaladas: formato de spec con trazabilidad regulatoria, gates de seguridad obligatorios en planes, orden test-first forzado, terminología de dominio, o localizar TODO el workflow a otro idioma. Apilables con orden de prioridad.

specify preset search · specify preset add <n>
Bundles — setup por rol
Manifiesto bundle.yml que empaqueta extensiones + presets + workflows versionados para un rol completo (PM, business analyst, security researcher, developer). Provisiona una persona de equipo con un comando. Instalación idempotente, confinada al proyecto, funciona offline contra fuentes pinneadas.

specify bundle install <id>
Cuál usar
Comando nuevo o herramienta externa → extensión. Formato/estándar organizativo → preset. Setup completo de rol en un comando → bundle. Ajuste de un solo proyecto → override local.
Lectura arquitectónica
Es un sistema de theming para procesos: el core define el pipeline, los presets lo visten, las extensiones lo amplían — resolución por prioridad tipo CSS cascade aplicada a prompts. La consecuencia interesante: podrías empaquetar FMI como preset + extensión de spec-kit (preset que impone tu vocabulario cerrado y las 3 capas en las plantillas de plan, extensión que añade la fase de cartografía HAR). Vía de adopción para OSCA sin construir tooling propio.
Advertencia de la propia GitHub Las contribuciones comunitarias son independientes: "revisa el código fuente antes de instalar y úsalo bajo tu criterio". Una extensión es un prompt + scripts que tu agente ejecutará con tus permisos — mismo vector de riesgo que un plugin de CI.
MISMO DIAGNÓSTICO, MECANISMOS OPUESTOS
Convergencia independiente Ambos parten del mismo diagnóstico ("la intención es la fuente de verdad, el código es última milla") y del mismo anti-patrón (vibe coding). Ambos usan TDD como contrato anti-alucinación, artefactos Markdown versionados, scripts deterministas fuera del LLM, y separación reglas-estables/trabajo-por-ciclo. La diferencia está en de dónde sale la intención.

LO QUE SPEC-KIT NO RESUELVE (Y FMI SÍ)
El hueco brownfield
Spec-kit dice: "captura la lógica de negocio esencial en una spec moderna". No dice CÓMO capturarla cuando el conocimiento no existe — ni en documentación ni en cabezas. Ese "cómo" es exactamente FMI/OSCA: extracción vía caja negra (web.xml + vistas como guía), caracterización HTTP, y clasificación línea-a-línea forzada por el target de Clean Architecture. Spec-kit asume la spec; FMI la fabrica. Son complementarios, no competidores: FMI produce el input que /speckit.specify necesita en brownfield.
LO QUE FMI PUEDE ROBARLE A SPEC-KIT
/speckit.clarify
Interrogatorio secuencial basado en cobertura, con registro formal de respuestas en el artefacto. Versión sistematizada de tu regla ANTI-ALUCINACIÓN "detente y pregunta" — pero como fase con protocolo, no como cláusula.
/speckit.converge
Auditoría post-implementación del drift código↔spec que APPENDEA tareas en vez de fallar. FMI valida con gates binarios (0.95 o rechazo); converge modela la reconciliación continua. Útil para las fases largas del orquestador.
Checklists como "tests para inglés"
Validar la CALIDAD DEL ARTEFACTO DE INTENCIÓN antes de gastarlo en generación. FMI valida outputs de código; spec-kit también valida los inputs textuales. Barato de adoptar en tus 00-orden.md.
taskstoissues
Puente artefacto→tracker. Tu equivalente sería volcar el DAG del SCHEDULER a issues — trazabilidad de la migración visible para stakeholders no técnicos sin abrir el repo.
CRÍTICA EXTERNA — PARA LA DISCUSIÓN DEL TFM
¿La venganza del Waterfall? Gojko Adzic (referente en specification-by-example) señala que SDD construye sobre las mismas ideas intent-first que BDD, pero advierte que su estructura podría reintroducir la rigidez de la que huyeron las metodologías ágiles — "las peores partes del Waterfall bajo un nombre más brillante". El contraargumento de GitHub: la spec es viva y regenerable, no un documento congelado de fase. Tensión real y citable: la respuesta depende de si el equipo trata la spec como artefacto vivo (loop converge) o como contrato firmado.
Posicionamiento sugerido para la memoria
Spec-kit (GitHub, 117k★) valida a escala industrial las tres apuestas nucleares de FMI: intención como fuente de verdad, TDD como contrato formal para agentes, y artefactos intermedios estructurados en lugar de prompting ad-hoc. FMI se diferencia donde spec-kit delega en el humano: la extracción de intención desde sistemas cuyo conocimiento se perdió. Frase para la defensa: "Spec-kit ejecuta specs; FMI las excava."
