PIRÁMIDE DE TESTING WEBDTE

El proyecto aplica una pirámide de testing adaptada a la migración FMI: la base son tests estructurales por reflection (validan contratos sin runtime), la capa media son tests de lógica de negocio con Mockito, y la cima son tests E2E que verifican el cableado hexagonal completo.

Base — Tests Estructurales (Reflection)
DTOs (14 ficheros, ~82 @Test): Constructores, getters/setters, tipos de campos.
Entities (5 ficheros, ~82 @Test): Inmutabilidad (final class, final fields), no setters, constructor signature.
Interfaces (6 ficheros, ~51 @Test): Métodos, parámetros, tipos genéricos (Optional<T>, List<T>).

Técnica clave: Class.forName() + getDeclaredFields() + Modifier.isFinal()
Media — Tests de Lógica (Mockito)
UseCases (11 ficheros, ~44 @Test): Mock de repositorios, verify de interacciones, ArgumentCaptor para validar entidades.

Técnica clave: mock(Repository.class) + when().thenReturn() + ArgumentCaptor
Cima — Tests E2E Estructurales
Controllers (6 ficheros, ~47 @Test): Herencia HttpServlet, constructor injection con UseCases correctos, métodos doGet/doPost, aislamiento hexagonal.

Técnica clave: HttpServlet.class.isAssignableFrom() + constructor param validation

💡 Filosofía: TDD-as-Spec
En FMI, los tests se escriben antes del código de producción. Actúan como especificación ejecutable: definen la estructura exacta (nombres de clase, tipos, herencia) que el código generado por IA debe cumplir. Esto convierte los tests en contratos formales de migración, no en tests de regresión convencionales.
TESTS DE DTOs — REFLECTION PURA

Los DTOs son objetos de transporte que viven en la capa Domain. Sus tests verifican que la estructura Java cumple el contrato: constructor sin args, getters, setters, y tipos de campo correctos. Se usan sin instanciar la aplicación, solo por reflection.

Java · JUnit 4
public class LoginRequestTest {

    @Test
    public void testNoArgConstructorExists() throws Exception {
        Constructor<LoginRequest> ctor =
            LoginRequest.class.getDeclaredConstructor();
        assertNotNull(ctor);
    }

    @Test
    public void testLoginGetterSetter() {
        LoginRequest dto = new LoginRequest();
        dto.setLogin("user123");
        assertEquals("user123", dto.getLogin());
    }

    @Test
    public void testFieldLogin() throws Exception {
        Field f = LoginRequest.class.getDeclaredField("login");
        assertEquals(String.class, f.getType());
    }
}
Patrón: Verificación de campo por nombre getDeclaredField("login") garantiza que la IA no renombre campos arbitrariamente. Si el legacy usaba usr_lgn y el DTO espera login, el test falla y el Mapper debe encargarse de la traducción.
TESTS DE ENTITIES — INMUTABILIDAD

Las entidades de dominio son inmutables por diseño: clase final, campos final, un solo constructor, cero setters. Los tests verifican estas propiedades vía Modifier.isFinal().

Java · JUnit 4
@Test
public void testClassIsFinal() {
    assertTrue("Usuario must be declared final",
        Modifier.isFinal(Usuario.class.getModifiers()));
}

@Test
public void testAllFieldsAreFinal() {
    for (Field f : Usuario.class.getDeclaredFields()) {
        assertTrue("Field '" + f.getName() + "' must be final",
            Modifier.isFinal(f.getModifiers()));
    }
}

@Test
public void testNoSetters() {
    for (Method m : Usuario.class.getDeclaredMethods()) {
        assertFalse("Setter found: " + m.getName(),
            m.getName().startsWith("set"));
    }
}
⚠️ Anti-patrón: Entity mutable
Si la IA genera un setNombre() en una Entity, el test testNoSetters() falla inmediatamente. Las entidades son Value Objects inmutables — toda mutación pasa por crear una nueva instancia. Esto previene bugs de estado compartido en la capa de dominio.
TESTS DE INTERFACES — CONTRATOS DE REPOSITORIO

Los tests de interfaces verifican que los contratos de repositorio tienen los métodos correctos con las firmas exactas, incluyendo tipos genéricos como Optional<Usuario> y List<Usuario>.

Java · JUnit 4
@Test
public void testFindByLoginMethod() throws Exception {
    Class<?> clazz = Class.forName("domain.interfaces.UsuarioRepository");
    Class<?> usuarioClass = Class.forName("domain.entities.Usuario");
    Method method = clazz.getMethod("findByLogin", String.class);

    // Verificar raw type = Optional
    assertEquals(Optional.class, method.getReturnType());

    // Verificar generic type = Optional<Usuario>
    ParameterizedType paramType =
        (ParameterizedType) method.getGenericReturnType();
    Type[] typeArgs = paramType.getActualTypeArguments();
    assertEquals(usuarioClass, typeArgs[0]);
}
Por qué Class.forName() en vez de import directo Los tests usan Class.forName("domain.interfaces.UsuarioRepository") en vez de importar directamente. Esto permite ejecutar los tests como especificación antes de que exista el código — si la clase no existe, el test falla con ClassNotFoundException en vez de error de compilación.
TESTS DE USECASES — MOCKITO

Los UseCases contienen la lógica de negocio. Se testean inyectando mocks de los repositorios y verificando que se llaman los métodos correctos con los datos correctos.

Java · JUnit 4 + Mockito
public class AuthenticateUserUseCaseTest {

    private UsuarioRepository repo;
    private AuthenticateUserUseCase useCase;
    private Usuario validUsuario;

    @Before
    public void setUp() {
        repo = mock(UsuarioRepository.class);
        useCase = new AuthenticateUserUseCase(repo);
        validUsuario = new Usuario(
            1, "EXP001", "Juan", "Garcia",
            "Dir", "j@e.com", "123456789",
            "Telecomunicacion", "1", "No",
            "user", "pass123");
    }

    @Test
    public void execute_success_returnsLoginResponseOk() {
        when(repo.findByLogin("user"))
            .thenReturn(Optional.of(validUsuario));

        LoginResponse response = useCase.execute("user", "pass123");

        assertNotNull(response);
        assertTrue(response.isOk());
        verify(repo).findByLogin("user");
    }

    @Test
    public void execute_wrongPassword_returnsLoginResponseFail() {
        when(repo.findByLogin("user"))
            .thenReturn(Optional.of(validUsuario));

        LoginResponse response = useCase.execute("user", "wrong");

        assertNotNull(response);
        assertFalse(response.isOk());
    }
}
ArgumentCaptor — la herramienta de oro ArgumentCaptor<RevisionExamen> permite capturar la entidad que el UseCase pasa al repositorio y verificar que los campos se mapearon correctamente. Esencial para validar la transformación Request → Entity. 
Java · ArgumentCaptor
ArgumentCaptor<RevisionExamen> captor =
    ArgumentCaptor.forClass(RevisionExamen.class);
when(repo.save(captor.capture())).thenReturn(1);

useCase.execute(42, request);

QUÉ SON LOS TESTS DE INTEGRACIÓN EN WEBDTE

En el contexto FMI, los tests de integración verifican que las capas se conectan correctamente entre sí: que un Controller recibe los UseCases correctos, que un UseCase usa la interfaz correcta del repositorio, y que los Mappers transforman datos sin perder campos.

Transport → Domain
Verificar que AuthController recibe AuthenticateUserUseCase y RegisterUserUseCase por constructor injection. Que doPost parsea JSON y delega al UseCase correcto.
Domain → Infrastructure
Verificar que AuthenticateUserUseCase recibe UsuarioRepository (interfaz) y que en runtime AppWiring le inyecta JdbcUsuarioRepository (implementación).
AppWiring — El Pegamento
AppWiringE2ETest verifica que las clases de dominio nunca importan tipos de infrastructure.persistence. Si un UseCase tiene un field cuyo tipo empieza por infrastructure.persistence, el test falla.
TEST DE AISLAMIENTO HEXAGONAL
Java · AppWiringE2ETest.java
// Verifica que NINGÚN UseCase depende directamente de la capa de persistencia
private static final String[] DOMAIN_USE_CASE_CLASSES = {
    "domain.usecases.AuthenticateUserUseCase",
    "domain.usecases.RegisterUserUseCase",
    "domain.usecases.ProcessRevisionUseCase",
    // ... 8 más
};

@Test
public void domainMustNotDependOnInfrastructurePersistence() {
    for (String className : DOMAIN_USE_CASE_CLASSES) {
        Class<?> clazz = Class.forName(className);
        for (Field f : clazz.getDeclaredFields()) {
            String fieldType = f.getType().getName();
            assertFalse(
                className + " depends on " + fieldType,
                fieldType.startsWith("infrastructure.persistence")
            );
        }
    }
}
⚠️ Este test es tu firewall arquitectónico
Si la IA genera un UseCase que importa JdbcUsuarioRepository en vez de UsuarioRepository, este test lo detecta inmediatamente. Es la garantía automatizada de que la Dependency Inversion se mantiene a lo largo de la migración.

Java · E2E Structural
@Test
public void authController_extendsHttpServlet() throws Exception {
    Class<?> clazz = Class.forName(
        "transport.controllers.AuthController");
    assertTrue(
        "AuthController must extend HttpServlet",
        HttpServlet.class.isAssignableFrom(clazz)
    );
}

@Test
public void authController_constructorTakesCorrectUseCases() throws Exception {
    Class<?> clazz = Class.forName(CLASS_NAME);
    Class<?> authenticateUseCase = Class.forName(
        "domain.usecases.AuthenticateUserUseCase");
    Class<?> registerUseCase = Class.forName(
        "domain.usecases.RegisterUserUseCase");

    boolean found = false;
    for (Constructor<?> ctor : clazz.getDeclaredConstructors()) {
        Class<?>[] params = ctor.getParameterTypes();
        if (params.length == 2) {
            Set<Class<?>> paramSet = new HashSet<>(Arrays.asList(params));
            if (paramSet.contains(authenticateUseCase) &&
                paramSet.contains(registerUseCase)) {
                found = true;
            }
        }
    }
    assertTrue("Must accept both UseCases", found);
}
E2E REALES PENDIENTES — PLAYWRIGHT

Para E2E reales (browser + servidor), el proyecto necesitaría Playwright con TypeScript. Estos son los flujos críticos a cubrir:

1
Flujo de Login completo
Navegar a /#/login → rellenar usuario/password → submit → verificar redirección a /#/principal → verificar cookie SESSION en headers → verificar que dte-nav-menu muestra el usuario logueado.
2
Flujo de Registro + Login
Navegar a /#/registro → rellenar todos los campos → submit → verificar mensaje de éxito → login con las mismas credenciales → verificar que funciona.
3
Solicitud de Revisión de Examen
Login → navegar a /#/revision → rellenar formulario (profesor, asignatura, fecha, motivo, convocatoria) → submit → verificar respuesta {ok: true} → navegar a /#/ver-solicitudes → verificar que aparece la solicitud.
4
Solicitud de Sellado de Asignaturas
Login → /#/sellado → seleccionar asignaturas → submit → verificar en ver-solicitudes.
5
Admin: Gestión de Temas
Login admin → /#/admin/temas → crear tema → activar/desactivar → verificar que alumnos ven solo temas activos.
6
Seguridad: Acceso sin autenticar
Navegar directo a /#/principal sin login → verificar redirección a /#/login. Intentar fetch('/api/usuarios/1') sin cookie → verificar 401.
💡 Playwright + Web Components
Los Web Components con Shadow DOM requieren selectores especiales en Playwright. Usar page.locator('dte-login').locator('internal:shadow=input[name="login"]') o la API experimental page.locator('dte-login >> shadow=input'). Alternativa: usar data-testid attributes en los templates del Shadow DOM.
TÉCNICA: SOURCE ANALYSIS (REGEX + ASSERT)

Los tests frontend de WebDTE no usan un browser ni JSDOM. Leen los ficheros .js como texto y verifican su estructura con expresiones regulares y assert de Node.js. Es una técnica de análisis estático ligero que no necesita dependencias externas.

ComponentStructureTest.js
Recorre todos los .js en frontend/components/. Verifica que cada componente: extiende HTMLElement, usa Shadow DOM, tiene connectedCallback(), NO tiene fetch() directo, y llama a customElements.define(). Verifica los 12 tags esperados.
AuthServiceTest.js
Verifica que auth-service.js: NO tiene console.log STUB, usa credentials: 'include' en fetch, verifica resp.ok antes de .json(), tiene los 5 métodos requeridos (login, register, logout, getUserData, updateUser), y los 5 endpoints correctos.
RouterTest.js
Verifica que app.js: usa hash-based routing (hashchange o location.hash), tiene las 10 rutas requeridas, NO tiene fetch() directo, e importa desde components/.
EJEMPLO: COMPONENT STRUCTURE TEST
JavaScript · Node.js assert
const source = fs.readFileSync(filePath, 'utf-8');

// 1. Must extend HTMLElement
if (!/class\s+\w+\s+extends\s+HTMLElement/.test(source)) {
  errors.push('Must extend HTMLElement');
}

// 2. Must use Shadow DOM
if (!/this\.(attachShadow|shadowRoot)/.test(source)) {
  errors.push('Must use Shadow DOM');
}

// 3. Must have connectedCallback
if (!/connectedCallback\s*\(/.test(source)) {
  errors.push('Must define connectedCallback()');
}

// 4. Must NOT contain direct fetch()
const noComments = source
  .split('\n')
  .filter(line => !/^\s*\/\//.test(line))
  .join('\n')
  .replace(/\/\*[\s\S]*?\*\//g, '');
if (/\bfetch\s*\(/.test(noComments)) {
  errors.push('Must NOT contain direct fetch()');
}

// 5. Must register custom element
if (!/customElements\.define\s*\(/.test(source)) {
  errors.push('Must call customElements.define()');
}

HERRAMIENTAS COMPLEMENTARIAS RECOMENDADAS
JUnit 5 (Jupiter)
Migración recomendada desde JUnit 4. Aporta @Nested para agrupar tests, @ParameterizedTest para data-driven, @DisplayName para nombres legibles, y assertThrows() para excepciones.

org.junit.jupiter:junit-jupiter:5.10+
H2 Database
Base de datos en memoria para tests de integración de repositorios JDBC. Soporta modo PostgreSQL para compatibilidad con producción. Cada test arranca limpio.

com.h2database:h2:2.2.224
Playwright
E2E real con browser. Auto-wait, selectores robustos, soporte Shadow DOM, network interception, tracing visual. Ideal para flujos completos (login → operación → verify).

npm install -D @playwright/test
JaCoCo
Cobertura de código Java. Genera reports HTML con % de cobertura por paquete, clase y método. Se integra con Maven y CI/CD para gates de calidad.

org.jacoco:jacoco-maven-plugin:0.8.12

💡 ArchUnit — Alternativa profesional a los tests de reflection
Los tests de estructura del proyecto (verificar herencia, campos final, no imports cruzados) se podrían reescribir con ArchUnit, que ofrece una DSL declarativa:
noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat().resideInAPackage("..infrastructure..")
Esto es exactamente lo que hace AppWiringE2ETest pero con una API mucho más expresiva y mantenible.

ORDEN DE EJECUCIÓN RECOMENDADO
1
Entities + DTOs (compilación)
mvn test -Dtest="domain.entities.*,domain.dto.*"
Si fallan aquí, la estructura básica del dominio es incorrecta. No tiene sentido seguir.
2
Interfaces (contratos)
mvn test -Dtest="tests.interfaces.*"
Valida que los repositorios tienen las firmas correctas antes de implementarlos.
3
UseCases (lógica)
mvn test -Dtest="domain.usecases.*"
Lógica de negocio con mocks. Depende de que Entities e Interfaces pasen primero.
4
Controllers E2E (cableado)
mvn test -Dtest="transport.controllers.*E2ETest"
Verifica que todo está ensamblado correctamente a nivel de Transport.
5
Frontend (estructura)
npm run test:all
Verifica componentes, services, router y shell. Independiente de Java.
💡 Flujo FMI: Tests primero, código después
En el workflow de migración FMI, la secuencia es: Oleada 1 genera todos los tests → se valida que compilan y tienen las assertions correctas → Oleada 2 genera el código de producción → SMOKE ejecuta los tests contra el código generado. Si un test falla, se corrige el código, nunca el test.

GITHUB ACTIONS WORKFLOW
YAML · .github/workflows/test.yml
name: WebDTE Tests
on: [push, pull_request]

jobs:
  backend-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
      - name: Run backend tests
        run: mvn test -B
      - name: JaCoCo report
        run: mvn jacoco:report
      - uses: actions/upload-artifact@v4
        with:
          name: jacoco-report
          path: target/site/jacoco/

  frontend-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - name: Run frontend tests
        run: |
          node tests/frontend/ComponentStructureTest.js
          node tests/frontend/AuthServiceTest.js
          node tests/frontend/AdminServiceTest.js
          node tests/frontend/ProcesoServiceTest.js
          node tests/frontend/SolicitudServiceTest.js
          node tests/frontend/RouterTest.js
          node tests/frontend/AppShellTest.js
          node tests/frontend/IndexHtmlTest.js

  e2e-browser:
    runs-on: ubuntu-latest
    needs: [backend-tests, frontend-tests]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - name: Run E2E
        run: npx playwright test
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: playwright-report
          path: playwright-report/
