EL MATIZ CLAVE
No es caja negra pura — tienes el código. Pero el código es ruido.
No es caja blanca — el código es ilegible, parcheado, sin docs.
Es caja negra guiada por esqueleto declarativo: usas los únicos artefactos que NO mienten (web.xml + HTML) para saber QUÉ probar, y Playwright para descubrir CÓMO se comporta.
FMI — Nivel 1: Caja negra con pistas estructurales
QUÉ MIRAS Y QUÉ IGNORAS
❌ IGNORAS — Código imperativo
Servlets con lógica de negocio mezclada con SQL.
JSPs con scriptlets que generan HTML + lógica.
Clases "Util" y "Helper" con 3000 líneas.
Condicionales anidados de 8 niveles.
Variables llamadas aux, tmp, flag2.

¿Por qué? La IA gasta 500K tokens descifrando esto y alucina. El código espagueti es ruido semántico con densidad informativa cercana a cero.
✅ MIRAS — Artefactos declarativos
web.xml → mapa completo de servlet-mappings.
HTML con <form action="/X" method="POST">.
Campos <input name="Y"> con types y validaciones HTML5.
<select> con opciones que revelan dominio.
URLs en <a href> que muestran la navegación.

¿Por qué? Son declarativos (no tienen lógica acoplada), estables (cambian poco), y dicen la verdad sobre qué endpoints existen y qué parámetros esperan.
💡 La intuición de fondo
El web.xml es el índice del libro — lista todos los capítulos (endpoints) sin obligarte a leer las 500 páginas de espagueti. Los formularios HTML son las interfaces de contrato — declaran qué datos espera cada endpoint. Juntos forman un esqueleto que permite a la IA generar tests de Playwright sin haber leído una sola línea de lógica de negocio.
POR QUÉ ESTA COMBINACIÓN ES SUPERIOR
EnfoqueInput para la IATokensRiesgoOutput
IA lee código 50.000 líneas de espagueti 500K+ 🔴 Alucinaciones masivas Tests que validan lo que la IA CREE que hace
Caja negra pura Solo URL, clic manual ~0 🟡 Cobertura baja, descubrimiento lento Tests de lo que un humano descubrió
Caja negra guiada web.xml + HTML forms (~200 líneas) ~5K 🟢 Datos reales + cobertura completa Tests de TODO lo que el sistema REALMENTE hace
Economía de tokens brutal: El web.xml + los formularios HTML suman ~200 líneas declarativas que contienen el 80% de la información semántica del sistema. Con 5K tokens la IA tiene suficiente contexto para generar tests de Playwright que cubran el 100% de los endpoints. Luego Playwright ejecuta y captura el comportamiento REAL — sin alucinaciones posibles.
PRECONDICIÓN: FRONT Y BACK DESACOPLADOS
Tu planteamiento asume SPA (o al menos formularios HTML que hacen POST/GET a endpoints separados). Esto es crucial porque significa que puedes analizar front y back por separado: los HTML te dan el contrato del front (qué campos envía, a dónde), y el HAR de Playwright te da el contrato del back (qué responde). Si la app genera HTML en el servidor (JSP con scriptlets), el enfoque sigue funcionando pero el HAR captura HTML completo en vez de JSON — la normalización del Golden Master es diferente.

Paso previo a la IA: Antes de pedirle a Gemini que genere tests, necesitas extraer y organizar los artefactos declarativos en un formato limpio que la IA pueda consumir eficientemente.

FICHA DE INVENTARIO POR ENDPOINT
Este es el artefacto intermedio clave. De cada par (web.xml mapping + HTML form) generas una ficha que resume todo lo que sabes SIN haber leído código. Esta ficha es lo que le pasas a Gemini para que genere el test de Playwright. 
// inventario/cuenta-alta.json
// Generado desde web.xml + form HTML — sin leer CuentaServlet.java
{
  "id": "alta-cuenta",
  "endpoint": {
    "path": "/api/cuentas",
    "method": "POST",
    "servlet": "CuentaServlet"       // del web.xml, NO leemos su código
  },
  "campos": [
    { "name": "email",    "type": "email",    "required": true },
    { "name": "nombre",   "type": "text",     "required": true, "maxlength": 100 },
    { "name": "dni",      "type": "text",     "required": true, "pattern": "[0-9]{8}[A-Z]" },
    { "name": "password", "type": "password", "required": true, "minlength": 8 },
    { "name": "tipo",     "type": "select",   "options": ["persona", "empresa"] }
  ],
  "pagina_origen": "/cuentas.html",
  "selector_form": "#form-alta",
  "selector_submit": "button[type=submit]",

  // Lo que NO sabemos (se descubrirá con Playwright)
  "incognitas": [
    "¿Qué status devuelve en éxito? ¿201? ¿302 redirect?",
    "¿Qué devuelve en el body? ¿JSON? ¿HTML?",
    "¿Hay validaciones server-side más allá de las del HTML?",
    "¿Qué pasa con email duplicado?",
    "¿Qué pasa con DNI inválido?"
  ]
}
💡 El campo "incógnitas" es lo más importante
Cada incógnita se convierte en un caso de test de Playwright. El esqueleto declarativo te dice QUÉ PROBAR; las incógnitas te dicen QUÉ DESCUBRIR. Playwright ejecuta → HAR responde las incógnitas con datos reales → las incógnitas desaparecen y se convierten en contratos del Golden Master.
SCRIPT DE EXTRACCIÓN AUTOMÁTICA
#!/bin/bash
# extraer-esqueleto.sh
# Extrae artefactos declarativos del código legacy sin leer lógica

LEGACY_SRC="./webdte-legacy/src"
OUTPUT="./esqueleto"

mkdir -p "$OUTPUT"

# 1. Copiar web.xml
cp "$LEGACY_SRC/main/webapp/WEB-INF/web.xml" "$OUTPUT/"

# 2. Extraer SOLO los formularios HTML (no JS, no lógica)
for html in "$LEGACY_SRC"/main/webapp/*.html; do
  # Extraer bloques <form>...</form> con sus inputs
  grep -Pzo '(?s)<form[^>]*>.*?</form>' "$html" > \
    "$OUTPUT/forms-$(basename $html)" 2>/dev/null
done

# 3. Extraer links de navegación
grep -rh 'href=' "$LEGACY_SRC"/main/webapp/*.html | \
  grep -v 'http' | sort -u > "$OUTPUT/navegacion.txt"

echo "✅ Esqueleto extraído en $OUTPUT/"
echo "   - web.xml"
echo "   - forms-*.html (solo formularios)"
echo "   - navegacion.txt (links internos)"
echo "   Total: $(wc -l $OUTPUT/* | tail -1) líneas declarativas"
EL PROMPT PARA GEMINI (O CLAUDE/QWEN)
El truco es qué le pasas y qué NO le pasas. Le das SOLO el esqueleto declarativo (web.xml + forms HTML). NO le pasas el código de los servlets. La IA genera tests de Playwright basándose en la estructura visible, y las incógnitas se formulan como assertions abiertas que Playwright resolverá al ejecutar.

`Actúa como un ingeniero de QA que hace arqueología de una app legacy.

CONTEXTO:
- App web legacy Java Servlets (2005), funcionando en producción
- El código fuente es ilegible (espagueti, sin docs, parcheado)
- Front y back desacoplados (HTML forms → POST/GET → Servlets → JSON/redirect)
- NO debes leer ni analizar código de servlets/lógica

TE PASO:
1. web.xml — mapa completo de servlet-mappings
2. forms-*.html — formularios HTML extraídos (solo la estructura <form>)

TU TRABAJO:
Genera tests de Playwright (.spec.ts) que:
1. Naveguen a la página que contiene cada formulario
2. Rellenen TODOS los campos con datos válidos de prueba
3. Envíen el formulario
4. Capturen la respuesta completa (status, headers, body)
5. Tomen screenshot antes y después del envío
6. Generen TAMBIÉN variantes para descubrir validaciones:
   - Campos vacíos (uno por uno)
   - Datos inválidos por campo (email mal formado, DNI sin letra, etc.)
   - Envío duplicado (mismo dato dos veces seguidas)

REGLAS CRÍTICAS:
- Cada test SOLO interactúa con la UI, NUNCA importa código backend
- Usa page.waitForResponse() para capturar la respuesta del servidor
- Registra TODO en un objeto "contrato" con: endpoint, method, status,
  requestBody, responseBody, timestamp
- Los contratos se escriben en ./contratos/{nombre-flujo}.json
- Si un campo tiene pattern="..." o type="email", genera un caso
  válido y otro inválido según ese patrón
- NO inventes validaciones que no estén en el HTML
- Marca con // _PENDIENTE_DESCUBRIR los comportamientos que no puedes
  predecir desde el HTML (ej: "¿devuelve 201 o 302?")

ANTI-ALUCINACIÓN:
- Si el formulario tiene un <select> con opciones, prueba TODAS
- Si el formulario NO tiene un campo, NO lo inventes
- Si no sabes qué devuelve el servidor, NO asumas — captura y registra

OUTPUT:
- Un .spec.ts por cada formulario/endpoint
- Un .json de contrato por cada flujo (se llenará al ejecutar)`

// tests/captura/alta-cuenta.spec.ts
// GENERADO por Gemini desde esqueleto declarativo
// El test NO sabe qué hace CuentaServlet.java — solo sabe qué campos
// tiene el form y a dónde apunta

import { test, expect } from '@playwright/test';
import { writeFileSync } from 'fs';

const CONTRATOS: any[] = [];

test.describe('Alta de Cuenta — Descubrimiento de comportamiento', () => {

  test.afterAll(() => {
    writeFileSync(
      './contratos/alta-cuenta.json',
      JSON.stringify(CONTRATOS, null, 2)
    );
  });

  // ─── CASO FELIZ: datos válidos ───
  test('alta con datos válidos', async ({ page }) => {
    await page.goto('/cuentas.html');
    await page.screenshot({ path: './captures/cuenta-00-antes.png' });

    // Rellenar según los campos del form HTML
    await page.fill('#form-alta [name="email"]',    'test001@prueba.com');
    await page.fill('#form-alta [name="nombre"]',   'Usuario Test');
    await page.fill('#form-alta [name="dni"]',      '12345678Z');
    await page.fill('#form-alta [name="password"]', 'Pass1234!');
    await page.selectOption('#form-alta [name="tipo"]', 'persona');

    // Enviar y capturar respuesta
    const [response] = await Promise.all([
      page.waitForResponse(r => r.url().includes('/api/cuentas')),
      page.click('#form-alta button[type="submit"]'),
    ]);

    const contrato = {
      caso: 'datos-validos',
      endpoint: new URL(response.url()).pathname,
      method: response.request().method(),
      status: response.status(),         // _PENDIENTE_DESCUBRIR: ¿201? ¿302?
      requestBody: response.request().postData(),
      responseBody: await response.text(),  // _PENDIENTE_DESCUBRIR: ¿JSON? ¿HTML?
      contentType: response.headers()['content-type'],
    };

    CONTRATOS.push(contrato);
    await page.screenshot({ path: './captures/cuenta-01-despues.png' });

    // Assertions mínimas — no asumimos nada
    expect(response.status()).toBeLessThan(500); // al menos no explota
  });

  // ─── VALIDACIÓN: email vacío ───
  test('rechazo email vacío', async ({ page }) => {
    await page.goto('/cuentas.html');

    // Todo válido EXCEPTO email
    await page.fill('#form-alta [name="nombre"]',   'Usuario Test');
    await page.fill('#form-alta [name="dni"]',      '12345678Z');
    await page.fill('#form-alta [name="password"]', 'Pass1234!');
    await page.selectOption('#form-alta [name="tipo"]', 'persona');

    // Intentar enviar — ¿el front bloquea o el back rechaza?
    const submitBtn = page.locator('#form-alta button[type="submit"]');
    await submitBtn.click();

    // Detectar si hay validación front (HTML5 required) o back
    const hayErrorFront = await page.locator('#form-alta [name="email"]:invalid')
      .count() > 0;

    if (hayErrorFront) {
      CONTRATOS.push({
        caso: 'email-vacio',
        validacion: 'front',  // HTML5 required bloqueó el envío
        detalle: 'El campo email tiene required, el navegador impide envío',
      });
    } else {
      // Si el front no bloqueó, capturar respuesta del back
      const response = await page.waitForResponse(
        r => r.url().includes('/api/cuentas'),
        { timeout: 3000 }
      ).catch(() => null);

      CONTRATOS.push({
        caso: 'email-vacio',
        validacion: 'back',
        status: response?.status(),
        responseBody: await response?.text(),
      });
    }
  });

  // ─── VALIDACIÓN: DNI formato inválido ───
  test('rechazo DNI inválido (sin letra final)', async ({ page }) => {
    await page.goto('/cuentas.html');

    await page.fill('#form-alta [name="email"]',    'test002@prueba.com');
    await page.fill('#form-alta [name="nombre"]',   'Test DNI');
    await page.fill('#form-alta [name="dni"]',      '12345678');  // sin letra
    await page.fill('#form-alta [name="password"]', 'Pass1234!');

    const [response] = await Promise.all([
      page.waitForResponse(r => r.url().includes('/api/cuentas'))
        .catch(() => null),
      page.click('#form-alta button[type="submit"]'),
    ]);

    CONTRATOS.push({
      caso: 'dni-sin-letra',
      validacion: response ? 'back' : 'front',
      status: response?.status(),
      responseBody: response ? await response.text() : null,
      // _PENDIENTE_DESCUBRIR: ¿valida el patrón el front o el back?
    });
  });

  // ─── DESCUBRIMIENTO: envío duplicado ───
  test('duplicado — mismos datos dos veces', async ({ page }) => {
    const datos = {
      email: 'duplicado@prueba.com',
      nombre: 'Test Duplicado',
      dni: '99999999R',
      password: 'Pass1234!',
      tipo: 'persona',
    };

    // Primer envío
    await page.goto('/cuentas.html');
    for (const [k, v] of Object.entries(datos)) {
      if (k === 'tipo') await page.selectOption(`#form-alta [name="${k}"]`, v);
      else await page.fill(`#form-alta [name="${k}"]`, v);
    }
    const [r1] = await Promise.all([
      page.waitForResponse(r => r.url().includes('/api/cuentas')),
      page.click('#form-alta button[type="submit"]'),
    ]);

    // Segundo envío — mismos datos
    await page.goto('/cuentas.html');
    for (const [k, v] of Object.entries(datos)) {
      if (k === 'tipo') await page.selectOption(`#form-alta [name="${k}"]`, v);
      else await page.fill(`#form-alta [name="${k}"]`, v);
    }
    const [r2] = await Promise.all([
      page.waitForResponse(r => r.url().includes('/api/cuentas')),
      page.click('#form-alta button[type="submit"]'),
    ]);

    CONTRATOS.push(
      { caso: 'duplicado-1er-envio', status: r1.status(), body: await r1.text() },
      { caso: 'duplicado-2do-envio', status: r2.status(), body: await r2.text() },
    );
    // _PENDIENTE_DESCUBRIR: ¿409 Conflict? ¿200 silencioso? ¿error genérico?
  });
});

DEL HAR A LOS TESTS DE INTEGRACIÓN (FRONT + BACK)
Este es tu paso clave: Una vez que Playwright ha ejecutado y tienes los contratos con datos reales, puedes construir tests de integración separados para front y back. Estos tests validan el comportamiento capturado y son la red de seguridad para refactorizar.
Playwright
Captura HAR: POST /api/cuentas {email, dni...} → 201 {id, email...}
Contrato
Formaliza: input → output con datos reales del HAR
Test Front
Valida: que el formulario envía correctamente al endpoint con el content-type y campos esperados
Test Back
Valida: que el endpoint responde con el status y body correctos para un input dado
Gherkin
Abstrae: la intención de negocio en lenguaje portable independiente de stack
TEST DE INTEGRACIÓN BACK — DESDE EL CONTRATO
// tests/integracion/back/cuenta-api.test.js
// Generado DESDE los contratos capturados por Playwright
// Valida el backend directamente vía HTTP (sin navegador)

import { describe, it, expect } from 'vitest';
import contratos from '../../contratos/alta-cuenta.json';

const BASE = process.env.BACKEND_URL || 'http://localhost:8080/WebDTE';

describe('API Cuentas — Contratos capturados', () => {

  // Test generado desde contrato caso='datos-validos'
  const casoFeliz = contratos.find(c => c.caso === 'datos-validos');

  it(`POST /api/cuentas con datos válidos → status ${casoFeliz.status}`, async () => {
    const res = await fetch(BASE + casoFeliz.endpoint, {
      method: 'POST',
      headers: { 'Content-Type': casoFeliz.contentType || 'application/x-www-form-urlencoded' },
      body: casoFeliz.requestBody,
    });

    expect(res.status).toBe(casoFeliz.status);

    // Validar estructura de respuesta (no valores dinámicos)
    if (casoFeliz.contentType?.includes('json')) {
      const body = await res.json();
      const expected = JSON.parse(casoFeliz.responseBody);
      // Validar que tiene los mismos campos (no valores exactos)
      expect(Object.keys(body).sort())
        .toEqual(Object.keys(expected).sort());
    }
  });

  // Test generado desde contrato caso='duplicado-2do-envio'
  const casoDup = contratos.find(c => c.caso === 'duplicado-2do-envio');
  if (casoDup) {
    it(`POST /api/cuentas duplicado → status ${casoDup.status}`, async () => {
      // Primero crear, luego duplicar
      await fetch(BASE + casoFeliz.endpoint, {
        method: 'POST',
        body: casoFeliz.requestBody,
      });
      const res = await fetch(BASE + casoFeliz.endpoint, {
        method: 'POST',
        body: casoFeliz.requestBody,
      });
      expect(res.status).toBe(casoDup.status);
    });
  }
});

💡 Los tests de integración tienen DOS orígenes de datos
Estructura viene del esqueleto declarativo (web.xml + HTML forms) — qué campos, qué endpoints, qué validaciones HTML5.
Comportamiento viene del HAR de Playwright — qué status, qué body, qué pasa con datos inválidos.

Juntos forman el contrato completo: el front sabe QUÉ enviar (del HTML), el back sabe QUÉ responder (del HAR). Esa combinación es la que permite refactorizar ambos lados con seguridad.
DISTINGUIR VALIDACIÓN FRONT vs BACK
Descubrimiento clave de Playwright: Al probar campos inválidos, Playwright revela DÓNDE vive cada validación. Si el required del HTML bloquea el envío (no hay response HTTP), la validación es front. Si llega al servidor y devuelve 400, es back. Esto es información que NO puedes obtener leyendo código espagueti — necesitas ejecutar.
Qué descubristeDónde viveQué test necesitasImplicación migración
:invalid en HTML Front (HTML5) Test front con jsdom Nuevo front debe mantener required/pattern
Response 400 del server Back (Servlet) Test back con fetch Nuevo back debe validar igual
Ambos (front bloquea + back también rechaza) Doble validación Test front + test back Mantener en ambas capas
Ni front ni back (acepta dato inválido) Bug del legacy Documentar como deuda técnica Decidir si corregir o mantener
DE CONTRATOS A TESTS DE 3 CAPAS
Una vez que tienes contratos con datos reales, puedes construir la pirámide de tests que necesitas para refactorizar a 3 capas. Cada nivel de test se genera desde los mismos contratos — cambia la granularidad, no la verdad.
E2E (tiene)
Playwright specs — ya los tienes de Fase 0. Validan el flujo completo navegador → back → respuesta. Son lentos pero completos. Sirven como red de seguridad máxima.
API contract
Tests HTTP directos — generados desde contratos. Validan solo el back (sin navegador). Rápidos. Perfectos para validar durante refactoring del backend.
Integration
Tests de integración por capa — Transport (Servlet + request/response), Domain (lógica pura), Infrastructure (DAO + BD). Se crean DESPUÉS de separar las 3 capas.
Unit
Tests unitarios de dominio — POJOs puros, sin dependencias. Se crean DESPUÉS del refactoring. Son los más rápidos y granulares. Los que tienes en testing-manual-servlets-spa.
Gherkin
Escenarios .feature — la capa de abstracción que conecta todo. Cada escenario se puede ejecutar a nivel E2E (Playwright) o API (fetch) o unit (función directa).

⚠️ Error que se evita
El error clásico es empezar escribiendo unit tests del código legacy. Pero si el código es espagueti, no hay "unidades" — todo depende de todo. Empezar por E2E (Playwright) y bajar hacia unit es el camino correcto: primero capturas el comportamiento global, luego descompones en capas, y los unit tests emergen naturalmente de la separación.

La semántica de un sistema legacy no está en su código — está en su ejecución.
Los artefactos declarativos (web.xml, HTML) son el índice del libro.
Playwright es el lector que ejecuta cada capítulo y registra qué ocurre.
Los contratos capturados son la verdad que ninguna IA puede inventar.
Los tests de integración son la red de seguridad para migrar sin riesgo.
Los Gherkin son el contrato portable que sobrevive a cualquier tecnología.
FMI — Caja Negra Guiada por Esqueleto Declarativo
APLICABILIDAD GENÉRICA
Este enfoque funciona para CUALQUIER app web legacy que cumpla dos condiciones:
1. Tenga un fichero de configuración de rutas (web.xml en Java, routes.rb en Rails, urls.py en Django, .htaccess en PHP).
2. Tenga formularios HTML con action y method explícitos (o equivalente SPA con fetch a endpoints conocidos).

No importa si el backend es Java, PHP, .NET, Python o COBOL detrás de un gateway HTTP. El esqueleto declarativo + Playwright captura el comportamiento independientemente del lenguaje. Esa es la portabilidad del enfoque: semántica sobre sintaxis.
