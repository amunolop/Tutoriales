01 — Arquitectura

Clean Architecture mapeada a tus 3 capas

Los anillos de Uncle Bob se simplifican en tres capas. El dominio es el centro intocable. Transporte e infraestructura son los "enchufes" que cambian al migrar de Servlets a Express, de MySQL a PostgreSQL, o de Apache FOP a una lib de Go.

Mapeo

Clean Architecture (Uncle Bob) → Tu modelo de 3 capas

Los 4 anillos de Robert C. Martin colapsados en 3 capas pragmáticas para aplicaciones web.

  Regla de Dependencia:
  → Las flechas apuntan SIEMPRE hacia el centro (dominio).
  → El dominio NO importa nada de transporte ni infraestructura.
  → Transporte e Infraestructura dependen del dominio, nunca al revés.
💡 La simplificación clave

Tu modelo colapsa "Interface Adapters" y "Frameworks & Drivers" en dos capas externas separadas por función (Transporte = HTTP, Infraestructura = persistencia/servicios). El dominio queda intacto. Es la misma idea con menos ceremonia y más claridad para el equipo.

DIP

Dependency Inversion — La clave de la portabilidad

Sin DIP, tu UseCase depende de MySQL. Con DIP, MySQL depende de tu UseCase. Esa inversión permite cambiar BD, mailer o generador de docs sin tocar lógica.

▶ 
  ❌ SIN DIP — Acoplado (no migrable)

  UseCase ──► JdbcFormDAO ──► MySQL          Cambiar MySQL = reescribir UseCase
  UseCase ──► SmtpMailer ──► Gmail           Cambiar mailer = reescribir UseCase
  UseCase ──► FopGenerator ──► Apache FOP    Cambiar generador = reescribir UseCase

  ────────────────────────────────────────────────────────────────────────

  ✅ CON DIP — Desacoplado (migrable)

                      ┌─────────────────────────┐
                      │  💎 DOMINIO              │
                      │                         │
  UseCase ─────────►  │  interface              │ ◄── JdbcFormDAO    (MySQL)
                      │  FormRepository         │ ◄── PgFormRepo     (PostgreSQL)
                      │                         │ ◄── MongoFormRepo  (MongoDB)
                      │                         │
  UseCase ─────────►  │  interface              │ ◄── SmtpMailer     (JavaMail)
                      │  MailService            │ ◄── NodemailerSvc  (Nodemailer)
                      │                         │ ◄── SendGridSvc    (API REST)
                      │                         │
  UseCase ─────────►  │  interface              │ ◄── FopDocGen      (Apache FOP)
                      │  DocumentGenerator      │ ◄── XsltProcGen    (xsltproc)
                      │                         │ ◄── WeasyPrintGen  (Python)
                      └─────────────────────────┘

  El dominio DEFINE la interfaz. La infra la IMPLEMENTA.
  Cambiar MySQL → Postgres = nueva clase. El UseCase no cambia.
⛔ La regla que no puedes romper

Si tu entidad tiene @Entity de JPA, o tu UseCase hace import javax.mail.*, o tu caso de uso referencia FopFactory directamente, la inversión se rompe. El dominio pasa a depender de la infra y ya no puedes migrar sin reescribirlo.

Entity

FormSubmission — Entidad de dominio pura

POJO puro sin anotaciones de framework. La lógica de transición de estado vive aquí. Observa que el código es prácticamente idéntico en los 3 lenguajes.

▶
✅ Regla de oro

Cero imports de framework. Sin @Entity, sin @Column, sin decoradores de TypeORM. La entidad es un objeto de datos puro cuya lógica de negocio (transiciones de estado, validaciones) vive en sus propios métodos.

// domain/entities/FormSubmission.java
// POJO puro — sin @Entity, sin JPA, sin Spring
package domain.entities;

import java.time.LocalDateTime;

public class FormSubmission {

    private final String id;
    private final String senderName;
    private final String senderEmail;
    private final String subject;
    private final String body;
    private String status;
    private final LocalDateTime createdAt;
    private LocalDateTime processedAt;

    public FormSubmission(String id, String senderName,
            String senderEmail, String subject, String body) {
        this.id = id;
        this.senderName = senderName;
        this.senderEmail = senderEmail;
        this.subject = subject;
        this.body = body;
        this.status = "PENDING";
        this.createdAt = LocalDateTime.now();
    }

    // ── Lógica de dominio ──
    public void markAsProcessed() {
        this.status = "PROCESSED";
        this.processedAt = LocalDateTime.now();
    }

    public void markAsSent() {
        if (!"PROCESSED".equals(status))
            throw new IllegalStateException("Formulario no procesado");
        this.status = "SENT";
    }

    public void markAsFailed() { this.status = "FAILED"; }
    public boolean isReadyToSend() { return "PROCESSED".equals(status); }

    // Getters (sin setters — inmutabilidad controlada)
    public String getId()          { return id; }
    public String getSenderName()  { return senderName; }
    public String getSenderEmail() { return senderEmail; }
    public String getSubject()     { return subject; }
    public String getBody()        { return body; }
    public String getStatus()      { return status; }
}

type FormSubmission struct {
    ID          string
    SenderName  string
    SenderEmail string
    Subject     string
    Body        string
    Status      string
    CreatedAt   time.Time
    ProcessedAt *time.Time
}

func NewFormSubmission(id, name, email, subj, body string) *FormSubmission {
    return &FormSubmission{
        ID: id, SenderName: name, SenderEmail: email,
        Subject: subj, Body: body,
        Status: "PENDING", CreatedAt: time.Now(),
    }

// ── Lógica de dominio ──

    f.Status = "PROCESSED"
    now := time.Now(); f.ProcessedAt = &now
}

func (f *FormSubmission) MarkAsSent() error {
    if f.Status != "PROCESSED" {
        return errors.New("formulario no procesado")
    }
    f.Status = "SENT"; return nil
}

func (f *FormSubmission) MarkAsFailed()    { f.Status = "FAILED" }
func (f *FormSubmission) IsReadyToSend() bool { return f.Status == "PROCESSED" }

Use Case

ProcessAndSendFormUseCase — Orquestación pura

Recibe interfaces por constructor (DIP). Orquesta: procesar → guardar → generar doc → enviar email → actualizar estado. No conoce ninguna tecnología concreta.

▶
💡 Observa el constructor

Recibe FormRepository, DocumentGenerator y MailService como interfaces. No sabe si detrás hay MySQL, PostgreSQL, Apache FOP, xsltproc, JavaMail o SendGrid. Eso es exactamente lo que permite la migración sin tocar este código.

// domain/usecases/ProcessAndSendFormUseCase.java
package domain.usecases;

import domain.entities.FormSubmission;
import domain.interfaces.*;

public class ProcessAndSendFormUseCase {

    private final FormRepository formRepo;
    private final DocumentGenerator docGenerator;
    private final MailService mailService;

    // ── DIP: recibe interfaces, no implementaciones ──
    public ProcessAndSendFormUseCase(
            FormRepository formRepo,
            DocumentGenerator docGenerator,
            MailService mailService) {
        this.formRepo = formRepo;
        this.docGenerator = docGenerator;
        this.mailService = mailService;
    }

    public void execute(FormSubmission form, String templateId) {
        // 1. Marcar como procesado (lógica de dominio)
        form.markAsProcessed();

        // 2. Persistir estado procesado
        formRepo.save(form);

        try {
            // 3. Generar documento (PDF vía XML/XSL/XSL-FO)
            byte[] pdfBytes = docGenerator.generate(form, templateId);

            // 4. Enviar por email con el PDF adjunto
            mailService.send(
                form.getSenderEmail(),
                "Confirmación: " + form.getSubject(),
                "Adjuntamos su formulario procesado.",
                pdfBytes
            );

            // 5. Marcar como enviado
            form.markAsSent();
        } catch (Exception e) {
            form.markAsFailed();
        }

        // 6. Persistir estado final
        formRepo.save(form);
    }
}
// domain/usecases/ProcessAndSendFormUseCase.ts
import { FormSubmission }    from "../entities/FormSubmission";
import { FormRepository }    from "../interfaces/FormRepository";
import { DocumentGenerator } from "../interfaces/DocumentGenerator";
import { MailService }       from "../interfaces/MailService";

export class ProcessAndSendFormUseCase {

  constructor(
    private readonly formRepo: FormRepository,
    private readonly docGenerator: DocumentGenerator,
    private readonly mailService: MailService,
  ) {}

  async execute(form: FormSubmission, templateId: string): Promise<void> {
    form.markAsProcessed();
    await this.formRepo.save(form);

    try {
      const pdfBytes = await this.docGenerator.generate(form, templateId);
      await this.mailService.send(
        form.senderEmail,
        `Confirmación: ${form.subject}`,
        "Adjuntamos su formulario procesado.",
        pdfBytes,
      );
      form.markAsSent();
    } catch {
      form.markAsFailed();
    }

    await this.formRepo.save(form);
  }
}
// domain/usecases/process_and_send.go
package domain

type ProcessAndSendFormUseCase struct {
    repo    FormRepository
    docGen  DocumentGenerator
    mailer  MailService
}

func NewProcessAndSendForm(
    r FormRepository, d DocumentGenerator, m MailService,
) *ProcessAndSendFormUseCase {
    return &ProcessAndSendFormUseCase{repo: r, docGen: d, mailer: m}
}

func (uc *ProcessAndSendFormUseCase) Execute(
    form *FormSubmission, templateID string,
) error {
    form.MarkAsProcessed()
    if err := uc.repo.Save(form); err != nil { return err }

    pdf, err := uc.docGen.Generate(form, templateID)
    if err != nil {
        form.MarkAsFailed()
        uc.repo.Save(form)
        return err
    }

    err = uc.mailer.Send(form.SenderEmail,
        "Confirmación: "+form.Subject,
        "Adjuntamos su formulario procesado.", pdf)
    if err != nil {
        form.MarkAsFailed()
    } else {
        form.MarkAsSent()
    }
    return uc.repo.Save(form)
}
Infra

FormRepository — Múltiples implementaciones de BD

La misma interfaz, 3 implementaciones. Cambiar de MySQL a PostgreSQL a MongoDB es sustituir qué clase se inyecta, sin tocar el UseCase.

▶ 
// infrastructure/persistence/JdbcFormRepository.java
// Implementa la interfaz del dominio con JDBC + MySQL
package infrastructure.persistence;

import domain.entities.FormSubmission;
import domain.interfaces.FormRepository;
import java.sql.*;

public class JdbcFormRepository implements FormRepository {

    private final Connection conn;

    public JdbcFormRepository(Connection conn) {
        this.conn = conn;
    }

    @Override
    public void save(FormSubmission form) {
        String sql = """
            INSERT INTO forms (id, sender_name, sender_email,
                               subject, body, status, created_at)
            VALUES (?, ?, ?, ?, ?, ?, ?)
            ON DUPLICATE KEY UPDATE status = ?, processed_at = ?
            """;
        try (PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setString(1, form.getId());
            ps.setString(2, form.getSenderName());
            ps.setString(3, form.getSenderEmail());
            ps.setString(4, form.getSubject());
            ps.setString(5, form.getBody());
            ps.setString(6, form.getStatus());
            ps.setTimestamp(7, Timestamp.valueOf(form.getCreatedAt()));
            ps.setString(8, form.getStatus());
            ps.setTimestamp(9, null);
            ps.executeUpdate();
        } catch (SQLException e) {
            throw new RuntimeException("Error guardando form", e);
        }
    }
    // findById similar...
}
// infrastructure/persistence/PgFormRepository.ts
// Implementa la interfaz del dominio con pg (PostgreSQL)
import { Pool } from "pg";
import { FormRepository } from "../../domain/interfaces/FormRepository";
import { FormSubmission } from "../../domain/entities/FormSubmission";

export class PgFormRepository implements FormRepository {

  constructor(private readonly pool: Pool) {}

  async save(form: FormSubmission): Promise<void> {
    await this.pool.query(
      `INSERT INTO forms (id, sender_name, sender_email,
                         subject, body, status, created_at)
       VALUES ($1,$2,$3,$4,$5,$6,$7)
       ON CONFLICT (id) DO UPDATE SET status=$6, processed_at=NOW()`,
      [form.id, form.senderName, form.senderEmail,
       form.subject, form.body, form.status, form.createdAt]
    );
  }

  async findById(id: string): Promise<FormSubmission | null> {
    const { rows } = await this.pool.query(
      "SELECT * FROM forms WHERE id = $1", [id]
    );
    return rows[0] ? /* mapear a entidad */ null : null;
  }
}

Pipeline

Pipeline de generación documental: Datos → XML → XSL → XSL-FO → PDF

Los datos del formulario se serializan a XML. Una plantilla XSL transforma el XML a XSL-FO. Un procesador FO renderiza el PDF final. Cada paso es un "enchufe" intercambiable.

▶ 
  FormSubmission (Entidad de dominio)
       │
       ▼  Serialización
  ┌────────────────┐
  │  XML de datos   │     form-data.xml
  │  (estructura)   │     Contiene: nombre, email, asunto, cuerpo, fecha...
  └────────┬───────┘
           │
           ▼  Transformación XSL        Se elige plantilla según templateId
  ┌────────────────┐                    ┌──────────────────────────────┐
  │  Plantilla XSL │ ◄──── selección ── │  templates/                  │
  │  (diseño)      │                    │  ├── informe-formal.xsl      │
  └────────┬───────┘                    │  ├── recibo-simple.xsl       │
           │                            │  ├── certificado-oficial.xsl │
           ▼  Resultado intermedio      │  └── notificacion-interna.xsl│
  ┌────────────────┐                    └──────────────────────────────┘
  │  XSL-FO        │     Documento intermedio con layout:
  │  (maquetación)  │     páginas, márgenes, tablas, tipografía...
  └────────┬───────┘
           │
           ▼  Renderizado              Procesador FO (enchufe infra)
  ┌────────────────┐                 ┌─────────────────────────────┐
  │  PDF final     │ ◄── render ─── │  Apache FOP   (Java)        │
  │  (bytes[])     │                 │  xsltproc+fop (CLI)         │
  └────────────────┘                 │  WeasyPrint   (Python)      │
                                     │  go-fop       (Go)          │
                                     └─────────────────────────────┘
           │
           ▼
  Se adjunta al email vía MailService
💡 Por qué XML/XSL/XSL-FO es perfecto para DIP

El pipeline tiene 3 pasos separados: datos (XML), diseño (XSL) y renderizado (procesador FO). Puedes cambiar la plantilla sin tocar el código, añadir nuevos tipos de documento sin modificar el UseCase, y sustituir Apache FOP por otro motor sin que el dominio se entere. Cada pieza es un "enchufe" independiente.

✅ Múltiples plantillas, mismo código

Añadir un nuevo tipo de documento (certificado, notificación, recibo) es crear un nuevo fichero .xsl en la carpeta de plantillas. No se toca ni una línea de Java, TypeScript ni Go. El templateId que llega al UseCase selecciona qué XSL aplicar.

Infra

DocumentGenerator — Apache FOP (Java) vs xsltproc (Node)

Dos implementaciones de la misma interfaz del dominio. Cada una usa el motor de renderizado nativo de su ecosistema.

▶ 
// infrastructure/documents/FopDocumentGenerator.java
import domain.entities.FormSubmission;
import domain.interfaces.DocumentGenerator;
import org.apache.fop.apps.*;
import javax.xml.transform.*;

public class FopDocumentGenerator implements DocumentGenerator {

    private final String templatesDir;

    public FopDocumentGenerator(String templatesDir) {
        this.templatesDir = templatesDir;
    }

    @Override
    public byte[] generate(FormSubmission data, String templateId) {
        // 1. Serializar entidad a XML
        String xml = toXml(data);

        // 2. Cargar plantilla XSL según templateId
        File xslFile = new File(templatesDir, templateId + ".xsl");
        Source xslt = new StreamSource(xslFile);

        // 3. Transformar XML → XSL-FO → PDF con Apache FOP
        FopFactory fopFactory = FopFactory.newInstance(new File(".").toURI());
        ByteArrayOutputStream out = new ByteArrayOutputStream();
        Fop fop = fopFactory.newFop(MimeConstants.MIME_PDF, out);

        TransformerFactory tf = TransformerFactory.newInstance();
        Transformer transformer = tf.newTransformer(xslt);
        transformer.transform(
            new StreamSource(new StringReader(xml)),
            new SAXResult(fop.getDefaultHandler())
        );

        return out.toByteArray();
    }

    private String toXml(FormSubmission f) {
        return "<form-submission>"
            + "<id>" + f.getId() + "</id>"
            + "<sender-name>" + f.getSenderName() + "</sender-name>"
            + "<sender-email>" + f.getSenderEmail() + "</sender-email>"
            + "<subject>" + f.getSubject() + "</subject>"
            + "<body>" + f.getBody() + "</body>"
            + "<status>" + f.getStatus() + "</status>"
            + "</form-submission>";
    }
}
// infrastructure/documents/XsltDocumentGenerator.ts
import { execSync } from "child_process";
import { writeFileSync, readFileSync, unlinkSync } from "fs";
import { DocumentGenerator } from "../../domain/interfaces/DocumentGenerator";
import { FormSubmission } from "../../domain/entities/FormSubmission";

export class XsltDocumentGenerator implements DocumentGenerator {

  constructor(private templatesDir: string) {}

  async generate(data: FormSubmission, templateId: string): Promise<Buffer> {
    // 1. Serializar a XML
    const xml = this.toXml(data);
    const tmpXml = `/tmp/${data.id}.xml`;
    const tmpFo  = `/tmp/${data.id}.fo`;
    const tmpPdf = `/tmp/${data.id}.pdf`;
    writeFileSync(tmpXml, xml);

    // 2. Transformar XML → XSL-FO con xsltproc
    const xslPath = `${this.templatesDir}/${templateId}.xsl`;
    execSync(`xsltproc -o ${tmpFo} ${xslPath} ${tmpXml}`);

    // 3. Renderizar XSL-FO → PDF con fop CLI
    execSync(`fop ${tmpFo} ${tmpPdf}`);

    const pdf = readFileSync(tmpPdf);
    [tmpXml, tmpFo, tmpPdf].forEach(unlinkSync);
    return pdf;
  }

  private toXml(f: FormSubmission): string {
    return `<form-submission>
      <id>${f.id}</id>
      <sender-name>${f.senderName}</sender-name>
      <sender-email>${f.senderEmail}</sender-email>
      <subject>${f.subject}</subject>
      <body>${f.body}</body>
      <status>${f.status}</status>
    </form-submission>`;
  }
}
Controller

FormController — Servlet vs Express vs Gin

Cambia al 100% entre lenguajes. Pero todos hacen lo mismo: validar input, construir la entidad, invocar el UseCase y devolver la respuesta.

▶ 
// transport/FormServlet.java
import domain.entities.FormSubmission;
import domain.usecases.ProcessAndSendFormUseCase;
import javax.servlet.http.*;
import java.util.UUID;

public class FormServlet extends HttpServlet {

    private final ProcessAndSendFormUseCase useCase;

    public FormServlet(ProcessAndSendFormUseCase useCase) {
        this.useCase = useCase;
    }

    @Override
    protected void doPost(HttpServletRequest req,
                           HttpServletResponse resp) {
        // 1. Extraer y validar input
        String name  = req.getParameter("name");
        String email = req.getParameter("email");
        String subj  = req.getParameter("subject");
        String body  = req.getParameter("body");
        String tmpl  = req.getParameter("template");

        // 2. Construir entidad de dominio
        var form = new FormSubmission(
            UUID.randomUUID().toString(),
            name, email, subj, body
        );

        // 3. Invocar caso de uso (dominio puro)
        useCase.execute(form, tmpl != null ? tmpl : "informe-formal");

        // 4. Responder
        resp.setStatus(201);
        resp.getWriter().write("{\"id\":\"" + form.getId() + "\"}");
    }
}
// transport/formRouter.ts
import { Router } from "express";
import { v4 as uuid } from "uuid";
import { FormSubmission } from "../domain/entities/FormSubmission";
import { ProcessAndSendFormUseCase } from "../domain/usecases/ProcessAndSendFormUseCase";

export function createFormRouter(useCase: ProcessAndSendFormUseCase) {
  const router = Router();

  router.post("/api/forms", async (req, res) => {
    const { name, email, subject, body, template } = req.body;

    const form = new FormSubmission(
      uuid(), name, email, subject, body
    );

    await useCase.execute(form, template ?? "informe-formal");

    res.status(201).json({ id: form.id, status: form.status });
  });

  return router;
}
// transport/form_handler.go
package transport

import ("github.com/gin-gonic/gin"; "github.com/google/uuid"; domain "myapp/domain")

type FormHandler struct { uc *domain.ProcessAndSendFormUseCase }

func NewFormHandler(uc *domain.ProcessAndSendFormUseCase) *FormHandler {
    return &FormHandler{uc: uc}
}

func (h *FormHandler) HandleSubmit(c *gin.Context) {
    var req struct {
        Name     string `json:"name"`
        Email    string `json:"email"`
        Subject  string `json:"subject"`
        Body     string `json:"body"`
        Template string `json:"template"`
    }
    c.BindJSON(&req)

    form := domain.NewFormSubmission(
        uuid.New().String(),
        req.Name, req.Email, req.Subject, req.Body,
    )
    tmpl := req.Template
    if tmpl == "" { tmpl = "informe-formal" }

    h.uc.Execute(form, tmpl)
    c.JSON(201, gin.H{"id": form.ID, "status": form.Status})
}
⛔ Lo que cambia vs lo que no cambia

El controller cambia completamente (distintas APIs HTTP). El UseCase que invoca es exactamente el mismo en los 3 lenguajes. Esa es la prueba de que el DIP funciona: el dominio es portable, el transporte es desechable.

Main

El punto de cableado — Donde se eligen los "enchufes"

En el main/bootstrap de la app es donde decides qué implementación concreta va detrás de cada interfaz. Este es el ÚNICO lugar que cambia para sustituir una BD, un mailer o un generador de docs.

▶

💡 El main() es el único lugar que "sabe todo"

Solo el punto de cableado conoce las implementaciones concretas. El UseCase solo conoce interfaces. El controller solo conoce el UseCase. Cambiar de MySQL a Postgres, o de JavaMail a SendGrid, es modificar una línea en el main. El resto del código no se toca.

Prueba

¿Qué cambia y qué no cambia al migrar?

La tabla definitiva: para cada tipo de migración (lenguaje, BD, mailer, generador de docs), qué ficheros se tocan y cuáles quedan intactos.

▶
Migración💎 Dominio🔌 Infraestructura🌐 Transporte⚡ Cableado
Java → TypeScript Se traduce (misma lógica) Se reescribe completo Se reescribe completo Se reescribe completo
MySQL → PostgreSQL NO cambia Nuevo repo (1 clase) NO cambia 1 línea
JavaMail → SendGrid NO cambia Nuevo mailer (1 clase) NO cambia 1 línea
Apache FOP → WeasyPrint NO cambia Nuevo generator (1 clase) NO cambia 1 línea
Nueva plantilla XSL NO cambia NO cambia NO cambia NO cambia
Servlets → Express NO cambia NO cambia Se reescribe Se adapta
✅ Conclusión

El dominio (entidades, interfaces, casos de uso) nunca cambia cuando sustituyes infraestructura. Y cuando migras de lenguaje, el dominio solo se "traduce" mecánicamente porque es lógica pura sin dependencias de framework. Esa es la promesa del DIP cumplida: la lógica de negocio es portable.
