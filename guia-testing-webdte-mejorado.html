3 TÉCNICAS, 3 PROPÓSITOS
REFLECTION ESTRUCTURAL
Verifica el contrato Java sin instanciar la app. Usa Class.forName(), getDeclaredFields(), Modifier.isFinal(), ParameterizedType. Aplica a: DTOs, Entidades, Interfaces, Controllers (E2E). Velocidad: instantánea. Cobertura: estructura, no comportamiento.
MOCKITO + ARGUMENTCAPTOR
Verifica la lógica de negocio aislando dependencias. mock(Repo.class) + when().thenReturn(Optional.of(x)). ArgumentCaptor captura entidades pasadas a .save() y verifica el mapeo Request → Entity. Aplica a: UseCases. Velocidad: rápida.
SOURCE-ANALYSIS
Verifica código JS con fs.readFileSync() + regex. Sin runtime, sin DOM, sin jest. Funciona en Node.js puro. Aplica a: Services y Components frontend. Detecta: stubs, fetch sin credentials, ausencia de resp.ok, Web Component mal estructurado.
💡 Filosofía: TDD-as-Spec
En FMI los tests se escriben antes del código de producción. Actúan como especificación ejecutable: definen la estructura exacta (nombres de clase, tipos, herencia) que el código generado por IA debe cumplir. Esto convierte los tests en contratos formales de migración, no en tests de regresión convencionales. Si un test falla, el código está mal — nunca el test.
TDD-AS-SPEC: TESTS COMO CONTRATO

El testing convencional verifica que el código funciona. El testing FMI verifica que el código cumple un contrato. La diferencia es sutil pero crítica: en FMI los tests existen antes de cualquier línea de código de producción, y son los que la IA debe satisfacer. No son red de seguridad — son la especificación.

Testing convencional
Cuándo se escriben: después del código.
Qué prueban: que no rompamos lo que ya funciona.
Quién los escribe: el mismo dev que el código.
Riesgo: tests que prueban lo que el código hace, no lo que debería hacer.
TDD-as-Spec (FMI)
Cuándo: antes del código (Oleada 1 V5M).
Qué prueban: que el código generado cumple el contrato declarado.
Quién: Test Worker (no el Code Worker).
Riesgo eliminado: el Code Worker no puede inventar — debe ajustarse al test.

TÉCNICA 1: REFLECTION ESTRUCTURAL

Reflection es la columna vertebral del testing FMI. Permite verificar la estructura de una clase Java sin instanciarla, lo que es perfecto para validar contratos de migración antes de tener una app funcionando.

Java · Las APIs reflection que más uso
// 1. Existencia de la clase
Class<?> clazz = Class.forName("domain.entities.Usuario");

// 2. Modificadores: final, abstract, interface
boolean isFinal = Modifier.isFinal(clazz.getModifiers());
boolean isInterface = Modifier.isInterface(clazz.getModifiers());

// 3. Campos declarados
for (Field f : clazz.getDeclaredFields()) {
    f.getName();        // "titulacion"
    f.getType();        // String.class
    Modifier.isFinal(f.getModifiers());
}

// 4. Constructores
Constructor<?>[] ctors = clazz.getDeclaredConstructors();
ctors[0].getParameterTypes().length;   // 12

// 5. Métodos declarados (no heredados)
for (Method m : clazz.getDeclaredMethods()) {
    m.getName();
    m.getReturnType();
    m.getParameterTypes();
}

// 6. Tipos genéricos (Optional<Usuario>, List<Tema>)
Method find = clazz.getMethod("findByLogin", String.class);
ParameterizedType ret = (ParameterizedType) find.getGenericReturnType();
ret.getRawType();              // Optional.class
ret.getActualTypeArguments()[0]; // Usuario.class

// 7. Herencia
HttpServlet.class.isAssignableFrom(clazz);
TÉCNICA 2: MOCKITO + ARGUMENTCAPTOR

Para los UseCases, reflection no basta — necesitamos verificar interacciones con repositorios. Mockito 1.x (compatible con Java 8) hace el trabajo. ArgumentCaptor es la pieza clave para validar que el mapeo Request → Entity preserva los campos correctos.

Java · Patrón Mockito básico
// 1. Setup
UsuarioRepository repo = mock(UsuarioRepository.class);
AuthenticateUserUseCase useCase = new AuthenticateUserUseCase(repo);

// 2. Stub: programar el mock
when(repo.findByLogin("user"))
    .thenReturn(Optional.of(validUsuario));

// 3. Acción
LoginResponse response = useCase.execute("user", "pass123");

// 4. Verify: el mock fue llamado correctamente
verify(repo).findByLogin("user");
verify(repo, never()).save(any());

// 5. ArgumentCaptor: capturar lo que se pasó al mock
ArgumentCaptor<RevisionExamen> captor =
    ArgumentCaptor.forClass(RevisionExamen.class);
when(repo.save(captor.capture())).thenReturn(1);

useCase.execute(42, request);

RevisionExamen saved = captor.getValue();
assertEquals("Prof", saved.getNombreProfesor());  // KI-1
assertEquals(42, saved.getUsuarioId());
ArgumentCaptor — verificar el mapeo correcto El verdadero valor de Mockito en FMI es ArgumentCaptor. Te permite responder a la pregunta crítica: "¿el UseCase mapeó el RevisionRequest al RevisionExamen con los campos correctos?". Esencial para validar Knowledge Injections como KI-1 (nombreProfesor debe propagarse, no perderse).
TÉCNICA 3: SOURCE-ANALYSIS PARA JS

El frontend Vanilla JS no se compila — no hay herramientas de reflection. La técnica adoptada es análisis del código fuente con regex: cargas el .js como texto, aplicas patrones, verificas presencia/ausencia. Funciona con Node.js puro, sin DOM, sin jest, sin webpack.

JavaScript · Patrón source-analysis
const fs   = require('fs');
const path = require('path');
const assert = require('assert');

const servicePath = path.resolve(__dirname,
    '../../frontend/services/auth-service.js');
const source = fs.readFileSync(servicePath, 'utf-8');

// Test 1: cero stubs
assert.ok(
    !/console\.log\s*\(\s*['"`][^'"`]*[Ss][Tt][Uu][Bb]/.test(source),
    'Found a console.log containing STUB'
);

// Test 2: credentials: 'include' en cada fetch
assert.ok(
    /credentials\s*:\s*['"]include['"]/.test(source),
    "Missing credentials: 'include' in fetch options"
);

// Test 3: resp.ok antes de .json()
const okIdx   = source.search(/\.ok\b/);
const jsonIdx = source.search(/\.json\s*\(\s*\)/);
if (jsonIdx !== -1) {
    assert.ok(okIdx < jsonIdx, '.ok must appear before .json()');
}
Por qué no jsdom o jest Web Components con Shadow DOM son difíciles de testear con jsdom — su soporte está incompleto. Source-analysis tiene una ventaja: detecta intenciones (¿hace fetch?, ¿valida resp.ok?) sin ejecutar el código. Es lento de escribir pero rápido de ejecutar y resistente a refactors menores.

El patrón de 5 tests por DTO de 2 campos Cada DTO tiene 2N + 1 tests donde N es el número de campos:

DTO INMUTABLE FACTORY — APIRESPONSE

ApiResponse es la única excepción a la regla de DTOs mutables. Es un Value Object con factory methods: ApiResponse.ok(data), ApiResponse.ok(message), ApiResponse.error(message). El constructor es privado. KI-11 garantiza que ningún Worker invente success() o fail().

public class ApiResponseTest {

    @Test
    public void testNoPublicConstructor() {
        Constructor<?>[] ctors = ApiResponse.class.getDeclaredConstructors();
        for (Constructor<?> c : ctors) {
            assertFalse("ApiResponse must NOT have public constructor",
                Modifier.isPublic(c.getModifiers()));
        }
    }

    @Test
    public void testFactoryOkWithData() throws Exception {
        Method ok = ApiResponse.class.getMethod("ok", Object.class);
        assertTrue(Modifier.isStatic(ok.getModifiers()));

        ApiResponse r = (ApiResponse) ok.invoke(null, "test-data");
        assertTrue(r.isOk());
        assertEquals("test-data", r.getData());
    }

    @Test
    public void testFactoryError() throws Exception {
        Method err = ApiResponse.class.getMethod("error", String.class);
        ApiResponse r = (ApiResponse) err.invoke(null, "failed");
        assertFalse(r.isOk());
        assertEquals("failed", r.getMessage());
    }
}

PATRÓN DE TEST: 6 ASPECTOS

Cada entidad se valida en 6 dimensiones independientes. Los primeros 5 son contratos estructurales (reflection pura, sin instanciar). El sexto es una verificación de getter por cada campo, que sí instancia vía reflection.

  1. testClassIsFinal — la clase es final
  2. testAllFieldsAreFinal — todos los campos son final
  3. testNoSetters — ningún método empieza con "set"
  4. testExactlyOneConstructor — un único constructor
  5. testConstructorHasNParameters — el constructor tiene N args (12 para Usuario)
  6. testGet{Field} — cada getter retorna el valor pasado al constructor

import java.lang.reflect.Modifier;

    private Usuario buildUsuario() throws Exception {
        Constructor<Usuario> ctor = Usuario.class.getDeclaredConstructor(
                int.class, String.class, String.class, String.class,
                String.class, String.class, String.class, String.class,
                String.class, String.class, String.class, String.class);
        ctor.setAccessible(true);
        return ctor.newInstance(
                1, "EXP-001", "Juan", "Garcia Lopez",
                "Calle Mayor 1", "juan@example.com", "600123456",
                "Ingeniería Informática", "4º", "TFM-2024",
                "jgarcia", "secret");

    // 1. La clase debe ser final
    @Test
    public void testClassIsFinal() {
        assertTrue("Usuario must be declared final",
                Modifier.isFinal(Usuario.class.getModifiers()));

    // 2. Todos los campos declarados deben ser final
    @Test
    public void testAllFieldsAreFinal() {
        for (Field f : Usuario.class.getDeclaredFields()) {
            assertTrue("Field '" + f.getName() + "' must be final",
                    Modifier.isFinal(f.getModifiers()));
        }
    }

    // 3. Sin setters
    @Test
    public void testNoSetters() {
        for (Method m : Usuario.class.getDeclaredMethods()) {
            assertFalse("Setter found but not allowed: " + m.getName(),

        }

    @Test

        assertEquals("Usuario must have exactly 1 constructor",
                1, Usuario.class.getDeclaredConstructors().length);
    }

        Constructor<?>[] ctors = Usuario.class.getDeclaredConstructors();
        assertEquals("Constructor must have 12 parameters",
                12, ctors[0].getParameterTypes().length);

        Usuario u = buildUsuario();

            Usuario.class.getMethod("getExpediente").invoke(u));

    @Test

        boolean hasTitulacion = false, hasEspecialidad = false;

            if ("titulacion".equals(f.getName())) hasTitulacion = true;

⚠️ Por qué inmutabilidad estricta
Si Usuario tuviera setters, el código de transporte podría modificar la entidad después de cargarla del repo. Esto rompe el modelo hexagonal: la entidad de dominio no debe estar acoplada al ciclo de vida HTTP. final class + final fields + 0 setters garantiza que cualquier cambio requiere construir una nueva entidad — explícito, trazable, sin estado compartido accidental.

💡 Por qué source-analysis es suficiente
Source-analysis no detecta bugs de runtime (división por cero, off-by-one, race conditions). Pero sí detecta los bugs estructurales que son el 80% de los problemas de migración: ¿olvidé credentials en este service?, ¿este componente sigue extiende HTMLElement?, ¿el router maneja el caso por defecto?

Los bugs de runtime se cazan en QA manual o en producción. Los bugs estructurales son los que se multiplican cuando una IA genera 20 ficheros en paralelo. Source-analysis es la herramienta correcta para ese problema concreto.

ANTI-PATRÓN 2: THENRETURN(NULL) EN OPTIONAL

Bug recurrente: el Test Worker mockea un repo que retorna Optional<T> con thenReturn(entity) directamente. La firma del método espera Optional, así que esto es type mismatch y NO compila. M16 documentó 5 tests rotos por esta causa.

❌ MAL — type mismatch
// repo.findByLogin retorna Optional<Usuario>
when(repo.findByLogin("u"))
    .thenReturn(usuario);  // ❌

when(repo.findByLogin("u"))
    .thenReturn(null);     // ❌ tampoco
✅ BIEN — Optional siempre
// Caso "encontrado":
when(repo.findByLogin("u"))
    .thenReturn(Optional.of(usuario));

// Caso "no encontrado":
when(repo.findByLogin("x"))
    .thenReturn(Optional.empty());
GATE check G5 El check G5 ejecuta grep -rE "thenReturn\([a-zA-Z]+\)" tests/usecases/ | grep -v "Optional". Si el resultado no está vacío, ABORT. Esto detecta cualquier thenReturn(usuario) directo sin tener que ejecutar Java.
ANTI-PATRÓN 3: CONSTRUCTOR ALL-ARGS INVENTADO

Otro hallazgo del post-mortem M16: el Test Worker inventa un constructor all-args para un DTO mutable. Por ejemplo, new LoginRequest("user", "pass") cuando el contrato dice "DTOs mutables = no-arg + setters". El Code Worker entonces tiene que decidir: ¿implemento el constructor inventado o respeto el contrato? Resultado: incoherencia.

❌ MAL — Constructor inventado

// → Constructor de 2 args es inventado
✅ BIEN — no-arg + setters

CONSIDERACIONES PARA DIGITALOCEAN APP PLATFORM

WebDTE migrado se despliega como WAR en un container Tomcat 5.5 sobre DigitalOcean App Platform. La metodología FMI fija algunos requisitos de runtime que el CI debe cumplir:

  • Java 8 estricto — el deploy target es Tomcat 5.5 con JDK 1.5/1.6, así que el bytecode generado debe ser compatible. maven.compiler.target=1.8 es el máximo aceptable.
  • WAR sin dependencias provided — servlet-api es provided en pom.xml. Tomcat lo aporta. Si lo incluyes, conflicto en runtime.
  • PostgreSQL JDBC en WEB-INF/lib — incluido como dependencia normal, no provided.
  • Deploy zero-downtime — DO App Platform hace blue/green automáticamente. El deploy desde CI solo dispara el evento; DO maneja el resto.
💡 La regla de oro: tests bloquean el deploy
El needs: en el job de deploy es la pieza clave. Si cualquiera de los 3 jobs anteriores falla (Java, Frontend, Smoke), el deploy NO se ejecuta. Esto convierte la suite de tests en un firewall efectivo contra deployments rotos. En FMI, donde el código se genera por IA, esta protección es crítica: una iteración del Architect que rompa naming canónico es atrapada por SMOKE antes de llegar a producción.
