🧩 La analogía definitiva

El LLM es el cerebro. El chatbot clásico era un contestador automático con menús pregrabados. El chatbot con IA es ese cerebro conversando contigo. El agente es ese cerebro con manos y autonomía para actuar en el mundo. Los embeddings son el traductor que convierte texto en matemáticas. La BBDD vectorial es la memoria a largo plazo. Y RAG es el sistema que une todo para que el LLM "sepa" cosas que no aprendió en su entrenamiento.

LLM (Large Language Model) es el salto tecnológico que lo cambió todo. No es una aplicación — es el modelo de IA en sí. Una red neuronal de miles de millones de parámetros que aprendió a comprender y generar lenguaje de forma extraordinariamente sofisticada. Es el motor, no el coche.
⚠️ Confusión muy común
Cuando dices "voy a usar ChatGPT" no estás usando solo un LLM. Estás usando una aplicación completa construida sobre un LLM (GPT-4o). El LLM por sí solo no tiene interfaz, no tiene memoria, no tiene acceso a internet, no tiene historial. Es solo el cerebro. GPT-4o, Claude, Gemini, Llama 3 → son LLMs. ChatGPT, Claude.ai, Gemini.app → son aplicaciones que envuelven esos LLMs.

Chatbot con IA: un LLM envuelto en una interfaz de conversación con memoria de sesión, instrucciones de sistema y (a veces) herramientas básicas. ChatGPT, Claude.ai, Gemini son ejemplos. Ojo: estas mismas herramientas pueden actuar también como agentes — el modo depende de cómo las uses, no de la herramienta en sí.
🔑 La distinción que más confunde
ChatGPT y Claude son chatbots con IA cuando tú los conduces: preguntas, ellos responden, tú decides qué pregunta hacer a continuación. Cada turno eres tú quien da la instrucción.

ChatGPT y Claude son agentes cuando les das un objetivo y los dejas actuar solos: ellos deciden qué pasos dar, qué herramientas usar, cuándo han terminado. Tú solo defines el objetivo final.

La diferencia no es la herramienta — es el grado de autonomía que le das.

Agente IA: un LLM con herramientas y un bucle de autonomía. La diferencia con el chatbot no es la herramienta que usas — es que el agente decide por sí solo los pasos para lograr un objetivo, puede ejecutar acciones reales (buscar, programar, enviar emails, consultar BBDD) y continúa hasta completar la tarea sin que tú intervengas en cada paso.
🎯 La frase que lo resume todo
Un chatbot responde. Un agente actúa.
Al chatbot le preguntas y obtienes una respuesta. Al agente le das un objetivo y él decide qué herramientas usar, en qué orden, cuántas veces, hasta que la tarea esté hecha.

⚠️ Hype vs realidad de los agentes

Los agentes son el mayor foco de inversión en IA, pero también los más propensos a fallar. Cada paso extra es una posibilidad de error encadenado. Hoy funcionan bien en tareas bien definidas con herramientas concretas. No todo lo que se vende como "agente" en redes es realmente autónomo — muchos son chatbots con buen marketing.

Embedding: la forma en que los LLMs convierten texto en números. Un embedding es un vector de cientos o miles de decimales que captura el significado semántico del texto. Es el puente entre el lenguaje humano y el cálculo matemático. Dos textos con significado similar → vectores similares (cercanos en el espacio).

Generar embeddings con Python
from openai import OpenAI
import numpy as np

client = OpenAI()

def get_embedding(texto):
  r = client.embeddings.create(
    input=texto,
    model="text-embedding-3-small"
  )
  return r.data[0].embedding  # 1536 números

# Similitud coseno entre dos textos
def similitud(t1, t2):
  v1, v2 = get_embedding(t1), get_embedding(t2)
  return np.dot(v1, v2) / (
    np.linalg.norm(v1) * np.linalg.norm(v2)
  )

similitud("gato", "felino")   # → 0.94 ✅
similitud("gato", "avión")    # → 0.11 ❌
Propiedad
Detalle
Dimensiones
384 (ligeros) hasta 3072 (OpenAI large). Más = más matices, más coste.
Similitud
Coseno: ángulo entre vectores. De -1 a 1. Más cerca de 1 → más parecidos.

Base de datos vectorial: una BBDD especializada en almacenar embeddings y hacer búsquedas por similitud semántica a alta velocidad. En lugar de buscar por coincidencia exacta de palabras (SQL LIKE), busca por cercanía de significado en el espacio vectorial. Es el componente de almacenamiento que hace posible RAG.

▸ Implementación RAG en ~30 líneas con LangChain
RAG end-to-end
from langchain.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_community.vectorstores import Chroma
from langchain.chains import RetrievalQA

# ── FASE 1: INDEXACIÓN ────────────────────────
docs = PyPDFLoader("manual.pdf").load()

chunks = RecursiveCharacterTextSplitter(
  chunk_size=500, chunk_overlap=50
).split_documents(docs)

vectorstore = Chroma.from_documents(
  documents=chunks,
  embedding=OpenAIEmbeddings(),
  persist_directory="./chroma_db"
)

# ── FASE 2: CONSULTA ──────────────────────────
rag = RetrievalQA.from_chain_type(
  llm=ChatOpenAI(model="gpt-4o"),
  retriever=vectorstore.as_retriever(
    search_kwargs={"k": 3}  # top-3 chunks
  )
)

r = rag.invoke("¿Cuál es la política de devoluciones?")
# ✅ Responde con tu PDF, no con su entrenamiento

from langchain_community.llms import Ollama

# ── CONFIGURACIÓN (todo local) ────────────────

# ── FASE 1: INDEXAR TUS DOCUMENTOS ───────────
docs   = PyPDFLoader("manual_privado.pdf").load()

  chunk_size=500, chunk_overlap=50
).split_documents(docs)

  documents=chunks,
  embedding=embeddings,

rag = RetrievalQA.from_chain_type(
  llm=llm,
  retriever=vectorstore.as_retriever(search_kwargs={"k": 3})
)

r = rag.invoke("¿Cuál es el procedimiento de baja de un empleado?")

▸ 2 · Memoria conversacional — los 4 tipos
Sin memoria, cada mensaje al LLM es como hablar con alguien que tiene amnesia total. Existen cuatro estrategias para darle "recuerdo" a tu chatbot, cada una con su trade-off entre coste de tokens y calidad del contexto.
📋 Buffer Memory
Qué hace: guarda todos los mensajes y los manda siempre al LLM.

Ventaja: contexto perfecto, sin pérdida de información.
Problema: los tokens crecen infinito → caro y lento en conversaciones largas.

Ideal para chats cortos
✂️ Window Memory
Qué hace: solo guarda los últimos N mensajes (ej. últimos 10).

Ventaja: tokens controlados, coste estable.
Problema: olvida lo que pasó antes de la ventana.

El más usado en producción
📝 Summary Memory
Qué hace: resume periódicamente el historial con el LLM y guarda solo el resumen.

Ventaja: retiene lo importante en pocos tokens.
Problema: puede perder detalles en el resumen.

Ideal para chats muy largos
🧩 Entity Memory
Qué hace: extrae y actualiza entidades clave (personas, lugares, hechos) en un mapa estructurado.

Ventaja: muy eficiente, recuerda hechos importantes.
Problema: más complejo de implementar.

Ideal para asistentes personales
Buffer + Window Memory con LangChain
from langchain_community.chat_models import ChatOllama
from langchain.memory import ConversationBufferWindowMemory
from langchain.chains import ConversationChain

llm = ChatOllama(model="llama3.1")

# Window: recuerda los últimos 5 intercambios
memoria = ConversationBufferWindowMemory(
  k=5,  # número de intercambios a recordar
  return_messages=True
)

chat = ConversationChain(
  llm=llm,
  memory=memoria,
  verbose=False
)

# Conversación con memoria
chat.predict(input="Me llamo Carlos")
chat.predict(input="¿Cómo me llamo?")
# → "Te llamas Carlos" ✅

▸ 1 · Tool Use / Function Calling — cómo el LLM llama a herramientas
El mecanismo fundamental: le dices al LLM qué herramientas tiene disponibles (nombre, descripción, parámetros). Cuando necesita una, devuelve una llamada estructurada en vez de texto. Tu código ejecuta la herramienta y devuelve el resultado. El LLM decide cuándo y cómo usarla.
Ciclo tool use
👤 Prompt + herramientas disponibles
→
🧠 LLM decide: ¿necesito una tool?
✅ Devuelve texto normal
← NO ←     → SÍ →
⚙️ Devuelve tool_call JSON
💻 Tu código ejecuta la función
🔄 Resultado → de vuelta al LLM
Definir herramientas con LangChain
from langchain.tools import tool
from langchain_community.chat_models import ChatOllama
from langchain.agents import AgentExecutor, create_tool_calling_agent
from langchain_core.prompts import ChatPromptTemplate

# 1. Definir las herramientas disponibles
@tool
def buscar_precio(producto: str) -> str:
  """Busca el precio actual de un producto en la BBDD."""
  precios = {"plan_pro": "29€/mes", "plan_basic": "9€/mes"}
  return precios.get(producto, "Producto no encontrado")

@tool
def crear_ticket(asunto: str, descripcion: str) -> str:
  """Crea un ticket de soporte con asunto y descripción."""
  # aquí iría tu lógica real
  return f"Ticket #{id(asunto)} creado correctamente"

# 2. Crear el agente con las herramientas
llm   = ChatOllama(model="llama3.1")
tools = [buscar_precio, crear_ticket]

prompt = ChatPromptTemplate.from_messages([
  ("system", "Eres un asistente de soporte. Usa las herramientas disponibles."),
  ("human", "{input}"),
  ("placeholder", "{agent_scratchpad}")
])

agente   = create_tool_calling_agent(llm, tools, prompt)
executor = AgentExecutor(agent=agente, tools=tools, verbose=True)

# 3. El agente decide solo qué herramienta usar
executor.invoke({"input": "¿Cuánto cuesta plan_pro y crea un ticket si es mayor a 20€"})
# → llama a buscar_precio("plan_pro") → 29€
# → llama a crear_ticket("Precio elevado", ...) ✅

▸ 2 · LangGraph — agentes con flujos controlados
LangGraph es el estándar actual para agentes complejos. A diferencia del AgentExecutor (que es un bucle libre), LangGraph te permite definir un grafo de estados: qué nodos existen, cómo se conectan y qué condiciones determinan el camino. Más control, más predecible, más robusto en producción.
Grafo de un agente LangGraph
🚀 START
→
🧠 Nodo: LLM razona
→
🔀 ¿necesita tool?
SÍ → ejecuta tool
→
🔧 Nodo: Tool
→ vuelve a LLM
NO → ha terminado
→
✅ END
Agente básico con LangGraph
from langgraph.graph import StateGraph, END
from langgraph.prebuilt import ToolNode
from langchain_community.chat_models import ChatOllama
from typing import TypedDict, Annotated
import operator

# 1. Definir el estado del grafo
class Estado(TypedDict):
  messages: Annotated[list, operator.add]

# 2. Nodo LLM
llm   = ChatOllama(model="llama3.1").bind_tools([buscar_precio, crear_ticket])
def nodo_llm(estado):
  return {"messages": [llm.invoke(estado["messages"])]}

# 3. Condición de salida
def hay_tool_call(estado):
  ultimo = estado["messages"][-1]
  return "tools" if getattr(ultimo, "tool_calls", None) else END

# 4. Construir el grafo
grafo = StateGraph(Estado)
grafo.add_node("llm",   nodo_llm)
grafo.add_node("tools", ToolNode([buscar_precio, crear_ticket]))
grafo.set_entry_point("llm")
grafo.add_conditional_edges("llm", hay_tool_call)
grafo.add_edge("tools", "llm")  # tras la tool vuelve al LLM

agente = grafo.compile()
resultado = agente.invoke({"messages": [{"role":"user", "content":"precio plan_pro"}]})

▸ Ejemplo CrewAI: equipo de agentes para investigar y redactar
Definir agentes y roles
from crewai import Agent, Task, Crew
from langchain_community.chat_models import ChatOllama
from langchain_community.tools import DuckDuckGoSearchRun

llm    = ChatOllama(model="llama3.1")
buscar = DuckDuckGoSearchRun()

# Agente 1: investigador
investigador = Agent(
  role="Investigador Senior",
  goal="Encontrar información actualizada y fiable sobre el tema",
  backstory="Experto en búsqueda y análisis de fuentes",
  tools=[buscar],
  llm=llm,
  verbose=True
)

# Agente 2: redactor
redactor = Agent(
  role="Redactor de Contenidos",
  goal="Escribir artículos claros y bien estructurados",
  backstory="Especialista en comunicación técnica",
  llm=llm
)
Definir tareas y lanzar el equipo
# Tarea 1: investigar
tarea_invest = Task(
  description="Investiga los últimos avances en LLMs locales. Busca datos concretos, modelos recientes y casos de uso.",
  expected_output="Lista de 5 puntos clave con fuentes",
  agent=investigador
)

# Tarea 2: redactar (usa el output de tarea 1)
tarea_redact = Task(
  description="Con la investigación anterior, escribe un artículo de blog de 300 palabras sobre LLMs locales.",
  expected_output="Artículo completo en markdown",
  agent=redactor,
  context=[tarea_invest]  # recibe el output del investigador
)

# Lanzar el equipo
equipo = Crew(
  agents=[investigador, redactor],
  tasks=[tarea_invest, tarea_redact],
  verbose=2
)
resultado = equipo.kickoff()
# → El investigador busca, el redactor escribe
Fine-tuning: proceso de re-entrenar un LLM ya existente con tus propios datos para que aprenda un estilo, un dominio técnico o un comportamiento específico. A diferencia de RAG (que da conocimiento externo en cada llamada), el fine-tuning "hornea" ese conocimiento directamente en los pesos del modelo. Saber cuándo usar uno u otro es una de las decisiones más importantes en IA aplicada.
▸ La pregunta clave: ¿RAG o Fine-tuning?
🔍 Usa RAG cuando...
Los datos cambian con frecuencia (FAQs, catálogos, normativas)
Necesitas transparencia: saber de qué fuente vino la respuesta
El presupuesto es limitado (no requiere GPU para entrenar)
Quieres resultados rápidos: de horas a días
El conocimiento es factual y está en documentos
Necesitas citar fuentes o mostrar el contexto recuperado
🎓 Usa Fine-tuning cuando...
Quieres cambiar el estilo o tono del modelo (más formal, más técnico, con jerga propia)
Necesitas un formato de respuesta muy específico y consistente
El modelo base no entiende tu dominio especializado (medicina, derecho, código propietario)
Tienes muchos ejemplos pares (input → output ideal) etiquetados
La latencia es crítica y no puedes añadir contexto en cada llamada
Combinas con RAG: fine-tune para el estilo, RAG para el conocimiento
🎯 La combinación ganadora
Fine-tuning + RAG juntos es la arquitectura más potente. Fine-tune para que el modelo hable con tu voz, con tu terminología y en tu formato. RAG para que tenga acceso a tu base de conocimiento actualizada. Son complementarios, no excluyentes.
▸ ¿Qué tipos de fine-tuning existen?
Técnica
Descripción y cuándo usarla
Full fine-tuning
Ajusta todos los pesos del modelo. Máxima calidad pero requiere hardware masivo (varias GPUs de 80GB) y muchos datos. Solo viable en cloud o empresa grande. No recomendado para empezar
LoRA / QLoRA
El método estándar hoy. Solo ajusta matrices pequeñas añadidas al modelo original. QLoRA lo hace además con cuantización 4-bit: puedes hacer fine-tuning de Llama 3.1 8B en una GPU de 16GB o incluso en Google Colab gratis. Recomendado para empezar
RLHF
Reinforcement Learning from Human Feedback. Los humanos puntúan respuestas y el modelo aprende a maximizar esa puntuación. Así se crean los modelos "chat" (ChatGPT, Claude). Muy complejo, para equipos especializados. Solo para labs de IA
Instruction tuning
Fine-tune con pares (instrucción → respuesta ideal). Convierte un modelo base en uno que sigue instrucciones. Es lo que hace que Llama-base se convierta en Llama-instruct. El más común en práctica
▸ Fine-tuning local con QLoRA — la forma accesible
Setup con Unsloth (el más rápido)
# Unsloth: fine-tuning 2x más rápido, 60% menos VRAM
# pip install "unsloth[colab-new] @ git+https://github.com/unslothai/unsloth.git"

from unsloth import FastLanguageModel
import torch

# Cargar modelo base con cuantización 4-bit (QLoRA)
model, tokenizer = FastLanguageModel.from_pretrained(
  model_name="unsloth/llama-3-8b-bnb-4bit",  # 5GB VRAM
  max_seq_length=2048,
  dtype=None,
  load_in_4bit=True,
)

# Añadir adaptadores LoRA (solo estos pesos se entrenan)
model = FastLanguageModel.get_peft_model(
  model,
  r=16,              # rango LoRA (8-64)
  target_modules=["q_proj", "k_proj", "v_proj"],
  lora_alpha=16,
  lora_dropout=0,
)
# → Solo ~0.1% de los parámetros se entrenan
# → El modelo base queda intacto (guardado separado)
Datos y entrenamiento
from datasets import Dataset
from trl import SFTTrainer
from transformers import TrainingArguments

# Formato de datos: pares instrucción → respuesta
datos = [
  {"text": """### Instrucción:
Responde en el tono formal de AcmeCorp.
¿Cuál es la política de devoluciones?

### Respuesta:
Estimado cliente, conforme a nuestra política
comercial vigente, las devoluciones se aceptan
dentro de un plazo máximo de 30 días naturales..."""},
  # ... cientos o miles de ejemplos más
]

dataset = Dataset.from_list(datos)

# Entrenar
trainer = SFTTrainer(
  model=model,
  tokenizer=tokenizer,
  train_dataset=dataset,
  dataset_text_field="text",
  args=TrainingArguments(
    per_device_train_batch_size=2,
    num_train_epochs=3,
    output_dir="./modelo_ft",
  )
)
trainer.train()
# → Guarda adaptadores LoRA (~50MB)
# → Carga sobre el modelo base cuando quieras
▸ Herramientas para hacer fine-tuning
🦥 Unsloth
La forma más accesible hoy. Fine-tuning 2x más rápido que HuggingFace con 60% menos de VRAM. Soporta Llama 3, Mistral, Phi, Qwen. Funciona en Google Colab gratis.
Empieza aquí. Tiene notebooks listos para usar.
RecomendadoColab gratuito
🤗 HuggingFace PEFT + TRL
La librería estándar. PEFT para LoRA, TRL para instruction tuning con SFTTrainer. Más control, más complejo. Unsloth usa estas librerías por debajo.
Cuando necesitas más personalización que Unsloth.
Estándar
🔥 Axolotl
Fine-tuning configurable vía YAML. Solo defines un fichero de configuración y lanza el entrenamiento. Muy usado por la comunidad para fine-tuning serio.
Cuando quieres reproducibilidad y configuración declarativa.
YAML-drivenOpen source
☁️ OpenAI / Together AI
Fine-tuning cloud con UI. Subes tus datos en formato JSONL y ellos entrenan. Sin configurar nada. OpenAI fine-tune de GPT-3.5/4o. Together AI para modelos open source.
Cuando no quieres gestionar infraestructura ni GPUs.

🗺 El mapa de decisión completo

¿El modelo no sabe cosas que están en documentos? → RAG. ¿El modelo no habla con tu estilo? → Fine-tuning. ¿Necesitas que el modelo tome acciones autónomas? → Agente. ¿Quieres privacidad total y sin coste? → Todo lo anterior pero local. La mayoría de aplicaciones reales del mundo empresarial combinan los cuatro.
