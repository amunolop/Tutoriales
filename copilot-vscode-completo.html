✅ Todo esto se versiona como código
Estos archivos van en tu repositorio Git, se revisan en PR y se comparten con tu equipo — no son configuración personal escondida en ajustes de la aplicación. Esa es la clave de por qué escalan bien en un equipo.
PUESTA EN MARCHA — 15 MINUTOS
Instala la extensión GitHub Copilot desde el Marketplace de VS Code e inicia sesión desde la barra de estado.
Abre Copilot Chat y ejecuta /init. Genera automáticamente un .github/copilot-instructions.md a partir de las convenciones reales de tu proyecto (no un genérico) — revísalo y ajústalo a mano.
Añade al menos un servidor MCP para que el agente pueda usar herramientas reales, no solo generar texto (lo ves en detalle en la pestaña 🔌 MCP).
Cambia el desplegable de modo del chat de Ask a Agent, elige el modelo que prefieras, y ya tienes tareas multi-paso ejecutándose de principio a fin.
Con esto, en menos de 15 minutos, Copilot deja de ser autocompletado de una línea y pasa a ser un asistente que conoce tus convenciones, tiene herramientas reales y actúa de forma autónoma.
EL EDITOR UNIFICADO — UN SOLO SITIO PARA LOS 4
Comando: Chat: Open Customizations (Command Palette). Abre el Agent Customizations editor, con pestañas separadas para Instructions, Prompts, Agents y Skills — puedes crear, editar y ver todos tus archivos de configuración desde un único sitio, sin ir carpeta por carpeta.

CUSTOM INSTRUCTIONS — SIEMPRE ACTIVAS
Markdown plano, sin frontmatter obligatorio. Se genera con /init o se crea a mano. Se aplica en cada chat y cada sugerencia dentro de ese proyecto. 
# .github/copilot-instructions.md

# Estándares del proyecto

## Reglas generales
- Usa TypeScript para todo el código nuevo
- Prioriza composición sobre herencia
- Documenta las APIs públicas con JSDoc

## Tests
- Framework: Jest
- Cobertura mínima: 80%
- Todo endpoint nuevo necesita test de integración
INSTRUCTIONS CON ÁMBITO — SOLO PARA CIERTOS ARCHIVOS
El campo applyTo es obligatorio y usa sintaxis glob. Si lo omites, el archivo no hace nada. Cuando varios .instructions.md coinciden a la vez (por ejemplo un .tsx dentro de src/api/), Copilot combina todas las capas que apliquen. 
# .github/instructions/security.instructions.md
---
applyTo: "src/api/**"
description: "Reglas de seguridad para el backend"
---

Valida siempre la entrada del usuario antes de usarla en una query.
Nunca construyas SQL con concatenación de strings — usa siempre
parámetros preparados. Registra los errores con logging estructurado,
nunca con print().
PROMPT FILES — REUTILIZABLES, BAJO DEMANDA
Se invocan escribiendo /nombre-del-archivo en el chat. Admiten variables como ${file}, ${selection} o ${input:variable} para pedirte un dato antes de ejecutarse. El frontmatter soporta estos campos: agent (qué modo/agente lo ejecuta: ask, agent, plan, o el nombre de un agente personalizado), description, model, name, tools y argument-hint. No existe un campo mode — es un error habitual heredado de versiones antiguas de la documentación. 
# .github/prompts/generar-tests.prompt.md
---
agent: agent
description: "Genera tests unitarios para el archivo seleccionado"
---

Genera tests unitarios con Jest para ${file}, cubriendo:
- El caso feliz
- Al menos dos casos límite (valores nulos, vacíos o negativos)
- Un caso de error esperado

Sigue el estilo de test ya existente en el proyecto.
✅ El mismo truco de "decisión + contexto + resultado esperado"
Un prompt file vago ("genera tests") da resultados mediocres. Uno específico como el de arriba — con casos concretos a cubrir — es lo que marca la diferencia entre un test superficial y uno útil.

FORMATO Y UBICACIÓN
Una skill vive en .github/skills/<nombre-skill>/SKILL.md (proyecto) o ~/.copilot/skills/ (personal, reutilizable entre proyectos). El frontmatter exige name y description — la description es lo que Copilot lee para decidir si esa skill es relevante para tu petición. 
# .github/skills/api-conventions/SKILL.md
---
name: api-conventions
description: >-
  Usa esta skill cuando el usuario cree o modifique un endpoint REST.
  Aplica las convenciones de nombrado, versionado y manejo de errores
  del equipo.
---

## Procedimiento
1. Prefija toda ruta nueva con /api/v1/
2. Usa códigos de estado HTTP estándar — nunca 200 con un error en el body
3. Todo error de validación devuelve {"error": {"code", "message"}}
4. Añade el endpoint a docs/api-reference.md
PROGRESSIVE DISCLOSURE — POR QUÉ NO SATURA EL CONTEXTO
L1 · Discoverysolo name + description
→
L2 · Instruccionesel cuerpo del SKILL.md
→
L3 · Recursosscripts/referencias, solo si hacen falta
Copilot solo carga el name+description de todas las skills instaladas por defecto (barato en tokens). El cuerpo completo del SKILL.md solo se carga cuando decide que esa skill es relevante para la tarea. Los archivos de referencia o scripts que la skill mencione solo se leen si de verdad hacen falta. Por eso puedes tener decenas de skills instaladas sin saturar el contexto.

AcciónCómo

✅ No tienes que escribir SKILL.md desde cero
Anthropic publica skill-creator, una skill de referencia (en github.com/anthropics/skills) que funciona igual en Copilot: le pides "crea una nueva skill" y te hace preguntas guiadas hasta generar la estructura completa por ti.
Regla práctica: mantén el SKILL.md por debajo de 500 líneas. Si necesitas más detalle, muévelo a una carpeta references/ dentro de la skill — así solo se carga cuando de verdad se usa (nivel L3).

AGENT MODE — EL MODO GENERAL
El desplegable de Copilot Chat tiene actualmente tres modos: Ask (solo responde, no toca archivos), Plan (analiza y propone un plan de implementación antes de tocar nada, útil para tareas grandes), y Agent (inspecciona el workspace, edita, ejecuta comandos de terminal, corre tests, lee errores y se auto-corrige hasta terminar). El antiguo modo Edit —que proponía cambios en varios archivos seleccionados a mano— ha quedado absorbido dentro de Agent: si ves documentación que aún lo menciona como modo independiente, está desactualizada.
AGENTES PERSONALIZADOS — .AGENT.MD
Un agente personalizado es una persona con nombre, con su propia lista de herramientas permitidas y, opcionalmente, un modelo preferido. Vive en .github/agents/<nombre>.agent.md (compartido con el equipo) o a nivel de usuario (personal). 
# .github/agents/code-reviewer.agent.md
---
name: code-reviewer
description: "Revisa PRs contra los estándares del equipo, sin modificar código"
tools: ['search', 'read']
---

Eres un revisor de código senior para este equipo.

Cuando te invoquen:
1. Inspecciona los archivos modificados antes de opinar
2. Busca: secretos hardcodeados, riesgos de inyección,
   validación de entrada ausente, tests que faltan
3. Clasifica cada hallazgo: crítico / aviso / sugerencia
4. No modifiques archivos salvo que se te pida explícitamente
Si omites tools, el agente tiene acceso a todas las herramientas — hazlo solo cuando de verdad las necesite todas (por ejemplo, un agente de testing que debe leer código, escribir tests, ejecutar el build y correr los tests). Si omites model, el usuario elige el modelo desde el selector.
ENCADENAR AGENTES — HANDOFFS
# .github/agents/plan.agent.md
---
description: "Genera un plan de implementación"
tools: ['search', 'web']
handoffs:
  - label: "Empezar implementación"
    agent: implementation
    prompt: "Implementa ahora el plan descrito arriba."
    send: false
---

Genera un plan de implementación detallado antes de escribir código.
Cuando el usuario ve el botón de handoff y lo pulsa, cambia al agente implementation con el prompt ya rellenado. Con send: true se enviaría automáticamente sin esperar confirmación.
DEPURAR UN AGENTE QUE FALLA
⚠️ Cuando el agente hace algo raro
Abre el menú ··· del panel de chat → Show Chat Debug View. Verás el system prompt completo que recibió, el contexto exacto enviado al modelo, y cada llamada a herramienta que hizo — es la forma más rápida de entender por qué se desvió.

EL ARCHIVO DE CONFIGURACIÓN
Se define en .vscode/mcp.json (por proyecto) o en el perfil de usuario (global, para todos tus workspaces). Cada servidor puede ser de tipo stdio (proceso local), http o sse (remoto). 
// .vscode/mcp.json
{
  "inputs": [
    {
      "type": "promptString",
      "id": "github_token",
      "description": "GitHub Personal Access Token",
      "password": true
    }
  ],
  "servers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp"
    },
    "filesystem-local": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem"]
    }
  }
}
⚠️ Nunca hardcodees claves en el JSON
Usa el bloque inputs con ${input:id} como referencia dentro de env — VS Code te pedirá el valor una vez, de forma enmascarada (password: true), y no queda escrito en texto plano en el repositorio.

SERVIDORES HABITUALES EN DESARROLLO
GitHub
Issues, PRs, repos — remoto en https://api.githubcopilot.com/mcp, sin instalar nada local.
Filesystem
Acceso controlado a archivos fuera del workspace actual.
Playwright
Automatización de navegador — útil para que el agente verifique un cambio de UI por sí mismo.
Bases de datos
Consultar esquemas y datos reales sin salir del chat.
✅ Portabilidad real
La mayoría de servidores MCP construidos para Claude Code funcionan igual aquí — es el mismo protocolo. VS Code incluso puede autodescubrir servidores ya configurados en Claude Desktop si activas chat.mcp.discovery.enabled.
Gobernanza en empresa: los administradores pueden fijar una lista de servidores MCP permitidos a nivel de organización — si trabajas en UST, es probable que esa política ya exista o se defina pronto.

EJEMPLO END-TO-END: AÑADIR UN ENDPOINT NUEVO
Base siempre activa: copilot-instructions.md ya define que usas TypeScript, Jest y JSDoc — Copilot lo aplica sin que se lo pidas.
Prompt file: escribes /generar-endpoint y te pide el nombre del recurso (${input:recurso}).
Skill auto-detectada: como la tarea es "crear un endpoint REST", Copilot carga solo, sin que lo invoques, la skill api-conventions con tus reglas de versionado y manejo de errores.
Agent mode actúa: crea el archivo de la ruta, el controlador, el test, ejecuta npm test, lee el fallo si lo hay, y corrige — todo en el mismo turno.
MCP de GitHub: antes de terminar, consulta el issue original para verificar que no falta ningún requisito mencionado allí.
Handoff opcional: al terminar, ofrece un botón para pasar el resultado al agente code-reviewer y hacer una segunda pasada antes de abrir el PR.
BUENAS PRÁCTICAS
Mínimo privilegio en agentes
No des tools ilimitadas a un agente que solo necesita leer código. El mismo principio de seguridad que ya viste en el examen CCDV-F.
copilot-instructions.md ligero
Se carga siempre, en cada request. Cuanto más grande, más contexto consume de fondo — mueve reglas específicas de un path a un .instructions.md con applyTo.
Un servidor MCP a la vez
Empieza con uno bien acotado antes de conectar varios — cada servidor es una superficie de acceso real a un sistema.
Versiona todo esto en Git
Instructions, agentes, skills y mcp.json son código de equipo — revísalos en PR igual que revisarías cualquier otro cambio.
