Definition

Workflow vs Agent — Decision Criteria

Fixed orchestration paths vs LLM-driven autonomous decision-making

Workflow
A fixed, predetermined orchestration path where every step is defined at design time. The developer controls which models are called, in what order, with which inputs. Claude executes each step but does NOT decide what to do next. Think pipeline: step A → step B → step C, always in that order.
Agent
An LLM-driven autonomous system where Claude decides what action to take next based on the current state. The model controls the flow — it chooses which tools to call, how many iterations to run, and when to stop. The developer defines the tools and constraints; the model drives execution.

4 Decision Criteria

CriterionWorkflowAgent
Path predetermined?Yes — every step defined at design timeNo — path depends on model's observations
Number of steps fixed?Yes — same steps every executionNo — could be 1 step or 15 depending on task
Model decides next action?No — developer's code routes each stepYes — model selects tools and actions
Cost predictable?Yes — fixed API calls = predictable costNo — variable iterations = variable cost
The exam tests this distinction directly. If ALL 4 answers are "fixed/predetermined/yes" → Workflow. If ANY answer is "variable/model-decides" → Agent. There is no hybrid middle ground on the exam.

Manager/Supervisor Hierarchies

In complex systems, a manager agent delegates subtasks to worker subagents. The manager decides what to delegate and coordinates results. Workers execute focused tasks with scoped tools. This is the orchestrator-workers pattern.

Workflow Code Pattern

# Workflow: Fixed pipeline — developer controls flow

translation = claude("Translate to French", summary)
quality = claude("Rate translation quality 1-10", translation)
# Always 3 steps, always in this order

Agent Code Pattern

# Agent: Model-driven loop — Claude decides flow
while True:
    response = claude(messages, tools=tools)
    if response.stop_reason == "end_turn":
        break  # Claude decided it's done
    # Execute tool calls, append results, continue
    messages.append(execute_tools(response))

Certification Focus

Workflow vs Agent — Exam Patterns

#1 — "Which orchestration pattern?": The exam describes a scenario and asks which pattern to use. Map: fixed steps → prompt chaining/routing. Variable steps, model decides → orchestrator-workers. Independent subtasks → parallelisation (fan-out/fan-in).
#2 — Fan-Out/Fan-In: Only use when subtasks are genuinely independent. If task B depends on task A's result, parallelisation is wrong — use prompt chaining.
#3 — Subagent Role: Subagents improve task execution by focusing on narrow subtasks with scoped tools. They do NOT communicate with each other directly — all communication flows through the coordinator/manager.
Trap: "Agent for everything": The exam often presents simple tasks where a workflow is the correct answer. A 3-step translation pipeline does NOT need an agent — it needs prompt chaining. Over-engineering with agents is a wrong answer.

Agent SDK & Construction Methods

Three ways to build Claude agents — SDK, custom loops, and managed platforms

Three Construction Approaches

ApproachWhat It IsWhen to Use
Claude Agent SDKAnthropic's official Python framework. Provides Agent class with built-in tool management, guardrails, handoffs, and tracing.Most production use cases — handles the loop, error recovery, and observability for you.
Custom Agent LoopRaw Messages API in a while loop. You control every aspect: tool execution, error handling, context management.When you need full control — custom retry logic, non-standard tool patterns, or the SDK doesn't support your architecture.
Managed DeploymentAnthropic-hosted or self-hosted agent infrastructure. Managed handles scaling, versioning, and monitoring.Enterprise production — when you need SLAs, scaling, and operational monitoring without building infra yourself.

SDK vs Custom Loop — Key Difference

SDK: The framework handles the agentic loop internally. You configure agent behaviour (tools, guardrails, handoffs). Custom Loop: You write the loop yourself — checking stop_reason, executing tools, appending results. The SDK is higher-level; the custom loop gives full control.

    name="support_agent",

Hooks for Deterministic Actions

Hooks provide deterministic enforcement within SDK agents:

  • PreToolUse — fires before a tool executes. Return block to prevent execution. Use for policy enforcement, input validation.
  • PostToolUse — fires after a tool returns. Use for output sanitisation, logging, data normalisation.
  • Guardrails — SDK-level constraints that check every turn. Block PII exposure, enforce identity verification, prevent dangerous actions.
Hooks are deterministic; prompts are probabilistic. If a rule MUST be enforced 100% of the time, it goes in a hook. If it's a preference, it goes in the system prompt.

Certification Focus

Agent Construction — Exam Patterns

#1 — SDK vs Custom Loop: "Which approach gives the developer the MOST control?" → Custom loop. "Which approach handles the loop, tracing, and guardrails automatically?" → Agent SDK. Know the trade-off: SDK = less code, less control. Custom = more code, full control.
#2 — Hooks vs System Prompt: "Agent must NEVER process refunds without identity verification" → Hook (PreToolUse that blocks). "Agent should prefer formal tone" → System prompt. The keyword is MUST vs SHOULD.
#3 — max_turns: A safety parameter that caps the number of loop iterations. It's a safety net, NOT the primary termination mechanism. The primary mechanism is stop_reason: end_turn.
#4 — Handoffs in SDK: When one agent transfers control to another. The handoff includes context about what was done and what needs to happen next. The receiving agent starts fresh — it does NOT inherit the sending agent's conversation history unless explicitly passed.

Agentic Loop Patterns

Tool-use loops, stop_reason control, and error recovery

The Agentic Loop
The core pattern: (1) Send messages + tools to Claude, (2) Check stop_reason, (3) If tool_use → execute tool, append result, loop back to step 1, (4) If end_turn → exit loop, return response. The loop runs until Claude decides it's finished.

stop_reason Values

ValueMeaningAction
end_turnClaude finished its responseSTOP — exit the loop
tool_useClaude wants to call a toolCONTINUE — execute tool, append result, loop
max_tokensResponse hit the token limitHandle truncation — may need to continue
pause_turnModel paused for external inputWait for input, then resume
stop_reason is the ONLY reliable termination signal. Never parse text content ("I'm done") to determine if the loop should end. Never use content[0].type == "text" — Claude can return text alongside tool_use blocks.

Error Recovery & Graceful Degradation

Error Recovery Strategies

StrategyWhen to UseImplementation
Retry with backoffTransient failures (network, rate limits)Exponential backoff: 1s, 2s, 4s, max 3 retries
Fallback to simpler strategyComplex tool fails repeatedlyTry tool A → fail → try simpler tool B
Graceful degradationPartial failure in multi-step taskReturn available results, report what's missing
Human escalationAgent cannot progressStructured handoff with context summary

The isError Flag

When returning tool results to Claude, the is_error field tells the model the tool failed. Without it, Claude may interpret error text as a normal result and incorporate error messages into its response.

# WRONG — error text treated as content
{"type": "tool_result", "content": "Error: timeout"}

# CORRECT — flagged as error
{"type": "tool_result",
 "content": "Error: timeout after 30s",
 "is_error": true}
Certification Focus

Loop Patterns — Exam Patterns

#1 — Three Anti-Patterns: (A) Parsing "I'm done" from text → unreliable. (B) Arbitrary iteration caps as PRIMARY control → wrong (OK as safety net). (C) Checking content[0].type == "text" → Claude can return text AND tool_use together.
#2 — is_error Flag: When asked "tool returns an error — what happens next?" the correct answer always involves is_error: true in the tool result, so Claude knows the execution failed.
#3 — Retry vs Escalate: Transient errors (network) → retry with backoff. Persistent errors (tool doesn't exist, permission denied) → escalate or fail gracefully. The exam tests whether you can distinguish transient from persistent.
#4 — tool_choice: "auto" = Claude may call a tool or not. "any" = Claude MUST call a tool. {"type":"tool","name":"X"} = forced specific tool. Forcing "any" when the agent is genuinely finished creates infinite loops.

Multi-Agent Context Rules

Two rules that apply regardless of framework:

  • Subagents do NOT inherit the coordinator's conversation history — context must be explicitly passed.
  • Subagents do NOT share memory between invocations — each call starts fresh.

Multi-Agent Topologies

Hierarchical vs Peer-to-Peer

TopologyHow It WorksWhen to Use
HierarchicalManager delegates to workers. All communication goes through manager.Clear task decomposition, need coordination and result synthesis.

Context Window Management in Agents

Long-running agents face context window limits. Management strategies:

  • Progressive summarisation — compress earlier turns while preserving exact values (amounts, IDs)
  • /compact — Claude Code's built-in compaction that preserves key facts
  • Scratchpad files — write intermediate results to disk, read back when needed
  • Memory via tools — use a memory tool to store and retrieve key facts across turns

Frameworks — Exam Patterns

#1 — Framework Selection: "Need AWS-native managed agents" → Strands. "Need graph-based state machine with branching" → LangGraph. "Need type-safe validated agents" → PydanticAI. "Need Anthropic-native with built-in guardrails" → Claude Agent SDK.
#2 — Context Isolation: "New subagent ignores instructions given to the coordinator" → Context was not explicitly passed. Subagents start with empty context unless the coordinator includes relevant information.
#3 — Handoff vs Message-Passing: Handoffs transfer CONTROL (one agent stops, another starts). Message-passing shares DATA (both agents continue). The exam tests whether you match the mechanism to the need.
Trap: "Framework X is always better": No framework is universally best. Each has trade-offs. The correct answer matches framework capabilities to specific requirements.

Definición

Flujo de Trabajo vs Agente — Criterios de Decisión

Rutas de orquestación fijas vs toma de decisiones autónoma impulsada por el LLM

Flujo de Trabajo
Una ruta de orquestación fija y predeterminada donde cada paso se define en tiempo de diseño. El desarrollador controla qué modelos se llaman, en qué orden y con qué entradas. Claude ejecuta cada paso pero NO decide qué hacer a continuación. Piensa en una tubería: paso A → paso B → paso C, siempre en ese orden.
Agente
Un sistema autónomo impulsado por el LLM donde Claude decide qué acción tomar a continuación según el estado actual. El modelo controla el flujo — elige qué herramientas llamar, cuántas iteraciones ejecutar y cuándo detenerse. El desarrollador define las herramientas y las restricciones; el modelo dirige la ejecución.

4 Criterios de Decisión

CriterioFlujo de TrabajoAgente
¿Ruta predeterminada?Sí — cada paso definido en tiempo de diseñoNo — la ruta depende de las observaciones del modelo
¿Número de pasos fijo?Sí — los mismos pasos en cada ejecuciónNo — podría ser 1 paso o 15 según la tarea
¿El modelo decide la siguiente acción?No — el código del desarrollador dirige cada pasoSí — el modelo selecciona herramientas y acciones
¿Coste predecible?Sí — llamadas API fijas = coste predecibleNo — iteraciones variables = coste variable
El examen evalúa esta distinción directamente. Si las 4 respuestas son "fijo/predeterminado/sí" → Flujo de Trabajo. Si CUALQUIER respuesta es "variable/el modelo decide" → Agente. No hay término medio híbrido en el examen.

Jerarquías Manager/Supervisor

En sistemas complejos, un agente manager delega subtareas a subagentes trabajadores. El manager decide qué delegar y coordina los resultados. Los trabajadores ejecutan tareas concretas con herramientas acotadas. Este es el patrón orquestador-trabajadores.

Flujo de Trabajo vs Agente — Patrones de Examen

#1 — "¿Qué patrón de orquestación?": El examen describe un escenario y pregunta qué patrón usar. Mapeo: pasos fijos → encadenamiento de prompts/enrutamiento. Pasos variables, el modelo decide → orquestador-trabajadores. Subtareas independientes → paralelización (fan-out/fan-in).
#2 — Fan-Out/Fan-In: Solo úsalo cuando las subtareas son genuinamente independientes. Si la tarea B depende del resultado de la tarea A, la paralelización es incorrecta — usa encadenamiento de prompts.
#3 — Rol del Subagente: Los subagentes mejoran la ejecución de tareas centrándose en subtareas concretas con herramientas acotadas. NO se comunican entre sí directamente — toda la comunicación pasa por el coordinador/manager.
Trampa: "Un agente para todo": El examen a menudo presenta tareas sencillas donde un flujo de trabajo es la respuesta correcta. Una tubería de traducción de 3 pasos NO necesita un agente — necesita encadenamiento de prompts. Sobreingeniería con agentes es una respuesta incorrecta.

SDK vs Bucle Personalizado — Diferencia Clave

SDK: El framework gestiona el bucle agéntico internamente. Tú configuras el comportamiento del agente (herramientas, guardarrailes, traspasos). Bucle Personalizado: Escribes el bucle tú mismo — comprobando stop_reason, ejecutando herramientas, añadiendo resultados. El SDK es de más alto nivel; el bucle personalizado da control total.

Hooks para Acciones Deterministas

Los hooks proporcionan aplicación determinista dentro de los agentes del SDK:

  • PreToolUse — se dispara antes de que se ejecute una herramienta. Devuelve block para impedir la ejecución. Útil para aplicar políticas y validar entradas.
  • PostToolUse — se dispara después de que una herramienta devuelva un resultado. Útil para sanear la salida, registrar logs, normalizar datos.
  • Guardrails — restricciones a nivel de SDK que se comprueban en cada turno. Bloquean la exposición de PII, obligan a verificar la identidad, previenen acciones peligrosas.
Los hooks son deterministas; los prompts son probabilísticos. Si una regla DEBE cumplirse el 100% de las veces, va en un hook. Si es una preferencia, va en el prompt del sistema.

Construcción de Agentes — Patrones de Examen

#1 — SDK vs Bucle Personalizado: "¿Qué enfoque da al desarrollador MÁS control?" → Bucle personalizado. "¿Qué enfoque gestiona el bucle, la trazabilidad y los guardarrailes automáticamente?" → Agent SDK. Conoce el compromiso: SDK = menos código, menos control. Personalizado = más código, control total.
#2 — Hooks vs Prompt del Sistema: "El agente NUNCA debe procesar reembolsos sin verificación de identidad" → Hook (PreToolUse que bloquea). "El agente debería preferir un tono formal" → Prompt del sistema. La palabra clave es DEBE frente a DEBERÍA.
#3 — max_turns: Un parámetro de seguridad que limita el número de iteraciones del bucle. Es una red de seguridad, NO el mecanismo principal de terminación. El mecanismo principal es stop_reason: end_turn.
#4 — Traspasos (Handoffs) en el SDK: Cuando un agente transfiere el control a otro. El traspaso incluye contexto sobre lo que se hizo y lo que hay que hacer a continuación. El agente receptor empieza de cero — NO hereda el historial de conversación del agente emisor a menos que se le pase explícitamente.

Patrones del Bucle Agéntico

Bucles de uso de herramientas, control de stop_reason y recuperación ante errores

El Bucle Agéntico
El patrón central: (1) Enviar mensajes + herramientas a Claude, (2) Comprobar stop_reason, (3) Si es tool_use → ejecutar la herramienta, añadir el resultado, volver al paso 1, (4) Si es end_turn → salir del bucle, devolver la respuesta. El bucle se ejecuta hasta que Claude decide que ha terminado.

Valores de stop_reason

ValorSignificadoAcción
end_turnClaude terminó su respuestaDETENER — salir del bucle
tool_useClaude quiere llamar a una herramientaCONTINUAR — ejecutar la herramienta, añadir el resultado, repetir
max_tokensLa respuesta alcanzó el límite de tokensGestionar el truncamiento — puede que haga falta continuar
pause_turnEl modelo se pausó esperando una entrada externaEsperar la entrada y luego reanudar
stop_reason es la ÚNICA señal fiable de terminación. Nunca analices el contenido de texto ("He terminado") para decidir si el bucle debe acabar. Nunca uses content[0].type == "text" — Claude puede devolver texto junto a bloques tool_use.

Recuperación ante Errores y Degradación Elegante

Estrategias de Recuperación ante Errores

EstrategiaCuándo UsarlaImplementación
Reintento con backoffFallos transitorios (red, límites de tasa)Backoff exponencial: 1s, 2s, 4s, máximo 3 reintentos
Recurrir a una estrategia más simpleUna herramienta compleja falla repetidamenteProbar herramienta A → falla → probar herramienta B más simple
Degradación eleganteFallo parcial en una tarea de varios pasosDevolver los resultados disponibles, informar de lo que falta
Escalado a humanoEl agente no puede progresarTraspaso estructurado con resumen de contexto

El Indicador isError

Al devolver resultados de herramientas a Claude, el campo is_error indica al modelo que la herramienta falló. Sin él, Claude puede interpretar el texto de error como un resultado normal e incorporar los mensajes de error en su respuesta.

# INCORRECTO — el texto de error se trata como contenido
{"type": "tool_result", "content": "Error: timeout"}

# CORRECTO — marcado como error
{"type": "tool_result",
 "content": "Error: timeout after 30s",
 "is_error": true}
Enfoque de Certificación

Patrones del Bucle — Patrones de Examen

#1 — Tres Antipatrones: (A) Analizar "He terminado" del texto → poco fiable. (B) Límites de iteración arbitrarios como control PRINCIPAL → incorrecto (vale como red de seguridad). (C) Comprobar content[0].type == "text" → Claude puede devolver texto Y tool_use juntos.
#2 — Indicador is_error: Cuando se pregunta "una herramienta devuelve un error — ¿qué pasa después?" la respuesta correcta siempre implica is_error: true en el resultado de la herramienta, para que Claude sepa que la ejecución falló.
#3 — Reintentar vs Escalar: Errores transitorios (red) → reintentar con backoff. Errores persistentes (la herramienta no existe, permiso denegado) → escalar o fallar con elegancia. El examen evalúa si sabes distinguir lo transitorio de lo persistente.
#4 — tool_choice: "auto" = Claude puede llamar a una herramienta o no. "any" = Claude DEBE llamar a una herramienta. {"type":"tool","name":"X"} = herramienta específica forzada. Forzar "any" cuando el agente realmente ha terminado crea bucles infinitos.

Reglas de Contexto Multiagente

Dos reglas que se aplican independientemente del framework:

  • Los subagentes NO heredan el historial de conversación del coordinador — el contexto debe pasarse explícitamente.
  • Los subagentes NO comparten memoria entre invocaciones — cada llamada empieza de cero.

Topologías Multiagente

Jerárquica vs Punto a Punto

TopologíaCómo FuncionaCuándo Usarla
JerárquicaEl manager delega a los trabajadores. Toda la comunicación pasa por el manager.Descomposición de tareas clara, se necesita coordinación y síntesis de resultados.
Punto a PuntoLos agentes se comunican directamente entre sí mediante paso de mensajes.Tareas colaborativas donde los agentes negocian o construyen sobre el trabajo del otro.

Gestión de la Ventana de Contexto en Agentes

Los agentes de larga duración se enfrentan a límites de ventana de contexto. Estrategias de gestión:

  • Resumen progresivo — comprime turnos anteriores conservando los valores exactos (importes, IDs)
  • /compact — la compactación integrada de Claude Code que conserva los datos clave
  • Archivos de bloc de notas — escribe resultados intermedios en disco, léelos de vuelta cuando haga falta
  • Memoria mediante herramientas — usa una herramienta de memoria para guardar y recuperar datos clave entre turnos

Frameworks — Patrones de Examen

#1 — Selección de Framework: "Necesito agentes gestionados nativos de AWS" → Strands. "Necesito una máquina de estado basada en grafos con ramificación" → LangGraph. "Necesito agentes con seguridad de tipos validados" → PydanticAI. "Necesito algo nativo de Anthropic con guardarrailes integrados" → Claude Agent SDK.
