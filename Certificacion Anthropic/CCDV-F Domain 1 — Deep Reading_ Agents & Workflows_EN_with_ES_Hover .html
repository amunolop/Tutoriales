The Core Distinction — Workflow vs Agent

Concept 1 — The single most-tested architectural decision in Domain 1

Exam Frequency:
Very High
Workflows vs Agents
Anthropic draws one architectural line and builds everything on it. Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents are systems where the LLM dynamically directs its own process and tool usage, maintaining control over how it accomplishes the task.

When (and When Not) to Build an Agent

Anthropic's guidance is explicit: find the simplest solution possible and only increase complexity when it demonstrably improves outcomes. Many use cases need just a single well-prompted LLM call with retrieval and in-context examples — not an agent.

Golden rule: Workflows offer predictability and consistency for well-defined tasks; agents are the better option when flexibility and model-driven decision-making are needed at scale. Agents trade latency and cost for adaptability — make that trade deliberately.
✗ Common Misconception

"If the task is complex, always use an agent — agents handle everything better."

✓ What the Exam Rewards

Use the simplest architecture that solves the problem. If a workflow works, don't build an agent. Agents add power but also unpredictability, variable cost, and debugging complexity.

The Five Workflow Patterns

Before reaching for a full agent, Anthropic identifies five composable workflow patterns along the autonomy spectrum:

PatternHow It WorksWhen to Use
Prompt ChainingFixed sequential steps; each output feeds the next, with validation gates.Document processing, ETL-style pipelines
RoutingClassify the input, then send it to a specialised handler.Email triage, ticket classification
ParallelisationRun independent subtasks concurrently (sectioning / voting), then aggregate.Multi-section analysis, guardrail voting
Orchestrator-WorkersA lead model dynamically decomposes the task and delegates to workers.Complex research, multi-file refactors
Evaluator-OptimizerOne call generates, another evaluates and gives feedback, looping until quality is met.Translation, iterative writing/refinement

On frameworks, Anthropic notes the Claude Agent SDK, Strands (AWS) and GUI builders help you start fast — but warns they add abstraction layers that can obscure prompts and complicate debugging. Learn the primitives first; adopt a framework second.

Choosing the Pattern

The decision criteria the exam tests — pick the minimum viable architecture

Decision Criteria: Workflow or Agent?

Criterion→ Workflow→ Agent
Path predictabilitySteps known at design timeSteps depend on intermediate results
Decision authorityYour code decides the next stepClaude decides the next step
AuditabilityFully traceable — code controls branchesHarder — Claude's reasoning drives the path
Cost predictabilityPredictable token usageVariable — 3 or 30 tool calls
ComplexityFewer than ~5 well-defined stepsOpen-ended, steps unpredetermined
Exam Language Cue: "the same steps every time" or "predetermined path" → workflow. "depends on what Claude discovers" or "cannot be determined in advance" → agent.

Agent SDK & Construction

Concept 2 — Building production agents with the Claude Agent SDK

Exam Frequency:
High
Claude Agent SDK
The SDK gives you the same tools, agent loop and context management that power Claude Code — programmable in Python and TypeScript. It handles the loop (call the model, run tools, feed results back), built-in tools for reading files / running commands / editing code, and permissions via an allowed_tools allow-list.

The Minimal Agent

import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions

async def main():
    async for message in query(
        prompt="Find and fix the bug in auth.py",
        options=ClaudeAgentOptions(allowed_tools=["Read","Edit","Bash"]),
    ):
        print(message)
asyncio.run(main())
Auth flexibility: the SDK works with the Claude API directly or via Amazon Bedrock, Google Vertex and Microsoft Foundry — the "managed vs self-hosted deployment" angle the exam likes.

The Design Philosophy — "Give Your Agent a Computer"

Rather than hand-wiring every tool, the SDK gives Claude a general-purpose environment (file access, shell, code editing) and lets it operate the way a developer would. The loop it runs for you:

  • Gather context — pull in files, search results and prior state
  • Take action — call tools / run commands
  • Verify work — check results, self-correct
  • Repeat until the task is complete

Hooks and guardrails let you enforce hard rules (things that MUST happen every time) around a probabilistic model. This "hook vs system-prompt" distinction — deterministic enforcement vs soft guidance — is a recurring exam theme.

SDK vs Custom Loop

The trade-off the exam tests — and where the official SDK repo helps

When to Use the SDK vs Hand-Writing the Loop

✗ Over-Engineering

Hand-writing the entire agentic loop, session store, and tool plumbing for a standard file/command/edit agent.

✓ Use the SDK

The SDK already implements the loop, built-in tools, context management and permissions. Reach for a custom loop only when you need control the SDK doesn't expose.

The official claude-agent-sdk-python repo bundles the Claude Code CLI automatically and ships runnable examples (email assistant, research agent) plus reference session-store adapters (S3, Redis, Postgres).

# pip install claude-agent-sdk   (Python 3.10+)
import anyio
from claude_agent_sdk import query

async def main():
    async for message in query(prompt="What is 2 + 2?"):
        print(message)
anyio.run(main)
Exam link: reading these examples shows the SDK doing the loop for you — the contrast with a hand-written while loop is exactly the "SDK vs custom loop" trade-off you'll be tested on.
🔗 Connect the Dots: The loop the SDK runs is the same stop_reason loop covered in Concept 3. Understand it there and you understand what the SDK is doing under the hood.

Agentic Loop, Tool Use & stop_reason

Concept 3 — The control mechanism behind every Claude agent

Exam Frequency:
Very High
stop_reason — the only reliable signal
Every Messages API response carries a stop_reason that tells you why Claude stopped. It is the authoritative, deterministic signal your loop uses to decide what to do next.

Quick Reference

  • end_turn — finished naturally → use the response / stop the loop
  • tool_use — Claude is calling a tool → run it, return the result, continue
  • max_tokens — hit the token limit → raise limit or continue
  • pause_turn — a server-tool loop hit its iteration cap → send content back to resume
  • refusal — Claude declined → read stop_details, retry on a fallback
if response.stop_reason == "end_turn":
    print(response.content[0].text)   # done
elif response.stop_reason == "tool_use":
    run_tools_and_continue(response)      # keep looping

The Tool Round-Trip

Define a tool with an input_schema → Claude replies with a tool_use block → you execute and return a tool_result matched to the tool_use_id → Claude uses it to answer. Client tools run in your app; server tools (web_search, code_execution) run on Anthropic's infrastructure.

tools = [{
  "name": "get_weather",
  "description": "Get current weather for a location.",
  "input_schema": {"type":"object",
     "properties":{"location":{"type":"string"}},
     "required":["location"]}}]

Errors & Anti-Patterns

is_error, graceful degradation, and the loop-control trap

Return Errors with the is_error Flag

# CORRECT — Claude knows the tool failed
{"type":"tool_result",
 "tool_use_id":"toolu_123",
 "content":"Error: timeout after 30s",
 "is_error": true}
Anti-Pattern: silently swallowing a tool error and returning an empty result. Claude assumes the tool succeeded with no data and hallucinates. Always propagate failures with is_error: true.

The Loop-Control Trap

A support agent stops after saying "Let me look up your order." The code checks response.content[0].type == "text" to decide the agent is finished.

✗ Content-Type Check

Claude can return text and a tool_use block together. Checking content type terminates prematurely — the lookup never runs.

✓ stop_reason Check

Only stop_reason == "end_turn" reliably means "done." When Claude still needs a tool, stop_reason is "tool_use" regardless of any text.

Graceful degradation and recovery depend on keeping the right context (exact IDs, amounts, prior tool errors) — not the most context. The customer-support-agent quickstart shows a concrete "degrade → escalate to human" path via its redirect_to_agent field.

🔗 Connect the Dots: Context engineering (curating the finite window across a long loop) directly supports error recovery — see the Effective Context Engineering blog in this concept's resources.

Frameworks — LangGraph, Strands & PydanticAI

Concept 4 — Recognition-level knowledge of the major agent frameworks

Exam Frequency:
High

🔷 LangGraph — graph-based state machines

A low-level orchestration framework for long-running, stateful agents, modelled as a graph of State · Nodes · Edges. Core benefits: durable execution (resume after failure), human-in-the-loop, short- and long-term memory, and mixing deterministic with model-driven steps in one graph.

from langgraph.graph import StateGraph, MessagesState, START, END
graph = StateGraph(MessagesState)
graph.add_node(mock_llm)
graph.add_edge(START, "mock_llm")
graph.add_edge("mock_llm", END)
graph = graph.compile()

🟠 Strands — AWS-native, model-driven

An open-source SDK (Python & TypeScript) that builds an agent from three parts: a model, a system prompt, and a set of tools. A lightweight agent loop, a @tool decorator, MCP support, and built-in multi-agent patterns (Swarms, Graphs, Workflows, Agent-to-Agent). First-class AWS integration and OpenTelemetry observability; used in production by Amazon Q, Kiro and AWS Glue.

🟣 PydanticAI — type-safe agents

"The FastAPI feeling for GenAI" — a fully type-safe, model-agnostic Python framework. Pydantic validation on every input/output moves whole classes of bugs to write-time. Ships the agent loop, structured outputs, tools, MCP and web search, plus evals and observability via Logfire.

You only need recognition-level knowledge here: what each framework is for, not how to build with it. The exam pairs a constraint with the right framework — memorise the mapping on the next page.

Multi-Agent & Context Isolation

Concept 5 — Orchestrator-workers and the context-isolation rule

Exam Frequency:
High
Multi-Agent System
Multiple LLM instances running with separate conversation contexts, coordinated through code. The common pattern is orchestrator-subagent: a lead agent spawns and manages specialised subagents for specific subtasks.

How the Research System Works

From Claude's own Research feature: a lead agent plans the work and spawns parallel subagents. Each subagent explores with its own context window, then compresses findings back to the lead. Separation of concerns — distinct tools, prompts and trajectories — reduces path dependency.

Context isolation (key exam fact): subagents do not inherit the coordinator's conversation history. The lead must explicitly pass the task/topic, or the subagent has nothing to work with. There is no shared memory between invocations.

The Three Situations Where Multi-Agent Wins

  • Context pollution — one context can't hold everything without degrading
  • Parallelism — subtasks can run at the same time
  • Specialisation — distinct prompts/tools improve focus and tool selection

Multi-agent systems burn far more tokens than a single agent. Reserve them for high-value, parallelisable, open-ended work — and always start by asking whether a well-prompted single agent would do.

When NOT to Go Multi-Agent

The over-engineering trap and the incomplete-report scenario

Start Single

✗ Over-Engineering

Building separate agents for planning, execution, review and iteration — losing context at every handoff and spending more tokens coordinating than executing.

✓ What the Exam Rewards

A well-designed single agent handles most workflows. Every extra agent is another failure point and coordination cost. Go multi-agent only for the three situations on the previous page.

Tracing an Incomplete Multi-Agent Output

A research system dispatches 5 subagents; all return successfully. But the final report only covers the first topic in depth.

✗ Wrong diagnosis: "the search subagent's queries were too narrow" — it searched thoroughly for what it was assigned.
✓ Correct diagnosis: the coordinator's decomposition only scoped synthesis to one topic. If the output is incomplete in scope (not depth), the coordinator's decomposition is almost always the root cause — not any downstream subagent.

Trace the runnable version in anthropics/claude-cookbooks · patterns/agents: watch how the orchestrator passes context into each worker call. That line of code is the concrete form of "subagents don't inherit history; context must be passed explicitly."
