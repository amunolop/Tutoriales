Claude API Mechanics

Messages API, streaming, batch, vision, thinking, caching, and vendor integration

Messages API — Core Request/Response

The Messages API is the primary interface for interacting with Claude. Every request includes a model, max_tokens, and a messages array of alternating user/assistant turns. The response includes content (text and/or tool_use blocks), stop_reason, and usage (token counts).

Multi-turn conversations: You build the conversation by appending both the assistant's response AND the next user message to the messages array. Claude has no memory between API calls — the full conversation must be included in every request.

Key API Features

FeatureWhat It DoesWhen to Use
StreamingReturns response tokens as they generate, not waiting for completionUser-facing applications where perceived latency matters
Batch APIProcesses large async workloads within a 24hr window at 50% reduced costOvernight bulk processing, non-urgent analytics — NOT blocking pipelines
VisionAccepts images (base64 or URL) alongside text in messagesDocument analysis, image understanding, multimodal tasks
Extended ThinkingDedicated reasoning space that doesn't consume the response budgetComplex multi-step reasoning, mathematical proofs, architectural decisions
Prompt CachingCaches static prefix content — 90% cheaper on cache hitsRepeated system prompts across many conversations (min 1,024 tokens)

API Mechanics — Implementation

Streaming vs Synchronous

# Synchronous — waits for full response
response = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=1024,
    messages=[{"role":"user","content":"Explain REST APIs"}])

# Streaming — tokens arrive as generated
with client.messages.stream(...) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)

Batch API — The Exam's Favourite Scenario

# Batch: 50% cost savings, up to 24hr window
batch = client.messages.batches.create(
    requests=[
        {"custom_id": "doc-001",
         "params": {"model": "claude-sonnet-4-6",
                    "max_tokens": 1024,
                    "messages": [{...}]}}
    ])
Batch API = WRONG for blocking operations. Pre-merge CI checks, real-time user requests, interactive features — all need synchronous or streaming API. The exam's sample question #1 tests exactly this.

Third-Party Vendor Integration

Claude is available through Amazon Bedrock, Google Vertex AI, and Azure AI Foundry. The API interface is similar but requires vendor-specific authentication and may have different feature availability. The exam tests whether you know which features are vendor-specific vs universal.

API Mechanics — Exam Patterns

#1 — Batch vs Real-Time (Sample Q from Exam Guide): "10,000 documents overnight, cost is primary concern, results not needed until morning" → Batch API. Synchronous (A), lower max_tokens (C), smallest model (D) are ALL wrong.
#2 — Prompt Caching Placement: Static content (system prompt, few-shot examples) must be at the START of the request. Cache matches from the beginning — dynamic content after a miss is processed fresh. Minimum 1,024 tokens to be eligible.
#3 — Streaming for User-Facing: When the scenario describes a chatbot or user-facing application, streaming is almost always the correct answer for "how to reduce perceived latency." Not batch, not lower max_tokens.
#4 — No Memory Between Calls: Claude does not remember previous API calls. The FULL conversation history must be included in every request. This is the most fundamental API concept.

Session Hygiene

Clean sessions prevent context pollution. Key practices:

  • Separate sessions per task — don't mix unrelated tasks in one conversation
  • Clear tool results — remove verbose tool outputs from earlier turns after they've been processed
  • Explicit context boundaries — mark where user content ends and system instructions begin

Schema Design & Content Boundaries

Structured Output with tool_use

Use tool_use with JSON Schema to guarantee valid output format. Key rules:

  • Mark fields required ONLY when always present — forces fabrication otherwise
  • Use type: ["string", "null"] for optional fields — allows explicit "no value"
  • Add "other" or "unclear" to enums — prevents forced categorisation
  • tool_use eliminates syntax errors, NOT semantic errors — output format is guaranteed, content accuracy is not

Content Boundaries

# WRONG: user content mixed with instructions
messages = [{"role":"user",
  "content": user_input + "

Please follow these rules..."}]

# CORRECT: user content separated from instructions
messages = [{"role":"user",
  "content": [
    {"type":"text", "text": "<user_input>"+user_input+"</user_input>"},
    {"type":"text", "text": "Analyse the user input above."}
  ]}]
Always tag untrusted content. Wrapping user input in XML tags (<user_input>) creates a clear boundary that helps Claude distinguish instructions from data — a key defence against prompt injection.

Application Design — Exam Patterns

#1 — Syntax vs Semantic: tool_use guarantees valid JSON format. It does NOT guarantee correct content. A decimal place error in an invoice amount is a semantic error — valid JSON, wrong value.
#2 — Required Field Fabrication: Making a field "required" when data is sometimes absent forces Claude to fabricate. Use type: ["string", "null"] for optional fields.
#3 — Content Boundaries: The exam tests prompt injection awareness. Untrusted input must be tagged and separated from instructions — this is tested in the Security domain too (Sample Q #2 from the exam guide).
#4 — Session Hygiene: Old tool results consuming context → clear them. Mixing tasks → separate sessions. Context pollution → leads to inconsistent behaviour.

SE Foundations — Exam Patterns

#1 — 429 = Retry: Rate limit errors (429) are transient — retry with exponential backoff. 401 (bad API key) is NOT transient — fix credentials, don't retry.
#2 — Async for Streaming: Streaming requires async I/O patterns. If the exam describes a synchronous app that blocks during streaming, the fix is to switch to async/await patterns.
#3 — Version Control for Prompts: System prompts should be version-controlled just like code. Changes to prompts can cause regressions — the same eval suite approach applies.
#4 — Refactoring with Claude: Small-scale refactoring (rename, extract function) → Direct mode. Large-scale refactoring (14 files, cross-cutting concerns) → Plan mode with dependency mapping.

SDLC for AI Systems

AI systems add unique SDLC considerations:

  • Prompt versioning — treat prompts as code, version-control changes, run eval suites before deployment
  • Model version pinning — pin to specific model versions to prevent breaking changes on model updates
  • Eval gates — run evaluations as part of the release process, not just during development
  • Monitoring — track accuracy, latency, cost, and error rates in production

Model Version Pinning

Pin to specific model identifiers (e.g., claude-sonnet-4-6) in production. Model updates can introduce breaking changes — a prompt that works perfectly on one version may behave differently on the next. Version pinning prevents surprise regressions.

When to update: Update model versions deliberately — test with eval suite, verify no regressions, then update the pin. Never use "latest" in production.

Config & Requirements — Exam Patterns

#1 — Business → Functional: The exam describes a business need and asks what functional spec is required. Map: "daily volume" → scaling + API choice. "Accuracy requirement" → eval gates. "Cost constraint" → batch vs real-time + caching.
#2 — Model Pinning: "App behaviour changed after Anthropic released a model update" → you weren't pinning model versions. Always pin in production.
#3 — CLAUDE.md vs settings.json: Conventions and preferences → CLAUDE.md. Hooks and enforcement → settings.json. The exam tests this distinction directly.
#4 — Prompt Versioning: Prompts should be in version control, tested with eval suites, and deployed through the same CI/CD pipeline as code changes.
