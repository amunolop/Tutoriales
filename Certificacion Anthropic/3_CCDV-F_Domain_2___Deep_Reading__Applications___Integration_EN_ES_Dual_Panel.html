Concept 1 · Definition

The Stateless Messages API

Task 2.1 — The one rule that underpins everything

High exam frequency
🔑 The Messages API is stateless. Claude remembers nothing between calls — you always send the full conversation history each turn. To continue a chat, append both Claude's reply and the next user message to the array.
message = anthropic.Anthropic().messages.create( model="claude-sonnet-4-6", max_tokens=1024, messages=[ {"role": "user", "content": "Hello, Claude"}, {"role": "assistant", "content": "Hello!"}, {"role": "user", "content": "Describe LLMs to me"}, ])

Every request has a model, max_tokens, and a messages array of alternating user/assistant turns. The response carries content (array of text/tool_use blocks), stop_reason, and usage (token counts for cost tracking).

Think of every API call as a brand-new conversation. Claude has no memory, no session, no cookies. The full message array IS the conversation — your code is the memory layer. This is why multi-turn chat apps must append every response before the next call, and why the Batch API is single-turn only.

Concept 1 · Certification Focus

Multi-Turn Assembly — The Alternating Roles Rule

The most-tested Messages API scenario

Scenario: A developer builds a chatbot but Claude seems to "forget" the conversation after every message. Each response acts as if it's the first turn.

Root Cause: The developer sends only the latest user message each call, not the full conversation history. Because the API is stateless, Claude sees a fresh, single-turn conversation every time.

Fix: Maintain a message array. After each response, append the assistant message, then the new user message, then call again with the full array. Roles must alternate: user → assistant → user → assistant.

📋 Exam Pattern: "Claude forgets the conversation" = developer isn't sending full history. "Claude ignores tool result" = assistant message with tool_use block wasn't included before the tool_result. Both are the stateless API rule applied differently.

Concept 1 · Case Study

The Missing Turn

Debugging stateless API misunderstandings

Bot sends only latest message — Claude has no memory ▶

Each API call must include the entire conversation. The developer's code only sent the latest user message, so Claude treated every call as turn 1. Fix: maintain an array, append assistant + user messages each turn, send the full array.

Tool result ignored — Claude makes up an answer ▶

The developer sent the tool_result but forgot to include the previous assistant message (containing the tool_use block). Without that assistant turn, the API can't link the result. Fix: append the full assistant response, then the user message with tool_result. Roles must alternate.

Thinking budget too high — request times out ▶

Extended thinking with budget_tokens above ~32K can exceed HTTP timeout limits. Fix: use the Batch API for large thinking budgets — it has a 24-hour processing window. Or use adaptive thinking with an effort level instead of a fixed budget.

SSE Streaming

Task 2.2 — Real-time token delivery for user-facing latency

High exam frequency

Set stream=true to receive the response incrementally via server-sent events (SSE) — tokens appear as they generate.

with client.messages.stream( max_tokens=1024, messages=[{"role":"user","content":"Hello"}], model="claude-sonnet-4-6") as stream: for text in stream.text_stream: print(text, end="", flush=True)
🔑 Event Flow: message_start → content_block_delta (many) → message_stop. An overloaded_error in the stream corresponds to HTTP 529. For any user-facing chatbot, streaming is the answer to "reduce perceived latency" — not batch, not lowering max_tokens.

Concept 2 · Certification Focus

The Cost Decision — Stream vs Batch vs Cache

The exam's favourite trade-off

Scenario: You need to classify 50,000 support tickets overnight. A colleague suggests streaming. Another suggests the Batch API. A third suggests prompt caching.

Correct Answer: Batch API for the 50% cost reduction on bulk async work. Prompt caching on top if the system prompt + examples are reused across tickets (another up to 90% on the repeated prefix). Streaming is wrong — it's for user-facing latency, not bulk processing.

📋 Exam Decision Tree: User-facing chatbot → streaming. Overnight bulk / weekly reports → Batch API. Repeated long prefix (book, codebase, examples) → prompt caching. Pre-merge CI checks → synchronous (not batch — blocking). Batch + caching can be combined.

Concept 2 · Case Study

The Broken Cache

Why the cache never hits

Cache hit rate is 0% despite cache_control being set ▶

A dynamic timestamp sits before the cache breakpoint. Every call has a different prefix, so the cache never matches. Fix: move all dynamic content (timestamps, UUIDs, user IDs) AFTER the cache breakpoint. Stable content (system prompt, examples, documents) must come first in the order: tools → system → messages.

Batch job used for CI pre-merge checks — pipeline blocks for hours ▶

The Batch API has a 24-hour processing window — it's async, not real-time. CI checks need synchronous/streaming responses. Fix: use standard synchronous API calls for blocking CI checks. Reserve batch for non-blocking bulk work like overnight reports.

Chat with 100K-token book: 11.5s to first token — too slow ▶

Cache the book as a prompt prefix. After the first call (cache write), subsequent calls read from cache: 11.5s → 2.4s to first token (−79%) with 90% cost reduction. The book must be in the stable prefix, before any dynamic query content.

Task 2.3 — Guaranteeing parseable output and handling errors

High exam frequency

Constrain Claude's response to a schema so downstream code always gets valid, parseable data.

FeatureWhat It DoesHow
JSON outputsWhole response is valid JSON matching schemaoutput_config.format
Strict tool useGuarantees schema validation on tool inputsstrict: true
🔑 Syntax ≠ Semantics: Constrained decoding removes JSON.parse errors, missing fields and type mismatches. But a wrong value ($150 instead of $1,500) is a SEMANTIC error the schema can't catch — that needs validation logic.

Schema Design Tips

Make a field required only when it's always present — otherwise Claude fabricates. Use ["string","null"] for optional fields. Add "other"/"unclear" to enums to avoid forced miscategorisation.

CodeNameAction
400invalid_requestFix request — don't retry

Concept 3 · Certification Focus

The 429 Decision — The Only Retryable 4xx

The most-tested error handling scenario

Scenario: Your agent receives a 429 error. A colleague suggests a tight retry loop. Another suggests fixing the request like any other 4xx.

Correct Answer: Exponential backoff honouring retry-after. A 429 is the ONLY 4xx that should be retried — it means the request is valid but you've hit a rate limit. A tight loop hammers the API and makes things worse.

📋 Exam Decision Tree: 400/401/403/404 → fix request, NEVER retry. 429 → backoff & retry (honour retry-after). 500/504/529 → retry with backoff. Mid-stream SSE error → handle in stream handler, not HTTP status.
❌ Wrong

"429 is a client error like 400 — fix the request."

✓ Correct

"429 means rate limited — the request is valid. Retry with exponential backoff."

Concept 3 · Case Study

The Wrong Retry

Debugging structured output and error handling

Valid JSON but wrong price — schema didn't catch it ▶

Structured Outputs guarantee syntax (valid JSON, correct fields) not semantics (correct values). A wrong price is a semantic error. Fix: add field-level validation in your code (range checks, cross-references) plus clear extraction instructions in the prompt.

Agent retries 401 five times before failing ▶

A 401 is an authentication error — the API key is invalid. Retrying will never fix it. Fix: fail immediately and report a credentials issue. Check whether the SDK's retry logic is misconfigured to include 401s.

Zod / Pydantic structured output from agent — SDK re-prompts on mismatch ▶

The Agent SDK validates the result and re-prompts if it doesn't match the schema. If it still fails within the retry limit, you get an error. For full type safety: Zod in TypeScript, Pydantic in Python. This gives you typed data you can drop straight into your app.

CLAUDE.md vs settings.json

Task 2.4 — Probabilistic conventions vs deterministic enforcement

High exam frequency

This is the exam's favourite config distinction: CLAUDE.md = probabilistic (guidance the model tries to follow). settings.json = deterministic (hooks, permissions, MCP servers that are always enforced).

FileNatureContainsWhen to Use
CLAUDE.mdProbabilisticProject conventions, commands, architecture"Prefer this style"
settings.jsonDeterministicHooks, MCP servers, permissions"MUST never happen"
🔑 Golden Rule: "MUST never happen" → a PreToolUse hook in settings.json (deterministic). "Prefer this style" → CLAUDE.md (probabilistic). A CLAUDE.md instruction alone will NOT reliably block a dangerous action.

Concept 4 · Certification Focus

Probabilistic vs Deterministic — The Config Trap

The most-tested config scenario

Scenario: A developer puts "never modify production database" in CLAUDE.md. An injected prompt convinces Claude to run a destructive query anyway.

Root Cause: CLAUDE.md is probabilistic — the model tries to follow it but isn't guaranteed to. A sufficiently crafted prompt can override it.

Fix: Add a PreToolUse hook in settings.json that blocks database-modifying commands (exit code 2 = deny). Deterministic enforcement can't be overridden by prompt injection.

📋 Exam Pattern: "MUST be enforced" → settings.json hook. "Should be followed" → CLAUDE.md. "Organisation-wide, non-overridable" → managed policy. "New developer doesn't see team conventions" → wrong scope (user vs project). CLAUDE.md targets <200 lines; it's loaded every session.
Domain 7 Link: This config distinction maps directly to the security domain. The trust hierarchy (D7) relies on settings.json hooks being deterministic. CLAUDE.md provides guidance; hooks provide enforcement. Both are needed for defence-in-depth.

Concept 4 · Case Study

The Ignored Convention

Debugging config scope and enforcement issues

New dev joins team — Claude Code doesn't follow team conventions ▶

The conventions are in the senior dev's user-scope CLAUDE.md (~/.claude/CLAUDE.md), not the project-scope one (.claude/CLAUDE.md). New team members don't inherit user-scope settings. Fix: move shared conventions to .claude/CLAUDE.md (committed to git) so every team member gets them automatically.

CLAUDE.md says "never use rm" but Claude runs it anyway ▶

CLAUDE.md is probabilistic — the model usually follows it, but a crafted prompt or edge case can override it. For hard requirements, add a PreToolUse hook in settings.json that checks for destructive commands and returns exit code 2 (block). Deterministic enforcement is the only reliable defence.

Community best-practice repo shows full settings hierarchy ▶

The claude-code-best-practice repo (63k★) documents every settings.json option with the scope hierarchy table: Managed → CLI → Local → Project → User. It covers hooks, permissions, MCP servers, model config, and memory. A good consolidated reference, but always cross-check against the official docs for enforcement details.

Concepto 1 · Definición

La API de Mensajes sin Estado

Tarea 2.1 — La única regla que lo sustenta todo

Alta frecuencia en el examen
🔑 La API de Mensajes no tiene estado. Claude no recuerda nada entre llamadas — siempre envías el historial completo de la conversación en cada turno. Para continuar un chat, añade tanto la respuesta de Claude como el siguiente mensaje del usuario al array.
message = anthropic.Anthropic().messages.create( model="claude-sonnet-4-6", max_tokens=1024, messages=[ {"role": "user", "content": "Hello, Claude"}, {"role": "assistant", "content": "Hello!"}, {"role": "user", "content": "Describe LLMs to me"}, ])

Cada solicitud tiene un model, max_tokens, y un array de messages con turnos alternados de usuario/asistente. La respuesta incluye content (array de bloques de texto/tool_use), stop_reason, y usage (recuento de tokens para el seguimiento de coste).

Piensa en cada llamada a la API como una conversación completamente nueva. Claude no tiene memoria, ni sesión, ni cookies. El array completo de mensajes ES la conversación — tu código es la capa de memoria. Por eso las apps de chat multi-turno deben añadir cada respuesta antes de la siguiente llamada, y por eso la Batch API es solo de un turno.

Concepto 1 · Enfoque de Certificación

Ensamblaje Multi-Turno — La Regla de Roles Alternados

El escenario más evaluado de la API de Mensajes

Escenario: Un desarrollador construye un chatbot pero Claude parece "olvidar" la conversación tras cada mensaje. Cada respuesta actúa como si fuera el primer turno.

Causa Raíz: El desarrollador envía solo el último mensaje del usuario en cada llamada, no el historial completo de la conversación. Como la API no tiene estado, Claude ve una conversación nueva y de un solo turno cada vez.

Solución: Mantén un array de mensajes. Después de cada respuesta, añade el mensaje del asistente, luego el nuevo mensaje del usuario, y llama de nuevo con el array completo. Los roles deben alternarse: usuario → asistente → usuario → asistente.

📋 Patrón de Examen: "Claude olvida la conversación" = el desarrollador no está enviando el historial completo. "Claude ignora el resultado de la herramienta" = no se incluyó el mensaje del asistente con el bloque tool_use antes del tool_result. Ambos son la misma regla de la API sin estado aplicada de forma distinta.

Concepto 1 · Caso Práctico

El Turno Perdido

Depurando malentendidos de la API sin estado

El bot solo envía el último mensaje — Claude no tiene memoria▶

Cada llamada a la API debe incluir la conversación completa. El código del desarrollador solo enviaba el último mensaje del usuario, así que Claude trataba cada llamada como el turno 1. Solución: mantén un array, añade los mensajes del asistente y del usuario en cada turno, envía el array completo.

Resultado de herramienta ignorado — Claude se inventa una respuesta▶

El desarrollador envió el tool_result pero olvidó incluir el mensaje anterior del asistente (que contenía el bloque tool_use). Sin ese turno del asistente, la API no puede vincular el resultado. Solución: añade la respuesta completa del asistente, luego el mensaje del usuario con el tool_result. Los roles deben alternarse.

Presupuesto de razonamiento demasiado alto — la solicitud agota el tiempo▶

El razonamiento extendido con budget_tokens por encima de ~32K puede exceder los límites de timeout HTTP. Solución: usa la Batch API para presupuestos de razonamiento grandes — tiene una ventana de procesamiento de 24 horas. O usa razonamiento adaptativo con un nivel de effort en lugar de un presupuesto fijo.

Streaming SSE

Tarea 2.2 — Entrega de tokens en tiempo real para latencia orientada al usuario

Alta frecuencia en el examen

Establece stream=true para recibir la respuesta de forma incremental mediante eventos enviados por el servidor (SSE) — los tokens aparecen a medida que se generan.

with client.messages.stream( max_tokens=1024, messages=[{"role":"user","content":"Hello"}], model="claude-sonnet-4-6") as stream: for text in stream.text_stream: print(text, end="", flush=True)
🔑 Flujo de Eventos: message_start → content_block_delta (varios) → message_stop. Un overloaded_error en el stream corresponde al HTTP 529. Para cualquier chatbot orientado al usuario, el streaming es la respuesta a "reducir la latencia percibida" — no el batch, ni bajar max_tokens.

Concepto 2 · Enfoque de Certificación

La Decisión de Coste — Streaming vs Batch vs Caché

El compromiso favorito del examen

Escenario: Necesitas clasificar 50.000 tickets de soporte durante la noche. Un compañero sugiere streaming. Otro sugiere la Batch API. Un tercero sugiere caché de prompts.

Respuesta Correcta: Batch API por la reducción de coste del 50% en trabajo asíncrono a granel. Caché de prompts encima si el prompt del sistema + ejemplos se reutilizan entre tickets (otro hasta 90% en el prefijo repetido). Streaming es incorrecto — es para latencia orientada al usuario, no procesamiento a granel.

📋 Árbol de Decisión del Examen: Chatbot orientado al usuario → streaming. Volumen nocturno / informes semanales → Batch API. Prefijo largo repetido (libro, código base, ejemplos) → caché de prompts. Comprobaciones de CI antes de fusionar → síncrono (no batch — es bloqueante). Batch + caché pueden combinarse.

Concepto 2 · Caso Práctico

La Caché Rota

Por qué la caché nunca acierta

La tasa de aciertos de caché es del 0% a pesar de tener cache_control configurado▶

Un timestamp dinámico se sitúa antes del punto de corte de la caché. Cada llamada tiene un prefijo distinto, así que la caché nunca coincide. Solución: mueve todo el contenido dinámico (timestamps, UUIDs, IDs de usuario) DESPUÉS del punto de corte. El contenido estable (prompt del sistema, ejemplos, documentos) debe ir primero en el orden: tools → system → messages.

Se usa un trabajo batch para comprobaciones de CI antes de fusionar — el pipeline se bloquea durante horas▶

La Batch API tiene una ventana de procesamiento de 24 horas — es asíncrona, no en tiempo real. Las comprobaciones de CI necesitan respuestas síncronas/streaming. Solución: usa llamadas síncronas estándar para comprobaciones de CI bloqueantes. Reserva el batch para trabajo a granel no bloqueante como informes nocturnos.

Chat con un libro de 100K tokens: 11,5s hasta el primer token — demasiado lento▶

Cachea el libro como prefijo del prompt. Tras la primera llamada (escritura en caché), las siguientes leen de la caché: 11,5s → 2,4s hasta el primer token (−79%) con un 90% de reducción de coste. El libro debe estar en el prefijo estable, antes de cualquier contenido dinámico de la consulta.

Salidas JSON y Uso Estricto de Herramientas

Tarea 2.3 — Garantizar salida analizable y manejar errores

Alta frecuencia en el examen

Restringe la respuesta de Claude a un esquema para que el código posterior siempre reciba datos válidos y analizables.

FunciónQué HaceCómo
Salidas JSONLa respuesta completa es JSON válido que coincide con el esquemaoutput_config.format
Uso estricto de herramientasGarantiza la validación de esquema en las entradas de herramientasstrict: true
🔑 Sintaxis ≠ Semántica: La decodificación restringida elimina errores de JSON.parse, campos faltantes y discordancias de tipo. Pero un valor incorrecto ($150 en vez de $1.500) es un error SEMÁNTICO que el esquema no puede detectar — eso necesita lógica de validación.

Consejos de Diseño de Esquemas

Haz que un campo sea required solo cuando siempre esté presente — de lo contrario Claude lo inventa. Usa ["string","null"] para campos opcionales. Añade "other"/"unclear" a los enums para evitar una clasificación forzada incorrecta.

CódigoNombreAcción

Concepto 3 · Enfoque de Certificación

La Decisión del 429 — El Único 4xx Reintentable

El escenario de manejo de errores más evaluado

Escenario: Tu agente recibe un error 429. Un compañero sugiere un bucle de reintento ajustado. Otro sugiere arreglar la solicitud como cualquier otro 4xx.

Respuesta Correcta: Backoff exponencial respetando retry-after. Un 429 es el ÚNICO 4xx que debe reintentarse — significa que la solicitud es válida pero has alcanzado un límite de tasa. Un bucle ajustado machaca la API y empeora las cosas.

📋 Árbol de Decisión del Examen: 400/401/403/404 → arregla la solicitud, NUNCA reintentes. 429 → backoff y reintento (respeta retry-after). 500/504/529 → reintenta con backoff. Error SSE a mitad de stream → maneja en el gestor del stream, no en el estado HTTP.
❌ Incorrecto

"El 429 es un error de cliente como el 400 — arregla la solicitud."

✓ Correcto

"El 429 significa límite de tasa alcanzado — la solicitud es válida. Reintenta con backoff exponencial."

Concepto 3 · Caso Práctico

El Reintento Erróneo

Depurando la salida estructurada y el manejo de errores

JSON válido pero precio incorrecto — el esquema no lo detectó▶

Las Salidas Estructuradas garantizan la sintaxis (JSON válido, campos correctos) no la semántica (valores correctos). Un precio incorrecto es un error semántico. Solución: añade validación a nivel de campo en tu código (comprobaciones de rango, referencias cruzadas) más instrucciones claras de extracción en el prompt.

El agente reintenta un 401 cinco veces antes de fallar▶

Un 401 es un error de autenticación — la clave API no es válida. Reintentar nunca lo arreglará. Solución: falla inmediatamente e informa de un problema de credenciales. Comprueba si la lógica de reintento del SDK está mal configurada para incluir los 401.

Salida estructurada Zod / Pydantic desde un agente — el SDK vuelve a pedir ante una discordancia▶

El Agent SDK valida el resultado y vuelve a pedir si no coincide con el esquema. Si sigue fallando dentro del límite de reintentos, obtienes un error. Para seguridad de tipos completa: Zod en TypeScript, Pydantic en Python. Esto te da datos tipados que puedes usar directamente en tu app.

CLAUDE.md vs settings.json

Tarea 2.4 — Convenciones probabilísticas vs aplicación determinista

Alta frecuencia en el examen

Esta es la distinción de configuración favorita del examen: CLAUDE.md = probabilístico (guía que el modelo intenta seguir). settings.json = determinista (hooks, permisos, servidores MCP que siempre se aplican).

ArchivoNaturalezaContieneCuándo Usarlo
CLAUDE.mdProbabilísticoConvenciones del proyecto, comandos, arquitectura"Prefiere este estilo"
settings.jsonDeterministaHooks, servidores MCP, permisos"NUNCA debe ocurrir"
🔑 Regla de Oro: "DEBE aplicarse siempre" → un hook PreToolUse en settings.json (determinista). "Debería seguirse" → CLAUDE.md (probabilístico). Una instrucción de CLAUDE.md por sí sola NO bloqueará de forma fiable una acción peligrosa.

Concepto 4 · Enfoque de Certificación

Probabilístico vs Determinista — La Trampa de Configuración

El escenario de configuración más evaluado

Escenario: Un desarrollador pone "nunca modificar la base de datos de producción" en CLAUDE.md. Un prompt inyectado convence a Claude de ejecutar una consulta destructiva de todos modos.

Causa Raíz: CLAUDE.md es probabilístico — el modelo intenta seguirlo pero no está garantizado. Un prompt suficientemente elaborado puede anularlo.

Solución: Añade un hook PreToolUse en settings.json que bloquee comandos que modifiquen la base de datos (código de salida 2 = denegar). La aplicación determinista no puede anularse mediante inyección de prompts.

📋 Patrón de Examen: "DEBE aplicarse" → hook en settings.json. "Debería seguirse" → CLAUDE.md. "En toda la organización, no anulable" → política gestionada. "El nuevo desarrollador no ve las convenciones del equipo" → ámbito incorrecto (usuario vs proyecto). CLAUDE.md apunta a <200 líneas; se carga en cada sesión.
Enlace con el Dominio 7: Esta distinción de configuración se relaciona directamente con el dominio de seguridad. La jerarquía de confianza (D7) depende de que los hooks de settings.json sean deterministas. CLAUDE.md ofrece guía; los hooks ofrecen aplicación. Ambos son necesarios para una defensa en profundidad.

Concepto 4 · Caso Práctico

La Convención Ignorada

Depurando problemas de ámbito y aplicación de configuración

Nuevo desarrollador se une al equipo — Claude Code no sigue las convenciones del equipo▶

Las convenciones están en el CLAUDE.md de ámbito de usuario del desarrollador senior (~/.claude/CLAUDE.md), no en el de ámbito de proyecto (.claude/CLAUDE.md). Los nuevos miembros del equipo no heredan la configuración de ámbito de usuario. Solución: mueve las convenciones compartidas a .claude/CLAUDE.md (confirmado en git) para que cada miembro del equipo las reciba automáticamente.

CLAUDE.md dice "nunca uses rm" pero Claude lo ejecuta de todos modos▶

CLAUDE.md es probabilístico — el modelo normalmente lo sigue, pero un prompt elaborado o un caso límite puede anularlo. Para requisitos estrictos, añade un hook PreToolUse en settings.json que compruebe comandos destructivos y devuelva el código de salida 2 (bloquear). La aplicación determinista es la única defensa fiable.

Un repositorio de mejores prácticas de la comunidad muestra la jerarquía completa de configuración▶

El repositorio claude-code-best-practice (63k★) documenta cada opción de settings.json con la tabla de jerarquía de ámbitos: Gestionado → CLI → Local → Proyecto → Usuario. Cubre hooks, permisos, servidores MCP, configuración de modelo y memoria. Una buena referencia consolidada, pero siempre contrasta con la documentación oficial para los detalles de aplicación.
