Lectura Profunda

La Distinción Central — Flujo de Trabajo vs Agente

Concepto 1 — La decisión arquitectónica más evaluada del Dominio 1

Frecuencia en el Examen:
Muy Alta
Flujos de Trabajo vs Agentes
Anthropic traza una única línea arquitectónica y construye todo sobre ella. Los flujos de trabajo son sistemas donde los LLM y las herramientas se orquestan mediante rutas de código predefinidas. Los agentes son sistemas donde el LLM dirige dinámicamente su propio proceso y el uso de herramientas, manteniendo el control sobre cómo lleva a cabo la tarea.

Cuándo (y Cuándo No) Construir un Agente

La indicación de Anthropic es explícita: buscar la solución más simple posible y aumentar la complejidad solo cuando eso mejore demostrablemente los resultados. Muchos casos de uso solo necesitan una única llamada al LLM bien diseñada, con recuperación de información y ejemplos en el propio contexto — no un agente.

Regla de oro: los flujos de trabajo ofrecen previsibilidad y consistencia para tareas bien definidas; los agentes son la mejor opción cuando se necesita flexibilidad y toma de decisiones impulsada por el modelo a gran escala. Los agentes cambian latencia y coste por adaptabilidad — haz ese intercambio de forma deliberada.
✗ Concepto Erróneo Común

"Si la tarea es compleja, usa siempre un agente — los agentes lo manejan todo mejor."

✓ Lo que Premia el Examen

Usa la arquitectura más simple que resuelva el problema. Si un flujo de trabajo funciona, no construyas un agente. Los agentes añaden potencia, pero también imprevisibilidad, coste variable y complejidad de depuración.

Los Cinco Patrones de Flujo de Trabajo

Antes de recurrir a un agente completo, Anthropic identifica cinco patrones de flujo de trabajo componibles a lo largo del espectro de autonomía:

PatrónCómo FuncionaCuándo Usarlo
Encadenamiento de PromptsPasos secuenciales fijos; cada salida alimenta la siguiente, con puertas de validación.Procesamiento de documentos, pipelines tipo ETL
EnrutamientoClasifica la entrada y luego la envía a un gestor especializado.Triaje de correos, clasificación de tickets
ParalelizaciónEjecuta subtareas independientes de forma concurrente (seccionado / votación) y luego agrega.Análisis multisección, votación de guardarrailes
Orquestador-TrabajadoresUn modelo líder descompone la tarea dinámicamente y delega a trabajadores.Investigación compleja, refactorizaciones multiarchivo
Evaluador-OptimizadorUna llamada genera, otra evalúa y da retroalimentación, repitiendo hasta alcanzar la calidad deseada.Traducción, escritura/refinamiento iterativo

Sobre los frameworks, Anthropic señala que el Claude Agent SDK, Strands (AWS) y los constructores con interfaz gráfica ayudan a empezar rápido — pero advierte que añaden capas de abstracción que pueden ocultar los prompts y complicar la depuración. Aprende primero las primitivas; adopta un framework después.

Criterios de Decisión: ¿Flujo de Trabajo o Agente?

SDK de Agentes y Construcción

Concepto 2 — Construcción de agentes de producción con el Claude Agent SDK

Frecuencia en el Examen:
Alta
Claude Agent SDK
El SDK te da las mismas herramientas, bucle de agente y gestión de contexto que impulsan a Claude Code — programable en Python y TypeScript. Gestiona el bucle (llamar al modelo, ejecutar herramientas, devolver resultados), herramientas integradas para leer archivos / ejecutar comandos / editar código, y permisos mediante una lista de permitidos allowed_tools.

El Agente Mínimo

import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions

async def main():
    async for message in query(
        prompt="Find and fix the bug in auth.py",
        options=ClaudeAgentOptions(allowed_tools=["Read","Edit","Bash"]),
    ):
        print(message)
asyncio.run(main())
Flexibilidad de autenticación: el SDK funciona directamente con la API de Claude o a través de Amazon Bedrock, Google Vertex y Microsoft Foundry — el enfoque de "despliegue gestionado vs autoalojado" que le gusta al examen.

La Filosofía de Diseño — "Dale a tu Agente un Ordenador"

En lugar de cablear manualmente cada herramienta, el SDK le da a Claude un entorno de propósito general (acceso a archivos, shell, edición de código) y le permite operar como lo haría un desarrollador. El bucle que ejecuta por ti:

  • Reunir contexto — incorporar archivos, resultados de búsqueda y estado previo
  • Actuar — llamar a herramientas / ejecutar comandos
  • Verificar el trabajo — comprobar resultados, autocorregirse
  • Repetir hasta que la tarea esté completa

Los hooks y guardarrailes te permiten imponer reglas estrictas (cosas que DEBEN ocurrir siempre) alrededor de un modelo probabilístico. Esta distinción "hook vs prompt del sistema" — aplicación determinista frente a orientación blanda — es un tema recurrente en el examen.

SDK vs Bucle Personalizado

La compensación que evalúa el examen — y dónde ayuda el repositorio oficial del SDK

Cuándo Usar el SDK frente a Escribir el Bucle a Mano

✗ Sobreingeniería

Escribir a mano todo el bucle agéntico, el almacén de sesiones y la plomería de herramientas para un agente estándar de archivos/comandos/edición.

✓ Usa el SDK

El SDK ya implementa el bucle, herramientas integradas, gestión de contexto y permisos. Recurre a un bucle personalizado solo cuando necesites un control que el SDK no expone.

El repositorio oficial claude-agent-sdk-python incluye automáticamente la CLI de Claude Code y aporta ejemplos ejecutables (asistente de correo, agente de investigación) además de adaptadores de referencia para el almacén de sesiones (S3, Redis, Postgres).

# pip install claude-agent-sdk   (Python 3.10+)
import anyio
from claude_agent_sdk import query

async def main():
    async for message in query(prompt="What is 2 + 2?"):
        print(message)
anyio.run(main)
Conexión con el examen: leer estos ejemplos muestra al SDK ejecutando el bucle por ti — el contraste con un bucle while escrito a mano es exactamente la compensación "SDK vs bucle personalizado" que se evaluará.

Bucle Agéntico, Uso de Herramientas y stop_reason

Concepto 3 — El mecanismo de control detrás de todo agente de Claude

Frecuencia en el Examen:
Muy Alta
stop_reason — la única señal fiable
Cada respuesta de la API de Messages incluye un stop_reason que indica por qué se detuvo Claude. Es la señal autoritaria y determinista que tu bucle usa para decidir qué hacer a continuación.

Referencia Rápida

  • end_turn — terminó de forma natural → usa la respuesta / detén el bucle
  • tool_use — Claude está llamando a una herramienta → ejecútala, devuelve el resultado, continúa
  • max_tokens — se alcanzó el límite de tokens → aumenta el límite o continúa
  • pause_turn — un bucle de herramienta del servidor alcanzó su límite de iteraciones → devuelve el contenido para reanudar
  • refusal — Claude rechazó → lee stop_details, reintenta con una alternativa
if response.stop_reason == "end_turn":
    print(response.content[0].text)   # hecho
elif response.stop_reason == "tool_use":
    run_tools_and_continue(response)      # sigue el bucle

El Ciclo de Ida y Vuelta de la Herramienta

Define una herramienta con un input_schema → Claude responde con un bloque tool_use → tú lo ejecutas y devuelves un tool_result emparejado con el tool_use_id → Claude lo usa para responder. Las herramientas de cliente se ejecutan en tu aplicación; las herramientas de servidor (web_search, code_execution) se ejecutan en la infraestructura de Anthropic.

tools = [{
  "name": "get_weather",
  "description": "Get current weather for a location.",
  "input_schema": {"type":"object",
     "properties":{"location":{"type":"string"}},
     "required":["location"]}}]

Enfoque de Certificación

Errores y Antipatrones

is_error, degradación elegante y la trampa del control de bucle

Devuelve Errores con el Indicador is_error

# CORRECTO — Claude sabe que la herramienta falló
{"type":"tool_result",
 "tool_use_id":"toolu_123",
 "content":"Error: timeout after 30s",
 "is_error": true}
Antipatrón: silenciar un error de herramienta y devolver un resultado vacío. Claude asume que la herramienta tuvo éxito sin datos y alucina. Propaga siempre los fallos con is_error: true.

La Trampa del Control de Bucle

Un agente de soporte se detiene después de decir "Déjame consultar tu pedido". El código comprueba response.content[0].type == "text" para decidir que el agente ha terminado.

✗ Comprobación por Tipo de Contenido

Claude puede devolver texto y un bloque tool_use juntos. Comprobar el tipo de contenido termina el bucle prematuramente — la consulta nunca se ejecuta.

✓ Comprobación de stop_reason

Solo stop_reason == "end_turn" significa de forma fiable "terminado". Cuando Claude todavía necesita una herramienta, stop_reason es "tool_use" independientemente de cualquier texto.

La degradación elegante y la recuperación dependen de mantener el contexto correcto (identificadores exactos, importes, errores previos de herramientas) — no el máximo contexto. La guía rápida customer-support-agent muestra una ruta concreta de "degradar → escalar a un humano" mediante su campo redirect_to_agent.

🔗 Conectando Ideas: la ingeniería de contexto (seleccionar la ventana finita a lo largo de un bucle largo) apoya directamente la recuperación ante errores — ver el blog Effective Context Engineering en los recursos de este concepto.

Frameworks — LangGraph, Strands y PydanticAI

Concepto 4 — Conocimiento de reconocimiento de los principales frameworks de agentes

Frecuencia en el Examen:
Alta

🔷 LangGraph — máquinas de estado basadas en grafos

Un framework de orquestación de bajo nivel para agentes de larga duración y con estado, modelado como un grafo de Estado · Nodos · Aristas. Beneficios principales: ejecución duradera (reanudar tras un fallo), humano-en-el-bucle, memoria a corto y largo plazo, y mezclar pasos deterministas con pasos impulsados por el modelo en un mismo grafo.

from langgraph.graph import StateGraph, MessagesState, START, END
graph = StateGraph(MessagesState)
graph.add_node(mock_llm)
graph.add_edge(START, "mock_llm")
graph.add_edge("mock_llm", END)
graph = graph.compile()

🟠 Strands — nativo de AWS, impulsado por el modelo

Un SDK de código abierto (Python y TypeScript) que construye un agente a partir de tres piezas: un modelo, un prompt del sistema y un conjunto de herramientas. Un bucle de agente ligero, un decorador @tool, soporte para MCP y patrones multiagente integrados (Swarms, Grafos, Flujos de Trabajo, Agente-a-Agente). Integración de primera clase con AWS y observabilidad mediante OpenTelemetry; usado en producción por Amazon Q, Kiro y AWS Glue.

🟣 PydanticAI — agentes con seguridad de tipos

"La sensación de FastAPI para la IA generativa" — un framework de Python totalmente seguro en tipos y agnóstico al modelo. La validación de Pydantic en cada entrada/salida traslada clases enteras de errores al momento de escritura. Incluye el bucle del agente, salidas estructuradas, herramientas, MCP y búsqueda web, además de evaluaciones y observabilidad mediante Logfire.

Aquí solo necesitas un conocimiento de nivel de reconocimiento: para qué sirve cada framework, no cómo construir con él. El examen empareja una restricción con el framework correcto — memoriza el mapeo en la siguiente página.

Multiagente y Aislamiento de Contexto

Concepto 5 — Orquestador-trabajadores y la regla de aislamiento de contexto

Frecuencia en el Examen:
Alta
Sistema Multiagente
Varias instancias de LLM ejecutándose con contextos de conversación separados, coordinadas mediante código. El patrón común es orquestador-subagente: un agente líder crea y gestiona subagentes especializados para subtareas concretas.

Cómo Funciona el Sistema de Investigación

Según la propia función de Investigación de Claude: un agente líder planifica el trabajo y crea subagentes en paralelo. Cada subagente explora con su propia ventana de contexto y luego comprime los hallazgos de vuelta al líder. La separación de responsabilidades — herramientas, prompts y trayectorias distintas — reduce la dependencia de la ruta.

Aislamiento de contexto (dato clave para el examen): los subagentes no heredan el historial de conversación del coordinador. El líder debe pasar explícitamente la tarea/tema, o el subagente no tendrá con qué trabajar. No hay memoria compartida entre invocaciones.

Las Tres Situaciones Donde Gana el Multiagente

  • Contaminación de contexto — un solo contexto no puede contenerlo todo sin degradarse
  • Paralelismo — las subtareas pueden ejecutarse al mismo tiempo
  • Especialización — prompts/herramientas distintos mejoran el enfoque y la selección de herramientas

Los sistemas multiagente consumen muchos más tokens que un solo agente. Resérvalos para trabajo de alto valor, paralelizable y abierto — y empieza siempre preguntándote si un único agente bien diseñado bastaría.

Enfoque de Certificación

Cuándo NO Pasar a Multiagente

La trampa de la sobreingeniería y el escenario del informe incompleto

Empieza con un Solo Agente

✗ Sobreingeniería

Construir agentes separados para planificación, ejecución, revisión e iteración — perdiendo contexto en cada traspaso y gastando más tokens en coordinar que en ejecutar.

✓ Lo que Premia el Examen

Un único agente bien diseñado maneja la mayoría de los flujos de trabajo. Cada agente adicional es otro punto de fallo y coste de coordinación. Pasa a multiagente solo en las tres situaciones de la página anterior.

Rastreando una Salida Multiagente Incompleta

Un sistema de investigación despliega 5 subagentes; todos regresan con éxito. Pero el informe final solo cubre el primer tema en profundidad.

✗ Diagnóstico incorrecto: "las consultas del subagente de búsqueda eran demasiado estrechas" — buscó a fondo lo que se le asignó.
✓ Diagnóstico correcto: la descomposición del coordinador solo delimitó la síntesis a un tema. Si la salida está incompleta en alcance (no en profundidad), la descomposición del coordinador es casi siempre la causa raíz — no ningún subagente posterior.
