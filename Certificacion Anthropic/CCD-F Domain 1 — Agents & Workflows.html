Definition

Workflow vs Agent — Decision Criteria

Fixed orchestration paths vs LLM-driven autonomous decision-making

Workflow
A fixed, predetermined orchestration path where every step is defined at design time. The developer controls which models are called, in what order, with which inputs. Claude executes each step but does NOT decide what to do next. Think pipeline: step A → step B → step C, always in that order.
Agent
An LLM-driven autonomous system where Claude decides what action to take next based on the current state. The model controls the flow — it chooses which tools to call, how many iterations to run, and when to stop. The developer defines the tools and constraints; the model drives execution.

4 Decision Criteria

CriterionWorkflowAgent
Path predetermined?Yes — every step defined at design timeNo — path depends on model's observations
Number of steps fixed?Yes — same steps every executionNo — could be 1 step or 15 depending on task
Model decides next action?No — developer's code routes each stepYes — model selects tools and actions
Cost predictable?Yes — fixed API calls = predictable costNo — variable iterations = variable cost
The exam tests this distinction directly. If ALL 4 answers are "fixed/predetermined/yes" → Workflow. If ANY answer is "variable/model-decides" → Agent. There is no hybrid middle ground on the exam.

Manager/Supervisor Hierarchies

In complex systems, a manager agent delegates subtasks to worker subagents. The manager decides what to delegate and coordinates results. Workers execute focused tasks with scoped tools. This is the orchestrator-workers pattern.

Workflow vs Agent — Orchestration Patterns

5 Orchestration Patterns

PatternTypeWhen to Use
Prompt ChainingWorkflowSequential steps with validation gates between each
RoutingWorkflowClassify input → send to specialised handler
ParallelisationWorkflowIndependent subtasks that can run concurrently (fan-out/fan-in)
Orchestrator-WorkersAgentManager decomposes tasks dynamically, delegates to worker subagents
Evaluator-OptimizerAgentGenerate → evaluate → refine loop until quality threshold met

Workflow Code Pattern

# Workflow: Fixed pipeline — developer controls flow
summary = claude("Summarise this document", doc)
translation = claude("Translate to French", summary)
quality = claude("Rate translation quality 1-10", translation)
# Always 3 steps, always in this order

Agent Code Pattern

# Agent: Model-driven loop — Claude decides flow
while True:
    response = claude(messages, tools=tools)
    if response.stop_reason == "end_turn":
        break  # Claude decided it's done
    # Execute tool calls, append results, continue
    messages.append(execute_tools(response))

Workflow vs Agent — Exam Patterns

#1 — "Which orchestration pattern?": The exam describes a scenario and asks which pattern to use. Map: fixed steps → prompt chaining/routing. Variable steps, model decides → orchestrator-workers. Independent subtasks → parallelisation (fan-out/fan-in).
#2 — Fan-Out/Fan-In: Only use when subtasks are genuinely independent. If task B depends on task A's result, parallelisation is wrong — use prompt chaining.
#3 — Subagent Role: Subagents improve task execution by focusing on narrow subtasks with scoped tools. They do NOT communicate with each other directly — all communication flows through the coordinator/manager.
Trap: "Agent for everything": The exam often presents simple tasks where a workflow is the correct answer. A 3-step translation pipeline does NOT need an agent — it needs prompt chaining. Over-engineering with agents is a wrong answer.

Agent SDK & Construction Methods

Three ways to build Claude agents — SDK, custom loops, and managed platforms

Three Construction Approaches

ApproachWhat It IsWhen to Use
Claude Agent SDKAnthropic's official Python framework. Provides Agent class with built-in tool management, guardrails, handoffs, and tracing.Most production use cases — handles the loop, error recovery, and observability for you.
Custom Agent LoopRaw Messages API in a while loop. You control every aspect: tool execution, error handling, context management.When you need full control — custom retry logic, non-standard tool patterns, or the SDK doesn't support your architecture.
Managed DeploymentAnthropic-hosted or self-hosted agent infrastructure. Managed handles scaling, versioning, and monitoring.Enterprise production — when you need SLAs, scaling, and operational monitoring without building infra yourself.

SDK vs Custom Loop — Key Difference

SDK: The framework handles the agentic loop internally. You configure agent behaviour (tools, guardrails, handoffs). Custom Loop: You write the loop yourself — checking stop_reason, executing tools, appending results. The SDK is higher-level; the custom loop gives full control.

Agent SDK — Components

SDK Agent Definition

from anthropic.agents import Agent, Tool

agent = Agent(
    name="support_agent",
    model="claude-sonnet-4-6",
    tools=[lookup_order, process_refund, escalate],
    system_prompt="You are a customer support agent...",
    guardrails=[block_pii_exposure, require_identity],
    max_turns=25,
)

# The SDK handles the loop — you just run it
result = agent.run("I want to return my order")

Hooks for Deterministic Actions

Hooks provide deterministic enforcement within SDK agents:

  • PreToolUse — fires before a tool executes. Return block to prevent execution. Use for policy enforcement, input validation.
  • PostToolUse — fires after a tool returns. Use for output sanitisation, logging, data normalisation.
  • Guardrails — SDK-level constraints that check every turn. Block PII exposure, enforce identity verification, prevent dangerous actions.
Hooks are deterministic; prompts are probabilistic. If a rule MUST be enforced 100% of the time, it goes in a hook. If it's a preference, it goes in the system prompt.

Agent Construction — Exam Patterns

#1 — SDK vs Custom Loop: "Which approach gives the developer the MOST control?" → Custom loop. "Which approach handles the loop, tracing, and guardrails automatically?" → Agent SDK. Know the trade-off: SDK = less code, less control. Custom = more code, full control.
#2 — Hooks vs System Prompt: "Agent must NEVER process refunds without identity verification" → Hook (PreToolUse that blocks). "Agent should prefer formal tone" → System prompt. The keyword is MUST vs SHOULD.
#3 — max_turns: A safety parameter that caps the number of loop iterations. It's a safety net, NOT the primary termination mechanism. The primary mechanism is stop_reason: end_turn.
#4 — Handoffs in SDK: When one agent transfers control to another. The handoff includes context about what was done and what needs to happen next. The receiving agent starts fresh — it does NOT inherit the sending agent's conversation history unless explicitly passed.

Agentic Loop Patterns

Tool-use loops, stop_reason control, and error recovery

The Agentic Loop
The core pattern: (1) Send messages + tools to Claude, (2) Check stop_reason, (3) If tool_use → execute tool, append result, loop back to step 1, (4) If end_turn → exit loop, return response. The loop runs until Claude decides it's finished.

stop_reason Values

ValueMeaningAction
end_turnClaude finished its responseSTOP — exit the loop
tool_useClaude wants to call a toolCONTINUE — execute tool, append result, loop
max_tokensResponse hit the token limitHandle truncation — may need to continue
pause_turnModel paused for external inputWait for input, then resume
stop_reason is the ONLY reliable termination signal. Never parse text content ("I'm done") to determine if the loop should end. Never use content[0].type == "text" — Claude can return text alongside tool_use blocks.

Error Recovery & Graceful Degradation

Error Recovery Strategies

StrategyWhen to UseImplementation
Retry with backoffTransient failures (network, rate limits)Exponential backoff: 1s, 2s, 4s, max 3 retries
Fallback to simpler strategyComplex tool fails repeatedlyTry tool A → fail → try simpler tool B
Graceful degradationPartial failure in multi-step taskReturn available results, report what's missing
Human escalationAgent cannot progressStructured handoff with context summary

The isError Flag

When returning tool results to Claude, the is_error field tells the model the tool failed. Without it, Claude may interpret error text as a normal result and incorporate error messages into its response.

# WRONG — error text treated as content
{"type": "tool_result", "content": "Error: timeout"}

# CORRECT — flagged as error
{"type": "tool_result",
 "content": "Error: timeout after 30s",
 "is_error": true}

Loop Patterns — Exam Patterns

#1 — Three Anti-Patterns: (A) Parsing "I'm done" from text → unreliable. (B) Arbitrary iteration caps as PRIMARY control → wrong (OK as safety net). (C) Checking content[0].type == "text" → Claude can return text AND tool_use together.
#2 — is_error Flag: When asked "tool returns an error — what happens next?" the correct answer always involves is_error: true in the tool result, so Claude knows the execution failed.
#3 — Retry vs Escalate: Transient errors (network) → retry with backoff. Persistent errors (tool doesn't exist, permission denied) → escalate or fail gracefully. The exam tests whether you can distinguish transient from persistent.
#4 — tool_choice: "auto" = Claude may call a tool or not. "any" = Claude MUST call a tool. {"type":"tool","name":"X"} = forced specific tool. Forcing "any" when the agent is genuinely finished creates infinite loops.

Third-party frameworks and multi-agent design patterns

Third-Party Agent Frameworks

The CCD-F exam explicitly tests knowledge of third-party frameworks:

FrameworkKey FeatureBest For
StrandsAWS-native, managed lifecycleEnterprise AWS deployments with managed scaling
LangGraphGraph-based state machinesComplex workflows with branching and conditional paths
PydanticAIType-safe, schema-validated agentsWhen you need strong typing and schema validation
Exam Tip: The exam tests whether you can select the right framework for a given constraint. AWS-native → Strands. Complex state machines → LangGraph. Type safety → PydanticAI. Claude-native with built-in guardrails → Agent SDK.

Multi-Agent Context Rules

Two rules that apply regardless of framework:

  • Subagents do NOT inherit the coordinator's conversation history — context must be explicitly passed.
  • Subagents do NOT share memory between invocations — each call starts fresh.

Multi-Agent Topologies

Hierarchical vs Peer-to-Peer

TopologyHow It WorksWhen to Use
HierarchicalManager delegates to workers. All communication goes through manager.Clear task decomposition, need coordination and result synthesis.
Peer-to-PeerAgents communicate directly with each other via message passing.Collaborative tasks where agents negotiate or build on each other's work.

Context Window Management in Agents

Long-running agents face context window limits. Management strategies:

  • Progressive summarisation — compress earlier turns while preserving exact values (amounts, IDs)
  • /compact — Claude Code's built-in compaction that preserves key facts
  • Scratchpad files — write intermediate results to disk, read back when needed
  • Memory via tools — use a memory tool to store and retrieve key facts across turns

Frameworks — Exam Patterns

#1 — Framework Selection: "Need AWS-native managed agents" → Strands. "Need graph-based state machine with branching" → LangGraph. "Need type-safe validated agents" → PydanticAI. "Need Anthropic-native with built-in guardrails" → Claude Agent SDK.
#2 — Context Isolation: "New subagent ignores instructions given to the coordinator" → Context was not explicitly passed. Subagents start with empty context unless the coordinator includes relevant information.
#3 — Handoff vs Message-Passing: Handoffs transfer CONTROL (one agent stops, another starts). Message-passing shares DATA (both agents continue). The exam tests whether you match the mechanism to the need.
Trap: "Framework X is always better": No framework is universally best. Each has trade-offs. The correct answer matches framework capabilities to specific requirements.
