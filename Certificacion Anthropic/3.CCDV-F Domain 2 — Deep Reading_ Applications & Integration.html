Concept 1 · Definition

The Stateless Messages API

Task 2.1 — The one rule that underpins everything

High exam frequency
🔑 The Messages API is stateless. Claude remembers nothing between calls — you always send the full conversation history each turn. To continue a chat, append both Claude's reply and the next user message to the array.
message = anthropic.Anthropic().messages.create( model="claude-sonnet-4-6", max_tokens=1024, messages=[ {"role": "user", "content": "Hello, Claude"}, {"role": "assistant", "content": "Hello!"}, {"role": "user", "content": "Describe LLMs to me"}, ])

Every request has a model, max_tokens, and a messages array of alternating user/assistant turns. The response carries content (array of text/tool_use blocks), stop_reason, and usage (token counts for cost tracking).

Think of every API call as a brand-new conversation. Claude has no memory, no session, no cookies. The full message array IS the conversation — your code is the memory layer. This is why multi-turn chat apps must append every response before the next call, and why the Batch API is single-turn only.

Multi-Turn Assembly — The Alternating Roles Rule

The most-tested Messages API scenario

Scenario: A developer builds a chatbot but Claude seems to "forget" the conversation after every message. Each response acts as if it's the first turn.

Root Cause: The developer sends only the latest user message each call, not the full conversation history. Because the API is stateless, Claude sees a fresh, single-turn conversation every time.

Fix: Maintain a message array. After each response, append the assistant message, then the new user message, then call again with the full array. Roles must alternate: user → assistant → user → assistant.

📋 Exam Pattern: "Claude forgets the conversation" = developer isn't sending full history. "Claude ignores tool result" = assistant message with tool_use block wasn't included before the tool_result. Both are the stateless API rule applied differently.

Concept 1 · Case Study

The Missing Turn

Debugging stateless API misunderstandings

Bot sends only latest message — Claude has no memory ▶

Each API call must include the entire conversation. The developer's code only sent the latest user message, so Claude treated every call as turn 1. Fix: maintain an array, append assistant + user messages each turn, send the full array.

Tool result ignored — Claude makes up an answer ▶

The developer sent the tool_result but forgot to include the previous assistant message (containing the tool_use block). Without that assistant turn, the API can't link the result. Fix: append the full assistant response, then the user message with tool_result. Roles must alternate.

Thinking budget too high — request times out ▶

Extended thinking with budget_tokens above ~32K can exceed HTTP timeout limits. Fix: use the Batch API for large thinking budgets — it has a 24-hour processing window. Or use adaptive thinking with an effort level instead of a fixed budget.

SSE Streaming

Task 2.2 — Real-time token delivery for user-facing latency

High exam frequency

Set stream=true to receive the response incrementally via server-sent events (SSE) — tokens appear as they generate.

with client.messages.stream( max_tokens=1024, messages=[{"role":"user","content":"Hello"}], model="claude-sonnet-4-6") as stream: for text in stream.text_stream: print(text, end="", flush=True)
🔑 Event Flow: message_start → content_block_delta (many) → message_stop. An overloaded_error in the stream corresponds to HTTP 529. For any user-facing chatbot, streaming is the answer to "reduce perceived latency" — not batch, not lowering max_tokens.

FactDetail
Cost50% lower than standard

The Cost Decision — Stream vs Batch vs Cache

The exam's favourite trade-off

Scenario: You need to classify 50,000 support tickets overnight. A colleague suggests streaming. Another suggests the Batch API. A third suggests prompt caching.

Correct Answer: Batch API for the 50% cost reduction on bulk async work. Prompt caching on top if the system prompt + examples are reused across tickets (another up to 90% on the repeated prefix). Streaming is wrong — it's for user-facing latency, not bulk processing.

📋 Exam Decision Tree: User-facing chatbot → streaming. Overnight bulk / weekly reports → Batch API. Repeated long prefix (book, codebase, examples) → prompt caching. Pre-merge CI checks → synchronous (not batch — blocking). Batch + caching can be combined.

Concept 2 · Case Study

The Broken Cache

Why the cache never hits

Cache hit rate is 0% despite cache_control being set ▶

A dynamic timestamp sits before the cache breakpoint. Every call has a different prefix, so the cache never matches. Fix: move all dynamic content (timestamps, UUIDs, user IDs) AFTER the cache breakpoint. Stable content (system prompt, examples, documents) must come first in the order: tools → system → messages.

Batch job used for CI pre-merge checks — pipeline blocks for hours ▶

The Batch API has a 24-hour processing window — it's async, not real-time. CI checks need synchronous/streaming responses. Fix: use standard synchronous API calls for blocking CI checks. Reserve batch for non-blocking bulk work like overnight reports.

Chat with 100K-token book: 11.5s to first token — too slow ▶

Cache the book as a prompt prefix. After the first call (cache write), subsequent calls read from cache: 11.5s → 2.4s to first token (−79%) with 90% cost reduction. The book must be in the stable prefix, before any dynamic query content.

JSON Outputs & Strict Tool Use

Task 2.3 — Guaranteeing parseable output and handling errors

High exam frequency

Constrain Claude's response to a schema so downstream code always gets valid, parseable data.

FeatureWhat It DoesHow
JSON outputsWhole response is valid JSON matching schemaoutput_config.format
Strict tool useGuarantees schema validation on tool inputsstrict: true
🔑 Syntax ≠ Semantics: Constrained decoding removes JSON.parse errors, missing fields and type mismatches. But a wrong value ($150 instead of $1,500) is a SEMANTIC error the schema can't catch — that needs validation logic.

Schema Design Tips

Make a field required only when it's always present — otherwise Claude fabricates. Use ["string","null"] for optional fields. Add "other"/"unclear" to enums to avoid forced miscategorisation.

Task 2.3 — The transient vs permanent distinction

CodeNameAction
400invalid_requestFix request — don't retry

Concept 3 · Certification Focus

The 429 Decision — The Only Retryable 4xx

The most-tested error handling scenario

Scenario: Your agent receives a 429 error. A colleague suggests a tight retry loop. Another suggests fixing the request like any other 4xx.

Correct Answer: Exponential backoff honouring retry-after. A 429 is the ONLY 4xx that should be retried — it means the request is valid but you've hit a rate limit. A tight loop hammers the API and makes things worse.

📋 Exam Decision Tree: 400/401/403/404 → fix request, NEVER retry. 429 → backoff & retry (honour retry-after). 500/504/529 → retry with backoff. Mid-stream SSE error → handle in stream handler, not HTTP status.
❌ Wrong

"429 is a client error like 400 — fix the request."

✓ Correct

"429 means rate limited — the request is valid. Retry with exponential backoff."

Concept 3 · Case Study

The Wrong Retry

Debugging structured output and error handling

Valid JSON but wrong price — schema didn't catch it ▶

Structured Outputs guarantee syntax (valid JSON, correct fields) not semantics (correct values). A wrong price is a semantic error. Fix: add field-level validation in your code (range checks, cross-references) plus clear extraction instructions in the prompt.

Agent retries 401 five times before failing ▶

A 401 is an authentication error — the API key is invalid. Retrying will never fix it. Fix: fail immediately and report a credentials issue. Check whether the SDK's retry logic is misconfigured to include 401s.

Zod / Pydantic structured output from agent — SDK re-prompts on mismatch ▶

The Agent SDK validates the result and re-prompts if it doesn't match the schema. If it still fails within the retry limit, you get an error. For full type safety: Zod in TypeScript, Pydantic in Python. This gives you typed data you can drop straight into your app.

CLAUDE.md vs settings.json

Task 2.4 — Probabilistic conventions vs deterministic enforcement

High exam frequency

This is the exam's favourite config distinction: CLAUDE.md = probabilistic (guidance the model tries to follow). settings.json = deterministic (hooks, permissions, MCP servers that are always enforced).

FileNatureContainsWhen to Use
CLAUDE.mdProbabilisticProject conventions, commands, architecture"Prefer this style"
settings.jsonDeterministicHooks, MCP servers, permissions"MUST never happen"
🔑 Golden Rule: "MUST never happen" → a PreToolUse hook in settings.json (deterministic). "Prefer this style" → CLAUDE.md (probabilistic). A CLAUDE.md instruction alone will NOT reliably block a dangerous action.

Concept 4 · Certification Focus

Probabilistic vs Deterministic — The Config Trap

The most-tested config scenario

Scenario: A developer puts "never modify production database" in CLAUDE.md. An injected prompt convinces Claude to run a destructive query anyway.

Root Cause: CLAUDE.md is probabilistic — the model tries to follow it but isn't guaranteed to. A sufficiently crafted prompt can override it.

Fix: Add a PreToolUse hook in settings.json that blocks database-modifying commands (exit code 2 = deny). Deterministic enforcement can't be overridden by prompt injection.

📋 Exam Pattern: "MUST be enforced" → settings.json hook. "Should be followed" → CLAUDE.md. "Organisation-wide, non-overridable" → managed policy. "New developer doesn't see team conventions" → wrong scope (user vs project). CLAUDE.md targets <200 lines; it's loaded every session.
Domain 7 Link: This config distinction maps directly to the security domain. The trust hierarchy (D7) relies on settings.json hooks being deterministic. CLAUDE.md provides guidance; hooks provide enforcement. Both are needed for defence-in-depth.

Concept 4 · Case Study

The Ignored Convention

Debugging config scope and enforcement issues

New dev joins team — Claude Code doesn't follow team conventions ▶

The conventions are in the senior dev's user-scope CLAUDE.md (~/.claude/CLAUDE.md), not the project-scope one (.claude/CLAUDE.md). New team members don't inherit user-scope settings. Fix: move shared conventions to .claude/CLAUDE.md (committed to git) so every team member gets them automatically.

CLAUDE.md says "never use rm" but Claude runs it anyway ▶

CLAUDE.md is probabilistic — the model usually follows it, but a crafted prompt or edge case can override it. For hard requirements, add a PreToolUse hook in settings.json that checks for destructive commands and returns exit code 2 (block). Deterministic enforcement is the only reliable defence.

Community best-practice repo shows full settings hierarchy ▶

The claude-code-best-practice repo (63k★) documents every settings.json option with the scope hierarchy table: Managed → CLI → Local → Project → User. It covers hooks, permissions, MCP servers, model config, and memory. A good consolidated reference, but always cross-check against the official docs for enforcement details.
