▸ Conceptos en un vistazo
📨
Producer
Aplicación que publica mensajes (eventos) en un topic de Kafka. Decide a qué partición enviar cada mensaje.
📥
Consumer
Aplicación que lee mensajes de uno o más topics. Pertenece a un Consumer Group para paralelismo.
📁
Topic
Categoría o canal donde se organizan los mensajes. Equivalente a una tabla en BD o carpeta de archivos.
🔀
Partition
Subdivisión de un topic que permite paralelismo. Cada partición mantiene orden estricto (FIFO).
🔢
Offset
Identificador numérico incremental de cada mensaje dentro de una partición. Permite replay de eventos.
🖥️
Broker
Servidor Kafka que almacena datos y sirve a producers y consumers. Un cluster tiene múltiples brokers.
Entender estos conceptos es fundamental antes de escribir una sola línea de código con Kafka. Cada uno cumple un rol específico en la arquitectura.
Concepto
Descripción
Topic
Canal lógico donde se publican mensajes. Inmutable: una vez escrito, el mensaje no se modifica. Puedes tener topics como orders, payments, user-events. Inmutable
Partition
Cada topic se divide en particiones. Los mensajes dentro de una partición mantienen orden estricto. Más particiones = más paralelismo. Paralelismo
Offset
Número secuencial único por partición. Kafka no borra mensajes al leerlos: el consumer controla su posición con el offset. Permite replay de eventos. Replay
Broker
Nodo servidor del cluster Kafka. Almacena particiones y sirve requests. Un cluster típico tiene 3+ brokers para alta disponibilidad. HA
Consumer Group
Conjunto de consumers que se reparten las particiones de un topic. Cada partición solo la lee un consumer del grupo a la vez. Escalado horizontal automático. Scale-out
Replication
Cada partición tiene réplicas en otros brokers. El replication.factor=3 significa 3 copias. Si un broker cae, otro toma el relevo sin pérdida de datos. Fault-tolerant
Leader / Follower
Cada partición tiene un broker leader (lee/escribe) y N followers (replican). Si el leader falla, un follower es elegido automáticamente como nuevo leader. Failover
Producer Key
Clave opcional en cada mensaje. Mensajes con la misma key siempre van a la misma partición, garantizando orden para esa entidad. Ordering
Retention
Kafka retiene mensajes por tiempo (retention.ms) o por tamaño (retention.bytes). Por defecto: 7 días. Configurable a indefinido. Configurable
ACKs
acks=0: fire-and-forget. acks=1: leader confirma. acks=all: todas las réplicas confirman. Tradeoff entre latencia y durabilidad. Tradeoff
La arquitectura de Kafka está diseñada para escalabilidad horizontal, tolerancia a fallos y alto throughput. Cada componente tiene un propósito claro.
Cluster y Brokers
▸
Un cluster Kafka es un conjunto de brokers (servidores) que trabajan juntos
▸
Cada broker almacena un subconjunto de las particiones del cluster
▸
Los brokers se coordinan entre sí para elegir leaders y gestionar réplicas
▸
Se recomienda un mínimo de 3 brokers en producción para tolerancia a fallos
Topics y Particiones
▸
Un topic es un log append-only distribuido en N particiones
▸
Las particiones se distribuyen entre los brokers del cluster
▸
El orden de mensajes solo se garantiza dentro de una partición
▸
Número de particiones define el paralelismo máximo de consumers
Consumer Groups
▸
Cada consumer group lee el topic completo de forma independiente
▸
Dentro del grupo, cada partición se asigna a exactamente un consumer
▸
Si un consumer cae, sus particiones se rebalancean a otros del grupo
▸
Añadir consumers al grupo = escalado horizontal automático
Replicación y Durabilidad
▸
Cada partición tiene un leader y N-1 followers (réplicas)
▸
ISR (In-Sync Replicas): followers que están al día con el leader
▸
min.insync.replicas=2 con acks=all garantiza que no se pierde ningún mensaje
▸
ZooKeeper (legacy) o KRaft (moderno) coordina la elección de leaders
Almacenamiento
▸
Los mensajes se persisten en disco en ficheros de segmento ordenados
▸
Kafka usa zero-copy y sequential I/O para rendimiento extremo
▸
Política de retención configurable: por tiempo, por tamaño, o compaction
▸
Log compaction mantiene solo el último valor por key (ideal para CDC)
KRaft (Sin ZooKeeper)
▸
Desde Kafka 3.3+, ZooKeeper ya no es necesario: el protocolo KRaft integra la gestión de metadatos
▸
Arquitectura simplificada: menos componentes que desplegar y operar
▸
Arranque más rápido y mejor rendimiento en clusters grandes
▸
En Kafka 4.0 ZooKeeper fue eliminado oficialmente KRaft
El Producer es la aplicación que envía mensajes a Kafka. Controla a qué topic y partición van los eventos, y qué nivel de garantía (acks) requiere.
▸ Producer con Java puro (kafka-clients)
// Dependencia: org.apache.kafka:kafka-clients:3.7.0

Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("key.serializer",
    "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer",
    "org.apache.kafka.common.serialization.StringSerializer");
props.put("acks", "all");       // Máxima durabilidad
props.put("retries", "3");      // Reintentos automáticos

try (KafkaProducer<String, String> producer =
        new KafkaProducer<>(props)) {

    // Crear el registro (key, value)
    ProducerRecord<String, String> record =
        new ProducerRecord<>(
            "orders",         // topic
            "order-123",     // key → misma partición
            "{\"id\":123,\"total\":59.99}"  // value (JSON)
        );

    // Enviar async con callback
    producer.send(record, (metadata, ex) -> {
        if (ex == null) {
            System.out.printf("Enviado a %s P%d offset %d%n",
                metadata.topic(), metadata.partition(),
                metadata.offset());
        } else {
            ex.printStackTrace();
        }
    });
}
▸ Configuraciones importantes del Producer
Propiedad
Efecto
acks
0: no espera confirmación (más rápido, riesgo de pérdida). 1: confirma el leader. all: confirman todas las réplicas ISR. acks=all recomendado
retries
Número de reintentos en caso de error transitorio. Con enable.idempotence=true no se duplican mensajes. Idempotente
batch.size
Tamaño del batch en bytes antes de enviar. Más grande = mejor throughput, más latencia. Default: 16384 (16 KB). Tradeoff
linger.ms
Tiempo máximo de espera para acumular mensajes en un batch. 0 = enviar inmediatamente. 5-20 ms = buen balance. Tuning
compression.type
none, gzip, snappy, lz4, zstd. Compresión reduce I/O de red y disco. lz4 o zstd recomendados. Recomendado
El Consumer lee mensajes de los topics. Se une a un Consumer Group para repartir la carga. Controla su propio offset, lo que permite reiniciar el consumo desde cualquier punto.
▸ Consumer con Java puro (kafka-clients)
// Dependencia: org.apache.kafka:kafka-clients:3.7.0

Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id", "payment-service");
props.put("key.deserializer",
    "org.apache.kafka.common.serialization.StringDeserializer");
props.put("value.deserializer",
    "org.apache.kafka.common.serialization.StringDeserializer");
props.put("auto.offset.reset", "earliest"); // Desde el inicio
props.put("enable.auto.commit", "false");  // Commit manual

try (KafkaConsumer<String, String> consumer =
        new KafkaConsumer<>(props)) {

    // Suscribirse al topic
    consumer.subscribe(List.of("orders"));

    while (true) {
        ConsumerRecords<String, String> records =
            consumer.poll(Duration.ofMillis(500));

        for (ConsumerRecord<String, String> r : records) {
            System.out.printf(
                "Key: %s | Value: %s | P: %d | Offset: %d%n",
                r.key(), r.value(),
                r.partition(), r.offset());

            // Procesar el mensaje...
            processOrder(r.value());
        }

        // Commit manual después de procesar
        consumer.commitSync();
    }
}
▸ Semánticas de entrega
Semántica
Descripción
At-most-once
Commit del offset antes de procesar. Si el consumer falla, el mensaje se pierde. Rápido pero arriesgado. Riesgo
At-least-once
Commit del offset después de procesar. Si falla tras procesar pero antes del commit, se reprocesa. El consumer debe ser idempotente. Recomendado
Exactly-once
Con transacciones Kafka (isolation.level=read_committed) + producer idempotente. Garantiza procesamiento único. Avanzado
Spring Kafka simplifica drásticamente la integración con Kafka. Con anotaciones y autoconfiguración, un producer/consumer se reduce a unas pocas líneas.
Producer — Spring Boot
// application.yml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      key-serializer: StringSerializer
      value-serializer: JsonSerializer

// OrderProducer.java
@Service
public class OrderProducer {
  private final KafkaTemplate<String, Order> kafka;

  public OrderProducer(KafkaTemplate<...> kafka) {
    this.kafka = kafka;
  }

  public void send(Order order) {
    kafka.send("orders",
        order.getId(),   // key
        order);          // value → JSON auto
  }
}
Consumer — Spring Boot
// application.yml
spring:
  kafka:
    consumer:
      group-id: payment-service
      auto-offset-reset: earliest
      key-deserializer: StringDeserializer
      value-deserializer: JsonDeserializer
      properties:
        spring.json.trusted.packages: "*"

// OrderConsumer.java
@Component
public class OrderConsumer {

  @KafkaListener(
      topics = "orders",
      groupId = "payment-service")
  public void handle(Order order) {
    // Spring deserializa JSON → Order
    System.out.println(
        "Pedido: " + order.getId());
    processPayment(order);
  }
}

✓ Usa Kafka cuando...

▸Necesitas desacoplar microservicios con comunicación asíncrona y event-driven.
▸Procesas grandes volúmenes de datos en tiempo real (logs, clicks, IoT, transacciones).
▸Requieres replay de eventos: volver a procesar datos históricos cuando se despliega un nuevo servicio.
▸Implementas CQRS o Event Sourcing y necesitas un log de eventos inmutable.
▸Necesitas que múltiples consumers lean los mismos datos de forma independiente.
▸Tu sistema necesita alta disponibilidad y tolerancia a fallos sin pérdida de datos.
▸Haces data pipelines: ingestar datos de múltiples fuentes a un data lake o data warehouse.

✗ No uses Kafka cuando...

▸Solo necesitas un request-response simple entre dos servicios (usa REST o gRPC).
▸Tu proyecto es pequeño con bajo volumen de mensajes (RabbitMQ o Redis Pub/Sub es más simple).
▸Necesitas routing complejo de mensajes con exchange/binding (RabbitMQ es mejor).
▸Buscas una cola de tareas con prioridades y delayed messages (usa RabbitMQ o SQS).
▸No tienes equipo DevOps para operar un cluster Kafka (considera servicios gestionados como Confluent o MSK).
▸La latencia sub-milisegundo es crítica y el volumen es bajo (comunicación directa es mejor).

Estos son los patrones arquitectónicos más comunes implementados con Kafka. Entenderlos te ayudará a diseñar sistemas robustos y escalables.
Event-Driven Architecture
▸
Los servicios publican eventos cuando algo ocurre (OrderCreated, PaymentCompleted)
▸
Otros servicios reaccionan a esos eventos de forma desacoplada
▸
Kafka actúa como el sistema nervioso central del ecosistema
CQRS + Event Sourcing
▸
Commands producen eventos que se almacenan en Kafka como fuente de verdad
▸
Consumers materializan vistas optimizadas para lectura (Query side)
▸
Replay completo del estado reconstruyendo desde el offset 0
Saga Pattern
▸
Transacciones distribuidas coordinadas mediante eventos Kafka
▸
Cada servicio publica su resultado y escucha los de otros
▸
Compensación automática si un paso falla (saga de compensación)
Change Data Capture (CDC)
▸
Captura cambios en la BD y los publica como eventos en Kafka
▸
Herramientas como Debezium + Kafka Connect lo automatizan
▸
Log compaction mantiene el último estado de cada registro
Dead Letter Queue (DLQ)
▸
Mensajes que fallan N veces se envían a un topic especial (DLT)
▸
Permite investigar errores sin bloquear el consumer principal
▸
Spring Kafka lo implementa con @RetryableTopic + @DltHandler
Kafka Streams
▸
Librería para procesamiento de streams stateful sobre Kafka
▸
Operaciones: filter, map, groupBy, aggregate, join, windowing
▸
Sin infraestructura adicional: se ejecuta como un JAR normal
▸ Ejemplo: flujo Event-Driven con Spring Kafka
// OrderService publica evento
@Service
public class OrderService {
  private final KafkaTemplate<String, OrderEvent> kafka;

  public Order createOrder(OrderRequest req) {
    Order order = orderRepo.save(toEntity(req));
    // Publicar evento para que otros servicios reaccionen
    kafka.send("order-events",
        order.getId(),
        new OrderEvent("CREATED", order));
    return order;
  }
}

// PaymentService reacciona al evento
@Component
public class PaymentListener {
  @KafkaListener(topics = "order-events")
  public void onOrderCreated(OrderEvent event) {
    if ("CREATED".equals(event.getType())) {
      processPayment(event.getOrder());
      // Publicar resultado del pago
      kafka.send("payment-events",
          event.getOrderId(),
          new PaymentEvent("COMPLETED", ...));
    }
  }
}

// NotificationService reacciona a ambos
@Component
public class NotificationListener {
  @KafkaListener(topics = {"order-events", "payment-events"})
  public void onEvent(String payload) {
    sendNotification(payload);
  }
}

Resumen

Apache Kafka es la columna vertebral de arquitecturas modernas basadas en eventos. Su modelo de log distribuido, combinado con la persistencia, el replay y el escalado horizontal, lo convierten en la elección natural para sistemas que necesitan procesar grandes volúmenes de datos en tiempo real con garantías de durabilidad. Con Spring Kafka, la integración es tan sencilla como añadir una anotación.
