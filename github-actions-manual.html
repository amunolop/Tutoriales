QUÉ ES GITHUB ACTIONS
GitHub Actions es el sistema de CI/CD integrado en GitHub. Automatiza cualquier tarea en respuesta a eventos del repositorio — push, pull request, release, cron, llamada manual. Se define en ficheros YAML dentro de .github/workflows/. Gratis para repositorios públicos. Para privados: 2.000 min/mes en el plan Free.

LA JERARQUÍA — WORKFLOW · JOB · STEP
Cómo leer el diagrama: El Workflow es el fichero .yml completo. El trigger (azul) lo dispara. Cada Job (verde) corre en su propio runner aislado. Los Steps (gris) se ejecutan secuencialmente dentro del job. Las Actions (morado) son bloques reutilizables del Marketplace. El job deploy (rojo) depende de test con needs: y tiene un environment production con aprobación humana.

RUNNERS — DÓNDE CORRE EL CÓDIGO
GitHub-hosted (gratis)
Máquinas virtuales gestionadas por GitHub. Se destruyen al terminar el job. Opciones:

ubuntu-latest — Linux Ubuntu (el más usado)
windows-latest — Windows Server
macos-latest — macOS (consume 10× más minutos)

Incluyen: Node, Python, Java, Docker, Git, etc. preinstalados.
Self-hosted
Tu propio servidor registrado como runner. Instalar el agente de GitHub y arrancarlo. Útil cuando: necesitas hardware específico, acceso a red interna, recursos que no están en los runners de GitHub, o quieres eliminar el límite de minutos.
Larger runners (pago)
Runners con más CPU/RAM para builds pesados. 4, 8, 16, 32 cores. Facturación por minuto a precio mayor que el estándar. Útil para compilaciones de proyectos grandes donde el runner estándar (2 cores) es demasiado lento.
ANATOMÍA DE UN WORKFLOW COMPLETO
.github/workflows/ci.yml YAML 
# ① Nombre del workflow — aparece en la pestaña Actions
name: CI · Build & Test

# ② Triggers — qué eventos disparan este workflow
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]
  workflow_dispatch:   # permite lanzarlo manualmente

# ③ Variables de entorno globales
env:
  NODE_VERSION: '20'
  REGISTRY: ghcr.io

# ④ Los jobs del workflow
jobs:

    # Nombre del job — puede ser cualquier identificador
  build-and-test:
    name: Build & Test
    runs-on: ubuntu-latest   # ⑤ el runner

        # ⑥ Permisos del GITHUB_TOKEN para este job
    permissions:
      contents: read
      packages: write

    steps:

            # ⑦ Checkout del código
      - name: Checkout
        uses: actions/checkout@v4   # Action del Marketplace

            # ⑧ Setup del entorno
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: npm           # cachea node_modules

            # ⑨ Comandos shell
      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}  # ⑩ Secret

            # ⑪ Condicional — solo en main
      - name: Build Docker image
        if: github.ref == 'refs/heads/main'
        run: docker build -t myapp .

            # ⑫ Outputs — pasar datos al siguiente job
      - name: Set version output
        id: version
        run: echo "tag=$(git describe --tags)" >> $GITHUB_OUTPUT
LAS EXPRESIONES — SINTAXIS ${{ }}
Todo lo que va dentro de ${{ }} es una expresión de GitHub Actions. Puede ser una variable, un secreto, un contexto o una función.
ExpresiónQué devuelve
${{ secrets.MI_TOKEN }}El secreto MI_TOKEN del repositorio (cifrado, nunca se imprime)
${{ env.NODE_VERSION }}Variable de entorno definida en env:
${{ github.ref }}La rama/tag que disparó el evento: refs/heads/main
${{ github.sha }}El commit SHA completo
${{ github.actor }}El usuario que disparó el workflow
${{ github.event_name }}El evento que lo disparó: push, pull_request, etc.
${{ runner.os }}El SO del runner: Linux, Windows, macOS
${{ steps.mi-step.outputs.tag }}Output generado por un step anterior con id mi-step
${{ needs.build.outputs.version }}Output de un job previo llamado build
${{ matrix.node }}El valor de la dimensión node en una matrix build
${{ toJSON(github) }}El contexto github completo como JSON (útil para debug)
${{ success() }}True si todos los steps anteriores tuvieron éxito
${{ failure() }}True si algún step anterior falló
${{ always() }}Siempre true — para steps que deben ejecutar siempre
LOS TRIGGERS MÁS USADOS
El trigger define cuándo se ejecuta el workflow. Puede haber uno o varios en el mismo fichero. Si hay varios, cualquiera de ellos puede disparar el workflow.
PUSH Y PULL_REQUEST
on:
    # Trigger en push — con filtros de rama y path
  push:
    branches:
      - main
      - develop
      - 'release/**'      # glob: release/1.0, release/2.0...
    branches-ignore:
      - 'docs/**'          # ignora ramas que empiezan por docs/
    paths:
      - 'src/**'           # solo si cambia algo en src/
      - 'package.json'
    paths-ignore:
      - '**.md'            # ignora cambios solo en markdown
    tags:
      - 'v*'              # dispara en tags tipo v1.0, v2.3.1

    # Pull request — con tipos de evento
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened]
        # opened: PR creada
        # synchronize: nuevo commit en la PR
        # reopened: PR reabierta
SCHEDULE — CRON
on:
  schedule:
        # Sintaxis cron: min hora día mes día-semana
    - cron: '0 8 * * 1-5'    # lunes a viernes a las 8:00 UTC
    - cron: '0 0 * * 0'      # cada domingo a medianoche
    - cron: '*/15 * * * *'   # cada 15 minutos
    - cron: '0 9 1 * *'      # el día 1 de cada mes a las 9:00

# Atención: los workflows inactivos (sin push en 60 días)
# son desactivados por GitHub automáticamente
WORKFLOW_DISPATCH — MANUAL
on:
  workflow_dispatch:
    inputs:
      environment:
        description: 'Entorno de deploy'
        required: true
        default: 'staging'
        type: choice
        options: [staging, production]
      version:
        description: 'Tag a desplegar'
        required: false
        type: string
      debug:
        description: 'Activar debug'
        required: false
        type: boolean
        default: false

# Usar los inputs en el workflow:
jobs:
  deploy:
    steps:
      - name: Deploy
        run: ./deploy.sh ${{ inputs.environment }} ${{ inputs.version }}

JOBS — UNIDADES DE EJECUCIÓN
Cada job corre en su propio runner, en paralelo por defecto. Si un job depende de otro, se usa needs: para establecer el orden. Los jobs en paralelo reducen el tiempo total del workflow.
DEPENDENCIAS ENTRE JOBS — NEEDS
jobs:

  test:
    runs-on: ubuntu-latest
    steps:
      - run: npm test

  build:
    runs-on: ubuntu-latest
    needs: test          # espera a que test termine OK
    steps:
      - run: npm run build

  deploy-staging:
    runs-on: ubuntu-latest
    needs: build          # espera a build
    steps:
      - run: ./deploy.sh staging

  deploy-production:
    runs-on: ubuntu-latest
    needs: [test, build]   # espera a AMBOS
    if: github.ref == 'refs/heads/main'
    steps:
      - run: ./deploy.sh production
El flujo resultante: test y build en paralelo → si test pasa, build ejecuta → deploy-staging espera a build → deploy-production espera a test Y build, y solo en main.
OUTPUTS ENTRE JOBS
jobs:
  build:
    runs-on: ubuntu-latest
        # Declarar los outputs del job
    outputs:
      image-tag: ${{ steps.tag.outputs.value }}
      version: ${{ steps.ver.outputs.value }}
    steps:
      - id: tag
        run: echo "value=ghcr.io/myapp:${{ github.sha }}" >> $GITHUB_OUTPUT
      - id: ver
        run: echo "value=$(cat package.json | jq -r .version)" >> $GITHUB_OUTPUT

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "Desplegando ${{ needs.build.outputs.image-tag }}"
      - run: docker pull ${{ needs.build.outputs.image-tag }}
CONCURRENCY — CANCELAR RUNS OBSOLETOS
# Cancelar el run anterior si llega uno nuevo para la misma rama
# Evita deploys en paralelo o tests redundantes
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

# Variante para deploy — no cancelar en production
concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}

STEPS — TIPOS Y OPCIONES
steps:
    # Tipo 1: Comando shell
  - name: Comando simple
    run: echo "Hola"

    # Tipo 1b: Multi-línea
  - name: Múltiples comandos
    run: |
      npm ci
      npm test
      npm run build

    # Tipo 2: Action del Marketplace
  - name: Checkout
    uses: actions/checkout@v4
    with:
      fetch-depth: 0        # 0 = historial completo

    # Tipo 3: Action local (en el mismo repo)
  - name: Mi Action custom
    uses: ./.github/actions/mi-action

    # Opciones comunes de cualquier step:
  - name: Step con opciones
    id: mi-step              # para referenciar su output
    if: success()             # condición de ejecución
    continue-on-error: true # no falla el job si falla el step
    timeout-minutes: 10     # cancela si tarda más de 10 min
    env:
      MI_VAR: valor           # variable solo para este step
    run: echo "ejecutando"

CACHÉ — ACELERAR WORKFLOWS
steps:
  - uses: actions/checkout@v4

    # Opción A: caché manual con actions/cache
  - name: Cache node_modules
    uses: actions/cache@v4
    with:
      path: ~/.npm
      key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
      restore-keys: |
        ${{ runner.os }}-node-

    # Opción B: caché integrada en setup-node (más simple)

    with:
      node-version: '20'
      cache: 'npm'          # cachea automáticamente ~/.npm

  - run: npm ci

    # Caché de Maven (Java)
  - uses: actions/setup-java@v4
    with:
      java-version: '21'
      distribution: 'temurin'
      cache: 'maven'       # cachea ~/.m2/repository
SECRETS — CREDENCIALES SEGURAS
Los secrets son variables cifradas que nunca se imprimen en los logs. Si intentas hacer echo ${{ secrets.MI_TOKEN }}, GitHub lo reemplaza por *** automáticamente. Se definen en el repositorio, en la organización o en un entorno (environment).
NIVELES DE SECRETS
NivelDónde se defineDisponible enCuándo usar
Repository secretSettings → Secrets → ActionsTodos los workflows del repoTokens específicos de ese repo
Environment secretSettings → Environments → [env] → SecretsSolo workflows que usan ese environmentCredentials de producción vs staging distintas
Organization secretOrg Settings → SecretsRepos de la organización seleccionadosTokens compartidos entre múltiples repos
GITHUB_TOKENAutomático — no hay que crearloSiempre disponibleAutenticarse con GitHub API, push al repo, etc.
USO DE SECRETS EN EL WORKFLOW
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:

            # Como variable de entorno del step
      - name: Deploy
        env:
          DO_TOKEN: ${{ secrets.DIGITALOCEAN_TOKEN }}
          DB_URL: ${{ secrets.DATABASE_URL }}
        run: ./deploy.sh

            # Como parámetro de una Action
      - name: Login Docker
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}  # automático

            # SSH a servidor remoto
      - name: Deploy via SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.VPS_HOST }}
          username: ${{ secrets.VPS_USER }}
          key: ${{ secrets.VPS_SSH_KEY }}
          script: |
            cd /app
            docker compose pull
            docker compose up -d
GITHUB_TOKEN — EL SECRET AUTOMÁTICO
GITHUB_TOKEN se genera automáticamente para cada run. Permite autenticarse con la API de GitHub para hacer operaciones en el propio repo — crear releases, comentar en PRs, publicar packages, etc. Caduca al terminar el workflow.
# Permisos del GITHUB_TOKEN — declarar los mínimos necesarios
# Se puede definir a nivel de workflow o de job
permissions:
  contents: write       # push, crear releases
  packages: write       # publicar en GHCR
  pull-requests: write  # comentar en PRs
  issues: write         # comentar en issues
  security-events: write # reportes de seguridad
  id-token: write       # OIDC para AWS/GCP sin secrets

# Uso del GITHUB_TOKEN en el workflow
steps:
  - name: Crear release
    uses: softprops/action-gh-release@v1
    with:
      files: dist/*.zip
      token: ${{ secrets.GITHUB_TOKEN }}
ENVIRONMENTS — ENTORNOS DE DEPLOY
Los Environments permiten definir reglas de deploy por entorno — staging, production — con sus propios secrets, aprobaciones y tiempos de espera. Un job que usa un environment espera a que se cumplan las reglas antes de ejecutar.
CREAR Y CONFIGURAR UN ENVIRONMENT
1
Repo → Settings → Environments → New environment
Crear un environment llamado production o staging.
2
Deployment protection rules
Required reviewers: personas que deben aprobar el deploy antes de ejecutar.
Wait timer: minutos de espera obligatoria antes de ejecutar (ej: 5 min para dar tiempo a cancelar).
Allowed branches: solo deploys desde main, por ejemplo.
3
Secrets del environment
Añadir secrets específicos de este entorno. Un secret de environment tiene prioridad sobre el secret del repo con el mismo nombre — permiten tener DATABASE_URL de staging en staging y de producción en producción.
USAR ENVIRONMENTS EN EL WORKFLOW
jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://staging.miapp.com  # se muestra en el UI
    steps:
      - run: ./deploy.sh staging
        env:
                    # Este DATABASE_URL viene del environment staging
          DATABASE_URL: ${{ secrets.DATABASE_URL }}

  deploy-production:
    runs-on: ubuntu-latest
    needs: deploy-staging    # espera a staging
    environment:
      name: production
      url: https://miapp.com
        # ← Si production tiene Required reviewers,
        # el workflow se pausa aquí hasta que alguien apruebe
    steps:
      - run: ./deploy.sh production
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
                    # ← El mismo nombre pero ahora viene de production
💡 El flujo completo con aprobación humana
Push a main → CI ejecuta tests → build Docker → deploy en staging automático → el workflow se pausa → GitHub envía notificación al reviewer → el reviewer inspecciona staging y hace click en "Approve" → deploy en producción ejecuta. Sin tocar más código. Sin scripts de aprobación. Todo gestionado por GitHub.
MATRIX BUILDS — RUNS EN PARALELO
Con matrix puedes ejecutar el mismo job en múltiples combinaciones de variables. Ideal para testear en varias versiones de Node/Java/Python, en varios sistemas operativos, o cualquier combinación de parámetros.
MATRIX BÁSICA — MÚLTIPLES VERSIONES
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [18, 20, 22]   # genera 3 jobs en paralelo
    steps:
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm test
MATRIX MULTI-DIMENSIONAL
jobs:
  test:
    strategy:
      fail-fast: false     # no cancelar todos si uno falla
      max-parallel: 6     # máximo 6 jobs en paralelo
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: [18, 20]
                # 3 OS × 2 versiones = 6 jobs en paralelo

    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm test
EXCLUDE E INCLUDE — PERSONALIZAR LA MATRIX
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest, macos-latest]
    node: [18, 20, 22]

        # Excluir combinaciones específicas
    exclude:
      - os: windows-latest
        node: 18    # no testear Node 18 en Windows
      - os: macos-latest
        node: 18    # no testear Node 18 en macOS

        # Añadir combinaciones extra con propiedades adicionales
    include:
      - os: ubuntu-latest
        node: 20
        coverage: true   # propiedad extra solo en esta combinación

steps:
  - name: Run tests
    run: npm test
  - name: Coverage
    if: matrix.coverage == true
    run: npm run coverage
MATRIX DINÁMICA — DESDE SCRIPT
jobs:
    # Job 1: generar la matrix dinámicamente
  setup:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.set-matrix.outputs.matrix }}
    steps:
      - id: set-matrix
        run: |
                    # Leer los servicios a testear de un fichero
          SERVICES=$(cat services.json)
          echo "matrix={\"service\":$SERVICES}" >> $GITHUB_OUTPUT

    # Job 2: usar la matrix generada
  test-services:
    needs: setup
    runs-on: ubuntu-latest
    strategy:
      matrix: ${{ fromJSON(needs.setup.outputs.matrix) }}
    steps:
      - run: ./test.sh ${{ matrix.service }}

CASO 3 — DOCKER BUILD + PUSH A GHCR + DEPLOY EN DIGITALOCEAN
# .github/workflows/release.yml — el pipeline completo
name: Release
on:
  push: { tags: ['v*'] }

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-push:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    outputs:
      image: ${{ steps.meta.outputs.tags }}
    steps:
      - uses: actions/checkout@v4

      - name: Login GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}

      - name: Build & Push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy:
    needs: build-push
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://miapp.com
    steps:
      - name: Deploy en DigitalOcean
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.DO_HOST }}
          username: root
          key: ${{ secrets.DO_SSH_KEY }}
          script: |
            docker pull ${{ needs.build-push.outputs.image }}
            docker stop app || true
            docker rm app || true
            docker run -d --name app \
              -p 80:8080 \
              --env-file /app/.env \
              ${{ needs.build-push.outputs.image }}

⚠️ El error más común — pinear versiones de Actions
Usar actions/checkout@v4 es más seguro que actions/checkout@main porque si el autor de la Action hace un cambio breaking, tu workflow sigue funcionando. Para máxima seguridad en entornos críticos, pinear al SHA completo: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 — así nadie puede cambiar lo que ejecutas aunque cambie el tag.
