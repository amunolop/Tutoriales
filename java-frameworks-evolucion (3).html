1997 Era CGI
Java Servlets Servlet 2.1 La petición llega, tú escribes el HTML a mano
Problema

CGI creaba un proceso nuevo por cada petición. Lento, sin reutilización de código ni estado entre peticiones.

Solución

Servlets: clases Java persistentes en Tomcat. Un único proceso atiende múltiples peticiones. Se introduce el ciclo init → service → destroy.

2001 Era MVC
Apache Struts Struts 1.x Por fin: separar la vista del controlador
Problema

Los Servlets mezclaban lógica y presentación. Se necesitaba un patrón que separara responsabilidades.

Solución

Struts impuso el patrón MVC. Un ActionServlet central enruta las peticiones. Las Actions contienen la lógica. Las JSPs solo pintan.

2004 Era Componentes
JavaServer Faces JSF 1.0 La UI como árbol de componentes, no como plantillas de texto
Problema

Struts seguía siendo orientado a peticiones HTTP crudas. El desarrollador construía la vista página a página con JSPs. Sin componentes reutilizables ni gestión automática del estado del formulario.

Solución

JSF introduce un modelo de componentes de UI (botones, tablas, formularios) con estado gestionado por el servidor. El ciclo de vida del formulario lo gestiona el framework, no el desarrollador.

Diferencia clave con Struts: en Struts tú gestionabas cada campo del formulario a mano. En JSF el framework mantiene el estado de los componentes entre peticiones (ViewState) y ejecuta el ciclo de validación y binding automáticamente. Tú solo defines el Bean y el Facelet.
2003 Era IoC / DI
Spring Framework Spring 1.0 El contenedor gestiona los objetos por ti
Problema

J2EE / EJBs eran enormes. El código estaba lleno de new MiServicio(). Sin gestión automática de dependencias ni ciclos de vida.

Solución

Spring introdujo el IoC Container: el contenedor crea los beans y los inyecta donde se necesitan. Tú declaras qué necesitas, Spring lo construye.

El cambio mental clave: antes tú creabas los objetos (new Servicio()). Con IoC el framework los crea e inyecta. Tus clases ya no dependen unas de otras directamente — dependen del contenedor.

2014 Era Boot
Spring Boot Boot 1.0 Cero configuración, arranca en segundos
Problema

Spring era potente pero configurarlo era costoso: decenas de XMLs, dependencias manuales, servidor de aplicaciones externo. Un proyecto nuevo tardaba días.

Solución

Spring Boot = Spring + autoconfiguración + servidor embebido. Un solo @SpringBootApplication y mvn spring-boot:run. El framework detecta el classpath y se configura solo.

El salto de productividad más grande: lo que antes requería días de configuración pasó a funcionar en 5 minutos. Spring Boot democratizó el desarrollo Java profesional.
2014 Era Batch

2019 Era Cloud
Quarkus Quarkus 1.0 Java nativo para la era de los contenedores
Problema

Spring Boot arranca en ~3-5 segundos y consume ~250 MB de RAM. En Kubernetes con cientos de pods o en funciones serverless, esto es demasiado.

Solución

Quarkus mueve el trabajo pesado (reflexión, escaneo de anotaciones, DI) al tiempo de compilación. Con GraalVM compila a binario nativo: arranca en <50ms y usa ~30 MB.

La pregunta que cada generación intentó responder: ¿cuánto debería hacer el framework por ti, y cuánto deberías controlar tú? La evolución no fue un camino único — hubo bifurcaciones donde dos respuestas distintas compitieron a la vez (JSF vs Spring MVC). La que ganó no fue la más potente, sino la menos invasiva.
1997 Herramientas
sin estructura
Java Servlets
Herencia pura

El primer paso fue simplemente meter Java en el servidor. HttpServlet te daba herramientas — request, response, el ciclo init/destroy — pero ninguna opinión sobre cómo organizar tu código. La herencia era el único contrato: extiende esta clase y sobreescribe doGet(). Lo demás era territorio libre.

El resultado predecible: lógica de negocio, SQL y generación de HTML mezclados en el mismo método. Funcionaba, pero no escalaba. El framework te dio un martillo y te dijo "construye lo que quieras".

Lo que aportó
Servidor persistente. Un proceso para múltiples peticiones. Java en la web.
Lo que faltaba
Cualquier tipo de estructura. El desarrollador organizaba (o no) a su criterio.
2001 Estructura
por herencia
Apache Struts
MVC obligatorio via herencia

Struts fue la primera vez que un framework Java dijo: "no solo te doy herramientas, te digo dónde va cada cosa". El patrón MVC pasó de ser una recomendación a ser un contrato. Si quieres que tu lógica funcione, extiende Action. Si quieres que el formulario funcione, extiende ActionForm.

El mecanismo seguía siendo herencia — el mismo que Servlets — pero ahora con propósito arquitectural: separar controlador, modelo y vista. El ActionServlet central enrutaba todo según el struts-config.xml. El desarrollador rellenaba los huecos definidos por el framework.

El salto
De "organízate como quieras" a "hay un sitio para cada cosa". Primera estructura MVC real en Java web.
El precio
Acoplamiento fuerte via herencia. XML masivo. Sin gestión de dependencias: new MiServicio() por todas partes.
2003 Inversión
de control
Spring Framework
IoC · POJOs · sin herencia forzada · configuración XML

Spring nació como reacción directa a J2EE y Struts: en lugar de tomar más control, tomó menos. Tus clases son POJOs normales, sin extender ni implementar nada del framework. Spring las gestiona desde fuera mediante el contenedor IoC, configurado inicialmente en applicationContext.xml.

Este es el cambio conceptual más profundo de toda la evolución. Antes el desarrollador llamaba al framework (extends Action, new MiServicio()). Con Spring, el framework te llama a ti: lee la configuración, construye los objetos, inyecta las dependencias. Tú declaras qué necesitas, Spring decide cómo construirlo. Las anotaciones (@Component, @Autowired) llegarían en Spring 2.0 (2006), pero la inversión de control ya era el núcleo desde el día uno.

El salto conceptual
Inversión de Control. POJOs testables sin servidor. Ganó la guerra contra J2EE y JSF porque era menos invasivo, no más.
El precio inicial
Configuración XML enorme. Arrancar un proyecto nuevo seguía siendo costoso. Ese problema lo resolvería Boot 10 años después.
2004 El framework
toma el control
JavaServer Faces
Componentes con estado · ciclo de vida gestionado

Justo cuando Spring apostaba por menos invasión, Sun/Oracle apostó por más: JSF llevó la idea de Struts al extremo proponiendo que el framework gestionara también el estado de cada componente de UI. A diferencia de Struts, JSF no usaba herencia — usaba @ManagedBean (un POJO anotado) — pero el nivel de control del framework era mucho mayor: cada botón, tabla y formulario tenía su ciclo de vida de 6 fases ejecutado automáticamente.

Era la apuesta oficial de Java EE y prometía máxima productividad. Pero llevó el acoplamiento al límite: el ViewState serializaba el estado de toda la página, las pruebas eran difíciles, y el modelo chocaba con la llegada de REST y AJAX. La historia demostró que Spring tenía razón: menos invasión gana a más control.

La idea
Componentes UI reutilizables. El framework gestiona validación, binding y estado automáticamente.
El problema
Acoplamiento máximo. Difícil de testar. ViewState pesado. Mal encaje con REST. Perdió terreno frente a Spring MVC.
2006 El SQL
desaparece
Hibernate / JPA
ORM · anotaciones como contrato · el framework genera el SQL

Mientras Spring resolvía la organización del código, Hibernate (existía desde 2001) recibió en 2006 la estandarización de JPA. La filosofía era la misma que Spring: tú describes el modelo con anotaciones (@Entity, @OneToMany), el framework genera el SQL. Sin extender clases, sin implementar nada — solo anotar tu POJO.

Spring Data JPA fue el paso final: ni siquiera necesitas implementar el repositorio. Declaras la interfaz y Spring genera la implementación completa en tiempo de arranque. findByEmailAndStatus() existe porque tú lo declaras, no porque lo programes.

El patrón
Anotaciones como contrato. El framework lee tu modelo y genera comportamiento. Sin herencia, sin implementación.
La trampa
La "magia" del ORM tiene coste: N+1 queries, Lazy Loading inesperado. Saber qué hace Hibernate por debajo sigue siendo esencial.
2014 Estructura
completa
Spring Boot
Autoconfiguración · convention over configuration

Spring resolvió el cómo organizar el código. Boot resolvió el cómo arrancar. Si tienes spring-boot-starter-web en el classpath, Spring Boot configura Tomcat, Spring MVC y Jackson automáticamente. No hay nada que declarar porque el framework infiere lo que necesitas.

Es el punto de llegada de la filosofía IoC: ahora ni siquiera describes la configuración. El framework observa lo que tienes y toma decisiones. Tú solo escribes tu @SpringBootApplication, tus @RestController, tus @Service. La estructura completa viene dada.

La madurez
De días de configuración a 5 minutos. El desarrollador junior puede arrancar un proyecto profesional desde el primer día.
El nuevo problema
Arranque lento (~3-5s) y alto consumo de RAM (~250MB). Aceptable en servidores, problemático en la nube con cientos de pods.
2014 Infraestructura
especializada
Spring Batch
El framework gestiona el cuándo · tú el qué

Spring Batch aplicó la filosofía IoC a un problema específico: procesar millones de registros. La separación entre "qué procesar" (tuyo: ItemReader, ItemProcessor, ItemWriter) y "cómo orquestar" (framework: reintentos, transacciones, restart) es total.

El patrón
Infraestructura batch completa. Tú pones la lógica pura. El framework orquesta todo lo demás.
La curva
El modelo Job/Step/Chunk tiene su propia lógica. La "magia" del restart y skip puede sorprender.
2019 La magia
al compilar
Quarkus / Micronaut
Build-time framework · la magia ocurre antes de ejecutar

El último giro: si el framework hace su trabajo leyendo anotaciones en tiempo de arranque, ¿por qué no hacerlo en tiempo de compilación? Quarkus y Micronaut mueven todo el trabajo pesado — escaneo, resolución de DI, proxies — al momento del build. El binario que arranca ya tiene todo resuelto.

La API para el desarrollador es casi idéntica a Spring (@Inject, @Path), pero el motor es completamente distinto. La misma filosofía IoC, ejecutada en un momento diferente del ciclo de vida.

El siguiente paso
La "magia" no tiene coste en runtime. <50ms de arranque, ~30MB de RAM. Java competitivo en serverless y Kubernetes.
La restricción
Lo que no se puede analizar en compilación no funciona fácilmente. El ecosistema aún madura respecto a Spring.
