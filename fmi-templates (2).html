DECISIONES DE DISEÑO XML
Atributos en tag raíz
agent, phase, task son atributos, no elementos hijo. El modelo los lee en el primer token. El Capataz los parsea con XPath simple sin leer el body.
hard como string de tokens
ZERO_DEPS STOP_ON_AMBIGUITY en una línea ahorra ~6 líneas vs un elemento por restricción. El modelo los trata como restricciones atómicas igual de bien.
Caveman quirúrgico
XML da el contexto. Caveman señaliza solo los failure points conocidos del pipeline. Si todo es mayúsculas, nada es mayúsculas.
Versionado semántico
git log CLAUDE.md muestra la evolución de reglas de arquitectura. git log .claude/templates/ muestra la evolución del pipeline. Diffs legibles, no ruido.
choice binario en output
Cada agente emite o <code> o <blocked>, nunca ambos. El Capataz no puede recibir output ambiguo. El contrato es forzado por el prompt.
Placeholders obligatorios
Todo [PLACEHOLDER] sin rellenar = ambigüedad garantizada = alucinación probable. La disciplina de inputs es donde se pierde el beneficio del pipeline.

  FMI TEMPLATE: IA1 — Arqueología de Intención
  Prerequisito de ia1-refactor.xml. No modifica código.

<prompt agent="IA1_Archaeologist" task="archaeo" phase="01" lang="es">

  <constraints>
    <hard>
      ZERO_MODIFICACIONES_AL_CODIGO — solo leer, no tocar.
      STOP_ON_AMBIGUITY — si el flujo no es claro, emite blocked y para.
      HAR_ES_VERDAD_ABSOLUTA — el código puede mentir, el tráfico no.
    </hard>
    <naming_forbidden>Service Manager Helper Util Handler</naming_forbidden>
  </constraints>

  <truth>
    <source type="HAR" trust="absolute">
      <!-- Pegar el bloque HAR del endpoint (request + response) -->
      [HAR_CONTENT]
    </source>
    <source type="semantic_log" trust="consult">
      <!-- Logs BUSINESS_INTENT de Phase 0, si existen -->
      [SEMANTIC_LOG_LINES]
    </source>
  </truth>

  <input>
    <file role="servlet">[RUTA_RELATIVA_SERVLET]</file>
    <file role="jsp"     optional="true">[RUTA_RELATIVA_JSP]</file>
    <file role="sql"     optional="true">[SQL_EMBEBIDO_O_RUTA]</file>
  </input>

  <steps>
    1. Leer el HAR. Identificar: método HTTP, endpoint, params, estructura respuesta.
    2. Leer el Servlet. Ignorar ruido técnico (JDBC, encoding, prints).
       Pregunta clave: ¿Qué regla de negocio implementa este código?
    3. Contrastar HAR vs código. Si divergen → marcar CONFLICT en la intención.
    4. Extraer intención por bloque doPost/doGet en vocabulario del dominio.
       Prohibido vocabulario técnico en las intenciones (no "query", "select", "servlet").
    5. Si hay ambigüedad que el HAR no resuelve → emitir blocked. No inferir.
  </steps>

  <o>
    <!-- Emitir UNO de los dos bloques. Nunca ambos. -->

    <intentions>
      <!-- Formato: verbo de dominio + objeto de negocio + condición si aplica.
           Ejemplo: "Registrar emisión de DTE cuando el RUT del emisor es válido" -->
      <intent id="1" conflict="false">[INTENCIÓN_EN_LENGUAJE_DE_DOMINIO]</intent>
      <intent id="2" conflict="false">[INTENCIÓN_EN_LENGUAJE_DE_DOMINIO]</intent>
    </intentions>

    <blocked reason="[MOTIVO_CONCRETO]" step="[1-5]"/>
  </o>

</prompt>
Vocabulario de dominio — ejemplos correctos vs prohibidos
✓ Correcto: "Validar RUT del contribuyente antes de registrar el DTE" · "Notificar al receptor cuando la emisión es aceptada por el SII"
✗ Prohibido: "Ejecutar query SELECT sobre tabla contribuyente" · "Llamar al servlet de validación con parámetro tipo=3"

El atributo layer= es clave para el Capataz
El Capataz valida aislamiento de capas leyendo el atributo layer antes de inspeccionar el código. Un archivo con layer="domain" que tenga imports de java.sql activa R4 automáticamente.

Por qué ZERO_LECTURA_CODIGO es la restricción más importante de IA2
Si IA2 lee el código legacy, su mapa de comportamiento hereda los bugs del legacy como si fueran comportamiento correcto. El test resultante certificaría los errores. La separación IA1 (código) vs IA2 (comportamiento observable) es lo que garantiza mapas sin sesgo.
capataz-validate.xml — Capataz · Validación de Outputs y Decisión de Pipeline El Capataz recibe outputs de IA1 e IA2, aplica reglas R1–R6, decide si el pipeline avanza. Emite exactamente uno de: pipeline_approved · pipeline_blocked · pipeline_rejected.
PLANTILLA
<?xml version="1.0" encoding="UTF-8"?>
<!--
  FMI TEMPLATE: CAPATAZ — Validación de Pipeline
  Lee outputs de IA1 e IA2. Aplica reglas. Decide avance o bloqueo.
  ZERO código de negocio. ZERO inferencia. Decisión binaria por regla.
-->
<prompt agent="Capataz" task="validate" phase="[01|02|03]" lang="es">

  <constraints>
    <hard>
      ZERO_IMPLEMENTACION — el Capataz no escribe código de negocio.
      DECISION_BINARIA — por cada output de agente: APPROVED o BLOCKED.
      TRUST_HIERARCHY — HAR > IA1_intentions > semantic_logs. En conflicto: HAR gana.
      STOP_ON_FIRST_BLOCK — si cualquier agente está blocked, el pipeline se detiene.
    </hard>
  </constraints>

  <pipeline_state>
    <flow>[NOMBRE_DEL_FLUJO_EN_CURSO]</flow>
    <current_phase>[01|02|03]</current_phase>
    <cycle>[NUMERO_DE_ITERACION]</cycle>
    <agents>
      <agent id="IA1_Archaeologist" status="[pending|running|approved|blocked]"/>
      <agent id="IA2_Cartographer"  status="[pending|running|approved|blocked]"/>
    </agents>
  </pipeline_state>

  <inputs>
    <from agent="IA1_Archaeologist" task="archaeo">
      <!-- Pegar bloque <intentions> o <blocked> de ia1-archaeo.xml -->
      [OUTPUT_IA1_ARCHAEO]
    </from>
    <from agent="IA1_Archaeologist" task="refactor">
      <!-- Pegar bloques <code> o <blocked> de ia1-refactor.xml -->
      [OUTPUT_IA1_REFACTOR]
    </from>
    <from agent="IA2_Cartographer" task="cartograph">
      <!-- Pegar bloques <code> o <blocked> de ia2-cartograph.xml -->
      [OUTPUT_IA2_CARTOGRAPH]
    </from>
  </inputs>

  <validation_rules>
    <!-- Aplicar en orden. Primera que falla → pipeline blocked. -->
    <rule id="R1" check="no_blocked_agents">
      Cualquier <blocked/> en <inputs> → STOP inmediato.
    </rule>
    <rule id="R2" check="har_coverage">
      Los <intentions> de IA1 deben cubrir TODOS los params del HAR.
      Param del HAR sin intención → STOP.
    </rule>
    <rule id="R3" check="naming_compliance">
      Prohibidos: Service Manager Helper Util Handler. Aparece → REJECT.
    </rule>
    <rule id="R4" check="layer_isolation">
      domain no importa javax, jakarta, java.sql. Aparece → REJECT con archivo + línea.
    </rule>
    <rule id="R5" check="zero_deps">
      Cero librerías externas. Java 21 puro. Aparece import externo → REJECT.
    </rule>
    <rule id="R6" check="e2e_parity">
      Cada intent de IA1 con Scenario en .feature de IA2. Sin cobertura → WARNING.
    </rule>
  </validation_rules>

  <steps>
    1. Verificar R1. Si falla → emitir pipeline_blocked inmediatamente.
    2. Aplicar R2–R5 en orden. Registrar resultado de cada una.
    3. Aplicar R6 → registrar warnings (no bloquea).
    4. Si todas PASS → calcular siguiente acción. Emitir pipeline_approved.
    5. Si alguna REJECT (R3/R4/R5) → emitir pipeline_rejected con violaciones.
  </steps>

  <o>
    <!-- Emitir UNO de los tres. Nunca más de uno. -->

    <pipeline_approved cycle="[N]" next_phase="[01|02|03]">
      <next_action>[ia1-refactor.xml | ia2-cartograph.xml | DONE]</next_action>
      <warnings>
        <warning rule="R6">[DESCRIPCION si aplica]</warning>
      </warnings>
    </pipeline_approved>

    <pipeline_blocked cycle="[N]" failed_rule="[ID|agent_blocked]">
      <reason>[DESCRIPCION_CONCRETA]</reason>
      <human_action_required>[INSTRUCCION_ESPECIFICA]</human_action_required>
    </pipeline_blocked>

blocked vs rejected — la diferencia semántica
pipeline_blocked: un agente no pudo completar su tarea. Requiere intervención humana — el HAR es insuficiente, hay ambigüedad real en el dominio.

pipeline_rejected: el agente completó su tarea pero el output viola una regla de calidad (naming, layer isolation, deps). El agente puede reintentar sin intervención humana.

Por qué el task prompt es el único que cambia en cada ciclo
El CLAUDE.md (system) codifica la arquitectura FMI — cambia solo cuando cambia la metodología. El task prompt codifica el trabajo — cambia por cada Servlet a migrar. Esta separación es lo que hace el sistema reutilizable sin tocar las reglas en cada invocación. git log tasks/ es el diario de migración del proyecto.
