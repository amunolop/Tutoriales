LA IDEA ORIGINAL
El sistema separa la semántica de la implementación, planifica el proceso según la complejidad del proyecto, y ejecuta cada fase con un motor multi-agente que garantiza calidad por construcción y optimiza recursos por diseño.
EL PROBLEMA

Migrar o refactorizar una aplicación web legacy es uno de los problemas más caros y arriesgados de la ingeniería del software. El código legacy tiene la logica de negocio mezclada con la implementación: acceso a datos dentro de los controladores, reglas de negocio junto a la respuesta HTTP, validaciones dispersas. Con el tiempo, nadie sabe ya exactamente que hace el sistema, solo que funciona.

Los enfoques tradicionales fallan porque intentan migrar el COMO (la implementación) en lugar del QUE (la semántica). Reescriben módulo por módulo copiando el acoplamiento original. El resultado es código nuevo con los problemas viejos.

La inversión conceptual No se migra código. Se extrae la Intención del sistema (que hace, que reglas cumple, que flujos ejecuta) y se reconstruye en el stack destino. El código legacy es solo evidencia de la intención, no la intención misma. De ahi el nombre: FMI, Framework de Migración de Intención.
QUE ES ESTE SISTEMA

Es un agente de migración y refactorización que funciona sobre Claude Code. No es una herramienta con interfaz ni un framework con código: es un procedimiento descrito en tres documentos Markdown que Claude Code interpreta y ejecuta. Orquesta multiples subagentes de IA, cada uno especializado, coordinados para producir código migrado con arquitectura limpia, tests y seguridad verificada.

LAS TRES Contribuciones
1. Semántica SOBRE Implementación
Se extrae QUE hace el legacy, no COMO lo hace. El resultado es una representación semántica compacta y re-targeteable a cualquier stack. La implementación destino la decide el prompt, no el legacy.
2. Planificación POR COMPLEJIDAD
El proceso no es fijo. Un escaneo analiza el proyecto y decide las fases según su complejidad real. El plan se adapta al proyecto, no al reves.
3. MOTOR MULTI-AGENTE
Cada fase se ejecuta con un motor batch paralelo que garantiza calidad por construcción (no por revision) y optimiza recursos por diseño (modelo adecuado por rol, contexto mínimo, cero redundancia).
SEPARAR EL QUE DEL COMO

La primera contribución del sistema es tratar la semántica del legacy como un artefacto extraible e independiente de su implementación. Esto se materializa en un artefacto compacto llamado DIGEST.

EL COMO (implementación legacy)
Código acoplado: acceso a datos concatenando consultas, sesiones gestionadas de forma insegura, credenciales en texto plano, respuestas con redirecciones. Obsoleto e inseguro. Se descarta.
EL QUE (semántica - DIGEST)
La intención del sistema: que entidades maneja, que reglas de negocio aplica, que flujos ejecuta, que contratos expone. Independiente de cualquier tecnología. Se conserva.

El proceso de extracción tiene dos pasos. Primero, un escaneo lee el legacy una sola vez y produce tres documentos: la estructura del código, el contexto (esquema de datos, patrones, mapeo de dominio) y los hallazgos de seguridad. Después, un agente META-ARQUITECTO analiza esos documentos y destila la semántica aplicando una lente de clasificación.

LA LENTE DE 4 CAPAS

El META-ARQUITECTO clasifica cada fragmento de código del legacy en una de cuatro categorias semanticas. Es fundamental entender que las 4 capas NO son la arquitectura destino: son el método de clasificación, la lente de análisis.

CapaQue capturaNaturaleza
DOMAINNegocio puro: entidades, invariantes, reglas, interfacesQue ES el sistema
APPLICATIONOrquestación: casos de uso, flujos, coordinación entre entidadesQue HACE el sistema
INFRASTRUCTUREAdaptadores: persistencia, hashing, sesión, configuracionCon que SE APOYA
TRANSPORTInterfaz externa: controladores, filtros, respuesta HTTPComo SE COMUNICA
Por que 4 capas: el DIGEST como Forma Normal Cuatro capas es la resolucion mínima para capturar la semántica completa sin perdida de información. Es el equivalente conceptual a normalizar una base de datos a la cuarta forma normal. Desde una representación en 4 capas se puede generar cualquier vista derivada (3 capas fusionando, microservicios agrupando por contexto). Pero si la extracción se hace directamente en 3 capas, se fusionan domain y application y se pierde la frontera entre las reglas de negocio y su orquestación. Esa información no se recupera. Extraer en 4 capas es la forma normal: completa y re-targeteable.
EL DIGEST: Semántica COMPRIMIDA
DOMAIN: Entidades, Interfaces de repositorio, Reglas de negocio, Invariantes
APPLICATION: Casos de uso, Flujos, Orquestación entre componentes
INFRASTRUCTURE: Estrategia de persistencia, Gestión de sesión, Seguridad
TRANSPORT: Endpoints, Forma de la respuesta, Filtros

El DIGEST es una representación compacta, de aproximadamente 2.000 tokens, que captura toda la semántica del legacy. Es la fuente de verdad que consumen todos los agentes del sistema. Ningun agente necesita volver a leer el código legacy original: el DIGEST contiene la intención destilada.

Por que la extracción es correcta La validez de la extracción semántica se demuestra por re-targetabilidad: a partir de un mismo DIGEST, cambiando unicamente el prompt, el sistema produce migraciones completas y funcionales a stacks tecnologicos radicalmente distintos. Si el DIGEST no capturara la semántica de forma correcta y completa, una migración a un stack distinto del original fallaria. Que no falle es la prueba de que la semántica se ha extraido bien: el DIGEST contiene el QUE, el prompt define el COMO.
EL PLAN: DECIDIR QUE EJECUTAR Y EN QUE ORDEN

El Plan de Migración Multi-Fase es la capa de estrategia. No genera código: decide como debe estructurarse la refactorización. Su principio fundamental es que el proceso se adapta a la complejidad del proyecto, no al reves.

EL FLUJO PASO A PASO
1
PRE-FLIGHT. Validar el código origen. Crear la estructura de trabajo. Escribir la configuracion de la ejecución.
2
ESCANEO DEL LEGACY. El Motor lee el código legacy una sola vez y produce tres documentos: estructura, contexto y hallazgos de seguridad. El escaneo propone las fases según la complejidad detectada.
3
META-ARQUITECTO. Único paso estratégico, ejecutado una sola vez con el modelo más capaz. Destila el DIGEST, define la arquitectura destino, prepara la configuracion de compilación base y concreta el plan de fases con sus criterios de calidad.
4
BUCLE DE FASES. Cada fase es una invocacion al Motor. Las fases sin dependencias entre si se lanzan en paralelo según el grafo de dependencias. Cada fase tiene su propio directorio de trabajo.
5
ESCANEO INTERMEDIO. Entre la capa de interfaz y la capa de nucleo. Lee la interfaz realmente generada, extrae los contratos exactos y los congela. El nucleo se construye implementando exactamente esos contratos.
6
Certificación FINAL. Verificación global, compilación completa, arranque, flujos críticos automatizados. La Definición de Terminado exige todas las condiciones cumplidas simultaneamente.
Planificación ADAPTATIVA POR COMPLEJIDAD

El número y la naturaleza de las fases no están predefinidos. El escaneo analiza el proyecto real y propone una descomposición en fases proporcionada a su complejidad. Un proyecto simple puede resolverse en tres fases; uno complejo puede requerir seis. El sistema se ajusta a lo que encuentra.

Paralelismo basado en grafo de dependencias El META-ARQUITECTO declara las dependencias entre fases como un grafo dirigido acíclico. Las fases sin aristas entre si se lanzan concurrentemente. El sistema verifica el paralelismo real: si dos fases declaradas independientes no presentan intervalos de tiempo solapados en la telemetría, significa que la ejecución degrado a secuencial, y eso se considera un fallo de certificación. El paralelismo no es una sugerencia, es un invariante verificable.
CONTRATOS DIRIGIDOS POR EL CONSUMIDOR

El Plan resuelve el problema clasico de desalineacion entre la capa de interfaz y la de nucleo con un orden deliberado: la interfaz se genera primero y define los contratos que necesita. El escaneo intermedio los congela como fuente de verdad. El nucleo se construye implementando exactamente esos contratos. El desacoplamiento entre capas es total y verificado: cambiar una capa no obliga a tocar la otra.

EL MOTOR: EJECUTAR UNA FASE CON GARANTIAS

El Motor de Ejecución es un motor batch paralelo genérico. No sabe que es una migración, ni un test, ni una capa arquitectonica. Recibe una especificacion de tarea y produce artefactos supervisados. Es la pieza reutilizable del sistema: el mismo Motor ejecuta cualquier fase de cualquier proyecto.

LOS 5 ROLES Y SUS MODELOS

El Motor distribuye el trabajo entre cinco roles, cada uno con un modelo de IA adecuado a su función. Esta es una decisión de optimización: no todos los roles necesitan el modelo más potente.

EL FLUJO DEL MOTOR PASO A PASO
1
PRE-FLIGHT. El Ejecutor crea el directorio de la tarea y el documento de seguimiento de fase.
2
ARQUITECTO. Lee la especificacion de la tarea. Decide el número de olas, cuantos workers en paralelo, el contrato de cada uno, y los criterios de verificación. Genera la configuracion de compilación.
3
OLEADA 1. N workers en paralelo, lanzados en un solo despacho. Con una sola ola generan el artefacto final; con dos olas generan la especificacion ejecutable.
4
GATE. Solo si hay dos olas. Verifica la forma de la especificacion generada. Es bloqueante: la Oleada 2 no arranca sin superar el GATE.
5
OLEADA 2. Solo si hay dos olas. N workers en paralelo que consumen la especificacion de la Oleada 1 y generan la implementación que la cumple.
6
SMOKE. Verificación estática barata sobre el código final. Umbral del 100%. Bloquea al Verificador hasta que todos los checks pasen.
7
VERIFICADOR. Compila, ejecuta todos los conjuntos de tests, construye el artefacto y arranca el servicio con comprobacion de salud.
8
REPORTE. El Ejecutor verifica que existen todos los registros obligatorios y escribe el resumen. Una fase sin registros se considera fallida.
LA HEURISTICA DE 1 O 2 OLAS
Tipo de artefactoOlasJustificacion
Casos de uso, repositorios, controladores, logica de negocio2 olasTienen contrato testeable. La especificacion fija la interfaz antes de implementar.
Componentes de interfaz, estilos, configuracion, objetos de transferencia planos1 olaEstructural o presentacional. La especificacion-como-contrato aporta poco valor.
Especificacion ejecutable como contrato Con dos olas, la primera genera una especificacion que NO se ejecuta: es el contrato formal, la definición exacta que la segunda ola debe cumplir. La especificacion fija la firma, las excepciones y los valores de retorno. La implementación de la segunda ola solo tiene que satisfacer ese contrato. No es un ciclo de prueba tradicional, sino especificacion ejecutable usada como guia de generación.
CALIDAD POR Construcción, NO POR REVISION
No es "genera código y luego lo reviso". Es "genera código que no puede no cumplir, porque el pipeline no permite lo contrario".
EL PRINCIPIO ANTI-ALUCINACION: CONSTRENIR, NO INSTRUIR

Cuando se dan instrucciones abiertas a un modelo de IA, el modelo tiende a alucinar porque no tiene restricciones que lo acoten. Cuando se establecen barreras infranqueables, el modelo se cine al espacio seguro. El sistema no pide perfeccion: define un perimetro de seguridad y deja que el modelo se mueva libremente dentro de el.

El sistema NO diceEl sistema dice
"implementa correctamente la separacion de responsabilidades"si una capa de negocio instancia directamente una clase de infraestructura, la verificación estática lo detecta y el pipeline aborta
"escribe tests"si la fase usa dos olas, sin la especificacion no se supera el GATE, y sin GATE no arranca la generación de código
"escribe código seguro"si aparece una función peligrosa o una credencial en texto plano, un check de seguridad falla y bloquea el avance
"respeta la arquitectura"el worker solo recibe la semántica destilada; si importa una capa que no debe, la verificación lo detecta
El enfoque es transferible Constrenir en lugar de instruir no es especifico de la migración de código. Es ingeniería de prompts defensiva: en cualquier dominio donde se use IA generativa, en lugar de pedir un resultado perfecto, se define un perimetro de invariantes y se deja que el modelo opere dentro de el. La calidad emerge del perimetro, no de la suerte.

PRINCIPIOS DE Diseño COMO PROPIEDAD EMERGENTE
PrincipioComo lo fuerza el pipeline
Responsabilidad únicaCada worker genera un solo artefacto. Cada caso de uso tiene un solo punto de entrada.
Inversión de dependenciasLos casos de uso reciben interfaces por constructor. La verificación estática comprueba que no hay instanciacion directa de infraestructura.
SeguridadLas reglas de seguridad son constraints de generación. Es imposible que el código las incumpla porque el pipeline lo bloquea antes de escribir el archivo.
La diferencia fundamental En un enfoque convencional, la calidad depende de una revision humana posterior; si el revisor no detecta un defecto, el defecto llega a produccion. En este sistema, el pipeline ES la revision: es automática, bloqueante y exhaustiva. La arquitectura, los tests y la seguridad no son el resultado de revisar el código, son una propiedad emergente del proceso que lo genera.

Telemetría: OBSERVABILIDAD DEL COSTE

Cada worker emite telemetría estructurada al terminar: tokens consumidos, duracion, divergencias respecto a su contrato, reintentos. El coordinador la consolida. Esto convierte el coste en una metrica observable: permite optimizar los contratos más caros, detectar workers ineficientes y medir la calidad de la planificación. El consumo de recursos no es una caja negra.

POR QUE EL SISTEMA ES ROBUSTO

La robustez del sistema no es accidental. Es una propiedad que emerge de tres decisiones de diseño: el estado vive en disco, los agentes son desechables, y las barreras de calidad son bloqueantes.

ESTADO EN DISCO, NO EN MEMORIA
La conversación no es la fuente de verdad. El disco lo es. El estado completo de la ejecución vive en archivos. Si la ventana de contexto se compacta, si la sesión se reinicia, si el proceso se interrumpe, el estado persistido permanece intacto. El sistema lee el documento de seguimiento y retoma desde el ultimo paso completado sin necesitar nada de la conversación previa.

AGENTES DESECHABLES E IDEMPOTENTES

Cada subagente nace con un contrato, ejecuta, escribe su artefacto a disco, emite telemetría y muere. Su ventana de contexto se destruye por completo. Si un worker falla, se relanza con el mismo contrato y produce el mismo resultado: es idempotente. El sistema tolera el fallo de cualquier agente individual sin que ese fallo contamine al resto del proceso.

EL PROCESO También ES UN INVARIANTE
Un sistema robusto verifica el resultado Y el proceso Un sistema puede producir código perfecto y aún así fallar si el proceso no se ejecuto correctamente: si no genero los registros de trazabilidad, si no ejecuto las fases en paralelo cuando debia, si salto un paso de validación. Por eso el sistema trata el proceso mismo como un invariante bloqueante. Una fase sin sus registros obligatorios se considera fallida aunque su código sea correcto. La trazabilidad y la repetibilidad no son opcionales.

SE EJECUTA EN CLAUDE CODE, SIN INFRAESTRUCTURA
CERO MONTAJE
No hay que instalar frameworks, configurar servidores ni desplegar nada. Son tres archivos Markdown. Se ejecuta directamente en Claude Code. Cualquier desarrollador con acceso a Claude Code puede usarlo de inmediato.
VERSIONABLE EN GIT
Los tres documentos se versionan como cualquier código fuente. El proceso es auditable, reproducible y mejorable. Cada cambio en el procedimiento queda registrado en el historial.
TRAZABILIDAD TOTAL
Cada ejecución deja registros completos en disco: que agentes intervinieron, cuánto consumieron, que verificaciones pasaron. La migración deja de ser una caja negra.

UNA HERRAMIENTA PARA CUALQUIER Migración

El sistema no está atado a ningun lenguaje ni a ningun tipo de aplicación concreto. Es un procedimiento genérico aplicable a cualquier proyecto de refactorización o migración de código legacy. El Motor es agnostico del dominio; el Plan es agnostico del lenguaje; solo el Prompt conoce el destino concreto.

QUIEN PUEDE USARLO
EMPRESAS CON SISTEMAS LEGACY
Muchas organizaciones mantienen aplicaciones criticas sobre tecnologías obsoletas. El sistema permite modernizarlas hacia stacks actuales sin reescribir a mano, conservando la logica de negocio verificada.
CONSULTORAS Y EQUIPOS DE SERVICIOS
Una consultora que realiza migraciones puede adoptar el sistema como metodología repetible. Cada proyecto reutiliza el Plan y el Motor; solo se escribe un Prompt nuevo. La migración deja de ser un trabajo artesanal.
EQUIPOS QUE REFACTORIZAN
No solo migraciones de stack. También refactorización pura: convertir un monolito acoplado en una arquitectura limpia con buenos principios de diseño y tests, dentro del mismo lenguaje.

POR QUE CONSIGUE SU OBJETIVO
El objetivo: migrar código legacy a código limpio, con arquitectura, tests y seguridad, de forma fiable y eficiente. Lo consigue porque cada parte del sistema ataca una dimension del problema. La extracción semántica garantiza que no se pierde la intención del sistema. La planificación adaptativa garantiza que el proceso encaja con el proyecto. El Motor garantiza que cada fase se ejecuta con calidad. Las barreras bloqueantes garantizan que el código cumple por construcción. El aislamiento de contexto garantiza que la calidad no se degrada con la duracion. El estado en disco garantiza que el proceso es robusto ante fallos. No es una sola idea brillante: son seis decisiones de diseño que se refuerzan mutuamente.
EL CAMPO QUE ABORDA

El sistema se situa en la interseccion de tres disciplinas: los sistemas multi-agente, la ingeniería de prompts y la ingeniería del software. No es investigacion sobre modelos de IA, ni ingeniería de prompts en sentido estricto, ni desarrollo de software clasico. Trata un area emergente: como construir sistemas fiables usando modelos de IA como componentes de ejecución, gestionando sus limitaciones inherentes (ventana de contexto finita, tendencia a alucinar, coste) como constraints arquitectonicos, e integrando la ingeniería del software como una propiedad emergente del proceso generativo.

TESIS FINAL
Se puede diseñar un proceso generativo multi-agente que tenga la ingeniería del software como propiedad emergente del proceso, no como resultado de una revision posterior.

El sistema no es una herramienta puntual, ni un framework con código, ni un proceso manual de revision. Es un procedimiento que, dado un prompt, produce código migrado con arquitectura limpia, buenos principios de diseño, tests y seguridad verificada, para cualquier lenguaje y cualquier stack. Y lo hace con tres archivos Markdown ejecutados sobre Claude Code, sin una sola línea de código de infraestructura.

El sistema en una frase Separa la semántica de la implementación, planifica el proceso según la complejidad del proyecto, y ejecuta cada fase con un motor multi-agente que garantiza calidad por construcción y optimiza recursos por diseño.
