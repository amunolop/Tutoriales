LA TESIS
Tengo el código pero es ilegible, parcheado, espagueti. La documentación no existe. Las especificaciones originales se perdieron. Pero la aplicación funciona perfectamente.

No voy a intentar «entender» el código. Voy a usar la IA para extraer lo que el código intenta hacer (sus intenciones), diseñar pruebas que cartografíen esas intenciones, ejecutarlas como caja negra con Playwright, y con los resultados reales construir la red de seguridad para migrar.

TRES CONCEPTOS QUE CAMBIAN TODO
🧠 Intención ≠ Implementación
El código INTENTA validar un DNI — con un if anidado en 8 niveles, un regex roto, o una tabla de lookup. No nos importa cómo. Nos importa QUÉ intenta hacer. La IA1 extrae la intención; la sintaxis se descarta.
🗺️ Cartografiar ≠ Validar
La IA2 no genera tests para comprobar si algo funciona — la app funciona. Genera tests para mapear exhaustivamente cómo funciona: qué acepta, qué rechaza, qué errores da, qué formatos tolera. El conjunto de resultados es el mapa completo.
🔬 Tests cartografía ≠ Tests validación
Los tests de cartografía son exploratorios: existen para descubrir, se ejecutan una o dos veces, su valor está en los HAR que producen. Los tests de validación son permanentes: se generan DESDE los HAR, se ejecutan en cada cambio, son la red de seguridad para migrar.
📐 Dos IAs por diseño
IA1 (Claude Code / Cursor) está contaminada por la sintaxis — y eso es bueno para extraer intención del espagueti. IA2 (Opus / razonador) está libre de sintaxis — y eso es bueno para diseñar tests exhaustivos sin sesgo de implementación.

ARQUITECTURA DE IA DUAL
IA1 · ANALISTA
Claude Code / Cursor / OpenCode
Tiene acceso al repositorio. Navega ficheros. Lee código espagueti. Su trabajo es extraer intenciones, no entender implementación.
Recibe:
• web.xml (mapa de endpoints)
• DDL de tablas (entidades de dominio)
• Páginas HTML con POST/GET (contratos de UI)
• Código de servlets/lógica (espagueti)

Produce:
• Documento de intenciones por funcionalidad
• «Este servlet INTENTA hacer X, Y, Z»
• Sin opinión sobre calidad ni refactoring

NO produce:
• Tests
• Código refactorizado
• Juicios sobre implementación
IA2 · CARTÓGRAFO
Claude Opus 4.6 / Modelo razonador
NO ve el código. Solo recibe intenciones. Diseña tests de Playwright que cartografían exhaustivamente cada intención.
Recibe:
• Documento de intenciones (de IA1)
• En 2ª pasada: HAR + logs semánticos

Produce:
• Batería de tests Playwright (.spec.ts)
• Casos felices + errores + límites + combinaciones
• Tests de secuencia (flujos con estado)

NO produce:
• Tests unitarios
• Tests de integración
• Nada que asuma implementación
En Claude Code: IA1 = Opus · Sesión 1 (acceso al repo, analiza artefactos en 2 pasos, revisa outcomes). ¿Por qué dos IAs y no una? Si la misma IA lee el espagueti y genera tests, genera tests contaminados por la implementación. Ve el if (dni.length() == 9) y genera UN test con DNI de 8 caracteres. Un modelo razonador que solo recibe «intención: validar formato DNI español» genera 15 variantes — porque piensa en la intención completa, no en el if concreto.

PATRÓN PLANNER / EXECUTOR
El mecanismo concreto detrás del IA Dual. Opus actúa como cerebro planificador (Sesión 1) y Sonnet como manos ejecutoras (Sesión 2). Se comunican exclusivamente por ficheros .md en el workspace compartido — sin memoria compartida, sin canales externos. El fichero es el bus.
SESIÓN 1 · PLANNER
Claude Opus
Analiza artefactos en 2 pasos separados. Revisa el outcome.md de Sonnet — nunca el código directamente. Toma decisiones: PASS, correctivo, o escalar.
Paso 1 → escribe:
• analysis.md — razona en voz alta
• unknowns.md — ambigüedades sin resolver

Paso 2 → escribe:
• directive.md — instrucciones para Sonnet
• Incluye formato obligatorio del outcome.md

Tras revisar outcome:
• PASS → escribe directive siguiente fase
• FAIL → escribe directive correctivo
• confidence < 0.4 → escala o para
SESIÓN 2 · EXECUTOR
Claude Sonnet
Lee directive.md y ejecuta exactamente lo indicado. Genera código o tests. Reporta en outcome.md con el formato que Opus exigió. No toma decisiones de arquitectura.
Lee:
• directive.md de Opus (único input)

Ejecuta:
• Genera código / tests según directive
• Aplica cambios en el repo

Escribe:
• outcome.md — status, qué hizo, qué falló
• JSON de evaluación con confidence
• Gaps que siguen abiertos

NO hace:
• Decisiones de diseño o arquitectura
• Cambios fuera del scope del directive
LOS 2 PASOS DE OPUS POR FASE
¿Por qué 2 pasos y no 1? Si Opus analiza y genera el directive en un solo paso, optimiza hacia el output y puede saltarse razonamiento crítico. Con 2 pasos se fuerza un Chain of Thought explícito: Opus se compromete con el análisis antes de instruir. Si el analysis.md está mal, se detecta antes de que contamine el directive.md.
1
Opus lee todos los artefactos de entrada
web.xml, DDL, HTML, código, telemetría (HAR + logs) según la fase. Lee sin escribir — solo acumula contexto.
2
Opus escribe analysis.md — razona en voz alta
Qué vio, qué contradice, qué no entiende, qué hipótesis formula. Las incertidumbres van a unknowns.md. Este fichero NO lo lee Sonnet.
3
Opus destila en directive.md — instrucciones para Sonnet
Solo lo que Sonnet necesita ejecutar. Incluye: scope exacto, contratos (NO cambiar), restricciones anti-alucinación, y el formato obligatorio del outcome.md.
4
Sonnet lee directive.md y ejecuta
Genera código o tests. Aplica cambios. Escribe outcome.md con el formato exigido por Opus. No improvisa fuera del scope.
5
Opus lee outcome.md — nunca el código directamente
Opus es un decision maker, no un code reviewer. Lee el reporte de Sonnet y decide: PASS (siguiente fase), FAIL (directive correctivo), o escalar. Solo en confidence < 0.4 lee el código como diagnóstico.
LOS 3 ARTEFACTOS DE COMUNICACIÓN
analysis.md
Autor: Opus · Solo lectura para: nadie (es interno)
Opus razona en voz alta. Contradicciones detectadas, hipótesis, incertidumbres. Es el «borrador mental» que garantiza que el directive esté fundamentado. Sonnet nunca lo lee.
directive.md
Autor: Opus · Lector: Sonnet
Instrucción quirúrgica. Scope exacto, contratos a respetar, restricciones, formato obligatorio del outcome. Es la única fuente de verdad de Sonnet en cada iteración.
outcome.md
Autor: Sonnet · Lector: Opus
Status (PASS/FAIL/PARTIAL), qué se hizo, qué falló exactamente, JSON de evaluación con confidence, gaps que siguen abiertos. Opus toma sus decisiones basándose únicamente en este fichero.
unknowns.md
Autor: Opus · Lector: humano
Ambigüedades que requieren decisión humana. Opus las registra durante el análisis y no genera código para ellas hasta tener respuesta. Acumulativo a lo largo de todas las fases.

💡 El outcome.md es la responsabilidad de Sonnet
Como Opus no lee el código directamente, toda la honestidad del ciclo depende de la precisión del outcome.md. Por eso el directive.md de Opus siempre incluye el formato obligatorio que Sonnet debe respetar: status exacto, tests pasando N/M, qué falló exactamente, gaps que siguen abiertos. Un outcome.md vago produce decisiones ciegas de Opus.
⚠️ Condiciones de parada del ciclo
Opus detiene el ciclo cuando: (1) 95%+ tests pasando — continúa a siguiente fase. (2) Mismo error repetido 2 veces sin mejora — reescribe módulo, no parchea. (3) confidence < 0.4 — Opus lee el código directamente como diagnóstico excepcional. (4) Deriva del sistema detectada — comportamiento diverge del contrato HAR. En casos 2, 3 y 4, Opus documenta la causa raíz en unknowns.md antes de escalar al humano.
FASE 0 — INSTRUMENTACIÓN CON LOGS SEMÁNTICOS
Única modificación al legacy permitida antes de cartografiar. No cambia lógica, solo añade trazas. El objetivo es que los logs capturen intención de negocio, no trazas técnicas. Se le pide a la IA que añada logs que ayuden a extraer comportamiento — la IA sabe mejor que el desarrollador original qué es relevante loguear.
PROMPT PARA GENERAR LOGS SEMÁNTICOS
// Prompt para IA1 (Claude Code / Cursor) — Fase 0

`Analiza este servlet/página y añade logging semántico.

NO cambies NINGUNA lógica, flujo, validación ni respuesta.
SOLO añade líneas de log.

Los logs deben capturar INTENCIÓN DE NEGOCIO, no trazas técnicas.

FORMATO — una línea JSON por operación de negocio:
{
  "intent": "NOMBRE_OPERACION_NEGOCIO",
  "input": { campos relevantes de entrada },
  "validations": { resultado de cada validación detectada },
  "result": "CREATED|REJECTED|ERROR|UPDATED|DELETED",
  "detail": "razón si es rechazo o error"
}

REGLAS:
- El campo "intent" debe ser un verbo de negocio en MAYÚSCULAS
  (ALTA_CUENTA, VALIDAR_CERTIFICADO, BUSCAR_CONTRATO)
- NO loguees: "entrando en método X", "param = Y", "saliendo"
- SÍ loguea: qué operación de negocio se intentó, con qué datos
  relevantes, y cuál fue el resultado
- Si hay un catch genérico, loguea la excepción REAL, no "error"
- Si hay múltiples validaciones, loguea el resultado de CADA UNA
- En el front: loguea eventos de formulario relevantes
  (submit, validación front, respuesta recibida)

ANTI-PATRÓN — esto NO sirve:
  log.debug("entering doPost()");
  log.debug("param email = " + email);
  log.debug("calling dao.insert()");

PATRÓN CORRECTO:
  log.info(jsonLog("ALTA_CUENTA",
    Map.of("email",email,"dni",dni),
    Map.of("email","OK","dni","FORMATO_INVALIDO"),
    "REJECTED", "DNI no cumple formato"));`

💡 ¿Por qué la IA genera mejores logs que el desarrollador original?
Porque la IA lee el código con la misión de extraer comportamiento, no de depurar bugs. El desarrollador original ponía log.debug donde tenía problemas en ese momento. La IA pone logs semánticos donde hay operaciones de negocio — que es exactamente lo que necesitas para cartografiar.
⚠️ Recordatorio: los logs son CONSULTA, no verdad
Aunque los logs semánticos son mucho mejores que los técnicos, siguen siendo código añadido sobre espagueti. Si la IA interpretó mal una intención al instrumentar, el log mentirá. Siempre: HAR manda, logs consultan. Si el log dice "result":"REJECTED" pero el HAR muestra un 200 con el registro creado, el HAR tiene razón.

Este baseline es imprescindible por dos razones: (1) necesitas medir si la migración mejora o empeora la seguridad, y (2) algunas vulnerabilidades del legacy pueden afectar a la cartografía (ej. un XSS en un formulario puede corromper los HAR si Playwright lo ejecuta).

async function ejecutarAlta(page, datos, caso) {
  await page.goto('/cuentas.html');

  for (const [campo, valor] of Object.entries(datos)) {
    const el = page.locator(`#form-alta [name="${campo}"]`);
    const tag = await el.evaluate(e => e.tagName);
    if (tag === 'SELECT') await el.selectOption(valor);
    else await el.fill(valor);
  }

  await page.screenshot({ path: `./captures/${caso}-pre.png` });

  // Intentar submit y capturar respuesta O validación front
  const responsePromise = page.waitForResponse(
    r => r.url().includes('/api/cuentas'), { timeout: 3000 }
  ).catch(() => null);

  await page.click('#form-alta button[type="submit"]');
  const response = await responsePromise;

  await page.screenshot({ path: `./captures/${caso}-post.png` });

  // Detectar si la validación fue front o back
  const invalidFields = await page.$$eval(
    '#form-alta :invalid',
    els => els.map(e => e.getAttribute('name'))
  );

  const contrato = {
    caso,
    datos_enviados: datos,
    validacion_front: invalidFields.length > 0 ? invalidFields : null,
    llego_al_back: !!response,
    status: response?.status() ?? null,
    responseBody: response ? await response.text() : null,
    contentType: response?.headers()['content-type'] ?? null,
    timestamp: new Date().toISOString(),
  };

  contratos.push(contrato);
  return contrato;
}

PREREQUISITO: AUTENTICACIÓN Y DATOS DE TEST
⚠️ Dos problemas que el protocolo no resuelve solo y debes resolver antes de la primera ejecución
1) Autenticación: La mayoría de apps legacy tienen login + sesión HTTP + posiblemente CSRF tokens. Playwright necesita autenticarse antes de cada test o reutilizar una sesión persistente. Si no lo resuelves, todos los tests reciben un 302 al login y los HAR son inútiles.

2) Datos de test: Los tests de cartografía crean datos (alta de cuenta, duplicados). En una BD legacy compartida, estos datos se acumulan entre ejecuciones, contaminan pasadas futuras, y pueden colisionar con datos de producción. Necesitas un mecanismo de aislamiento.

💡 Por qué dos pasadas y no tres
La primera pasada descubre el 80% del comportamiento. La segunda refina y cubre los huecos. Una tercera pasada tendría rendimientos decrecientes — la cartografía ya está suficientemente completa para construir tests de validación fiables. Si durante la migración aparece un caso no cubierto, se añade un test puntual, no una tercera cartografía completa.
⚠️ Límites duros para evitar el bucle infinito
Sin límites explícitos, la IA2 puede descubrir edge cases que generan más tests que descubren más edge cases indefinidamente. Reglas de corte obligatorias:

Máximo 3 iteraciones por funcionalidad. Si tras 3 ciclos de refinamiento la cobertura no llega al 90%, el problema no es la cartografía — es una ambigüedad del legacy que requiere decisión humana. Se documenta en unknowns.md y se avanza.

Rendimiento decreciente: <5% mejora → parar. Si la iteración 2 solo descubre un 3% más de comportamiento que la iteración 1, la cartografía está suficientemente completa. Continuar tiene coste de tokens y tiempo sin retorno proporcional.

Timebox por funcionalidad: máximo 1 día. Una funcionalidad (un Servlet con sus intenciones) no debería consumir más de 1 día de cartografía. Si excede, se divide en sub-funcionalidades más pequeñas.

GOLDEN MASTER — EL NOMBRE TÉCNICO DE LO QUE HACEMOS
Lo que el FMI llama "tests de validación desde HAR" tiene un nombre canónico en la industria desde hace 20 años: Golden Master testing. El concepto fue formalizado por Michael Feathers en "Working Effectively with Legacy Code" (2004) y es el patrón estándar de la industria para asegurar que un refactor preserva el comportamiento de un sistema legacy.
"Characterization tests are tests that characterize the actual behavior of a piece of code. There's no 'what should it do' here, only 'what does it do.' These tests aren't bug detectors. They are behavior preservers. […] When we write characterization tests, we are documenting current behavior, including buggy behavior. We are not endorsing the behavior. We are just describing it."
Michael Feathers · Working Effectively with Legacy Code (2004)
EL PROTOCOLO GOLDEN MASTER APLICADO AL FMI
Paso clásico Golden MasterCómo lo hace el FMI
1. Capturar output actual del sistema con muchos inputs de ejemplo Cartografía Playwright (Fases 2-4) ejecuta cientos de variantes de cada endpoint y captura todo en HAR
2. Guardar ese output como "verdad de oro" (Golden file) Extracción a contracts.json en Fase 5 — el HAR destilado a contratos auditables
3. Convertir el output capturado en tests automatizados Tests de integración back (Jersey + H2) y front (jsdom + MSW) generados por agents.md de Fase 5
4. Refactorizar con esos tests como red de seguridad Fase 6 — refactor a 3 capas con tests verde tras cada cambio
5. Si los tests fallan, el refactor cambió el comportamiento FMI lo formaliza: cualquier fallo requiere o corrección o ADR explícito en decisions/
El FMI extiende el Golden Master clásico con dos mejoras: (1) IA dual genera la cobertura: en Golden Master clásico, escribías tests a mano (lentos, incompletos). El FMI usa IA2 razonadora para generar variantes exhaustivas. (2) Aislamiento por lado: el Golden Master clásico ejecuta el sistema completo. El FMI separa back (H2) y front (MSW) usando el mismo contracts.json como fuente compartida — más rápido y determinista.
💡 Para el TFM, esta sección da peso académico inmediato
Cuando el tribunal pregunte "¿qué hay de novedoso en su metodología?", la respuesta correcta NO es "tests de comportamiento" — eso es Golden Master de 2004. La respuesta correcta es "composición de Golden Master con IA dual + cartografía exhaustiva por modelo razonador + aislamiento por lado mediante contracts.json". Lo novedoso es la composición y la aplicación de IAs LLM a un patrón validado, no el patrón en sí.
PRINCIPIO CRÍTICO: CADA LADO SE VALIDA AISLADO
Los tests de validación NO hacen comunicación real front↔back. Cada lado se valida de forma independiente usando el contracts.json como fuente compartida de verdad. El front falsea las respuestas del back con MSW. El back falsea la BD con H2 en memoria. No se levanta Tomcat, no hay HTTP real entre capas. Esto hace los tests rápidos (segundos, no minutos) y deterministas, capaces de correr en cada commit sin servidor vivo.
LADO BACK — AISLADO
Servlet + H2 en memoria
El Servlet legacy se arranca en memoria con JUnit 5 + Jersey Test Framework (o similar). La BD real se reemplaza por H2 en memoria, precargada con datos del contracts.json. El test envía un HTTP request al Servlet, captura la response, verifica contrato.
No requiere:
• Tomcat arrancado
• BD de producción
• Red
• Front

Velocidad: 2-5 seg por test
Fidelidad: El Servlet REAL (espagueti incluido), BD FALSA
Qué valida: Contrato HTTP completo — status, headers, body, redirects, manejo de duplicados, validaciones del back
LADO FRONT — AISLADO
HTML + jsdom + MSW
El HTML legacy se carga en memoria con Vitest + jsdom. jQuery corre como en producción. Las peticiones fetch y XMLHttpRequest las intercepta Mock Service Worker, devolviendo respuestas falsas extraídas del contracts.json. El form se rellena, submit, verifica.
No requiere:
• Navegador real
• Backend vivo
• Red
• Servlet

Velocidad: 100-500 ms por test
Fidelidad: El HTML REAL, el JS REAL, respuestas FALSAS
Qué valida: Validaciones HTML5 del form, flujo de submit, parseo de respuestas, visualización de errores
💡 ¿Por qué aislados y no E2E real?
Los tests de validación corren en CADA commit. Si cada test arranca Tomcat + BD + navegador, un pipeline de 50 tests tarda 10+ minutos y falla si algo en el entorno no está disponible. Aislados corren en 30 segundos y son deterministas. La fidelidad E2E real se reserva para la suite nightly (ver pestaña OPERACIONES). Además, en Fase 5 todavía NO hemos refactorizado — solo existen los servlets monolíticos legacy, así que no se pueden hacer unit tests de "dominio" (aún no hay dominio).

// tests/validacion/front/setup.ts — handlers MSW desde contracts.json

import { setupServer } from 'msw/node';
import { http, HttpResponse } from 'msw';
import contracts from '../../phase-5-validation/contracts.json';

// Construir handlers MSW dinámicamente desde los contratos
const handlers = contracts.map(c => {
  const method = c.method.toLowerCase();
  return http[method](c.endpoint, async ({ request }) => {
    const body = await request.text();

    // Matching simple: si el body del test coincide con el del contrato
    if (body === c.requestBody) {
      return new HttpResponse(c.responseBody || null, {
        status: c.responseStatus,
        headers: c.responseHeaders || {}
      });
    }
    return HttpResponse.json({ error: 'no match' }, { status: 500 });
  });
});

export const server = setupServer(...handlers);

public class CuentaServlet extends HttpServlet {

  // ❌ Variable de instancia con estado — race condition
  private Connection conn;

  @Override
  protected void doPost(HttpServletRequest req, HttpServletResponse res)
      throws ServletException, IOException {

    // ❌ Parámetros dispersos por todo el método
    String email = req.getParameter("email");
    String dni = req.getParameter("dni");
    String password = req.getParameter("password");
    String nombre = req.getParameter("nombre");

    PrintWriter out = res.getWriter();

    try {
      // ❌ Validaciones inline con regex hardcoded
      if (email == null || !email.matches(".+@.+\\..+")) {
        out.write("<html><body>Email inválido</body></html>");
        return;
      }
      if (password == null || password.length() < 8) {
        out.write("<html><body>Password muy corto</body></html>");
        return;
      }

      // ❌ HttpSession como cache de usuarios recientes
      HttpSession session = req.getSession();
      List<String> recientes = (List<String>) session.getAttribute("recientes");
      if (recientes == null) recientes = new ArrayList<>();

      // ❌ JDBC embebido en el doPost
      conn = DriverManager.getConnection("jdbc:...");
      PreparedStatement check = conn.prepareStatement(
        "SELECT 1 FROM cuentas WHERE email=?");
      check.setString(1, email);
      ResultSet rs = check.executeQuery();
      if (rs.next()) {
        out.write("<html><body>Email ya existe</body></html>");
        return;
      }

      // ❌ INSERT mezclado con response handling
      PreparedStatement insert = conn.prepareStatement(
        "INSERT INTO cuentas(email,dni,password,nombre) VALUES(?,?,?,?)");
      insert.setString(1, email);
      insert.setString(2, dni);
      insert.setString(3, password); // ❌ password sin hashear
      insert.setString(4, nombre);
      insert.executeUpdate();

      // ❌ Forward a otro servlet — acoplamiento
      recientes.add(email);
      session.setAttribute("recientes", recientes);
      RequestDispatcher rd = req.getRequestDispatcher("/AuditServlet");
      rd.include(req, res);

      res.sendRedirect("/cuentas?msg=creado");

    } catch (Exception e) {
      // ❌ Catch genérico — pierde información
      out.write("<html><body>Error</body></html>");
    }

public class JdbcCuentaFinder implements CuentaFinder {
  private final DataSource ds;
  public JdbcCuentaFinder(DataSource ds) { this.ds = ds; }

  @Override
  public Optional<Cuenta> porEmail(String email) {
    try (Connection c = ds.getConnection();
         PreparedStatement ps = c.prepareStatement(
           "SELECT email,dni,password_hash,nombre FROM cuentas WHERE email=?")) {
      ps.setString(1, email);
      try (ResultSet rs = ps.executeQuery()) {
        if (!rs.next()) return Optional.empty();
        return Optional.of(new Cuenta(
          rs.getString(1), rs.getString(2),
          rs.getString(3), rs.getString(4)));
      }
    } catch (SQLException e) {
      throw new InfrastructureException("Error consultando cuenta", e);
    }
  }
}

// src/main/java/domain/CrearCuentaUseCase.java
public class CrearCuentaUseCase {

  private final CuentaFinder finder;
  private final CuentaStore store;
  private final AltaCuentaValidator validator;
  private final PasswordHasher hasher;

  // Inyección manual por constructor — sin Spring, filosofía vanilla
  public CrearCuentaUseCase(CuentaFinder finder, CuentaStore store,
                              AltaCuentaValidator validator, PasswordHasher hasher) {
    this.finder = finder;
    this.store = store;
    this.validator = validator;
    this.hasher = hasher;
  }

  public Cuenta ejecutar(AltaCuentaDto dto) {
    // Orquesta — sin HTTP, sin SQL, solo lógica de negocio
    validator.validar(dto);

    if (finder.porEmail(dto.email).isPresent())
      throw new DuplicateException("Email ya existe");

    Cuenta cuenta = new Cuenta(
      dto.email, dto.dni, hasher.hash(dto.password), dto.nombre
    );
    store.guardar(cuenta);
    return cuenta;
  }
}

public class DispatcherServlet extends HttpServlet {
  private final MiddlewareChain chain;
  private final Router router;

  protected void service(HttpServletRequest req, HttpServletResponse res) {
    RequestContext ctx = RequestContext.fromHttp(req);
    chain.next(ctx); // ejecuta todos los middleware en orden

    if (!ctx.isAborted()) { // si ningún middleware abortó (ej. auth fallida)
      router.dispatch(ctx, req, res); // delega al servlet/handler correcto
    }
  }
}

// domain/middleware/AuthenticationMiddleware.java
public class AuthenticationMiddleware implements Middleware {

  private final SessionValidator sessionValidator;
  private final Set<String> publicPaths = Set.of("/login", "/health");

  @Override
  public void handle(RequestContext ctx, MiddlewareChain chain) {
    if (publicPaths.contains(ctx.path())) {
      chain.next(ctx); // rutas públicas: seguir sin verificar
      return;
    }

    Optional<UserSession> session = sessionValidator.validate(ctx.sessionId());
    if (session.isEmpty()) {
      ctx.abort(401, "Sesión inválida o expirada");
      return;
    }

    ctx.setAttribute("currentUser", session.get().user());
    ctx.setAttribute("currentRole", session.get().role());
    chain.next(ctx); // autenticado → continuar cadena
  }
}

// domain/middleware/SecurityHeadersMiddleware.java
public class SecurityHeadersMiddleware implements Middleware {

  @Override
  public void handle(RequestContext ctx, MiddlewareChain chain) {
    ctx.setResponseHeader("X-Content-Type-Options", "nosniff");
    ctx.setResponseHeader("X-Frame-Options", "DENY");
    ctx.setResponseHeader("X-XSS-Protection", "1; mode=block");
    ctx.setResponseHeader("Strict-Transport-Security", "max-age=31536000");
    ctx.setResponseHeader("Content-Security-Policy", "default-src 'self'");
    ctx.setResponseHeader("Referrer-Policy", "strict-origin-when-cross-origin");
    chain.next(ctx);
  }
}

// domain/middleware/CsrfMiddleware.java
public class CsrfMiddleware implements Middleware {

  private final CsrfTokenStore tokenStore;

  @Override
  public void handle(RequestContext ctx, MiddlewareChain chain) {
    if ("GET".equals(ctx.method())) {
      // GET: generar token y ponerlo disponible para el form
      String token = tokenStore.generate(ctx.sessionId());
      ctx.setAttribute("csrfToken", token);
      chain.next(ctx);
      return;
    }

    // POST/PUT/DELETE: verificar token
    String submitted = ctx.header("X-CSRF-Token");
    if (!tokenStore.validate(ctx.sessionId(), submitted)) {
      ctx.abort(403, "CSRF token inválido");
      return;
    }
    chain.next(ctx);
  }
}

💡 Este bloque es prerequisito — ANTES que cualquier servlet individual
Los servlets individuales se refactorizan DESPUÉS de tener el pipeline de middleware funcionando. La razón: los servlets ya no extienden BaseServlet — son clases independientes registradas en el Router. Si migras un servlet antes de tener el Router, tienes que mantener la herencia legacy como puente temporal, lo que complica todo.
Las 3 capas no son arbitrarias. Son la materialización de un principio: cada capa habla un solo lenguaje. Transport habla HTTP. Domain habla negocio. Infrastructure habla SQL. Quien viola esto, paga el precio en mantenimiento durante años.
REFACTORING A 3 CAPAS — ARQUITECTURA
Transport
Servlet / Controller — solo recibe request, extrae parámetros, delega en Domain, formatea response. Conoce HTTP, jamás SQL ni reglas de negocio. Los tests de validación back protegen el contrato HTTP de esta capa.
Domain
POJOs puros, sin dependencias de frameworks ni de BD. Lógica de negocio, validaciones, reglas, casos de uso. Las dependencias de infraestructura entran como interfaces (Finder, Store) cuya implementación se inyecta. Unit tests con Mockito verifican esta capa.
Infrastr.
DAOs / Adapters — implementan las interfaces de Domain. Acceso a BD, servicios externos, sistemas legacy (SOAP, AS400, MQ). Tests de integración con H2 o testcontainers verifican esta capa.
Los tests de validación de Fase 5 no cambian durante el refactor. Si el test dice «POST /api/cuentas con datos válidos → 302», eso se mantiene sea cual sea la estructura interna. Solo se modifican tests cuando se toma una decisión consciente de cambiar comportamiento (ADR obligatorio).

¿POR QUÉ 3 CAPAS Y NO LOS 4 ANILLOS DE CLEAN ARCHITECTURE?
Decisión arquitectónica deliberada. Robert C. Martin propone 4 anillos concéntricos en Clean Architecture (Entities, Use Cases, Interface Adapters, Frameworks). El FMI usa 3 capas (Transport, Domain, Infrastructure). No es por simplificar — es por optimizar la legibilidad para una IA que asiste la migración.

El problema práctico más difícil: Tu Servlet devuelve HTML con response.getWriter().write("<tr>..."). El front legacy espera ese HTML. Pero el front migrado (Web Component) necesita JSON. ¿Cómo conviven durante la migración sin duplicar el Servlet? 
// Estrategia: UN Servlet, DOS formatos, CERO duplicación
// El Servlet ya tiene toda la lógica. Solo añades un IF al final.

protected void doPost(HttpServletRequest req, HttpServletResponse res) {
    // ... lógica de negocio existente (UseCase, sin tocar) ...
    Cuenta cuenta = useCase.ejecutar(dto);

    // ═══ NUEVO: content negotiation ═══
    String accept = req.getHeader("Accept");

    if (accept != null && accept.contains("application/json")) {
        // FRONT MIGRADO → JSON
        res.setContentType("application/json");
        res.setStatus(201);
        res.getWriter().write(new Gson().toJson(cuenta));
    } else {
        // FRONT LEGACY → HTML redirect (comportamiento original)
        res.sendRedirect("/cuentas?msg=creado");
    }
}

// El JSP viejo sigue llamando sin header → recibe HTML

💡 Impacto en los tests de validación
Los tests de Fase 5 envían Content-Type: application/x-www-form-urlencoded sin header Accept → reciben 302 redirect → pasan sin cambios. Los tests del front migrado envían con Accept: application/json → reciben 201 + JSON. Ambos conjuntos de tests coexisten. Cuando se eliminan todos los JSPs, se borran los tests de redirect y solo quedan los de JSON.

// src/main/java/infra/FeatureFlags.java
public class FeatureFlags {
    private static final Map<String, Integer> ROLLOUT = Map.of(
        "alta_cuenta_v2", Integer.parseInt(System.getenv().getOrDefault("FF_ALTA_V2", "0"))
    );

    public static boolean enabled(String flag, HttpServletRequest req) {
        int percent = ROLLOUT.getOrDefault(flag, 0);
        if (percent >= 100) return true;
        if (percent <= 0) return false;
        // Hash determinista por usuario para consistencia (mismo usuario → mismo lado)
        String userKey = req.getSession().getId();
        return Math.abs(userKey.hashCode() % 100) < percent;

}

// domain/SessionState.java — abstracción del estado de sesión
public interface SessionState {
    Optional<String> ultimoContratoId();
    void guardarUltimoContrato(String id);
    Optional<String> usuarioActual();
}

// infra/HttpSessionAdapter.java — impl que respeta la estructura LEGACY
public class HttpSessionAdapter implements SessionState {
    private final HttpSession session;

    public HttpSessionAdapter(HttpSession session) { this.session = session; }

    @Override
    public Optional<String> ultimoContratoId() {
        Map<String, Object> carrito = (Map) session.getAttribute("carrito");
        if (carrito == null) return Optional.empty();
        return Optional.ofNullable((String) carrito.get("ultimo_contrato"));
    }

    @Override
    public void guardarUltimoContrato(String id) {
        // Mantiene la estructura legacy intacta
        Map<String, Object> carrito = (Map) session.getAttribute("carrito");
        if (carrito == null) carrito = new HashMap<>();
        carrito.put("ultimo_contrato", id);
        session.setAttribute("carrito", carrito);
    }
}

// El UseCase ahora trabaja con SessionState (testeable, mockeable)
public class CrearContratoUseCase {
    private final SessionState session;

    public Contrato ejecutar(ContratoDto dto) {
        // Usa la abstracción, no HttpSession directamente
        Contrato c = construir(dto);
        store.guardar(c);
        session.guardarUltimoContrato(c.id());
        return c;
    }
}
¿Cuándo NO migrar la sesión todavía? Si el atributo de sesión lo usan 3+ servlets no migrados, NO cambies su estructura. El SessionAdapter respeta el formato legacy mientras quede un servlet que lo lea. Cuando todos los servlets que tocan ese atributo estén migrados, puedes refactorizar la estructura interna (ADR obligatorio).

✅ Regla: NO tocar schema durante la migración
El schema legacy funciona. Los tests de validación asumen esa estructura. Si cambias una columna VARCHAR(50) a VARCHAR(100) o renombras una tabla, puedes romper los tests y la lógica legacy simultáneamente. Migra código primero, schema después. Las 3 capas encapsulan el schema feo en el DAO — el Domain trabaja con objetos limpios.
⚡ Excepción: cambios aditivos seguros
Añadir una columna (ALTER TABLE ADD COLUMN) es seguro — no rompe nada existente. Añadir un índice es seguro. Renombrar o eliminar columnas NO es seguro durante la migración. Si necesitas un schema nuevo, crea una vista SQL que mapee legacy → limpio, y el DAO nuevo lee de la vista.
La seguridad no es un paso opcional que se añade al final. Es un pilar transversal al mismo nivel que la arquitectura de 3 capas y los tests. Cada servlet refactorizado se verifica contra OWASP Top 10, comparando con el baseline de Fase 0. El objetivo es que la versión migrada sea más segura que la legacy, no solo equivalente.

Si el grafo tiene ciclos (ServletA llama a ServletB que llama a ServletA), normalmente es síntoma de deuda técnica acumulada. No hay un orden seguro porque cualquiera de los dos rompe al otro al migrar.

CASO 1 — CÓDIGO COMPILADO SIN FUENTES
Problema: Tu app importa un legacy-billing-2008.jar sin fuentes Java disponibles. El equipo original ya no existe. Hay clases BillingProcessor que se invocan desde varios servlets pero nadie sabe qué hacen exactamente.
Opción A: Decompilar
Usar CFR, Procyon o Fernflower. Genera Java reconstruido (sin comentarios, con nombres de variables genéricos como var1). Suficiente para entender la lógica si la decompilación es limpia. Riesgo: el código generado puede tener bugs de decompilación, especialmente con switches o lambdas.

Tratar el JAR como caja negra TOTAL. La cartografía Playwright (Fases 2-4) revela qué hace observando inputs/outputs. Reconstruyes la funcionalidad desde cero usando los HAR y logs como especificación. Más lento pero más seguro: no arrastras bugs del legacy.

// FASE 6 estrategia: el DAO llama al SP, NO migrar SP todavía

// domain/FacturaProcessor.java — interfaz
public interface FacturaProcessor {
    Resultado procesar(Factura factura);
}

// infra/StoredProcFacturaProcessor.java — IMPL invoca al SP intacto
public class StoredProcFacturaProcessor implements FacturaProcessor {
    private final DataSource ds;

    @Override
    public Resultado procesar(Factura factura) {
        try (Connection c = ds.getConnection();
             CallableStatement cs = c.prepareCall("{ ? = call SP_PROCESAR_FACTURA(?, ?) }")) {
            cs.registerOutParameter(1, Types.NUMERIC);
            cs.setLong(2, factura.id());
            cs.setBigDecimal(3, factura.importe());
            cs.execute();
            return Resultado.desde(cs.getInt(1));
        } catch (SQLException e) {
            throw new InfrastructureException("Error invocando SP_PROCESAR_FACTURA", e);
        }
    }
}

// El UseCase no sabe que hay un SP — solo conoce la interfaz
public class ProcesarFacturaUseCase {
    private final FacturaProcessor processor;

    public Resultado ejecutar(Factura factura) {
        return processor.procesar(factura);
    }
}

CASO 6 — FLUJOS MULTI-PASO CON ESTADO
Problema: "Formulario de contratación en 5 pantallas". El usuario entra datos en pantalla 1, navega a la 2, sigue a la 3, vuelve a la 1 a corregir, finalmente envía en la 5. El estado se mantiene entre pantallas — normalmente en HttpSession. Refactorizarlo sin entender la máquina de estados es invitar a bugs sutiles. 
// Estrategia FMI: extraer la máquina de estados a Domain

// domain/ContratoEnProgreso.java — Entity inmutable que representa el estado
public final class ContratoEnProgreso {
    private final String id;
    private final Paso pasoActual;
    private final Map<Paso, DatosPaso> datosCompletados;

    public ContratoEnProgreso avanzar(Paso siguiente, DatosPaso datos) {
        // Validaciones de máquina de estados
        if (!pasoActual.permiteAvanzarA(siguiente))
            throw new TransicionInvalidaException(pasoActual, siguiente);
        Map<Paso, DatosPaso> nuevos = new HashMap<>(datosCompletados);
        nuevos.put(pasoActual, datos);
        return new ContratoEnProgreso(id, siguiente, nuevos);
    }

    public boolean puedeFinalizar() {
        return datosCompletados.keySet().containsAll(Set.of(Paso.values()));
    }
}

// transport/ContratoFlujoServlet.java — orquesta los pasos
protected void doPost(HttpServletRequest req, HttpServletResponse res) {
    SessionState session = new HttpSessionAdapter(req.getSession());
    ContratoEnProgreso actual = session.contratoEnProgreso()
        .orElseGet(() -> ContratoEnProgreso.iniciar());

    Paso siguiente = Paso.valueOf(req.getParameter("paso"));
    DatosPaso datos = DatosPaso.desdeRequest(req);

    ContratoEnProgreso actualizado = actual.avanzar(siguiente, datos);
    session.guardarContratoEnProgreso(actualizado);

    if (actualizado.puedeFinalizar()) {
        useCase.finalizarContrato(actualizado);
    }
    // Renderizar siguiente pantalla...
}
Tests: los tests unit del Domain prueban la máquina de estados (transiciones válidas, inválidas, finalización). Los tests integration verifican el flujo completo paso a paso. Los E2E navegan las 5 pantallas como un usuario real.

// infra/SoapBancoFirmaService.java — encapsula el SOAP feo
public class SoapBancoFirmaService implements FirmaService {

    private final BancoFirmaWSPortType client; // generado por wsimport

    @Override
    public Firma solicitar(Documento documento, Certificado cert) {
        try {
            FirmaRequest req = new FirmaRequest();
            req.setDocumentoBase64(Base64.encode(documento.bytes()));
            req.setCertificadoX509(cert.x509());
            FirmaResponse resp = client.firmar(req);
            return new Firma(resp.getId(), resp.getTimestamp());
        } catch (WebServiceException e) {
            throw new ExternalSystemException("Banco SOAP no disponible", e);
        }
    }
}

// El UseCase NO sabe que hay SOAP — solo conoce FirmaService
public class FirmarContratoUseCase {

    public Contrato ejecutar(Contrato contrato, Certificado cert) {
        Firma f = firmaService.solicitar(contrato.documento(), cert);
        return contrato.conFirma(f);
    }
}

## REGLAS DE REFACTOR — LOS 6 PASOS

### Paso 1: Identificar el DTO

  - Cada request.getParameter(x) → campo del DTO
  - Mapeo 1:1 con lo que viene en el form HTML
  - NO validar en el DTO — solo recibir datos
  - Constructor estático desdeRequest(HttpServletRequest)

### Paso 2: Extraer el Entity

  - Campos que representan la entidad de dominio
  - Inmutable (solo getters, constructor con validación de invariantes)
  - DISTINTO del DTO: el Entity puede tener campos derivados o calculados
  - Ej: el Entity Cuenta tiene passwordHash, NO password en plano

### Paso 3: Extraer las validaciones

  - Cualquier if/throw/regex que valide datos → mover a Validator
  - Los mensajes de error se extraen del HAR
    (responseBody con "ya existe", etc.)
  - Lanzar excepciones de dominio (ValidationException, DuplicateException),
    nunca RuntimeException genérico

### Paso 4: Extraer el DAO

  - Toda Connection / PreparedStatement / ResultSet → mover a Jdbc*Impl
  - Crear interfaces Finder / Store en domain con métodos del caso de uso
  - El Domain NO importa java.sql
  - Try-with-resources obligatorio en Impl

### Paso 5: Extraer el UseCase

  - Orquesta: validar → guardar → devolver
  - Recibe DTO, devuelve Entity (o lanza excepción de dominio)
  - Inyección por constructor (DI manual, sin framework)
  - NO conoce HTTP ni SQL

### Paso 6: Reescribir el Servlet

  - Máximo 15 líneas en doPost / doGet
  - Pattern: parsear DTO → invocar UseCase → catch errores → formatear response
  - Si Accept: application/json → JSON
  - Si NO → mantener formato legacy (HTML/redirect)

TRES NIVELES DE PROTECCIÓN
1
Git tags — rollback en 2 minutos
Antes de cada migración de servlet: git tag pre-migrate-contrato-v1. Si falla: git checkout pre-migrate-contrato-v1 + redeploy. Cada tag es un punto seguro al que volver. Suficiente para tu TFM con un solo entorno de deploy.
2
Canary — 10% del tráfico al migrado
Legacy en /api/v1/contratos y migrado en /api/v2/contratos. Un proxy o filtro envía 10% al v2. Si los tests de validación pasan con tráfico real → 50% → 100%. Si falla → todo al v1, sin downtime. Para producción enterprise.
3
Shadow mode — comparar respuestas sin riesgo
Cada request va a v1 Y v2 simultáneamente. Se responde SIEMPRE con v1 (seguro), pero se compara la respuesta de v2. Si difieren → log de discrepancia. Cuando las discrepancias llegan a 0 durante 48h → cambiar a v2. Riesgo cero. Máxima confianza.

CRITERIOS DE ABORTO INMEDIATO
⚠️ Si CUALQUIERA de estos ocurre → rollback inmediato a legacy
1. Cualquier error 5xx no visto en cartografía — el sistema migrado está produciendo errores que el legacy no producía. Algo está roto que los tests no detectaron.

2. Latencia p99 más de 2× la del legacy — el código migrado es significativamente más lento. Puede ser carga real que los tests no simularon.

3. Discrepancia de datos en BD — el migrado escribe datos diferentes (campos perdidos, formatos cambiados) que el legacy. Riesgo de corrupción.

4. Quejas de usuarios reales — los soportes reciben tickets sobre comportamiento anómalo. Aunque los logs no muestren errores, la percepción del usuario es la realidad.

5. Volumen de logs anómalo — explosión de warnings o errores que no aparecían antes. Síntoma de algo que está fallando silenciosamente.

CI/CD — CUÁNDO SE EJECUTAN LOS TESTS
El FMI genera dos tipos de tests con momentos de ejecución distintos. Los de cartografía se ejecutan manualmente durante las fases 2-4. Los de validación se ejecutan automáticamente en cada commit. Sin esta integración en el pipeline, un desarrollador puede romper lo ya migrado sin enterarse.
En cada commit
Tests de validación back (Vitest / fetch contra servidor de test) — ~5 seg. Si falla alguno → el commit se bloquea. Estos protegen los contratos HTTP confirmados por HAR. Son la línea roja que nadie puede cruzar.
En cada PR
Tests de validación front (Playwright headless) — ~30 seg. Verifican que los formularios mantienen las validaciones confirmadas (DNI, email, password). Más lentos que los de back pero imprescindibles antes de merge.
Nightly
Suite E2E completa (Playwright con todos los flujos) — ~5 min. Cubre los flujos completos (crear → listar → buscar → editar → borrar). Detecta regresiones que los tests unitarios no ven (problemas de navegación, estado entre páginas, sesión).
Pre-deploy
Comparación HAR (shadow mode si aplica) — variable. Antes de desplegar a staging/producción, ejecutar la suite contra el entorno destino y comparar HAR con los de referencia. Si hay discrepancias no cubiertas por un ADR → bloquear deploy.
Manual
Tests de cartografía (solo durante fases 2-4) — bajo demanda. No forman parte del pipeline automático. Se ejecutan cuando se inicia la cartografía de un nuevo servlet. Una vez producen los HAR, se archivan.
