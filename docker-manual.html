QUÉ ES DOCKER
Docker empaqueta una aplicación con todo lo que necesita para correr en un contenedor aislado. El contenedor incluye el SO base, las librerías, el runtime, las dependencias y el código. Corre igual en tu portátil, en CI/CD y en producción. "Funciona en mi máquina" ya no es excusa.
IMAGEN · CONTENEDOR · VOLUMEN · RED

EL FLUJO COMPLETO
# 1. Escribir el Dockerfile
FROM node:20-alpine
WORKDIR /app
COPY . .
RUN npm ci
CMD ["node", "src/index.js"]

# 2. Construir la imagen
docker build -t mi-app:1.0 .

# 3. Correr un contenedor desde la imagen
docker run -d -p 3000:3000 --name mi-app mi-app:1.0

# 4. Ver que está corriendo
docker ps

# 5. Ver los logs
docker logs mi-app

# 6. Parar y borrar
docker stop mi-app && docker rm mi-app
INSTRUCCIONES DEL DOCKERFILE
InstrucciónQué haceEjemplo
FROMImagen base. Siempre primera instrucción.FROM node:20-alpine
WORKDIRDirectorio de trabajo dentro del contenedor.WORKDIR /app
COPYCopia ficheros del host al contenedor.COPY package*.json .
ADDComo COPY pero soporta URLs y descomprime .tar.ADD https://x.com/f.tar.gz /opt/
RUNEjecuta un comando al construir la imagen. Cada RUN = nueva capa.RUN npm ci --only=production
CMDComando por defecto al arrancar el contenedor. Solo uno por Dockerfile.CMD ["node", "src/index.js"]
ENTRYPOINTEjecutable principal. CMD pasa como argumentos.ENTRYPOINT ["python", "app.py"]
ENVVariable de entorno disponible en build y en runtime.ENV NODE_ENV=production
ARGVariable solo en build time (no disponible en runtime).ARG VERSION=1.0
EXPOSEDocumenta qué puerto usa el contenedor (no abre nada).EXPOSE 3000
VOLUMEDeclara un punto de montaje para datos persistentes.VOLUME /data
USERCambia el usuario que ejecuta los siguientes comandos.USER node
HEALTHCHECKDefine cómo verificar que el contenedor está healthy.HEALTHCHECK CMD curl -f http://localhost:3000/health
LABELMetadatos de la imagen (autor, versión, descripción).LABEL maintainer="antonio@mail.com"
DOCKERFILE PARA NODE.JS — PRODUCCIÓN
Dockerfile
FROM node:20-alpine

# Usuario no-root por seguridad
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app

# Copiar package.json PRIMERO para cachear npm ci
COPY package*.json .
RUN npm ci --only=production

# Copiar el resto del código
COPY . .

# Cambiar al usuario no-root
USER appuser

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=3s \
  CMD wget -qO- http://localhost:3000/health || exit 1

CMD ["node", "src/index.js"]
DOCKERFILE PARA PYTHON / FASTAPI
Dockerfile
FROM python:3.12-slim

WORKDIR /app

# Copiar requirements PRIMERO para cachear pip install
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Usuario no-root
RUN useradd -m appuser
USER appuser

EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

💡 Clave: separar COPY en dos fases
Copiar primero package.json / requirements.txt y luego ejecutar npm ci / pip install. Después copiar el resto del código. Docker cachea cada capa — si el código cambia pero las dependencias no, la capa de npm ci se reutiliza del caché. Eso acelera los builds de minutos a segundos.

ALPINE VS SLIM VS FULL — CUÁNDO USAR CADA UNO
:alpine (~5-50MB)
Basada en Alpine Linux (musl libc). La más pequeña. Usa apk en vez de apt. Ideal para producción. Cuidado: algunos paquetes Python con extensiones C no compilan bien con musl — si falla, usar :slim.
:slim (~80-120MB)
Basada en Debian pero sin paquetes innecesarios. Usa glibc (compatibilidad total). Buena opción por defecto para Python. Más grande que alpine pero sin problemas de compilación.
sin sufijo (~300MB+)
Imagen Debian completa. Tiene build-essential, gcc, etc. preinstalado. Usar solo para builds que necesitan compilar extensiones nativas. En producción siempre usar :alpine o :slim.
⚠️ Nunca usar :latest en producción
node:latest puede ser Node 20 hoy y Node 22 mañana — rompiéndote el build sin que hayas cambiado nada. Siempre pinear la versión exacta: node:20-alpine, postgres:16-alpine. Es la misma regla que con los paquetes npm — versiones fijas para reproducibilidad.
DOCKER COMPOSE — MULTI-CONTENEDOR EN UN FICHERO
Docker Compose define todo el stack en un solo fichero docker-compose.yml. Un comando (docker compose up) levanta la app, la BD, el caché, el proxy — todo conectado en la misma red. Ideal para desarrollo local y para despliegues sencillos en producción.
EJEMPLO COMPLETO — APP + BD + REDIS + ADMINER
docker-compose.yml
version: '3.8'

services:

  # ── La aplicación ──────────────────────────────
  app:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgresql://user:pass@db:5432/myapp
      REDIS_URL: redis://redis:6379
      NODE_ENV: development
    volumes:
      - ./src:/app/src               # bind mount para hot reload
      - /app/node_modules             # proteger node_modules del host
    depends_on:
      db:
        condition: service_healthy   # espera a que la BD esté lista
      redis:
        condition: service_started
    restart: unless-stopped

  # ── Base de datos ──────────────────────────────
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data   # datos persistentes
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql  # seed
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d myapp"]
      interval: 5s
      timeout: 3s
      retries: 5
    restart: unless-stopped

  # ── Cache ──────────────────────────────────────
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    volumes:
      - redisdata:/data
    restart: unless-stopped

  # ── UI para la BD ──────────────────────────────
  adminer:
    image: adminer
    ports:
      - "8080:8080"
    depends_on: [db]

# ── Volúmenes nombrados ────────────────────────
volumes:
  pgdata:        # datos PostgreSQL persistentes
  redisdata:     # datos Redis persistentes
COMANDOS DE COMPOSE
# Levantar todo en background
docker compose up -d

# Ver logs en tiempo real
docker compose logs -f
docker compose logs -f app          # solo de un servicio

# Parar todo
docker compose down

# Parar y borrar volúmenes (reset BD)
docker compose down -v

# Reconstruir la imagen (después de cambiar Dockerfile)
docker compose build
docker compose up -d --build         # build + arrancar

# Ejecutar un comando dentro de un contenedor corriendo
docker compose exec app sh           # shell dentro de app
docker compose exec db psql -U user -d myapp  # psql directo

# Ver el estado de los servicios
docker compose ps

VOLÚMENES — DATOS QUE SOBREVIVEN
Sin volumen, los datos del contenedor se pierden al borrarlo. Los volúmenes son el mecanismo para que los datos de la BD, los uploads del usuario, los logs — persistan independientemente del ciclo de vida del contenedor.
TRES TIPOS DE MONTAJE
TipoSintaxisCuándo usar
Named volumepgdata:/var/lib/postgresql/dataDatos de BD y servicios en producción. Docker gestiona la ubicación. El más seguro.
Bind mount./src:/app/srcDesarrollo: hot reload del código fuente. Monta una carpeta del host dentro del contenedor.
tmpfstype=tmpfs,destination=/tmpDatos temporales que no necesitan persistir ni escribir a disco (logs temporales, caché).
# Named volume — producción
docker run -v pgdata:/var/lib/postgresql/data postgres:16-alpine

# Bind mount — desarrollo
docker run -v $(pwd)/src:/app/src -v /app/node_modules mi-app

# tmpfs — temporal en memoria
docker run --tmpfs /tmp:rw,size=100m mi-app

# Gestionar volúmenes
docker volume ls                   # listar
docker volume inspect pgdata       # ver detalles
docker volume rm pgdata            # borrar
docker volume prune                # borrar los no usados
REDES — CONTENEDORES QUE SE VEN ENTRE SÍ
Docker Compose crea una red automáticamente para todos los servicios del fichero. Los contenedores se ven entre sí por nombre de servicio: db resuelve a la IP del contenedor de PostgreSQL, redis a la de Redis. No necesitas IPs — solo nombres. 
# La app se conecta a la BD por nombre de servicio
DATABASE_URL=postgresql://user:pass@db:5432/myapp
#                                    ^^ nombre del servicio en compose

# Crear una red manualmente
docker network create mi-red
docker run --network mi-red --name app mi-app
docker run --network mi-red --name db postgres

# Ver las redes
docker network ls

# En compose — red con nombre explícito
services:
  app:
    networks: [frontend, backend]
  db:
    networks: [backend]       # la BD no es accesible desde frontend
  nginx:
    networks: [frontend]

networks:
  frontend:
  backend:
MULTI-STAGE BUILDS — IMÁGENES MÍNIMAS
Multi-stage separa el build del runtime. La primera etapa compila/construye con todas las herramientas. La segunda etapa copia solo el resultado a una imagen mínima. La imagen final no tiene compiladores, headers ni dependencias de build — solo lo necesario para correr.
NODE.JS — MULTI-STAGE
Dockerfile
# ── ETAPA 1: Build ─────────────────────────────
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json .
RUN npm ci
COPY . .
RUN npm run build                  # genera dist/

# ── ETAPA 2: Producción ────────────────────────
FROM node:20-alpine AS production
WORKDIR /app
COPY package*.json .
RUN npm ci --only=production       # solo deps de producción
COPY --from=builder /app/dist ./dist  # copia solo el build
USER node
EXPOSE 3000
CMD ["node", "dist/index.js"]

# Resultado: imagen sin devDependencies, sin src/, sin herramientas de build
REACT — BUILD + NGINX
Dockerfile
# ── Build con Node ─────────────────────────────
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json .
RUN npm ci
COPY . .
RUN npm run build                  # genera dist/ con los HTML/JS/CSS

# ── Servir con nginx ───────────────────────────
FROM nginx:1.25-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80

# Imagen final: ~25MB (nginx + HTML estático)
# No tiene Node, ni npm, ni node_modules, ni src/
GO — BUILD + SCRATCH
Dockerfile
# ── Build con Go SDK ───────────────────────────
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod go.sum .
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /server ./cmd/server

# ── Imagen final: SOLO el binario ──────────────
FROM scratch
COPY --from=builder /server /server
EXPOSE 8080
ENTRYPOINT ["/server"]

# Imagen final: ~10-15MB (solo el binario Go compilado)
# Sin SO, sin shell, sin nada más. Mínima superficie de ataque.
💡 Comparativa de tamaño
Node sin multi-stage: ~400MB (node_modules + devDependencies + código fuente).
Node con multi-stage: ~80MB (solo runtime + producción deps + dist/).
React con nginx: ~25MB (solo nginx + HTML/JS/CSS estáticos).
Go con scratch: ~12MB (solo el binario compilado).

Menos tamaño = deploy más rápido + menos superficie de ataque + menos coste de almacenamiento.

CONTENEDORES
# Crear y arrancar
docker run -d -p 3000:3000 --name mi-app mi-app:1.0
#  -d         = detached (background)
#  -p 3000:3000 = puerto host:contenedor
#  --name     = nombre del contenedor

# Con variables de entorno
docker run -d -e NODE_ENV=production -e DB_URL=... mi-app:1.0
docker run -d --env-file .env mi-app:1.0       # desde fichero

# Con volumen y red
docker run -d -v pgdata:/data --network mi-red mi-app:1.0

# Interactivo (shell dentro del contenedor)
docker run -it node:20-alpine sh               # nuevo contenedor
docker exec -it mi-app sh                      # contenedor existente

# Ver estado
docker ps                                       # corriendo
docker ps -a                                    # todos (incluso parados)

# Logs
docker logs mi-app
docker logs -f mi-app                            # follow en tiempo real
docker logs --tail 100 mi-app                   # últimas 100 líneas

# Parar / arrancar / reiniciar / borrar
docker stop mi-app
docker start mi-app
docker restart mi-app
docker rm mi-app                                # (tiene que estar parado)
docker rm -f mi-app                              # forzar borrado

# Stats en tiempo real (CPU, RAM, red)
docker stats

# Copiar ficheros host ↔ contenedor
docker cp mi-app:/app/logs/error.log ./error.log
docker cp ./config.json mi-app:/app/config.json

# Inspeccionar (IP, volúmenes, config completa)
docker inspect mi-app
